## OpenART 跟随算法

OpenART 视觉侧当前只负责面向辅车跟随的色标识别与速度修正量生成。

### 采集与预处理

- 摄像头使用 `QVGA` 与 `RGB565` 画面格式。
- 传感器侧开启垂直翻转与水平镜像, 让画面尽量接近实际安装方向。
- 曝光固定为 `300us`, 自动增益、自动白平衡和自动曝光关闭。
- 每帧尝试做镜头畸变校正, 内存不足时跳过本帧校正并继续运行。

### 目标检测

- 当前检测任务只保留 `red` 色块。
- 色块检测使用固定颜色阈值, 并要求候选区域满足像素数和面积下限。
- 每个候选目标使用 `blob.rect()` 得到外接矩形, 再统一转换为 `left / top / right / bottom` 边界。
- 纵向边界按图像高度做一次归一化, 统一到“地板在下方”的坐标语义。
- 当前目标尺度量来自最小外接旋转矩形四个大角点, 取上底和下底长度的平均值。
- 调试画面只绘制当前选中目标的四个大角点和中心点。

### 候选目标选择

- 每帧会先收集所有颜色候选目标, 再选择单个目标进入控制量计算。
- 候选目标优先靠近画面横向中线, 同时底边更靠近地板。
- 选择评分使用横向中心偏差和归一化底边距离共同计算。

### 误差定义

- 横向误差来自目标中心 x 坐标相对画面中心的像素偏差。
- 纵向误差来自当前目标尺度量相对目标尺度量的差值, 不直接使用目标中心 y 坐标。
- 当前纵向目标尺度量为 `45px`。
- 横向死区为 `15px`, 纵向死区为 `8px`。

### Y 值算法

OpenART 输出短包中的 `vy` 来自目标尺度量闭环, 这里的 `y` 不是图像坐标中的纵向位置。

当前算法按以下顺序生成纵向控制输入:

1. 对选中的红色色块读取最小外接旋转矩形四个大角点。
2. 计算四角点上边长度与下边长度。
3. 取上边长度和下边长度的平均值, 作为当前目标尺度量 `marker_span`。
4. 用 `marker_span - 45` 得到纵向误差。
5. 对纵向误差四舍五入后进入阶段判断。

算法含义:

- `marker_span` 表示色标在画面中的可见尺度, 用作目标距离代理量。
- `45px` 表示当前期望跟随距离对应的目标尺度量。
- `marker_span` 大于 `45px` 时, 目标在画面中偏大, 纵向误差为正。
- `marker_span` 小于 `45px` 时, 目标在画面中偏小, 纵向误差为负。
- 归一化后的底边位置只参与候选目标选择, 不参与 `vy` 计算。
- 目标中心 y 坐标只作为候选目标信息保留, 不参与 `vy` 计算。

纵向误差进入控制量生成后:

1. 误差绝对值不超过 `8px` 时, `vy` 为 `0`。
2. 误差绝对值超过 `8px` 时, `vy` 按 `err_y * -0.15` 生成。
3. `vy` 最终限制在 `[-5, 5]` 范围内。
4. `marker_span` 偏大时 `vy` 为负, `marker_span` 偏小时 `vy` 为正。

### 阶段与控制量

- 无有效目标时阶段为 `MARKER_MISSING`, `vx` 与 `vy` 均为 `0`。
- 横向和纵向都在死区内时阶段为 `CENTER_HOLD`, `vx` 与 `vy` 均为 `0`。
- 只有横向超出死区时阶段为 `ALIGN_X`, 只输出横向速度修正量。
- 只有纵向超出死区时阶段为 `ALIGN_Y`, 只输出纵向速度修正量。
- 横向和纵向同时超出死区时阶段为 `ALIGN_XY`, 同时输出两个方向的速度修正量。
- 横向速度修正量按 `err_x * 0.04` 生成。
- 纵向速度修正量按 `err_y * -0.15` 生成, 并限制在 `[-5, 5]` 范围内。
- 阶段名只服务 OpenART 内部判断和主机侧行为检查, 不进入串口载荷。

### 输出规则

- OpenART 每抓取一帧就发送一帧速度短包。
- 正式输出固定为 `v,<vx>,<vy>`, 数值文本使用紧凑格式。
- 接近零的速度修正量输出为 `0`。
- 无目标和保持阶段都显式发送 `v,0,0`。
- `UART6` 视觉链路不发送 `omega`, 不附带阶段名、序号、有效位或其他跟随元信息。

## 角色链路

- 当前代码按 `vision/master/` 与 `vision/assistant/` 角色层组织角色运行入口。
- `vision/master/` 是主车上游控制与速度转发入口：接管 `UART3` 速度短包，并按 [串口通信协议](protocol.md) 中的 `UART8` 主辅前馈链路转发给辅车，同时写入主车共享底盘执行。
- 主车角色入口不接视觉输入，不消费视觉观测，也不做自主行控。
- `vision/assistant/` 是辅车角色运行入口：负责接入 `UART8` 前馈输入与 `UART6` 视觉输入。
- `vision/assistant/follow_runtime.py` 会创建辅车角色运行时对象，并在 `step()` 控制周期中参与双路速度输入读取编排和底盘调度。
- 辅车角色层在控制周期内统一编排 `UART8` 与 `UART6` 的读取：两路短包按 [串口通信协议](protocol.md) 的链路定义解释；任一路单独存在时也可以直接形成最终速度。
- 辅车把 `UART8` 解释为前馈输入、把 `UART6` 解释为视觉输入；最终生效的 `vx / vy` 通过两路按轴裸相加形成，`omega` 只由 `UART8` 提供；角色层对两路都采用“保持上一包”的语义，不额外追加等待式同步逻辑。
- 视觉代码可以按设备侧分别维护，但角色入口统一在 `vision/master/` 与 `vision/assistant/` 下；其中主车包只承担串口转发职责。
- 正常运行入口会先识别车号，再切到 `vision/master/` 或 `vision/assistant/` 对应包。
- 辅车车体提供可识别标记，辅车底盘不处理图像数据。

## 路线职责

### 寻找态状态机集

- 寻找态从边线重新起步。
- 主车负责搜索下一个物体。
- 辅车通过识别主车上的色标进行跟随。
- 这一阶段的视觉输入首先服务于“主车找目标、辅车跟主车”。
- 视觉观测需要支撑边线平移避让、主前辅后构型建立、主车绕行和搬运前切入准备。

### 搬运态状态机集

- 搬运态从找到物体并完成切入后开始。
- 这一阶段的视觉输入首先服务于搬运物体保持、构型推进和避障插入。
- 直行推进时，视觉关注两车与搬运物体之间的协同关系。
- 横向协同时，视觉需要服务左右推构型下的推进和稳定性判断。
- 边界收尾阶段与灰度传感器共同服务越线确认。

## 使用原则

- 视觉输入按阶段理解：寻找态和搬运态关注的对象不同，不能混写成同一种观测任务。
- 主车承担视觉相关决策与任务状态切换主线；`vision/master/` 负责 `UART3` 上游控制接入和 `UART8` 速度转发，不在该入口内接入视觉消费实现。
- 主车视觉包作为主车视觉职责落点，不把主车视觉判断逻辑压回共享底盘。
- 辅车角色层当前只承担前馈输入、视觉输入的编排与共享底盘速度写回，不在角色层额外扩第二套底盘执行内核。
- 辅车角色层同时消费 `UART8` 与 `UART6` 上的速度短包；`UART8` 负责提供前馈向量，`UART6` 负责提供视觉修正向量；任一路单独存在时都可以直接形成速度；最终速度控制继续回到共享底盘原生入口。
- 辅车角色层对两路输入按统一速度向量理解：`UART8` 当前包形成前馈向量，`UART6` 当前包形成视觉向量；未出现的速度轴按 `0` 处理；两路都按最近一包持续生效；最终输出对 `vx / vy` 取两路逐轴裸相加结果，对 `omega` 只取 `UART8` 当前值。
- `UART8` 与 `UART6` 的速度短包解析复用同一份共享边界，空白、缺省轴和非法输入判定保持一致；具体字段归属以 [串口通信协议](protocol.md) 为准。
- 视觉职责文档描述“看什么、如何形成控制输入、服务谁、用于什么切换”，不承载逐行实现细节。
- 引入更多视觉设备、更多观测字段或更丰富的环境感知能力时，应在单独设计中明确职责分工与协议字段，再同步更新开发文档。
