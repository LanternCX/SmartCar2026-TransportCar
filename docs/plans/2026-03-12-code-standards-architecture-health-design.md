# code-standards 架构健康规范升级设计文档

## 背景

当前 `.agents/skills/code-standards/SKILL.md` 已经覆盖分层目录, 依赖方向, MicroPython 约束和基本可维护性规则, 但对以下架构健康问题约束不足：

1. God object 在目录和依赖表面正确时继续膨胀。
2. command handler 通过私有字段直接打穿宿主封装。
3. 以“未来扩展”为理由提前引入事件总线, 通用框架或多余适配层。
4. import-time 自动注册伴随静默吞错, 降低系统可观测性。

这些问题不会总是表现为跨层 import 错误, 却会持续破坏长期架构健康。

## 目标

1. 在 `code-standards` skill 中明确“架构健康”不是软建议, 而是 review 必查项。
2. 新增反深耦合, 反过度设计和状态单一所有权规则。
3. 让未来 agent 在 review 时能主动指出职责错位, 边界泄漏和抽象税问题。
4. 保持 skill 简洁可检索, 不把它写成冗长的架构教科书。

## 非目标

1. 不把 skill 改成具体实现方案手册。
2. 不要求所有模块都抽成接口或 protocol。
3. 不鼓励为了满足规则而额外增加样板代码。

## 基线压力场景

基于当前 skill 的基线分析, 存在以下缺口：

1. God object 继续膨胀时, 现有规则主要依赖文件行数和目录归位, 容易放过“职责失控”。
2. command handler 直接改宿主私有字段时, 现有规则没有明确禁止“同层内部也不能打穿封装”。
3. 过早引入事件总线或通用框架时, 现有规则没有“无证据不抽象”的约束。
4. import-time 自动注册伴随静默吞错时, 现有规则没有要求副作用注册必须可观测和可失败。

## 设计方案

### 1. 新增架构健康原则

在 `Core Rules` 和 `Architecture` 段落中补充以下规则：

- 一个运行时状态只能有一个主拥有者。
- 模块协作必须通过显式接口或受控数据结构完成, 禁止依赖跨模块私有字段协议。
- `services/` 只做编排, 不承载算法细节或隐藏状态机。
- 新增抽象必须有真实复用压力支撑, 不能只因为“未来可能会用到”。

### 2. 新增反过度设计规则

- 没有 2 个以上真实消费者时, 不要引入通用框架式抽象。
- 不要为了理论优雅引入事件总线, 插件系统或多层适配器链。
- 优先简单对象边界和可追踪数据流, 再考虑统一抽象。

### 3. 新增反深耦合规则

- 禁止从一个模块直接读写另一个模块的 `_private` 状态。
- 禁止 handler 直接操纵 God object 内部字段。
- import-time 自动注册必须显式失败, 禁止静默吞错后继续运行。

### 4. 升级 review checklist

新增 review 问题：

1. 当前改动是否新增了状态双写或状态归属不明。
2. 当前改动是否让下游模块了解上游对象内部实现。
3. 当前抽象是否真的减少复杂度, 还是只把复杂度搬到了更多文件。
4. 当前实现是否用副作用注册掩盖初始化失败。
5. 当前模块是否在职责上已经接近 God object。

### 5. 升级 review 输出要求

要求 future agent 在 review 中不仅判断“代码是否能跑”, 还要明确指出：

- 职责边界是否清晰。
- 状态是否只有单一主拥有者。
- 是否存在深耦合。
- 是否存在抽象税。
- 是否存在可以先简单实现, 却被过度设计替代的情况。

## 文案策略

1. 保持 skill 描述简洁, 不在 `description` 中写流程摘要。
2. 在 `SKILL.md` 中用短规则和 checklist 落地, 避免大段口号式文字。
3. `README.md` 与 `SKILL.md` 同步, 但以 `SKILL.md` 为主要执行来源。

## 验证策略

1. 使用 4 个基线压力场景复测升级后的 skill。
2. 预期升级后, future agent 能明确指出 God object, 私有字段协议, 过度抽象和静默吞错问题。
3. 若仍存在模糊空间, 继续补充反例与 checklist, 直到规则足够明确。

## 验收标准

1. `code-standards` skill 明确包含架构健康, 反深耦合和反过度设计规则。
2. `README.md` 与 `SKILL.md` 的核心规范保持一致。
3. 基线压力场景在升级后能够得到更明确的 review 结论。
