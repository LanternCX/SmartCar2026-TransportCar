## Title
完成搬运车最小内存占用重构设计与实施计划

## Background / Issue
在板端持续 OOM 和 `TransportCar` import-time 峰值过高的背景下, 讨论结论已从“继续围绕单点 OOM 补丁”转为“以最小内存占用指标为唯一硬门禁, 对 `TransportCar` 及其 owner 边界做系统性重构”。用户进一步要求, 不仅要拆分 `TransportCar`, 还要把节省内存的详细要求写入代码规范, 并让 code review 以内存占用而不是结构整洁度为第一目标。

## Change Unit
完成搬运车最小内存占用重构的正式设计与实施计划，并把内存门禁提升为评审硬约束。

## Actions / Outcome
- Approach 1: 先基于板端证据总结问题形态 -> 确认 `TransportCar` 已演化为 God object, 且 `from services.transport_car import TransportCar` 就可能因申请约 `4168 bytes` 而失败, 不再适合继续做局部 OOM 补丁
- Approach 2: 讨论“先拆文件”与“先做内存资产盘点”两条路径 -> 收敛为先盘点常驻内存和状态 owner, 再按最小依赖原则拆 owner, 避免落入“文件变小但常驻内存不降”的假重构
- Approach 3: 设计内存资产模型和 review 门禁 -> 将运行时对象分为 A/B/C/D/E 五类, 并要求 review 以 `mem_free_after_import/core_init/feature_init/runtime_idle` 与最小诊断面存活作为硬指标
- Final approach: 完成正式设计文档 `docs/superpowers/specs/2026-03-16-transportcar-memory-budget-design.md` 和实施计划 `docs/superpowers/plans/2026-03-16-transportcar-memory-budget.md` -> 明确把 `TransportCar` 降级为编排器, 抽出 `RuntimeCore`、`MinimalCommandRuntime`、`MinimalDiagnostics`、`MotionRuntime`、`VisionRuntimeService`、`FullCommandRuntime`, 并要求同步更新 `AGENTS.md` 与 `code-standards` skill, 把“最小内存占用指标”写入规范和 code review

## Lessons / Refinements
- 在 RT1021 + MicroPython 这类板端环境里, “结构更清晰”不是有效验收标准; 若导入峰值和常驻内存没有下降, 则拆分无效
- 真正治根的顺序应是: 内存资产盘点 -> owner 收口 -> 延迟装配 -> 规范固化 -> review 门禁, 而不是先围绕局部 OOM 点反复补丁
- 代码风格和架构边界需要一起服务于“最小依赖加载”; 全局变量治理本质上是状态 owner 治理, 不能只靠命名或注释约束
- 后续所有 `TransportCar` 相关 review 都应先回答“新增了哪些常驻对象、为什么必须常驻、板端内存证据是什么”, 再讨论结构美观度
