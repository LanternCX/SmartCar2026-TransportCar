## Title
修复 services.car.vision 对 types 模块的板端兼容问题

## Background / Issue
在继续推进搬运车最小内存占用重构后, 板端首个失败点已经从更早的 import-time / init-time OOM 后移到视觉延迟装配路径。最新裸板 traceback 落在 `src/services/car/vision.py`, 具体表现为顶层 `import types` 触发 `ImportError: no module named 'types'`。这说明当前 blocker 已从内存峰值继续后移到 MicroPython 标准库兼容边界。

## Change Unit
修复 services.car.vision 顶层依赖 types 模块导致的 MicroPython 板端导入失败。

## Actions / Outcome
- Approach 1: 先按 TDD 在 `tests/unit/services/test_micropython_compatibility.py` 中新增 `services.car.vision` 的显式装载回归测试, 并模拟板端不存在 `types` 模块 -> 成功复现失败, 错误链明确指向 `src/services/car/vision.py:8`
- Approach 2: 检查 `src/services/car/vision.py` 中 `types` 的真实用途 -> 确认只在禁用视觉路径使用一次 `types.SimpleNamespace`, 没有必要保留整模块依赖
- Final approach: 在 `src/services/car/vision.py` 内新增本地轻量 `_DisabledVisionService`, 替代禁用视觉路径的 `types.SimpleNamespace`, 并移除顶层 `import types` -> 保持 `enabled`, `vision_runtime`, `vision_coordinator` 三个兼容字段不变, 同时消除裸板导入失败

## Lessons / Refinements
- 当板端首错持续后移时, 要先按最新 traceback 修真实 blocker, 不要继续把所有问题都归因为 OOM
- 对 MicroPython 兼容修复应优先采用模块内最小对象替代, 避免为单一占位场景引入新的跨文件抽象
