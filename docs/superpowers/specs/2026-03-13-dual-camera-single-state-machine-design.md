# 主车双摄单状态机协同设计文档

## 背景

当前 `docs/developer/strategy.md` 和 `docs/developer/tasks.md` 的主线仍偏向“主车双摄本地感知, 从车无视觉执行”的早期口径, 但本轮讨论已经把系统边界进一步明确为以下约束:

1. 主车维护唯一任务状态机, 负责双车协同决策。
2. 辅车不处理任何图像数据, 只接收控制目标并执行。
3. 主车安装两颗正交视角摄像头, 两份视觉代码可分开维护。
4. 两颗摄像头共用主车同一条视觉串口, 通过主车轮询实现时分复用。
5. 被点名相机必须立即返回当前缓存结果, 未被点名相机必须严格静默。

与此同时, 当前仓库里的视觉协议、诊断接口和推进任务仍建立在“单一路视觉输入、单框观测”的假设上。若不先把方向文档和执行任务同步改写, 后续实现会同时受到旧方案和新方案牵引, 很容易在协议、状态机所有权和串口资源分配上反复摇摆。

## 目标

1. 明确主车双摄、主车唯一状态机、辅车纯执行的系统主线。
2. 明确两份视觉代码可分开维护, 但必须遵循统一车端协议。
3. 明确双摄共享单视觉串口时的轮询约束, 避免默认成“相机自由持续发包”。
4. 明确 `boot.py` 的新职责: `D8/D9` 负责主车/辅车角色, 上电长按按钮负责脚本入口。
5. 将上述边界落入方向文档和任务清单, 为后续协议和代码实现提供稳定基线。

## 非目标

1. 本轮不直接修改运行时代码、视觉代码或 `docs/Protocol.md` 的线协议细节。
2. 本轮不强制两颗相机共用同一份视觉实现, 只统一协议与车端消费方式。
3. 本轮不要求一次性敲定所有检测类别、置信度字段或串口报文压缩格式。

## 设计原则

1. 任务状态机只能由主车维护, 不允许视觉端或辅车重复维护动作决策主线。
2. 视觉协议传的是观测, 不是动作; 视觉端可以分开实现, 车端动作决策必须统一。
3. 单视觉串口的核心约束不是带宽, 而是轮询秩序; 未被点名相机必须严格静默。
4. 在“稳定完赛优先”的前提下, 优先保证边界清晰、可调试、可回退, 再追求协议通用性。
5. `boot.py` 只负责板级启动入口与角色判定, 不承载任务状态机或视觉业务逻辑。

## 总体方案

### 1. 角色与状态机所有权

- 主车是唯一任务状态机宿主。
- 主车负责双摄观测融合、目标选择、搬运阶段切换、避障决策和辅车控制。
- 辅车不处理图像数据, 只接收主车下发的控制目标并回传执行状态。
- 辅车车体提供可被主车识别的标记, 供主车完成副车对正与阵型保持。

### 2. 双摄分工

- 主车安装两颗视角正交的摄像头。
- 两颗摄像头各自运行独立视觉代码, 不要求同仓统一实现。
- 其中一颗相机重点负责搬运物体与辅车标记观测。
- 另一颗相机重点负责避障与环境观察。
- 两颗相机都只向主车提供观测结果, 不直接驱动车体动作。

### 3. 统一协议边界

- 两份视觉代码虽然分开维护, 但对车端必须遵循同一套查询/响应协议。
- 协议按“单次查询对应单个相机当前缓存帧”来组织, 不要求两颗相机在同一条消息里汇总结果。
- 单次查询允许返回多条检测消息; 返回多少个框, 就回多少条消息。
- 这些消息都属于同一次查询的同一帧结果, 因此协议必须包含批次边界语义, 例如 `frame_id` 和显式结束标记。
- 主车消费的是“来自某个相机当前帧的检测集合”, 而不是“某个固定单框”。

### 4. 轮询与实时性策略

- 主车通过同一视觉串口轮询两颗相机。
- 两颗相机本地持续运行识别算法并维护最新结果缓存。
- 主车发起查询后, 被点名相机立即回当前缓存结果, 不在查询后才开始识别。
- 未被点名相机必须完全静默, 防止同一物理 RX 上发生争线与丢包。
- 搬运同时避障场景下, 建议主车采用有优先级的轮询调度, 不默认严格平均轮询。

### 5. `boot.py` 启动语义

- `D8/D9` 不再用于选择 `PID` / `IMU` / 正常运行脚本。
- `D8/D9` 只用于声明当前车的角色, 即主车或辅车。
- 上电长按按钮 1 时进入 `script/pid_identify.py`。
- 上电长按按钮 2 时进入 `script/calibrate_gyro.py`。
- 上电时未长按按钮则进入 `script/remote_control.py`。
- 角色判定与脚本选择相互独立: 先识别按钮入口, 再在正常运行脚本里读取角色并加载主车/辅车 profile。

## 为什么选择这条路线

### 相比“副车也处理视觉”

- 避免跨车汇聚图像或观测结果, 故障点更少。
- 保持任务状态机单点维护, 不引入双状态机竞争。
- 辅车仍可复用底盘执行链路, 但不会承担视觉协议复杂度。

### 相比“每个目标单独查询一次”

- 查询次数更少, 总线开销更稳定。
- 单次查询取回单相机当前帧的一组结果, 更贴近“缓存帧快照”语义。
- 主车更容易把多条检测结果作为同一批观测来消费。

### 相比“通用多类多框大包一次塞完”

- 串口消息更短, 解析和调试更直观。
- 协议升级可以先围绕“单相机一帧多条消息”落地, 不必一步做成复杂大包。
- 便于不同视觉实现按统一规则分批输出检测结果。

## 风险与约束

1. 若任一相机无法严格静默, 单串口轮询方案立即失效。
2. 若查询响应缺少明确结束标记, 主车无法判断一帧结果是否收齐。
3. 若轮询周期设计不当, 搬运同时避障时仍可能出现观测盲窗。
4. 若主车状态机直接依赖视觉端内部实现细节, 双摄独立维护会迅速失控。
5. `docs/Protocol.md` 仍基于单框输入假设, 后续必须单独升级, 不能长期与本设计并存。
