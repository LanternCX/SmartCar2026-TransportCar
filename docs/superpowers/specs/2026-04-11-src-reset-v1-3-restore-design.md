# 2026-04-11 清空当前 `src` 并恢复 `v1.3.0` 主线设计

> 状态: archive

## 背景

当前仓库的正式运行目录同时包含 `src/legacy`、`src/master`、`src/assistant` 三套结构。它们分别代表：

1. 旧系统归档。
2. 上一轮主辅拆分重构后的新结构。
3. 当前仍在仓库内占位的历史迁移痕迹。

这套结构在上一阶段有过明确用途，但随着近期底盘重构暴露出大量调试困难、功能边界不清和内存压力问题，它已经不再适合作为后续继续推进的正式基础。

用户当前已经明确改变路线：

1. 不再继续围绕当前 `master / assistant` 重构主线修补。
2. 回到自己更熟悉、调试经验更充分的 `v1.3.0` 旧稳定版本。
3. 先把当前仓库的正式运行根重新收敛为单一 `src/`。
4. 后续新的重构、3.0 适配、串口优化与内存治理，都在这个恢复后的单一主线上继续进行。

同时，近期调试已经收敛出一个重要结论：当前阶段最值得后续保留的修补，主要集中在串口热路径和内存分配压力控制上，而不是继续维持当前这套多运行结构本身。因此，这轮更适合先完成“删旧并恢复旧稳定主线”，把后续问题拆到下一轮处理。

## 目标

本轮只追求以下目标：

1. 删除当前 `src/` 下现有的 `legacy / master / assistant` 运行结构。
2. 结束当前仓库中“旧归档 + 中间态重构 + 新主线预留”并存的状态。
3. 以 `../SmartCar2026-TransportCar-donor` 中的 `v1.3.0` 代码为主参考，把旧稳定主线重新恢复到当前仓库的 `src/` 下。
4. 尽量保持 `v1.3.0` 原有目录与运行方式，不在本轮主动做结构再设计。
5. 为下一轮的 3.0 入口适配和串口稳定性修补，准备一个更单纯、更容易继续调试的正式基线。

## 非目标

本轮明确不做以下事情：

1. 不做 `main.py` 单入口的 3.0 固件适配。
2. 不做按钮脚本分发改造。
3. 不做车号开关识别落地。
4. 不做串口协议简化。
5. 不做串口热路径与内存碎片化修补迁移。
6. 不做长期 mono repo 结构优化。
7. 不把当前 `master / assistant` 中已经修过的问题直接混入本轮恢复动作。
8. 不在当前仓库内继续保留 `legacy` 或 `backup` 形式的参考目录。

## 为什么单开这份 spec

现有仓库里的设计文档大多建立在以下前提上：

1. `src/legacy` 作为旧系统冻结归档。
2. `src/master` 与 `src/assistant` 作为当前正式主线。
3. 后续工作围绕主辅拆分结构继续演进。

而用户当前的决定已经改变了这些前提：

1. 当前主辅拆分结构不再继续作为正式主线。
2. `legacy` 不再需要继续留在当前仓库内占位。
3. 当前仓库的正式主线将重新回到单一 `src/`。
4. `v1.3.0` 恢复动作优先于 3.0 适配和后续优化。

这不是对某一份旧 spec 的局部续写，而是一次明确的阶段性回退与基线重建，因此需要单开新的 spec 来约束这轮工作的目标、边界和执行顺序。

## 方案选择

本轮采用“纯恢复型”方案。

其含义是：

1. 先删除当前 `src/` 的现有运行结构。
2. 再尽量按 donor `v1.3.0` 的原有形式恢复到新的 `src/`。
3. 本轮不在恢复动作中主动引入新的目录重构和入口适配。

选择该方案的原因如下：

1. 用户当前最优先的目标是回到熟悉、可控、可继续调试的旧稳定基线，而不是立刻重新设计一套新骨架。
2. 如果在恢复 `v1.3.0` 的同时继续做 3.0 入口改造或新目录设计，会重新把变量数拉高，重复当前这轮“大改动面之后难调试”的问题。
3. 当前仓库内旧 `master / assistant` 的串口修补虽然有参考价值，但它们更适合作为仓库外参考源，而不是继续留在本轮正式结构里。

## 核心决策

### 决策一：当前仓库只保留一个正式运行根 `src/`

本轮完成后，当前仓库内只保留一个正式运行根：`src/`。

这意味着：

1. 后续要运行、要继续修改、要继续调试的正式代码，都直接落在 `src/` 下。
2. 当前 `src/legacy`、`src/master`、`src/assistant` 这类并存结构不再继续保留。
3. 当前仓库不再承担“正式代码”和“参考归档”同时共存的职责。

### 决策二：`v1.3.0` donor 是本轮唯一主参考

本轮恢复动作以 `../SmartCar2026-TransportCar-donor` 中的 `v1.3.0` 为唯一主参考。

这意味着：

1. 第二阶段的首要目标是尽量恢复 donor 的旧稳定主线。
2. 当 donor 代码与当前仓库现状冲突时，本轮优先 donor，而不是优先当前 `master / assistant`。
3. 当前 `master / assistant` 中的已知修补，本轮最多只作为后续查阅参考，不进入本轮正式恢复目标。

### 决策三：参考代码放在仓库外，不放在当前 `src/` 内

用户已经确认，为了保持正式目录整洁，参考代码不应继续塞在当前仓库内部。

因此：

1. donor 仓库继续作为仓库外参考源存在。
2. 若需要保留当前 `master / assistant` 这批代码及其中的串口修补，应通过单独 clone 的仓库在仓库外保留。
3. 当前仓库内不再建立 `backup/`、`legacy/` 之类的参考目录。

### 决策四：本轮恢复优先于适配和优化

本轮的顺序必须固定为：

1. 先删除当前运行结构。
2. 再恢复 `v1.3.0` 主线。

以下动作明确留给后续新 spec：

1. 3.0 固件入口适配。
2. `main.py` 单入口重建。
3. 按钮脚本分发与车号识别设计。
4. 串口协议简化。
5. 串口热路径内存压力修补迁移。

这样做的原因是：

1. 恢复行为基线和优化行为基线不应在同一轮混做。
2. 先恢复旧稳定主线，才能更可靠地判断后续适配和优化到底引入了什么变化。

## 两阶段执行设计

### 阶段一：删除当前 `src` 运行结构

第一阶段只做“退出当前结构”，不做“建立新能力”。

具体要求如下：

1. 删除当前 `src/legacy`、`src/master`、`src/assistant` 及其相关运行内容。
2. 删除或同步调整当前仅服务于这三套结构的测试、布局断言和文档引用。
3. 清理完成后，当前仓库不再保留上一轮结构实验的正式运行目录。

该阶段的完成标准不是“仓库已经能运行”，而是“上一轮正式结构已经被明确退出”。

### 阶段二：恢复 donor `v1.3.0` 到新的 `src`

第二阶段只做“恢复旧稳定主线”，不做“顺手重构”。

具体要求如下：

1. 将 donor `v1.3.0` 的 `src/` 主体重新恢复到当前仓库的 `src/`。
2. 尽量保持 donor 原有目录布局和文件组织。
3. 保留 donor 当时的入口文件、脚本组织和运行方式。
4. 只允许做恢复动作所必须的最小同步，不主动引入 3.0 适配、新目录分层或新的结构抽象。

该阶段的目标不是“恢复后立刻变成最终版本”，而是“让当前仓库重新回到一个你熟悉的旧稳定主线”。

## 提交边界

虽然本轮 spec 只有两个阶段，但提交边界不应被粗暴压成两个巨型提交。

本轮遵循以下约束：

1. “删除当前结构”和“恢复 donor 主线”必须是两个独立改动单元，不能混在一个提交里。
2. 第二阶段如有必要，可以拆成少量几个提交，但每个提交都必须只围绕“恢复 donor 主线”这一类动作展开。
3. 不允许出现把删除、恢复、入口适配、串口修补、目录优化混在一起的大杂烩提交。

判断标准很简单：每个提交都应该能用一句简洁的话说明自己只做了什么。

## 影响范围

本轮会影响以下几类内容：

1. `src/` 下当前所有正式运行目录。
2. 与 `legacy / master / assistant` 布局强绑定的测试文件。
3. 与当前结构强绑定的布局断言和工具口径。
4. 当前描述 `legacy / master / assistant` 并存结构的文档内容。

本轮不应直接影响以下主题：

1. 后续 3.0 入口改造方案。
2. 串口稳定性修补方案。
3. 未来 mono repo 的角色边界设计。
4. 新一轮控制链或视觉链的行为优化。

## 验收标准

本轮完成后，至少需要满足以下标准：

1. 当前仓库内不再保留 `src/legacy`、`src/master`、`src/assistant` 作为正式运行结构。
2. 当前仓库 `src/` 已经重新恢复为 donor `v1.3.0` 的单一正式主线。
3. 当前仓库的正式目录不再混入用于参考的旧重构代码。
4. 本轮没有提前混入 3.0 入口适配、串口协议优化和内存治理改动。
5. 当前仓库后续可以在恢复后的 `src/` 基线上继续推进下一轮适配工作。

## 测试与验证口径

本轮验证重点不是“恢复后已经适配 3.0 并跑通全部新链路”，而是验证结构和基线是否已经正确回退。

因此，本轮验证口径应收紧为：

1. 删除阶段的相关测试和布局检查已经同步更新，不再继续锁定 `legacy / master / assistant` 并存结构。
2. 恢复阶段完成后，当前仓库 `src/` 的目录内容与 donor `v1.3.0` 主线保持一致或只存在恢复所必须的最小差异。
3. 所有与后续阶段有关的 3.0 入口适配、串口优化和新结构设计，都不应在本轮被误报为“已完成”。

## 风险与后续

### 当前已知风险

1. 一旦当前 `src` 被清空，依赖 `master / assistant` 的现有测试和工具链会短暂失效，必须同步调整，不能指望旧测试继续成立。
2. donor `v1.3.0` 恢复后，入口方式和目录组织仍然是旧口径，这会与下一轮 3.0 适配目标形成明显差异，但这是本轮有意保留的差异，而不是遗漏。
3. 当前 `master / assistant` 中已经修过的一些串口问题不会自动进入恢复后的主线，后续必须单独重新规划迁移，不能误以为“恢复 donor”就已经包含这些修补。

### 后续新 spec 的主题

本轮完成后，下一轮应单开新 spec 处理以下主题：

1. `v1.3.0` 恢复后的 3.0 固件入口适配。
2. `main.py` 单入口、按钮脚本分发和车号识别设计。
3. 串口热路径和内存碎片化问题的修补迁移。

## 结论

这轮工作的本质不是“继续打磨当前重构”，而是一次有意识的主线回退：

1. 先把当前仓库从 `legacy / master / assistant` 并存结构里退出来。
2. 再把 donor `v1.3.0` 重新恢复为当前仓库唯一正式主线。
3. 把 3.0 适配和串口优化明确留到下一轮。

这样做的价值不在于一步到位，而在于先把当前仓库重新变回一个边界清楚、便于继续推进的单一基线。
