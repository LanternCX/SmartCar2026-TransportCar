# 主辅运行时控制边界与迁移补完规范

## 背景

上一轮已经完成了一次主辅运行时结构清晰化重构, 主要解决了以下问题:

1. `config.py` 与 `runtime_params.py` 的边界开始收口。
2. 主车重复入口壳已经删除。
3. 主辅入口装配已经明显收薄。
4. 辅车跨周期状态已经从控制层名义上剥离出来。
5. `stability/` 目录已经从主线删除。

但这轮 review 进一步暴露出一个更深的问题:

**目录层级已经比之前清楚, 但控制职责仍然没有真正从大运行时里拆出来, 注释质量也还不足以支撑后续维护。**

当前剩下的问题不是“还有几个文件名不够好”, 而是:

1. `motion_runtime.py` 仍然过重, 同时承担长期状态、硬件读写、控制计算、命令处理和部分控制状态维护。
2. `ctrl/` 目录名已经表达了控制边界, 但真正属于控制的内容仍有相当一部分滞留在运行时 owner 中。
3. `src/assistant/ctrl/chassis.py` 仍然保留了一个没有真实职责的空壳边界, 与“不保留兼容层”的要求冲突。
4. 现有注释很多仍停留在“文件标题”层, 没有解释职责、边界、依赖关系和保留原因。
5. `stability/` 虽然已经从目录层删除, 但需要对原先承担过的有效能力逐项对表, 证明哪些已经迁移、哪些已经并回其他职责、哪些已确认不再需要。

因此这一轮不是补零碎问题, 而是要把“运行时 owner”和“控制层”继续拆开, 并把上一轮留下的迁移闭环补完整。

## 当前版本基线结论

基于当前仓库代码与删除前 `stability/` 文件的对照, 本轮先确认一个事实基线, 后续实现必须直接以此为起点, 不再把“是否完整保留”留作开放式检查题:

1. **当前版本没有完整保留旧 `stability` 的全部能力落点。**
2. **当前版本仍然保留了车自身状态稳定和滤波主链所需的核心运行能力, 但这些能力大多还塞在 `motion_runtime.py` 里, 没有回到清晰的控制边界。**
3. **当前版本没有证明旧 `stability` 的全部辅助能力都已被明确迁移或明确退役。**

具体按当前代码可分为三类:

### 一、已实际保留在运行主链中的能力

这些能力当前仍在主线运行, 只是多数仍滞留在 `motion_runtime.py` 内部实现中:

1. 角速度低通滤波。
2. 编码器速度中值滤波与差值限幅。
3. 双窗口回归滤波链。
4. 基于四元数积分的朝向估计。
5. 轮速闭环与输出限幅。
6. 车体系到世界系的位移换算, 至少辅车 `rotate_body_delta_to_world` 已迁出到 `ctrl/kinematics.py`。

### 二、当前仍存在但落点不正确的能力

这些能力没有丢, 但还没有按本轮目标回到明确的控制层:

1. 主辅运行中的滤波链对象与滤波状态。
2. 主辅运行中的姿态积分状态。
3. 主辅运行中的运动学与里程更新辅助。
4. 主辅运行中的轮速控制器状态。

这些内容当前集中在 `src/master/motion_runtime.py` 和 `src/assistant/motion_runtime.py`, 所以本轮的计划不是“再去确认它们在不在”, 而是**把这些已存在能力迁回正确边界并写清职责**。

### 三、当前未见明确承接或已不再暴露的旧能力

下面这些旧 `stability` 能力在当前版本中未见明确承接入口, 也没有被正式声明为退役:

1. `euler_to_quaternion`
2. `quaternion_to_euler`
3. `body_axis_semantics`
4. `HeadingController`
5. `build_speed_filter_chain`
6. `build_gyro_filter`

这些项不能继续保持“可能不需要, 但也没有明确结论”的状态。本轮必须把它们逐项归为以下两类之一:

1. **仍然是维护车自身状态稳定或滤波链路所必需的能力**: 则迁回明确控制落点并补测试或留证。
2. **仅是旧辅助接口, 当前主线已不再需要**: 则在对表文档中明确写出删除依据, 不能只靠“没人调用”。

## 本轮 review 收口

本轮 review 统一收口为 5 个主目标:

1. 把不合格注释按仓库规则重写, 不再保留空注释和标题式注释。
2. 拆轻主辅 `motion_runtime.py`, 把错误聚集在大对象中的状态和控制职责继续拆开。
3. 删除辅车 `ctrl/chassis.py` 空壳, 不保留任何没有真实职责的兼容层。
4. 把真正属于控制层的计算、滤波、控制器状态和控制辅助逻辑继续并回 `ctrl/`。
5. 对已删除的 `stability/` 做逐项对表, 明确原能力现在的真实归属, 并把未迁完的部分补齐。

## 目标

本轮必须同时达成以下目标:

1. 主线运行链优先按面向过程方式组织, 不再默认先封装成大运行时对象。
1. 主辅 `motion_runtime.py` 产出一份拆分清单, 明确当前仍保留在运行时 owner 中的内容及保留理由。
2. 长期状态、控制内部状态、控制算法、硬件访问、命令处理的落位规则形成可复核的对照说明。
3. `ctrl/` 目录中的主要文件都有可解释的真实职责, 不再只是目录名叫控制层。
4. `src/assistant/ctrl/chassis.py` 这类空壳边界被删除, 不再保留无职责文件。
5. 关键注释形成明确补齐范围, 不再停留在重复文件名或类名的层面。
6. 原 `stability/` 的有效能力逐项对表, 可以清楚解释现在分别落到哪里。
7. 如果发现某项 `stability` 能力只是被删掉而没有迁移, 必须在本轮补齐或明确判定为不再需要。
8. 凡是跨控制周期维护的变量, 默认统一收口到 `state/` 目录管理, 不再散落在运行时 owner 顶层属性里。

## 非目标

本轮不做以下内容:

1. 不改变主车与辅车现有业务目标。
2. 不重新引入新的总控运行时或新的跨目录总装配层。
3. 不为了“看起来抽象更完整”而平白增加新的空目录、空类或空壳文件。
4. 不为了未来兼容继续保留无真实调用价值的别名层、导出层或兼容层。
5. 不修改当前主辅最小协议语义, 除非为了把职责迁回正确位置且行为保持一致。
6. 不把这轮工作扩展成新的功能开发。

## 核心边界

### 一、运行时 owner 边界

1. 主线运行链默认按面向过程方式展开, 例如按“读取输入 -> 更新状态 -> 计算控制 -> 下发输出”组织。
2. `motion_runtime.py` 只保留整周期编排、硬件链路驱动、状态 owner 持有和对外主入口职责。
3. 不再默认把整条主线封装成大运行时对象; 只有确实需要跨周期保存的状态, 才进入 `state/` 容器。
4. 运行时 owner 可以调用控制层, 但不应继续内嵌过多控制实现细节。
5. 运行时 owner 不再承担“控制工具箱”职责。
6. 运行时 owner 内部若仍需保留少量辅助状态, 必须能解释其为什么不能移入控制层或状态层。

### 二、状态边界

1. 长期状态只保存跨周期状态字段与最小状态语义。
2. 长期状态不承担控制计算、滤波、控制器输出更新和硬件访问。
3. 控制器自身需要跨周期保存的内部状态, 也应统一收口到 `state/` 目录中的状态容器, 不再散落在 `motion_runtime.py` 顶层属性里。
4. `state/` 是跨控制周期变量的统一入口, 但不要求都写在一个文件中; 可以按职责拆成多个状态文件或状态容器。
5. 运行时 owner 持有状态对象, 但不能把跨周期变量继续直接挂满 owner 顶层属性。

### 状态与控制落位对照

1. 业务长期状态放在状态对象中, 例如跟随状态、里程、朝向、最小状态输出相关字段。
2. 跨控制周期的控制内部状态也放在 `state/` 目录中的状态容器里, 例如滤波窗口、积分项、控制器输出缓存。
3. `ctrl/` 负责消费这些状态并做单周期计算, 但不负责分散持有跨周期变量。
4. 运行时 owner 只保留调度所必需的少量装配状态, 例如硬件句柄、周期缓存、最近一次快照。
5. 若某项状态既不属于调度装配, 又需要跨周期保存, 默认视为应进入 `state/`。
6. 若某项内容无法直接归入以上三类, 需要在实现中写明“为什么必须暂留在 owner 中”。

### 三、控制边界

1. `ctrl/` 只保留真正属于控制的东西: 控制计算、滤波、运动学、姿态估计辅助、控制器内部状态容器或控制工具函数。
2. 控制层不持有业务长期状态 owner, 也不承担协议命令分发。
3. 控制层可以读取 `state/` 中统一维护的跨周期状态, 但不再自己零散创建和挂载这些状态。
4. 如果某段逻辑在主辅两侧本质上都是单周期控制计算, 应优先收回 `ctrl/` 而不是留在 `motion_runtime.py`。
5. 控制层文件必须能解释“这个文件为何存在、输入是什么、输出是什么”。

### 四、注释边界

1. 文件头注释必须说明职责, 不能只重复文件名。
2. 较长类和关键函数必须写清楚: 它负责什么、依赖什么、为什么放在这里。
3. 对跨周期状态容器、控制状态容器、运行时 owner、迁移落点文件都要补足边界注释。
4. 不补流水账注释, 只补帮助理解边界和保留原因的注释。

### 五、迁移闭环边界

1. `stability/` 删除不等于迁移完成。
2. 必须逐项列出原 `stability` 中曾承担的有效能力。
3. 对每一项能力, 必须说明现在是:
   - 已迁移到哪个文件
   - 已并入哪个既有职责
   - 已确认不再需要, 以及为什么不再需要
4. 不接受“目录没了且测试能过”作为迁移完成的唯一证据。

## 结构约束

### 一、`motion_runtime.py` 拆轻要求

1. 先盘点主辅两个 `motion_runtime.py` 中的内容, 按以下类别分类:
   - 长期业务状态
   - 控制内部状态
   - 硬件访问
   - 单周期控制计算
   - 命令处理与调度
   - 状态回包
2. 其中“单周期控制计算”和“控制内部状态”优先评估是否可迁入 `ctrl/`。
3. 迁移后主线优先改写成顺序清楚的过程式链路, 而不是继续堆在大类的方法集合里。
4. 迁移后 `motion_runtime.py` 应保留为“调度 owner”或最小主线入口, 而不是“大型实现仓库”。
5. 如果某段逻辑因性能或内存原因必须暂留 `motion_runtime.py`, 需要在注释里明确说明保留理由。

### 二、空壳文件清理

1. 删除 `src/assistant/ctrl/chassis.py`。
2. 本轮只额外清理与本次拆责直接相关、且已确认无真实职责的同类空壳文件。
3. 不得为了“未来可能有用”保留无实现、无调用、无唯一职责的边界文件。

### 三、`ctrl/` 目录收口要求

1. `ctrl/` 下的文件要按真实职责命名和承载。
2. 不把“运行时 owner 的私有实现堆”伪装成控制层。
3. 运动学、滤波、姿态、控制器、限幅和类似控制辅助逻辑, 应优先聚合到控制层。
4. 主辅两侧的 `ctrl/` 至少要做到“看目录名就能大致知道控制职责在哪里”。

## `stability/` 逐项对表要求

本轮必须产出一份可复核的迁移对表, 以原 `src/master/stability/` 与 `src/assistant/stability/` 的文件和其中有效能力为基线逐项列出, 不接受只按大类概述。

对表时每一项至少要回答:

1. 原文件路径。
2. 原能力名称或作用。
3. 现在的落点文件, 或“已删除”。
4. 去留结论: 已迁移、已并入、已删除。
5. 这样处理的依据。
6. 对应验证方式, 例如现有测试、补充测试或人工可复核说明。

对表必须至少覆盖原 `stability/` 中的姿态、滤波、控制、运动学相关能力。如果对表后发现仍有遗漏, 需要把遗漏项补迁或补注释说明, 不允许继续保持“目录删了, 但职责悬空”的状态。

本轮对表不能停留在“列清单”, 还必须直接输出结论与动作:

1. 哪些能力当前已经在主线运行, 但需要迁回 `ctrl/`。
2. 哪些能力当前仍在 `motion_runtime.py` 中承担稳定或滤波职责, 需要拆出。
3. 哪些旧能力确认不再需要, 可以正式退役。
4. 哪些旧能力如果缺失会影响车自身状态稳定或滤波链路通畅, 必须在本轮补回。

其中“影响车自身状态稳定或滤波链路通畅”的能力, 本轮默认至少包括:

1. 朝向估计与朝向保持相关能力。
2. 速度输入滤波链相关能力。
3. 轮速控制与输出限幅相关能力。
4. 里程与车体位移换算相关能力。

因此这份 spec 的执行目标不是再去判断“要不要检查”, 而是**按上述分类直接完成迁移、退役说明和承接落点收口**。

## 测试与验证约束

### 一、测试约束

1. 新增或调整测试时, 优先保护职责边界和迁移结果, 而不是保护目录形状。
2. `motion_runtime` 拆轻相关测试应优先验证:
   - 运行时 owner 仍能驱动主链
   - 控制层真实入口生效
   - 状态对象与控制内部状态不再混用
3. `stability` 迁移相关测试应优先验证迁移后真实入口行为, 而不是验证旧目录消失。

### 二、验证约束

1. 必须补一份 `stability` 迁移对表留证, 作为本轮完成标准的一部分。
2. 至少完成与实际改动直接相关的主机侧测试回归。
3. 若本轮改动触及主辅运行时入口或控制主链, 再同步更新对应板端验证文档。
4. 不允许只凭主观解释宣称“已经迁移完成”。

## 本轮优先修改点

1. 先盘点主辅 `motion_runtime.py` 中哪些内容属于控制层, 形成拆分清单。
2. 删除辅车 `ctrl/chassis.py` 空壳。
3. 先把主线改写为清楚的过程式执行链, 再决定哪些最小状态容器必须保留。
4. 把可独立的控制计算、控制器状态和控制辅助逻辑迁回 `ctrl/`。
5. 把长期业务状态和控制内部状态统一收口到 `state/` 目录, 按职责拆分维护, 不再全堆在大运行时对象顶层。
5. 重写关键注释, 至少覆盖 `src/master/motion_runtime.py`、`src/assistant/motion_runtime.py`、状态对象文件、承担迁移结果的控制文件以及 `stability` 对表文档中列出的承接文件, 重点写职责和边界。
6. 先按“已保留但落点错误 / 未明确承接 / 可正式退役”三类整理原 `stability/` 能力, 再执行对应迁移或退役说明。
7. 对会影响车自身状态稳定和滤波链路通畅的能力优先补位, 不把这部分留到后续再判断。
8. 更新测试与验证材料, 证明迁移后的真实入口仍然成立。

## 完成标准

1. 主辅主线已经改成以过程式链路为主, 不再默认依赖大运行时对象承载整条流程。
2. 产出主辅 `motion_runtime.py` 拆分结果清单, 明确哪些内容留在 owner、哪些迁入 `ctrl/`、哪些进入状态对象。
3. 产出状态与控制落位对照说明, 能逐项解释长期状态、控制内部状态和 owner 装配状态分别放在哪里, 并明确跨控制周期变量已统一收口到 `state/` 目录。
4. `src/assistant/ctrl/chassis.py` 已删除, 且没有新的空壳替代它。
5. 主辅 `ctrl/` 中承接本轮拆分的运动学、滤波、姿态、控制器和限幅相关能力已有明确真实落点, 并在文件注释或文档中可复核。
6. `src/master/motion_runtime.py`、`src/assistant/motion_runtime.py`、状态对象文件、承担迁移结果的控制文件以及 `stability` 对表文档中列出的承接文件已补足职责边界注释。
7. 原 `stability/` 的有效能力已有逐项对表, 每项都能看到原位置、现位置、去留结论、依据与验证方式。
8. 若有原 `stability` 能力未继续保留, 已写明删除依据; 若需保留, 已完成补迁。
9. 车自身状态稳定与滤波链路所需能力已有明确承接落点, 不再存在“当前仍靠 `motion_runtime.py` 私有实现硬撑, 但 spec 未要求收口”的遗漏。
10. 跨控制周期变量不再零散挂在 `motion_runtime.py` 顶层属性上, 而是统一进入 `state/` 目录管理。
11. 与本轮实际改动直接相关的主机侧测试回归通过。
12. 若本轮改动触及 HIL 文档对应入口, 相关文档已同步更新。
