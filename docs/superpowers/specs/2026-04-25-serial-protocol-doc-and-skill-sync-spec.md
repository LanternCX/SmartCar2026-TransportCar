# 串口协议文档与 Skill 约束同步 Spec

执行状态：Archive  
创建日期：2026-04-25  
范围：只修改协议相关文档与仓库 Skill 约束，不修改运行时代码。

## 1. 目标

本 Spec 只描述如何把当前串口协议文档演进为两层通信模型：

1. UDP 模式：用于高频、短包、允许丢包的数据流。
2. TCP 模式：用于低频、必须确认、可重复发送的可靠同步。

本 Spec 同时要求把“低带宽串口上不能膨胀高频包”等约束写入开发者文档正文。Skill 只保留路由与执行约束，不作为正式协议正文的主要承载位置。

本 Spec 不设计具体状态机，不定义各模块职责，不规定具体任务含义，不修改代码。

本次协议文档重构不保留兼容层。旧协议正文、旧查询说明和旧字段口径若不属于新 UDP / TCP 双模式协议，应直接删除或改写，不通过“兼容旧格式”“历史保留”“旧版说明”等方式继续留在正式正文中。

## 2. 背景约束

串口链路带宽有限，其中无线串口链路尤其需要控制包长。协议设计必须优先保证高频包短小，不能为了可靠性把所有包都做成重字段结构。

通信可靠性需求分为两类：

- 高频数据只关心最新值，允许丢包。
- 低频同步不能依赖单次发送，需要建立可靠确认过程。

因此，协议文档应把“数据流”和“可靠同步”分开描述，而不是把所有信息塞进同一种包结构。

## 3. 协议总体模型

协议分为两层：

### 3.1 UDP 模式

UDP 模式用于高频数据流。它的目标是低带宽占用和最新值优先。

约束：

- 包结构必须短。
- 默认不确认。
- 默认不重传。
- 默认只保留最近一包。
- 丢包不触发状态回退。
- 需要归零或停用时必须显式发送零量或停用量，不能把缺包解释成零量。
- 高频包不默认携带完整同步上下文，避免包长膨胀。

### 3.2 TCP 模式

TCP 模式用于低频可靠同步。它的目标是让双方确认某个同步上下文已经建立。

约束：

- 使用短包。
- 发送端重复发送同步包，直到收到确认。
- 接收端收到同步包后回确认。
- 同一个同步包重复到达时，接收端必须按幂等规则处理。
- 旧同步包到达时，接收端必须能忽略。
- TCP 模式只做轻量可靠同步，不实现完整 TCP 协议。

## 4. 抽象包类型

协议文档应定义抽象包类型，而不是绑定到具体业务模块。

最小类型：

| 类型 | 模式 | 抽象用途 |
| --- | --- | --- |
| `s` | TCP | 同步上下文 |
| `a` | TCP | 确认同步上下文 |
| `v` | UDP | 速度或控制量数据流 |
| `o` | UDP | 观测或误差数据流 |
| `r` | UDP 或半可靠 | 状态或结果回报 |

后续可以在这两种模式上继续扩展更多包类型，但扩展时必须先判断它属于 UDP 还是 TCP。

## 5. TCP 同步过程

可靠同步使用“重复发送 + 确认 + 幂等”的最小过程。

基本流程：

1. 发送端生成新的同步编号。
2. 发送端发送同步包。
3. 接收端收到同步包后，更新本地同步上下文。
4. 接收端发送确认包。
5. 发送端收到确认包后，认为同步完成。
6. 若发送端未收到确认包，则间隔重发同步包。
7. 接收端再次收到同一同步包时，不重复初始化，只重新确认。
8. 接收端收到旧同步包时，忽略该包。

同步包表达的是“当前同步上下文”，不是一次性事件。这样重发不会造成重复动作。

## 6. UDP 数据流过程

UDP 数据流在同步上下文建立后运行。

基本规则：

- 数据流按当前已建立的同步上下文解释。
- 数据流只保留最新值。
- 数据流不等待上一包处理完成。
- 数据流不要求逐包确认。
- 数据流包长优先级高于可读性。
- 如果某类数据流必须带同步编号，必须说明为什么值得牺牲带宽。

## 7. 包长设计规则

协议文档应明确：高频包优先使用短字段、位置字段或固定顺序字段。

推荐方向：

```text
v,1.2,0.3
s,12,3,1
a,12
```

不推荐把高频包写成冗长键值结构：

```text
type=stream,state=12,vx=1.2,vy=0.3
```

键值结构可用于低频调试、人工可读文档示例或非高频链路，但不得作为无线高频链路的默认要求。

## 8. 可扩展性规则

后续新增协议字段或包类型时，应先回答：

1. 它属于 UDP 模式还是 TCP 模式。
2. 它是否高频发送。
3. 它是否必须可靠到达。
4. 它是否必须每包携带同步上下文。
5. 它是否会显著增加无线串口带宽占用。

只有低频 TCP 同步包可以优先考虑可读性；高频 UDP 包必须优先考虑短包。


## 9. 兼容层删除原则

本次虽然是文档修改，但协议口径按正式重构处理，不保留兼容层。

要求：

- 不保留旧协议格式作为正式可用路径。
- 不保留旧查询协议作为正式可用路径。
- 不用“兼容旧链路”解释新协议。
- 不在正式协议正文中维护旧字段和新字段的双轨说明。
- 若旧内容只服务历史理解，应删除；需要追溯时依赖 git 历史，而不是正式文档。

## 10. 车端查询协议退役

当前协议文档中的车端状态查询内容属于冗余设计。后续同步协议文档时，应删除正式协议中的状态查询部分，不再把车端查询作为主线能力保留。

退役范围包括：

- 面向常规运行的车端状态查询协议。
- 为查询协议保留的字段表、响应格式和长期维护说明。
- 因查询协议引入的正式链路复杂度。

保留边界：

- 必要的现场调试可以使用临时日志、临时脚本或人工联调记录承接。
- 临时调试能力不得反向写成正式通信协议。
- 若未来确实需要诊断能力，应作为独立调试链路重新设计，不默认恢复通用查询协议。
