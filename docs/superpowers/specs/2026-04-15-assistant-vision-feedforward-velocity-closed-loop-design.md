# 2026-04-15 辅车视觉层速度前馈与本地视觉闭环设计

> 状态: Archive
> 当前约束以 `docs/developer/control.md`、`docs/developer/vision.md` 与 `.agents/skills/using-rules/references/strategy-and-control.md` 为准。

## 背景

当前仓库已经在 `src/vision/` 下为主车与辅车预留了角色层入口, 其中 `src/vision/assistant/` 是辅车运行链的正式角色边界。

本轮要接入的能力只聚焦一条最小但真实的辅车闭环:

1. 主车通过 `UART3` 向辅车转发当前已有控制协议中的速度控制量。
2. 辅车通过本地视觉输入持续观察主车标记并形成纠偏量。
3. 辅车把“现有控制协议中的速度控制量 + 本地视觉闭环”合成为统一的速度控制目标。
4. 合成结果直接进入辅车底盘当前已有的速度执行主链。

本轮有两条已经固定的实施边界:

1. 不改 `TransportCar` 与 `services/` 下的内核实现。
2. 只在 `src/vision/assistant/` 这一层完成接入和角色逻辑。

因此, 这次设计的关键不是继续扩内核, 而是把 `src/vision/assistant/` 从“角色入口”提升为“辅车闭环正式入口”, 让它真正承担辅车侧的信号接入、融合和失效收口职责。

## 目标

1. 在 `src/vision/assistant/` 内建立辅车专属的速度闭环入口。
2. 让 `UART3` 上的现有控制协议和 `UART6` 上的现有视觉协议进入同一条辅车运动控制链, 不能形成两套并行控制。
3. 保持底盘内核、底层控制环和现有执行核心不改动。
4. 保持辅车主控制量为速度式表达, 不回退到位置式主链。
5. 保留当前角色分层方向: 辅车如何跟随由 `vision/assistant` 负责, 内核只负责稳定执行。
6. 保持主车侧职责收口为“当前速度控制量转发”, 不在本轮扩展主车侧新的控制协议主题。

## 非目标

1. 不在本轮实现完整的寻找态、搬运态或双车总状态机。
2. 不在本轮重构 `TransportCar`、`command_router`、`services/vision_*` 或共享控制核心。
3. 不在本轮重写辅车本地视觉算法本身, 只规定车端如何接入和消费它的输出。
4. 不在本轮改动板级硬件分配、引脚定义和串口硬件事实。
5. 不在本轮引入新的主车侧自主任务逻辑。
6. 不在本轮把所有异常恢复策略扩成比赛全流程规则, 只收口这条闭环自身的最小安全语义。

## 已确认边界

1. 当前正式角色边界已经固定在 `src/vision/master/` 与 `src/vision/assistant/`。
2. 当前内核已经具备速度指令入口, 可消费 `vx / vy / omega` 这类速度目标。
3. 当前内核已经具备基础执行、安全停下和状态查询能力。
4. 当前 `UART6` 视觉输入正式文本格式为单行 `vx=<vx>,vy=<vy>`。
5. 当前主辅通信链路使用 `UART3` 字符串协议。
6. 本轮用户明确要求不动内核, 只在 `vision` 层接入。
7. 本轮用户明确要求辅车闭环必须融入辅车运动控制主链, 不能做成外挂修正层。
8. 本轮用户明确要求主控制量按速度式主链理解。

## 方案比较

### 方案一: 继续让内核直接消费两路输入, `vision/assistant` 只做轻量转发

这个方案的表面改动最少, 但有两个直接问题:

1. 辅车本地视觉和 `UART3` 上的控制协议速度量会分别进入不同入口, 控制权边界不清楚。
2. `vision/assistant` 仍然只是空壳, 辅车专属逻辑继续回流到内核。

这个方案不满足“闭环融入辅车运动控制, 但角色差异留在视觉层”的要求, 不采用。

### 方案二: 在 `vision/assistant` 建立辅车闭环正式入口, 通过现有速度接口和内核通信

这个方案的核心做法是:

1. `vision/assistant` 负责接管辅车本地视觉输入和 `UART3` 上现有控制协议中的速度控制包。
2. `vision/assistant` 在本层完成缓存、新鲜度判断、融合和最小失效处理。
3. `vision/assistant` 把融合后的统一速度目标通过当前已有速度接口交给内核执行。

这个方案满足本轮全部关键边界:

1. 功能完整地进入辅车运动控制主链。
2. 内核不改动。
3. 辅车专属逻辑停留在角色层。

本轮推荐采用这个方案。

### 方案三: 直接给内核增加辅车跟随模式

这个方案从长期看可能更统一, 但和本轮边界直接冲突:

1. 它要求修改 `TransportCar` 与共享控制核心。
2. 它会把辅车专属逻辑重新压回共享层。

本轮不采用。

## 推荐方案

本轮采用方案二。

一句话概括为:

`src/vision/assistant/` 负责把 `UART3` 上现有控制协议中的速度控制量和 `UART6` 的本地视觉纠偏融合成一份辅车速度目标, 再通过现有速度接口交给内核执行。

这个方案的判断依据如下:

1. 它满足“闭环必须融入辅车运动控制主链”的要求。
2. 它满足“当前先不动内核”的硬边界。
3. 它把辅车专属逻辑放在已经存在的角色层, 没有重新发明入口。
4. 它保持主辅通信继续沿用现有控制协议, 不需要再为这条闭环单独发明新的串口协议。

## 总体架构

### 角色层职责

`src/vision/assistant/` 在本轮承担以下职责:

1. 接管辅车本地视觉输入的读取与解释。
2. 接管 `UART3` 上现有控制协议速度控制包的读取与解释。
3. 真正进入辅车运行时控制周期, 而不是只在入口层返回一个对象。
4. 真正参与串口读取编排, 而不是把两路输入继续完全留给共享底盘默认处理。
5. 维护控制协议速度控制包缓存和视觉缓存的新鲜度判断。
6. 根据两路输入生成统一的辅车速度控制目标。
7. 在输入异常时输出保守的停下或降级语义。
8. 向内核提交融合后的速度目标。
9. 对外暴露最小调试观测, 便于联调时判断当前由哪一路主导。

### 内核职责

内核在本轮继续只承担以下职责:

1. 执行融合后的速度目标。
2. 保持自身底层速度环、方向保持和安全约束。
3. 保持当前查询、复位和基础诊断能力。

内核在本轮不新增辅车跟随语义, 不直接理解“为什么跟”或“如何融合”。

### 层间边界

本轮层间边界固定如下:

1. `vision/assistant` 对内核只提交统一的速度目标。
2. `vision/assistant` 不直接改写内核控制算法。
3. `vision/assistant` 不把两路输入分别交给内核各自处理。
4. 内核不反向承担辅车视觉闭环融合职责。
5. `vision/assistant/runtime.py` 必须成为实际运行时的一部分, 进入 `step()` 控制周期并承担串口读取编排边界, 不能继续停留在“创建后直接 return”的空壳形态。

## 控制语义

### 统一控制量

本轮统一控制量采用辅车车体系速度:

1. `x+` 表示右移。
2. `y+` 表示前进。
3. `omega+` 表示顺时针。
4. 最终输出量为 `vx / vy / omega`。

所有融合结果都以辅车车体系速度表达后再交给内核执行。

### 控制协议语义

主车发送给辅车的是当前已有控制协议中的速度控制量, 不是新协议, 也不是位置目标。

本轮将其定义为:

1. `UART3` 上继续沿用当前已有控制协议。
2. 辅车角色层在其中只消费速度控制包, 最小字段集包含 `vx / vy / omega`。
3. 这些速度控制量在辅车角色层内被解释为节奏输入, 不表达视觉纠偏结果。

这条边界意味着:

1. 本轮不新增主辅通信协议字段。
2. 主车侧只负责把当前速度控制量按现有控制协议转发给辅车。
3. 辅车侧角色层负责把这些现有控制协议速度包当作融合输入, 而不是让它们先直接落进共享内核执行。

### 视觉语义

辅车本地视觉继续通过 `UART6` 输入, 文本格式继续按单行 `vx=<vx>,vy=<vy>` 接入, 但在辅车角色下, 这两个字段的消费语义由 `vision/assistant` 解释为本地闭环观测输入。

本轮只固定以下事实:

1. 视觉输入服务于辅车本地纠偏。
2. 视觉输入不会直接绕过角色层进入内核控制决策。
3. 视觉侧输出的具体识别算法、目标提取方法和参数调法不在本 spec 中展开。

### 融合规则

本轮融合规则固定为“控制协议速度量给节奏, 视觉做纠偏”。

即:

1. `vx / vy` 由“控制协议中的速度控制量 + 本地视觉修正速度”合成。
2. `omega` 默认以 `UART3` 上转发来的当前角速度控制量为主, 没有有效控制量时回到辅车本地方向保持。
3. 本地视觉在本轮不单独生成外部角度目标。
4. 融合输出必须经过统一限幅后再提交给内核。

这条规则的目的不是让视觉和控制协议速度量互相抢主导, 而是让它们在同一条速度链里各自承担不同职责。

## 输入接管规则

当前内核本身已经具备默认串口消费逻辑。为了满足“只在视觉层接入, 但不让两套控制并行”的要求, 本轮需要在 `vision/assistant` 明确接管两路输入:

1. 辅车角色下, `UART6` 上供本地视觉闭环使用的数据由 `vision/assistant` 优先消费。
2. 辅车角色下, `UART3` 上现有控制协议中的速度控制包由 `vision/assistant` 优先消费。
3. `UART3` 上的普通查询和非速度控制命令仍按当前链路留给内核处理。

这样可以保证:

1. 本地视觉输入不会同时触发内核内部的默认视觉控制链。
2. `UART3` 上的速度控制包不会先被当成普通速度命令直接写入内核, 再被角色层二次覆盖。

## 最小状态

本轮在 `vision/assistant` 内只建立最小工作状态, 不引入比赛级大状态机。

建议状态集合如下:

1. `idle`: 当前没有形成有效闭环输出, 向内核提交零速度。
2. `tracking`: 视觉有效且控制协议速度量有效, 输出融合后的正式跟随速度。
3. `vision_only`: 视觉有效但控制协议速度量超时, 仅保留视觉闭环, 同时收紧速度上限。
4. `fault_stop`: 视觉失效或输入非法, 立即提交零速度并等待有效输入恢复。

这个状态集合体现两条判断:

1. `UART3` 上转发来的速度控制量是增强项, 超时后可以降级为保守的视觉单撑模式。
2. 本地视觉是当前辅车闭环的安全锚点, 一旦失效就不能继续盲跑。

## 失效处理

本轮异常收口采用保守语义, 但不牺牲闭环完整性。

### 视觉失效

视觉失效包含以下情况:

1. `UART6` 输入超时。
2. 数据格式非法。
3. 观测值被判定为无效。

处理原则:

1. 立即切到 `fault_stop`。
2. 向内核提交零速度。
3. 不沿用上一拍速度继续盲跑。

### 控制协议速度量失效

控制协议速度量失效包含以下情况:

1. `UART3` 上的速度控制包输入超时。
2. 速度控制包格式非法。
3. 速度控制值越界。

处理原则:

1. 清空控制协议速度量贡献。
2. 若视觉仍有效, 降级到 `vision_only`。
3. 若视觉也无效, 进入 `fault_stop`。

这个判断比“`UART3` 速度控制量一断就直接停”更贴近本轮目标, 因为当前真正的闭环锚点是辅车本地视觉, 而主车转发来的控制量职责是把跟随链路做硬而不是替代视觉。

## 目录与职责建议

本轮 spec 推荐 `src/vision/assistant/` 内至少形成以下职责分工:

1. `runtime.py`
   负责装配辅车角色运行链, 创建底层内核对象, 并挂接辅车角色层。
2. `follow_runtime.py`
   负责角色层主循环、输入接管、状态推进和对内核的统一输出。
3. `control_protocol_input.py`
   负责解析 `UART3` 上现有控制协议中的速度控制包, 并维护最近一次有效控制量与超时判断。
4. `vision_input.py`
   负责解析 `UART6` 本地视觉输入并维护视觉缓存与有效性判断。
5. `velocity_fusion.py`
   负责把控制协议速度量和视觉纠偏速度融合为统一输出。
6. `diagnostics.py`
   负责组织辅车角色层最小观测信息。

这组划分的目标不是为了把文件拆多, 而是为了把“输入接管、融合、状态、输出”四类职责分清, 避免所有逻辑重新堆回 `runtime.py`。

## 和内核的通信方式

本轮固定采用现有速度接口和内核通信。

推荐边界如下:

1. 角色层把融合结果整理成统一的 `vx / vy / omega` 速度目标。
2. 角色层通过当前已有速度命令入口把该目标交给内核。
3. 角色层在需要全量停下时使用当前已有复位或零速度语义, 不新增内核专用模式开关。

这条边界的重要价值在于:

1. 内核不需要理解辅车角色层的内部状态。
2. 角色层也不需要直接改写内核的控制算法和控制周期。

## 调试观测

本轮至少需要在角色层可观测到以下信息:

1. 当前角色层状态。
2. 最近一次有效控制协议速度量的时间年龄。
3. 最近一次有效视觉的时间年龄。
4. 当前控制协议速度量贡献。
5. 当前视觉纠偏贡献量。
6. 当前融合后的输出量。

这组观测的作用是让联调时能快速分辨问题落在“`UART3` 速度控制量没来”“视觉没来”“融合过大”还是“内核执行不对”。

## 验收标准

本轮完成后, 至少要同时满足以下条件:

1. `src/vision/assistant/` 成为辅车闭环正式入口, 不再只是空装配壳。
2. 辅车本地视觉输入和 `UART3` 上现有控制协议中的速度控制包在角色层被统一接管和融合。
3. 融合结果以速度目标形式进入辅车内核执行主链。
4. 本轮不修改 `TransportCar` 与共享控制核心。
5. 视觉失效时辅车能够稳定停下。
6. 控制协议速度量失效时辅车能够降级为保守的视觉单撑模式, 而不是直接失控或盲跑。
7. 辅车角色层可暴露最小调试观测, 便于定位输入、融合和执行链问题。

## 验证口径

### 主机侧验证

主机侧至少覆盖以下内容:

1. 辅车角色运行入口会装配真实的角色层, 而不是直接回到裸内核对象。
2. `UART3` 上现有控制协议中的速度控制包能被角色层识别、缓存和超时清理。
3. `UART6` 本地视觉输入能被角色层识别、缓存和超时清理。
4. 有效控制协议速度量 + 有效视觉时, 角色层会输出融合后的速度目标。
5. 视觉失效时, 输出立即收口为零速度。
6. 控制协议速度量失效但视觉仍有效时, 输出进入保守降级模式。
7. 普通查询和非速度控制命令不会被角色层错误吞掉。

### 板端联调留证

板端至少要确认以下现象:

1. 辅车角色能稳定进入辅车视觉层运行链。
2. 主车转发现有速度控制量正常时, 辅车能明显跟上主车节奏。
3. `UART3` 速度控制量临时断开时, 辅车会收紧速度并保留基本视觉跟随。
4. 本地视觉断开时, 辅车立即停下。

## 结论

本轮设计把 `src/vision/assistant/` 定义为辅车闭环的正式角色层: 它负责接管 `UART3` 上的现有控制协议速度控制包和 `UART6` 上的现有视觉协议输入, 完成速度融合并通过现有速度接口和内核通信。这样既满足“闭环必须真正进入辅车运动控制主链”的要求, 也满足“当前先不动内核、也不新增主辅协议”的边界。
