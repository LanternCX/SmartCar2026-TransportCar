# 2026-04-14 车号识别驱动的主辅车视觉包切换设计

## 背景

当前仓库已经明确采用单仓库协作方向, 并约定通过 `D8/D9` 拨码输入识别当前板子的车号与角色。现有正式入口已经把按钮脚本分发与 `D8/D9` 角色识别语义拆开, 但运行时层面还没有一条正式的“先识别车号, 再按角色切换视觉包”的薄边界。

同时, 当前讨论已经明确以下判断:

1. 当前阶段不重构 `TransportCar` 这类大文件, 也不引入新的全局共享可变状态。
2. 当前阶段需要把后续主车/辅车差异收口到尽量薄的边界上, 控制改动面。
3. 主车和辅车的核心差异, 不是“有没有视觉”, 而是“如何利用视觉信号”。
4. 主车后续需要把视觉结果组织成自身动作意图和面向辅车的速度前馈意图。
5. 辅车后续需要把本车视觉校准与主车发来的速度前馈融合后再执行。

如果这一轮不先把“车号识别 -> 视觉包切换”这条边界立起来, 后续的辅车跟随、速度前馈和视觉校准很容易继续回流到现有大文件内部, 导致角色边界、内存边界和改动面一起恶化。

## 目标

1. 建立一条正式、清晰且尽量薄的运行时边界: 先识别车号, 再切换主车或辅车的视觉包。
2. 保持当前单仓库方向不变, 不把主车和辅车演变成两套完全独立工程。
3. 只让主辅差异落在 `vision/master/` 与 `vision/assistant/` 下, 不把新的角色专属逻辑继续堆进当前大文件。
4. 为后续“辅车视觉校准 + 主车速度前馈”预留稳定落点。
5. 让本轮设计尽量服务最小改动, 便于后续按多个小提交推进。

## 非目标

1. 本轮不重构 `TransportCar` 的内部结构, 不拆分当前大文件。
2. 本轮不固化共享执行核的最终形态, 也不顺手改写底盘公共控制边界。
3. 本轮不引入全局共享可变状态层。
4. 本轮不直接实现辅车的视觉校准与速度前馈融合算法。
5. 本轮不修改跨串口文本协议的正式格式。

## 已确认事实

1. `D8/D9` 角色输入带上拉, 读到 `1` 表示开关关闭, 读到 `0` 表示开关闭合。
2. 本轮用户确认的有效组合为:
   - 主车 = `01`
   - 辅车 = `10`
   - 其余组合按异常处理
3. `main.py` 当前只承担按钮脚本分发, 不再负责 `D8/D9` 相关语义。
4. 当前正式视觉输入协议仍是单行 `vx=<vx>,vy=<vy>` 文本观测。
5. 当前讨论已经明确: 同车内部不继续以字符串层层传递控制信息, 但跨串口链路仍保持字符串协议。

## 核心判断

### 判断一: 切换点应放在“视觉包”, 而不是放在共享执行核

本轮的重点不是重新定义整台车的共享执行架构, 而是用最小改动把“主车如何使用视觉”和“辅车如何使用视觉”分开。由于两台车底层骨架大体一致, 当前最值得切开的差异并不是底盘基础能力, 而是视觉信号进入运行时之后的使用方式。

因此, 本轮推荐把车号识别驱动的分流点落在视觉包:

1. 车号识别先给出当前角色。
2. 根据角色加载主车视觉包或辅车视觉包。
3. 共享执行部分保持暂时不动。

这样做可以避免本轮主题扩散到共享执行核、全局状态层或大文件重构。

### 判断二: 主辅差异应定义为“视觉信号如何被消费”

主车和辅车的差异不宜定义为“主车有视觉, 辅车无视觉”, 也不宜定义为“除视觉外其他全部共享”。这两种表述都太粗, 后续一旦接入速度前馈, 主辅边界会重新变脏。

更准确的边界是:

1. 主车视觉包负责把视觉信号用于环境理解、目标判断和动作意图组织。
2. 辅车视觉包负责把视觉校准和主车前馈意图用于本地融合执行。

也就是说, 两台车的差异不是“有没有看”, 而是“看见之后怎么用”。

### 判断三: 同车内部不再继续传字符串, 但也不引入全局共享大状态

本轮已经确认:

1. 跨串口链路仍保留字符串协议。
2. 同车内部的数据进入运行时后, 应尽快变成轻量的内部控制量。
3. 当前阶段不通过全局共享可变状态层来组织这些内部量。

因此, 角色视觉包的职责应是“在本包内部维护最小必要输入与输出”, 而不是继续把字符串传到更深层, 也不是要求全局所有模块都共享一份大状态。

## 总体方案

### 1. 新增一层很薄的角色视觉包装配边界

在当前正常运行入口之后, 增加一个很薄的装配边界, 用于完成以下两件事:

1. 读取并解码车号。
2. 根据角色选择主车视觉包或辅车视觉包。

这层边界放在 `src/vision/` 下, 不负责视觉解析细节, 不负责底盘控制细节, 也不负责把所有共享模块重新整理。它只承担“当前板子应该接哪一个角色视觉包”的决定权。

### 2. 主车视觉包职责

主车视觉包是主车对视觉信号的正式消费入口。本层只关心两件事:

1. 视觉观测如何转为主车当前阶段的判断依据。
2. 判断结果如何转为主车动作意图与面向辅车的速度前馈意图。

这层不负责辅车执行策略, 不直接关心辅车本地如何融合输入, 也不把辅车逻辑回流到主车内部。

### 3. 辅车视觉包职责

辅车视觉包是辅车对外部信号的正式消费入口。本层只关心三件事:

1. 本车视觉校准量如何被解释。
2. 主车发来的速度前馈意图如何被接收。
3. 两路输入如何在辅车本地形成统一执行意图。

这层不承担主车的环境理解和任务判断职责, 也不要求辅车反向维护主车视角下的状态机。

### 4. 字符串协议与内部控制量的边界

本轮设计明确保留以下边界:

1. 主车到辅车的跨串口通信继续使用字符串协议。
2. 一旦数据进入本车内部, 就不继续在多层之间以字符串形式流动。
3. 角色视觉包内部维护最小必要的控制量表达。
4. 角色视觉包对下只暴露统一的内部控制意图, 不把字符串协议继续扩散到更深层。

这样可以把“跨车可观测协议”和“车内轻量控制表达”明确分开。

## 分层边界

### 共享层保留到哪里

本轮设计不重新定义共享执行核, 但要明确共享层的讨论止步位置:

1. 共享层只视为当前已经存在的底层基础能力与现有运行基线。
2. 本轮不要求把这些共享部分重新抽象或重新命名。
3. 只要本轮新增的主辅差异不再回流进去, 就视为满足当前设计目标。

### 角色层从哪里开始

本轮把角色差异的开始位置明确为“运行入口按车号切到 `src/vision/master/` 或 `src/vision/assistant/` 的那一层”。从这一层开始:

1. 主车走主车视觉包。
2. 辅车走辅车视觉包。
3. 两者共享协议边界, 但不共享如何消费这些信号的内部逻辑。

### 为什么不把角色差异继续压回大文件

当前大文件职责已经过多, 但本轮不重构它。为了不让问题继续恶化, 需要明确一条硬边界:

1. 新的主车视觉判断逻辑不再继续往当前大文件里堆。
2. 新的辅车视觉校准与前馈融合逻辑也不再继续往当前大文件里堆。
3. 当前大文件在本轮只被视作现有底座, 本轮不通过给它新增注入口来承接角色分流。

## 对后续速度前馈的承接方式

本轮不直接实现速度前馈融合, 但需要给后续承接关系留出明确口径。

### 主车侧承接

主车视觉包后续负责组织面向辅车的速度前馈意图。这里的关键是“组织与输出”, 而不是提前假设辅车的具体融合细节。

### 辅车侧承接

辅车视觉包后续负责把本车视觉校准与主车前馈意图组合为本地执行意图。这里的关键是“辅车本地融合”, 而不是让主车替辅车完成所有执行决策。

### 本轮留出的扩展性

由于角色分流点已经固定在视觉包, 后续速度前馈接入时不需要重新发明角色边界, 只需要沿着以下方向扩展:

1. 主车入口下补速度前馈输出。
2. 辅车入口下补融合策略。
3. 共享底层保持尽量不动。

## 风险与约束

1. 如果本轮把角色差异错误地下沉到共享执行层, 改动面会迅速扩大, 偏离当前主题。
2. 如果把主辅差异写成“只有视觉模块名不同, 其余都共用”, 后续速度前馈接入时边界会重新变脏。
3. 如果继续在车内多层之间传播字符串协议, 后续融合逻辑会变得笨重且难维护。
4. 如果为了省事引入全局共享可变状态, 角色边界会重新失控。
5. 如果后续新功能仍继续塞进当前大文件, 即使本轮立了边界, 也会很快失效。

## 本轮建议的实现范围

当后续进入实现阶段时, 本轮建议只围绕以下范围推进:

1. 车号识别的正式读取与角色解码。
2. `src/vision/` 下的角色视觉包装配边界。
3. `vision/master/` 与 `vision/assistant/` 的最小入口定义。

以下内容不应混入同一变更单元:

1. `TransportCar` 结构性重构。
2. 共享执行核重新定型。
3. 全局共享状态设计。
4. 辅车完整融合算法与参数细化。
5. 串口协议大改。

## 验收标准

当满足以下条件时, 可认为本轮设计目标成立:

1. 角色识别正式用于切换主车或辅车的视觉包。
2. 主辅差异被明确写成“如何消费视觉信号”, 而不是被粗暴写成“是否有视觉”。
3. 当前大文件不再继续承担新增主车判断逻辑与辅车融合逻辑。
4. 后续速度前馈接入时, 不需要重新发明角色边界。
5. 本轮设计可以以较小改动面推进, 并支持拆成多个小提交实现。
6. 当前车号识别模块归属 `src/vision/vehicle_role.py`, 与 `vision/master/`、`vision/assistant/` 一起维护角色视觉边界。
