# 2026-04-20 辅车视觉输入与速度前馈裸相加设计

> 状态: Archive
> 当前约束以 `docs/developer/strategy.md`、`docs/developer/tasks.md`、`docs/developer/control.md`、`docs/developer/vision.md` 与 `.agents/skills/using-rules/references/strategy-and-control.md` 为准。

## 背景

当前辅车角色层已经具备一套可复用的双路输入基础:

1. `UART6` 与 `UART8` 都由 `vision/assistant/` 在角色层读取。
2. 两路都已经复用同一份速度字段解析边界。
3. 两路都已经具备“最近一包持续生效”的基础形态。
4. 两路当前都会把解析结果收口到共享底盘统一速度入口。

但这条基础链路当前有两个问题:

1. 文档和规则中对 `UART6` / `UART8` 的职责存在冲突口径。
2. 当前实现把两路都当成同类速度来源, 还没有明确“视觉输入 + 前馈输入”的职责边界。

本轮用户已经明确给出新的正式口径:

1. `UART6` 是视觉输入。
2. `UART8` 是速度前馈输入。
3. `UART6` 当前发送到车端的是 `vx` 和 `vy` 两个速度量。
4. 调试时不希望通过显式禁用某一路来切模式。
5. 纯视觉单独输入时要能跑。
6. 纯前馈单独输入时也要能跑。
7. 两路同时存在时, 直接按轴裸相加。
8. 两路都采用“保持上一包”的语义, 不做超时清零。

## 目标

1. 明确 `UART6` 为视觉速度输入, `UART8` 为速度前馈输入。
2. 保留当前双路异步读取和共享解析基础, 不重开两套输入框架。
3. 两路都不等待对方, 不做报文配对或同步阻塞。
4. 每个控制拍都用两路各自最近一次有效值完成融合。
5. 最终 `vx` / `vy` 按轴裸相加。
6. 两路任一单独存在时都能自然形成最终速度输出。
7. 不通过额外模式开关区分“纯视觉 / 纯前馈 / 融合态”。

## 非目标

1. 不引入新的串口协议主题。
2. 不增加“纯视觉模式”“纯前馈模式”之类的显式运行模式切换。
3. 不做取最大值、平均值或带权融合。
4. 不新增跨路同步等待或时间配对逻辑。
5. 不引入新的超时清零规则。
6. 不扩展视觉侧新的 `omega` 语义。
7. 不改动当前硬件事实与串口接线口径。

## 当前问题

### 1. 口径冲突

当前正文和规则入口存在冲突:

1. `docs/developer/control.md` 与 `docs/developer/vision.md` 把 `UART6` / `UART8` 都写成普通速度输入, 并写成逐轴相加。
2. `.agents/skills/using-rules/references/strategy-and-control.md` 又把两路写成“前馈 + 视觉”, 但端口分配与用户刚确认的口径不一致。

因此本轮必须先把“谁是视觉, 谁是前馈”重新写清楚。

### 2. 融合语义缺少正式定义

用户这次明确强调的不是“只做一条链”, 而是:

1. 单路调试时, 任一路单独存在都能直接跑。
2. 融合调试时, 不希望显式禁用另一边。
3. 正式链路里希望直接裸相加, 以获得最直接的合成效果和最简单的逻辑。

这意味着本轮设计不能把两路做成“主从选择”或“二选一接管”, 而是要保持统一运行路径。

## 方案比较

### 方案一: 裸相加, 推荐

做法:

1. `UART6` 保存视觉输入最近一包 `vx / vy`。
2. `UART8` 保存前馈输入最近一包 `vx / vy / omega`。
3. 每个控制拍都读取两路当前最新有效值。
4. 最终输出按轴融合:
   - `final_vx = uart8_vx + uart6_vx`
   - `final_vy = uart8_vy + uart6_vy`
   - `final_omega = uart8_omega`
5. 任一路没有有效包时, 该路贡献按 `0` 处理。
6. 任一路停更后继续保持上一包, 直到被新包改写或被显式零包清空。

优点:

1. 最符合用户当前调试顺序。
2. 纯视觉、纯前馈和融合态共用一条路径。
3. 不需要增加切模式逻辑。
4. 语义直接, 最容易联调和观察。
5. 最大限度复用当前角色层输入编排和共享解析基础。

这是本轮推荐方案。

### 方案二: 取最大值

做法:

1. 两路都先形成各自的速度量。
2. 每轴取幅值更大的一路作为最终输出。

问题:

1. 这更像控制权竞争, 不是融合。
2. 一路容易把另一条链路完全吃掉。
3. 不符合用户希望的“直接相加”。

本轮不采用。

### 方案三: 取平均值或带权平均

做法:

1. 两路都先形成各自的速度量。
2. 再按固定系数求平均或加权平均。

问题:

1. 会同时削弱两边单独调好的效果。
2. 融合态手感会和单路调试结果明显不同。
3. 还会引入额外调参负担。

本轮不采用。

## 推荐方案

本轮采用方案一。

一句话概括:

`UART6` 作为视觉速度输入提供 `vx / vy`, `UART8` 作为速度前馈输入提供 `vx / vy / omega`, 两路都按最近一包持续生效, 每个控制拍直接取两路当前最新值做按轴裸相加, 不等待、不配对、不切模式。

## 设计细节

### 1. 输入角色

本轮把两路正式职责固定为:

1. `UART6`: 视觉输入, 当前协议只消费 `vx / vy` 两个速度量。
2. `UART8`: 速度前馈输入, 当前协议消费 `vx / vy / omega / w`。

这里的关键不是换掉当前输入框架, 而是把已经存在的双路输入基础重新赋予正确职责。

### 2. 输入同步方式

本轮的“同步”不是报文级同步, 而是控制拍同步。

固定规则如下:

1. 每个控制拍都分别轮询 `UART6` 与 `UART8`。
2. 每一路把本拍能读到的数据都先收进自己的缓冲和状态。
3. 两路互不等待, 不要求本拍必须同时到新包。
4. 到本拍要输出时, 直接取两路各自最近一次有效值完成一次融合。

因此本轮不会实现:

1. 按时间戳配对。
2. 等两路都更新后再计算。
3. 因为一边暂时没新包而阻塞另一边。

### 3. 状态保持语义

两路都采用“保持上一包”的规则。

固定规则如下:

1. 某一路收到新有效包时, 覆盖该路上一包状态。
2. 某一路本拍没有新包时, 继续沿用该路上一包状态。
3. 不做超时清零。
4. 只有显式零包才会把该路贡献清到零。

这样三种调试场景都会自然成立:

1. 只给 `UART6` 发包时, 视觉链单独跑。
2. 只给 `UART8` 发包时, 前馈链单独跑。
3. 两边同时发包时, 直接进入融合态。

### 4. 融合规则

本轮融合规则固定为裸相加:

1. `final_vx = uart8_vx + uart6_vx`
2. `final_vy = uart8_vy + uart6_vy`
3. `final_omega = uart8_omega`

附带约束:

1. 若 `UART6` 当前没有有效包, 其 `vx / vy` 贡献按 `0` 处理。
2. 若 `UART8` 当前没有有效包, 其 `vx / vy / omega` 贡献按 `0` 处理。
3. 视觉侧当前没有 `omega` 语义, 这一轴不由 `UART6` 贡献。

### 5. 单路与融合态统一路径

本轮不增加“纯视觉模式”“纯前馈模式”“融合模式”三个显式模式。

实际行为按输入自然退化:

1. `UART6` 有值、`UART8` 为零或空时, 输出就是视觉量本身。
2. `UART8` 有值、`UART6` 为零或空时, 输出就是前馈量本身。
3. 两边都有值时, 输出就是两边裸相加。

这正是用户要求的“调试时不需要显式禁用任何一边”。

### 6. 与共享底盘的边界

本轮保持当前共享底盘边界尽量不变:

1. 角色层仍然负责接管双路输入读取、解析和融合。
2. 融合完成后, 仍然通过共享底盘现有统一速度入口写回。
3. 不在共享底盘里新增第二套视觉控制内核。
4. 不在共享底盘里增加报文同步器。

### 7. 诊断口径

为了支持联调, 角色层诊断需要能明确表达:

1. `UART6` 当前视觉输入状态。
2. `UART8` 当前前馈输入状态。
3. 两路各自最近一次有效速度量。
4. 当前最终融合输出。

这样联调时才能区分:

1. 是某一路根本没进来。
2. 还是两路都进来了, 但融合结果不符合预期。

## 需要验证的行为

本轮至少固定下面这些行为:

1. `UART6` 单独输入时, 视觉链可以直接驱动车体。
2. `UART8` 单独输入时, 前馈链可以直接驱动车体。
3. 两路同时输入时, `vx / vy` 为两路裸相加结果。
4. `omega` 只由 `UART8` 控制。
5. 任一路本拍没有新包时, 继续保持上一包。
6. 任一路显式零包时, 只清该路自己的贡献。
7. 两路异步输入时, 不互相等待、不互相阻塞。
8. 角色层诊断能看出视觉输入、前馈输入和最终输出三者关系。

## 风险与约束

1. 裸相加会让双路同时存在时总速度更大, 这正是用户当前接受并希望保留的语义, 不能在实现阶段偷偷改成平均或限权。
2. 当前视觉侧只确认 `vx / vy`, 没有确认 `omega`, 因此这一轴不能自行猜测扩展。
3. 既然采用“保持上一包”, 就必须把显式零包清零语义测透, 否则联调时容易误判为串口卡死或残留输出。
4. 本轮完成后要同步修正文档和规则入口, 否则仓库会继续同时保留两套相互冲突的职责口径。
