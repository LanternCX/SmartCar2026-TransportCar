# Superpowers 文档按 PR 归档设计

## 背景

当前 `docs/superpowers/specs/` 与 `docs/superpowers/plans/` 已经积累了较多历史文档。它们一方面承担设计与实施过程留痕, 另一方面又被直接当作当前工作区使用。

随着文档数量持续增加, 当前目录出现了两个明显问题:

1. 打开目录后, 很难第一眼分辨哪些是当前仍在推进的文档, 哪些只是历史留档。
2. 如果直接按日期或批量搬运做归档, 容易把“当前正在使用的文档”和“已经收口的文档”混在新的层级里, 只把拥挤从一个目录搬到另一个目录。

这次调整的目标不是重做整个知识库结构, 也不是把历史文档重新按主题彻底洗牌, 而是先用最小规则把“当前工作区”和“历史归档区”明确分开, 降低日常查找和继续写新文档时的噪音。

## 目标

本轮设计需要同时满足以下目标:

1. 让 `specs/` 与 `plans/` 根目录承载当前工作区文档, 包括当前仍在推进的文档, 以及少量暂未判定归属的待判断文档。
2. 让多数已经收口的文档可以按 PR 批次整体归档, 便于回看某轮改动的上下文; 对跨多个 PR 持续演进的文档, 允许以最终收口 PR 为准归档。
3. 保持目录结构足够简单, 不把归档动作本身做成新的长期维护负担。
4. 为后续继续写新的 spec 和 plan 提供稳定、低心智负担的落点规则。

## 非目标

本轮明确不做以下事情:

1. 不按主题重写全部历史文档分类。
2. 不试图一次性修复所有历史文档之间的交叉引用。
3. 不把每份文档强行拆分到多个 PR 目录中。
4. 不新建 `now/`、`active/` 一类额外工作区目录。

## 核心设计

### 一、根目录就是当前工作区

`docs/superpowers/specs/` 与 `docs/superpowers/plans/` 根目录直接表示“当前工作区文档”。其中包括两类内容:

1. 当前仍在推进、仍可能继续修改、仍被本轮工作直接依赖的文档。
2. 少量暂未判定归属、因此本轮暂不迁移的待判断文档。

也就是说, 当前工作区不再额外新建 `now/` 子目录, 以避免路径再多一层但没有实际收益。新文档继续直接写在根目录下, 直到对应工作真正收口。

### 二、历史文档进入 `archive/PR#<id>/`

两类目录都新增归档层:

```text
docs/superpowers/specs/archive/PR#<id>/
docs/superpowers/plans/archive/PR#<id>/
```

其中 `PR#<id>` 表示一轮已经收口的变更批次。某个 PR 对应的 spec 与 plan 分别归入各自目录下的同名批次, 这样既保留 `specs` / `plans` 的类型边界, 又保留按 PR 回看的能力。

### 三、归档依据是“收口状态”, 不是“文档创建日期”

文档是否归档, 以它是否仍属于当前工作区为准, 而不是以文件名日期为准。

归档触发条件统一为:

1. 这批文档已经对应到一个明确 PR。
2. 这批工作已经完成本轮收口, 后续不再作为当前正在编辑的主线文档继续演进。
3. 将其移出根目录后, 不会妨碍当前正在推进的文档阅读与追加。

这样可以避免“虽然文件很旧, 但其实还在当前主线里继续追加”的文档被过早搬走。

### 四、跨多个 PR 的主题不强拆

如果某个主题横跨多个 PR, 但核心文档仍在持续演进, 则这份文档继续留在根目录, 直到这一轮真正收口后再归入最后承载它的 PR 目录。

本设计明确不为了追求目录整齐, 把一份仍在演进的文档硬拆成多个历史副本。优先保证“当前工作区真正可用”, 再保证历史分桶整齐。

因此,“按 PR 回看”在本设计中的含义是: 对大多数已经稳定归属到单个 PR 的文档, 可以直接按 PR 回看; 对跨多个 PR 持续演进的少数核心文档, 允许在较早 PR 缺失正文, 由最终收口 PR 承接完整归档。

## 目录结构

本轮目标结构如下:

```text
docs/superpowers/specs/
  2026-04-05-xxx-design.md
  2026-04-06-yyy-design.md
  archive/
    PR#101/
      2026-03-23-aaa-design.md
      2026-03-24-bbb-design.md

docs/superpowers/plans/
  2026-04-05-xxx-plan.md
  2026-04-06-yyy-plan.md
  archive/
    PR#101/
      2026-03-23-aaa-plan.md
      2026-03-24-bbb-plan.md
```

其中:

1. 根目录只保留当前文档与少量待判断文档。
2. `archive/` 只承载已收口文档。
3. `archive/PR#<id>/` 是最小归档单元。

## 归档规则

### 一、什么文档留在根目录

下列文档继续留在根目录:

1. 仍在本轮工作中持续修改。
2. 仍会继续追加内容或仍在被直接编辑。
3. 主题尚未收口, 还不能稳定归属到某一个已结束 PR。
4. 虽然不一定仍在编辑, 但本轮暂时无法稳定判断归属, 因而被标记为“待判断”。

判断优先级固定如下:

1. 是否仍在被直接编辑, 优先级最高。
2. 是否已经明确归属到某个已结束 PR, 次之。
3. 仅为了回看历史而偶尔打开, 不算“当前工作区依据”。

### 二、什么文档进入归档目录

下列文档进入 `archive/PR#<id>/`:

1. 已对应到明确 PR 的设计文档与实现计划。
2. 这轮变更已经结束, 文档主要承担历史留痕作用。
3. 从根目录移出后, 不会妨碍当前继续推进同类工作。

### 三、什么情况暂不归档

下列情况暂不归档:

1. 当前仍经常被直接打开作为工作依据。
2. 尚未确定最终归属到哪个 PR。
3. 一旦移动就会让当前 review 和追加工作明显变麻烦。

这类文档统一记为“待判断”, 默认继续留在根目录, 本轮不迁移。只有在后续整理中满足归档条件后, 才进入对应 `archive/PR#<id>/`。

## 命名与维护约束

### 一、目录命名

归档目录统一使用 `archive`, 不引入新的近义目录名。PR 目录统一使用 `PR#<id>` 形式, 避免同一层里同时出现 `pr-123`、`PR123`、`pull-123` 等多种写法。

这里保留 `PR#<id>` 是为了和用户当前审阅习惯一致, 以显示可读性优先。该命名在命令行与路径复制时会有少量额外摩擦, 但本轮先不为此改动用户已经认可的表达方式。

### 二、最小维护原则

本设计刻意只引入一层 `archive/PR#<id>/`, 不再继续增加月份层、主题层或 `now/active/current` 子目录。原因很简单:

1. 当前目录本身已经可以表达“当前”。
2. 归档分层过多会增加写文档和回看文档时的判断成本。
3. 先把“当前 / 历史”分开, 已经能解决当前最主要的问题。

## 执行顺序

为避免搬运过程中把当前文档误收进历史目录, 执行顺序固定如下:

1. 先建立 `specs/archive/` 与 `plans/archive/` 基础目录。
2. 再梳理根目录中的文档, 标出“当前保留 / 可归档 / 待判断”三类。
3. 先迁移“可归档”里归属明确、收口明确的一批文档。
4. 最后复查根目录, 确认只剩当前文档与少量待判断文档。

## 验收标准

本轮完成后, 至少应满足以下标准:

1. 打开 `docs/superpowers/specs/` 或 `docs/superpowers/plans/` 根目录时, 能明显看出当前工作区比现在更干净, 且只包含当前文档与少量待判断文档。
2. 已收口文档可以按 `archive/PR#<id>/` 回看对应批次。
3. 当前仍在推进的文档不会因为提前归档而变得难找或难改。
4. 后续新增 spec 与 plan 时, 不需要额外判断 `now/active/current` 等多套落点规则。

## 风险与控制

### 一、风险: 某些文档明明跨多个 PR, 却被过早收入历史目录

控制方式:

1. 以“是否仍在推进”为第一判断条件。
2. 对跨 PR 主题优先保留在根目录, 不强拆。
3. 只有真正收口后再进入对应 `PR#<id>`。

### 二、风险: 归档目录按 PR 增长后再次变乱

控制方式:

1. 先只解决“当前 / 历史”混杂问题。
2. 若后续 `archive/` 继续膨胀, 再补统一索引, 而不是现在提前增加层级。
3. 当前阶段不做额外主题化重组, 避免维护成本反噬。

### 三、风险: 搬运后部分历史引用路径失效

控制方式:

1. 归档执行时优先处理归属清晰的一批文档。
2. 对仍被频繁引用的文档允许暂缓归档。
3. 真正执行搬运时再统一检查并修正必要的引用。

## 后续计划入口

待本设计经用户确认后, 下一阶段计划将细化为目录创建、批次划分、首批迁移与迁移后复查的执行计划, 用于实际落地当前区与 PR 归档区的整理。
