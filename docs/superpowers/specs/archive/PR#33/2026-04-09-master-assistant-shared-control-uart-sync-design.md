# 2026-04-09 主辅车底盘控制与 UART3 共享边界同步设计

> 状态: archive

## 背景

从 `2713d7c fix(control): align assistant follow runtime behavior` 开始，辅车底盘控制链已经补齐了一组更贴近当前控制内核的基础规则，包括：

1. 里程累计使用姿态更新前朝向。
2. 三轮目标在超上限时统一按比例缩放。
3. 速度环在零周期场景下按固定控制节拍回退。

随后主车又在 `92a52bc fix(control): refine master follow control and diagnostics` 中推进了跟随阶段和诊断收口，但这轮主车改动主要集中在视觉跟随状态机与诊断路径，并没有把上述底盘基础规则一起同步回主车底座控制链。

同时，主辅车 `UART3` 直连链路在近期也分别做过串口读入强化，但当前 spec 还没有明确“出现分叉时到底保留哪一边”的裁决规则。

用户当前要求不是做新功能扩展，而是回头检查近期几个改动面，把与底盘控制、串口读取相关的共享设计做主辅双向同步，保证两侧代码在共享边界上保持一致。

## 目标

本轮只追求以下目标：

1. 把已经在辅车落地、且属于底盘共享基础能力的控制保护逻辑同步到主车。
2. 明确近期分叉的裁决规则：以最近一次有效改动为准，而不是只写“要统一”。
3. 只把近期真正发生过分叉的共享读取设计纳入同步范围，不把无关或更早的差异混进来。
4. 保持“共享边界优先”的同步口径，不把本轮扩大成协议统一或主辅业务同构改造。
5. 通过定向测试固定这次同步的最小行为，避免后续再出现同类分叉。

## 非目标

本轮明确不做以下事情：

1. 不改主车视觉状态机、按轴跟随阶段或视觉决策参数。
2. 不改辅车位置式累计目标、速度模式和超时处理语义。
3. 不统一主辅协议层字段、命令种类或状态回包格式。
4. 不把主车 `UART6/UART8` 的视觉口读取预算策略搬到辅车 `UART3`。
5. 不把 `write_line()` 这类不属于本轮“近期串口读取设计”的旧差异强行纳入同步。
6. 不做“主辅所有同类文件完全同构”的大范围整理。

## 为什么要单开新 spec

现有 spec 分别收口了各自主题：

1. 辅车几份 spec 主要描述跟随目标累计、位置速度上限、控制模式一致性和 legacy 控制核对齐。
2. 主车 spec 主要描述“先对正 `x`，再对正 `y`”的视觉跟随阶段设计。

而这次新增任务关注的是另一类问题：

1. 哪些底盘规则属于主辅共用的控制基础边界。
2. 哪些串口读取策略属于主辅 `UART3` 共用的实现边界。
3. 哪些差异是角色差异，应保留；哪些差异只是近期改动后留下的同步缺口，应补齐。

这不是原有任何一份 spec 的自然续写，因此需要单开新的 spec 来描述这轮“共享边界同步”变更单元。

## 裁决规则

### 规则一：以最近一次有效改动为准

本轮所有“主辅双向同步”的裁决都按下面的顺序执行：

1. 先按具体设计点拆开判断，不按整文件粗暴判断。
2. 追溯这个设计点最近一次有效改动发生在哪一侧。
3. 如果最近是主车改了、辅车没跟上，就以主车为准同步辅车。
4. 如果最近是辅车改了、主车没跟上，就以辅车为准同步主车。

这里的“有效改动”只指功能或设计语义的变化，不把单纯注释、文案或文件整理视为设计裁决依据。

### 规则二：角色专属改动不外扩

即使某一侧最近改过，如果该改动只服务于本侧专属链路，也不自动外扩到另一侧。例如：

1. 主车 `UART6/UART8` 的视觉口读取预算只属于主车视觉链。
2. 辅车的跟随累计目标和超时执行语义只属于辅车执行链。

因此，本轮只同步“最近改过且属于共享边界”的设计点。

## 现状分叉

### 分叉一：主车底盘控制链缺少与辅车一致的三项基础保护

当前主车与辅车虽然都使用三轮底盘和类似的底层控制链，但主车仍缺少以下几项已经在辅车收口的基础规则：

1. 三轮统一按比例缩放，而不是只在速度环入口逐轮各自硬截断。
2. 零周期时速度环按固定控制节拍回退，而不是把 `dt` 当成异常值直接带进控制输出。
3. 里程累计使用姿态更新前朝向，而不是天然固定依赖姿态更新后的朝向。

这三项都属于底盘共享基础能力，不依赖主车视觉业务，也不依赖辅车执行语义，因此应该同步。

### 分叉二：串口读取侧需要先区分“共享读取设计”和“角色专属读取设计”

当前两侧 `UART3` 都已经具备：

1. 基于内部缓冲的按行重组。
2. `read_latest_line()` 语义。
3. 对超长半行的丢弃和重同步。

进一步追溯近期改动可以发现：

1. 辅车 `UART3` 读入强化最近一次有效改动是 `c237eb4 fix(hardware): harden assistant uart3 debug intake`。
2. 主车最近一次串口读入强化是 `137b890 fix(hardware): harden master vision uart intake`，但它主要收口的是 `UART6/UART8` 视觉口预算，不是主辅共享的 `UART3` 直连边界。

这说明“近期串口读取设计”的裁决应进一步细分：

1. 共享 `UART3` 读取边界，以辅车最近改动为准。
2. 主车 `UART6/UART8` 视觉口预算继续保留为主车专属设计，不向辅车扩散。

经当前代码核对，主车现有 `UART3` 读入语义已经与辅车这轮 `UART3` 强化结果兼容。但在用户后续追问后，本轮同步口径进一步明确为：除了验证边界，还要把 master 侧近期已经落地的通用读取结构同步到 assistant，只是不把 `UART6/UART8` 的视觉口专属预算扩散过去。

### 分叉三：并不是所有差异都需要同步

当前主辅仍然存在一些差异，但这些差异并不属于本轮应处理的同步缺口：

1. 主车 `UART6/UART8` 视觉口存在专属读取预算，这是视觉链路特有约束，不属于辅车 `UART3`。
2. 主车视觉状态机和决策层承担“阶段切换和输出选择”，辅车运行时承担“执行和保护”，这属于角色差异，不应强行统一。
3. 辅车协议层需要解析控制命令，主车协议层需要组织发包，这属于上下游职责差异，也不属于本轮共享边界。

因此，本轮同步必须只处理真正共享的底层边界，不能借机扩大改动面。

## 设计原则

### 原则一：共享边界优先

只有同时满足以下条件的差异，才进入本轮同步范围：

1. 该差异发生在主辅共用的底层能力边界。
2. 该差异不依赖主车或辅车各自独有的业务角色。
3. 同步后能提升控制稳定性、热路径稳态或代码一致性。

### 原则二：先补缺口，不做大整理

本轮不是“看见不同就全改成一样”，而是：

1. 找出近期提交后真正出现的共享设计缺口。
2. 用最小改动把缺口补齐。
3. 保留那些本来就应该存在的角色差异。

### 原则三：最近改动优先于主观整齐

当“哪边看起来更整齐”和“哪边最近刚改过”发生冲突时，优先服从最近一次有效改动，不按主观偏好裁决。

### 原则四：测试先固定边界，再动实现

这次同步的每个共享规则都应先通过定向测试明确下来，再去做代码修改，避免出现“代码看起来更整齐，但实际边界被改坏”的情况。

## 同步设计

### 设计一：底盘共享规则以辅车最近改动为准，主车补齐

底盘控制这组共享规则最近一次有效改动发生在辅车 `2713d7c`，因此本轮以辅车为准，把主车补齐到相同口径。需要同步的规则包括：

1. 三轮目标超过上限时，三轮一起按同一比例缩放。
2. 零周期时，速度环回退到固定控制拍长，而不是使用无效 `dt`。
3. 里程累计使用姿态更新前朝向。

这样做的原因是：

1. 这三项都只属于底盘控制基础能力，不属于主车视觉业务。
2. 辅车已经用测试把这些规则固定下来，主车继续缺失会让同一底盘基础行为在两侧分叉。
3. 同步后可以降低后续调参与排查时“同底盘、不同基础口径”的额外心智负担。

本轮不把辅车的跟随目标累计、控制模式状态字段或超时执行语义搬到主车，因为这些已经进入角色特定业务层，不再是底盘共享边界。

### 设计二：串口读取共享规则按最近有效改动裁决，并同步通用读取结构

串口读取这组共享规则本轮按以下方式处理：

1. 共享 `UART3` 读取边界以辅车 `c237eb4` 的最近有效改动为准。
2. 主车 `UART6/UART8` 的读取预算继续保留为主车专属设计，不同步到辅车。
3. 在不引入视觉口专属预算的前提下，把 master 侧近期已经落地的通用读取结构同步到 assistant。
4. `write_line()` 不属于这轮“近期串口读取设计”的有效分叉点，从本轮同步目标中移除。

这样做的原因是：

1. 这符合“以最近有效改动为准”的裁决规则。
2. 这能回应用户新增要求：master 侧通用读取结构不能只停留在测试结论，也要同步到 assistant。
3. 这仍然避免把“串口读取设计”误扩大成“串口所有接口都要统一”。
4. 这也避免把并非近期变化来源的旧差异误判成当前同步目标。

### 设计三：读取侧只保持现有一致性，不额外扩散视觉口策略

本轮不把主车 `UART6/UART8` 的视觉口读取预算搬到辅车，也不改两侧当前 `read_latest_line()` 的总体语义。

原因是：

1. 主辅 `UART3` 当前都已经具备按行缓冲、积压清理和最新完整行优先的基本语义。
2. `UART6/UART8` 的读取预算是主车视觉口特定设计，不属于共享边界。
3. 如果未来要讨论“所有 UART 口统一预算策略”，那是另一个新主题，应单开 spec。

## 影响范围

本轮只应触及以下文件：

1. `src/master/ctrl/kinematics.py`
2. `src/master/ctrl/pid.py`
3. `src/master/motion_runtime.py`
4. `src/assistant/hw/uart.py`
5. 对应的主车与辅车单元测试文件

本轮明确不应触及：

1. `src/master/vision/*`
2. `src/master/protocol.py`
3. `src/assistant/protocol.py`
4. `src/assistant/motion_runtime.py` 中与跟随目标累计和超时语义相关的业务逻辑

## 验收标准

本轮完成后，至少需要同时满足以下标准：

1. 主车底盘输出在三轮任一轮超上限时，三轮保持统一比例缩放。
2. 主车速度环在零周期场景下使用固定控制拍长回退。
3. 主车里程累计使用姿态更新前朝向，行为与辅车当前口径一致。
4. 共享 `UART3` 读取设计继续保持与辅车最近强化结果一致，且不误伤主车 `UART6/UART8` 专属预算。
5. 现有主车视觉状态机、辅车累计目标与协议行为不被本轮改坏。

## 测试与验证口径

### 自动化验证

本轮至少需要补齐或回归以下测试：

1. 主车三轮统一按比例缩放的回归。
2. 主车零周期速度环回退固定控制拍长的回归。
3. 主车里程累计使用姿态更新前朝向的回归。
4. 主车串口读取相关回归在需要时补齐共享 `UART3` 边界断言。
5. 受影响主辅测试集整体通过。

### 验证命令

实现完成后，优先运行以下定向测试：

1. `python3 -m pytest tests/unit/master/test_motion_runtime.py tests/unit/master/test_stability_baseline.py tests/unit/master/test_runtime_loop.py tests/unit/assistant/test_runtime_loop.py -q`

如果这组测试通过，就足以说明本轮最小共享边界同步已经生效；不需要把整套视觉或协议测试一起拉进来扩大验证范围。

## 风险与控制

### 风险一：同步底盘基础规则时误伤主车视觉主线

控制方式：

1. 只改主车底盘基础文件，不改 `vision/` 目录。
2. 不改主车按轴跟随状态机和决策输出层。

### 风险二：把角色差异误判成共享缺口

控制方式：

1. 只同步底盘基础规则和 `UART3` 共享读取边界。
2. 主车视觉口专属预算、辅车协议执行语义一律不纳入本轮。

### 风险三：串口同步扩大成无关接口改造

控制方式：

1. 只处理近期读取设计分叉，不把旧写出差异一并卷入。
2. 不改命令格式，不改状态回包格式，不改解析器。

## 实施入口

本 spec 对应的实现只围绕以下最小改动展开：

1. 给主车补齐与辅车最近控制改动一致的底盘基础规则。
2. 按最近有效改动原则，把 master 侧通用串口读取结构同步到 assistant，但不引入 `UART6/UART8` 专属预算。
3. 继续排除 `write_line()` 这类不属于本轮范围的旧差异。
4. 用定向测试固定本轮同步边界。

如果后续还要继续推进协议层统一、视觉口串口策略统一，或主辅更大范围的控制链同构，应另开新 spec，不在本文件上继续叠加。
