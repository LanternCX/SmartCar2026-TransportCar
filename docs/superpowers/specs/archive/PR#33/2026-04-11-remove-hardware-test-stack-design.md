# 2026-04-11 移除当前主线硬件测试体系设计

> 状态: archive

## 背景

当前仓库仍保留一整套围绕板端验证组织起来的测试链路, 包括:

1. `tests/hil/` 下的硬件在环留证文档。
2. `stage2` 与 `stage3` 的板端验证分层口径。
3. 与 `stage2 / stage3 / HIL` 绑定的工具入口、测试说明和任务说明。
4. 当前规则与文档中仍把硬件验证视为正式测试体系组成部分的表述。

这套结构在过去阶段有过明确用途, 但用户当前已经明确改变工作方式:

1. 不再保留硬件在环测试体系。
2. 当前这套自动与手动混合的板端测试并不完善, 实际效率也不如直接人工调试和问答协作。
3. 后续代码 review 与板端确认, 希望通过用户与 AI 的对话方式完成, 以便更直接地理解仓库与改动。
4. 本地自动测试即 TDD 主线仍然保留, 因为它仍然适合承担主机侧快速回归。

因此, 当前仓库需要把“本地自动测试”和“板端协作确认”彻底分开: 保留前者, 退出后者的仓库内制度化结构。

## 目标

本轮只追求以下目标:

1. 从当前正式主线中移除 `stage2 / stage3 / HIL` 硬件测试体系。
2. 删除 `tests/hil/` 以及所有明确服务于该体系的板端工具入口。
3. 保留本地自动测试, 不破坏 `tests/unit/` 等主机侧回归主线。
4. 把当前文档、规则入口和任务口径统一改成: 仓库正式测试体系只保留本地自动测试; 板端确认通过用户与 AI 的对话协作完成。
5. 保留历史归档材料, 但不再把它们当作当前正式测试体系的现行规则。

## 非目标

本轮明确不做以下事情:

1. 不删除本地自动测试。
2. 不重构 `tests/unit/` 或当前 TDD 主线。
3. 不在本轮建立新的板端自动化替代工具。
4. 不把“以后如何和用户对话完成板端确认”扩展成新的复杂流程设计。
5. 不删除归档 spec、memory 和历史留证材料本身。
6. 不改当前正式运行代码。

## 为什么单开这份 spec

这轮变更不是简单的“删一个目录”, 而是在调整仓库对“什么叫测试”的正式定义。

当前仓库同时存在两类验证口径:

1. 主机侧自动测试, 用于快速回归。
2. 板端验证分层, 用于真实设备观察和留证。

用户已经明确决定保留前者、退出后者。这个边界变化会影响:

1. 测试目录结构。
2. 板端工具入口。
3. 当前文档与规则入口。
4. 后续新会话如何理解仓库中的“验证”和“完成证据”。

因此需要单开 spec, 明确哪些内容退出当前主线, 哪些内容保留, 避免只删文件而不改口径, 导致仓库进入半残状态。

## 方案选择

本轮采用“当前主线彻底去掉硬件测试体系, 历史归档先保留”的方案。

其含义是:

1. 删除当前正式主线中的 `tests/hil/`、`stage2`、`stage3` 相关工具和口径。
2. 保留 `tests/unit/` 等本地自动测试主线。
3. 保留 archive 与 memory 中的历史材料, 但明确它们只代表过去阶段, 不再代表当前正式规则。

选择该方案的原因如下:

1. 它能立刻把当前仓库的正式测试口径收干净。
2. 它不会把历史演进记录也一起打碎, 仍然保留回看价值。
3. 它与用户当前的真实工作方式一致: 板端确认继续做, 但不再作为仓库内测试制度维护。

## 核心决策

### 决策一: 当前正式测试体系只保留本地自动测试

本轮完成后, 当前仓库中的正式测试体系只保留本地自动测试。

这意味着:

1. `tests/unit/` 和仍然有效的主机侧自动验证继续保留。
2. 板端验证不再被仓库组织成正式测试层级。
3. 当前“完成证据”的正式仓库内表达, 以本地自动测试为主。

### 决策二: 硬件在环测试体系整体退出当前主线

本轮退出的不只是 `tests/hil/` 目录本身, 而是整套硬件测试体系。

这包括:

1. `tests/hil/` 目录。
2. `stage2 / stage3 / HIL` 的正式测试分层口径。
3. 对应的板端工具入口与探针脚本。
4. 当前文档中要求补 `stage2 / stage3 / HIL` 留证的现行表述。

### 决策三: 板端确认改为对话协作, 不再固化为仓库测试层

用户已经明确后续板端确认方式调整为用户与 AI 的对话协作。

因此:

1. 当前仓库不再继续维护板端自动测试入口。
2. 当前仓库不再继续维护板端手动留证模板。
3. 后续若需要板端验证, 由用户通过会话直接询问、确认、观察和 review, 而不是先要求仓库内存在 `stage2 / stage3 / HIL` 流程。

### 决策四: 历史材料保留, 但不再代表当前规则

本轮不删除 archive、memory 和旧留证材料本身。

这意味着:

1. 历史 spec 和 memory 中出现的 `stage2 / stage3 / HIL` 仍作为历史记录保留。
2. 当前规则入口、主文档和任务文档必须明确: 这些历史材料不再定义当前正式测试体系。
3. 后续新会话默认不应再从历史材料反向推出“当前仍必须保留 HIL 体系”。

## 删除边界与保留边界

### 删除边界

本轮应删除以下内容:

1. `tests/hil/` 整个目录。
2. 所有明确服务于 `stage2 / stage3 / HIL` 的板端工具入口。
3. `pytest.ini` 中与 `hil` 相关的 marker 口径。
4. `tests/README.md` 中把 `stage2 / stage3 / HIL` 当作正式测试分层的说明。
5. 当前主文档、任务文档和规则入口中把硬件测试体系写成现行要求的表述。

### 保留边界

本轮应保留以下内容:

1. `tests/unit/` 和仍然有效的本地自动测试。
2. 当前仍能帮助用户 review 代码的主机侧测试说明。
3. archive 与 memory 中的历史材料本身。
4. 任何不属于硬件测试体系的普通主机侧工具与验证逻辑。

## 当前口径如何改写

本轮不应只删除文件, 还必须同步改写当前口径。

### 当前测试说明

测试说明应改成:

1. 当前仓库正式测试体系只保留本地自动测试。
2. 板端确认不再属于仓库内测试分层。
3. 若需要板端现象确认, 由用户与 AI 在会话中直接协作完成。

### 当前规则入口

规则入口应改成:

1. 新会话默认不再把 `stage2 / stage3 / HIL` 当作当前正式验证门禁。
2. 当前“验证完成”优先看本地自动测试与用户 review。
3. 归档中的硬件测试材料只作为历史参考, 不作为当前默认要求。

### 当前任务文档

当前任务文档应改成:

1. 删除现行任务里要求补 HIL 记录模板和 HIL 证据的条目, 或改成更一般的“结果记录/人工复盘”。
2. 不再把硬件测试体系写作当前阶段固定交付项。

## 执行设计

本轮执行应分为三个动作单元:

### 单元一: 删除硬件测试目录与板端工具

只处理目录与工具退出:

1. 删除 `tests/hil/`。
2. 删除与 `stage2 / stage3` 强绑定的板端工具入口与探针脚本。
3. 删除不再需要的板端测试说明文件。

### 单元二: 收口当前测试与规则口径

只处理当前正式文档与规则入口:

1. 更新 `tests/README.md`、`pytest.ini`。
2. 更新当前主文档、任务文档和规则入口。
3. 明确当前仓库只保留本地自动测试体系。

### 单元三: 最小验证与自洽检查

最后做当前主线自洽验证:

1. 确认本地自动测试入口仍可用。
2. 确认当前仓库中不再残留 `stage2 / stage3 / HIL` 的现行测试入口。
3. 确认当前文档不会继续把硬件测试体系写成默认要求。

## 提交边界

本轮提交应遵循以下原则:

1. “删除目录与工具”和“收口文档口径”可以分为独立提交。
2. 不要把这轮改动和后续 `tests/unit/` 重构混在一起。
3. 不要把运行时代码改动混入这轮提交。

## 影响范围

本轮会影响以下几类内容:

1. `tests/hil/` 及其相关说明。
2. `stage2 / stage3` 对应的板端工具入口。
3. 当前主文档、任务文档和规则入口。
4. `pytest.ini` 与测试说明文件。

本轮不应直接影响以下主题:

1. `tests/unit/` 的结构与覆盖范围。
2. 当前正式运行代码。
3. 3.0 入口适配。
4. 底盘控制或视觉协议行为。

## 验收标准

本轮完成后, 至少应满足以下标准:

1. 当前仓库中不再保留 `tests/hil/`。
2. 当前仓库中不再保留 `stage2 / stage3 / HIL` 的正式测试入口与工具入口。
3. 当前测试说明与规则入口已明确: 正式测试体系只保留本地自动测试。
4. 当前任务文档不再把硬件测试体系写成现行要求。
5. archive 与 memory 中的历史材料仍保留, 但不会继续误导当前主线。

## 风险与后续

### 当前已知风险

1. 删除板端工具后, 仓库将不再提供现成的硬件测试入口; 后续如果想重新引入类似能力, 需要重新设计而不是直接依赖旧口径。
2. 历史归档中仍会保留大量旧 `stage2 / stage3 / HIL` 表述; 如果当前规则入口没有收干净, 新会话仍可能被带偏。
3. 若本轮只删目录不改文档, 仓库会进入“文件已删、规则还在”的半残状态, 因此口径收口是本轮必要部分。

### 后续主题

本轮完成后, 下一轮更合适的主题是:

1. 重构当前 `tests/unit/` 与主机侧测试说明。
2. 明确“通过用户与 AI 对话完成板端确认”的简明协作口径。
3. 继续推进当前正式主线的代码重构, 而不是重新恢复硬件测试体系。

## 结论

这轮工作的本质不是“反对板端验证”, 而是把板端验证从仓库内正式测试体系中退出。

本轮完成后:

1. 当前仓库的正式测试体系将只保留本地自动测试。
2. 硬件在环测试体系将不再继续维护。
3. 板端确认改为用户与 AI 的对话协作。
4. 历史材料保留, 但不再代表当前主线规则。

这样做的价值在于把当前仓库的测试口径重新收敛到用户真正愿意使用、也更利于 review 的工作方式上。
