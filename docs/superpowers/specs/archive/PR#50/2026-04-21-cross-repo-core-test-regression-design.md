# 2026-04-21 双仓库核心回归与行为测试补强设计

> 状态: Archive
> 当前约束以 `docs/developer/strategy.md`、`docs/developer/tasks.md`、`tests/README.md`、`../SmartCar2026-Vision/AGENTS.md` 与双方现有测试目录约定为准。

## 背景

当前两个仓库都已经有一批关键测试, 但更偏“单点约束”而不是“核心功能回归网”。

这带来两个直接问题:

1. 后续做 TDD 时, 很难快速判断某次改动是否碰到了不该动的核心行为。
2. 两边各自演进时, 通信协议口径可能在没有明显报警的情况下慢慢漂移。

本轮用户目标已经明确:

1. 只补回归测试和行为测试。
2. 重点服务后续开发时的 TDD 便利性。
3. 允许把双仓库间的通信协议测试一起纳入。
4. 不额外追求治理文档、目录结构或实现细节层的测试扩张。

## 目标

1. 在车端仓库补出一层稳定的核心行为回归网。
2. 在 Vision 仓库补出一层稳定的核心行为回归网。
3. 增加一层最小通信协议对齐测试, 防止两边核心口径漂移。
4. 新增测试默认面向外部行为与历史回退风险, 不把实现步骤写死。

## 非目标

1. 不追求覆盖率数字。
2. 不系统扩写治理文档、目录长相、技能存在性之类测试。
3. 不把测试写成内部状态快照、工厂调用次数快照或日志逐字快照。
4. 不做板端联调自动化。

## 方案比较

### 方案一: 最小核心回归网, 推荐

做法:

1. 车端仓库只补最关键的主车转发、辅车跟随、角色入口与异常不中断行为测试。
2. Vision 仓库只补最关键的目标到输出命令链路测试。
3. 双仓库之间只补一层最小通信协议对齐测试。

优点:

1. 直接服务后续 TDD。
2. 改动面可控。
3. 最不容易重新引入过度约束测试。

### 方案二: 主要分支一起系统补齐

做法:

1. 在方案一基础上, 把更多异常分支、次级分支和文档契约一起补齐。

问题:

1. 改动面明显变大。
2. 更容易把这轮变成测试体系重建。
3. 会稀释“先守住核心行为”的重点。

本轮不采用。

### 方案三: 只补通信协议

做法:

1. 只锁 Vision 输出和车端消费之间的关键字段与文本格式。

问题:

1. 只能防协议漂移。
2. 对仓库内部核心行为回归帮助不够。

本轮不采用。

## 推荐方案

本轮采用方案一。

一句话概括:

围绕“车端核心行为”“Vision 核心行为”“双仓库最小协议对齐”三层补测试, 让后续 TDD 能优先拦住真正不该回退的核心功能。

## 设计细节

### 1. 车端仓库测试边界

车端仓库本轮只覆盖这些主题:

1. 主车对上游输入的关键转发行为。
2. 辅车对前馈与视觉输入的关键融合行为。
3. 角色分流和入口装配的最小外部行为。
4. 串口异常、解码异常、非法输入这类历史高风险回退点。

不覆盖这些主题:

1. 内部对象长什么样。
2. 工厂调用了几次。
3. 中间事件完整顺序。
4. 默认桩值必须是多少。

### 2. Vision 仓库测试边界

Vision 仓库本轮只覆盖这些主题:

1. 有目标时输出命令的关键方向和字段语义。
2. 无目标或保持阶段时的安全输出。
3. 目标偏差变化对输出命令的关键行为影响。
4. 历史协议切换后不应回退的关键口径。

不覆盖这些主题:

1. 文档治理词句。
2. 技能文件 frontmatter 细节。
3. 目录结构和文件清单。
4. 内部阶段名字符串本身。

### 3. 双仓库通信协议对齐层

这一层只锁双方共同依赖的最小公共面:

1. Vision 发出的关键字段名。
2. 关键数值表达方式与零值语义。
3. 车端当前会消费或透传的最小文本口径。
4. 明确哪些旧字段已经不再属于正式主线。

这一层不做:

1. 复杂联调模拟。
2. 串口时序仿真。
3. 板端环境依赖。

### 4. 测试风格约束

本轮新增测试统一遵守以下约束:

1. 优先断言外部结果。
2. 重点 bug 可以保留更强断言。
3. 行为测试只锁关键输入输出和关键副作用。
4. 不为补测试而增加兼容层。

### 5. 完成标准

当以下条件同时满足时, 本轮算完成:

1. 两边仓库都新增了核心回归测试或行为测试。
2. 至少补上一层双仓库协议对齐测试。
3. 两边主机侧相关测试都通过。
4. 新增测试没有明显重新绑定实现细节。
