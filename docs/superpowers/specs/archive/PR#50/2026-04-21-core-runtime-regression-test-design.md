# 2026-04-21 core 运行时回归与行为测试补强设计

> 状态: Archive
> 归档原因: 被“core 测试目录整理与系统补强”设计替代。
> 当前约束以 `docs/developer/strategy.md`、`docs/developer/tasks.md`、`tests/README.md` 与仓库现有 `command/`、`core/`、`vision/` 分层为准。

## 背景

当前仓库已经有一批测试, 但覆盖重心主要在这些位置:

1. 入口脚本与角色分流。
2. 主车/辅车运行时。
3. 命令路由与若干协议边界。

`src/core/` 当前只有 `runtime.py` 与 `diagnostics.py`, 却承担了底盘公共运行时的大部分核心职责:

1. 周期控制主循环。
2. 串口输入处理与命令落地。
3. 姿态控制、位置/速度目标切换。
4. 电机目标分配与安全收口。
5. 查询与诊断快照。

现在的问题不是完全没有测试, 而是 `core` 层没有形成一套独立、系统、按主题分文件的回归测试和行为测试。

这会直接带来两个后果:

1. 后续改 `core` 时, 很难快速判断有没有碰到不该回退的公共能力。
2. 现有测试更像从外围间接覆盖 `core`, 不能清晰表达 `core` 自己的公共行为与高风险内部规则。

本轮用户已经把方向收紧为:

1. 先不改 Vision 仓库。
2. 先把车端 `core` 补好。
3. 这轮既要覆盖 `core` 公共行为, 也要补少量高风险内部辅助行为。
4. 串口输入处理、命令路由与状态切换、电机与姿态相关安全边界都要纳入。
5. 测试需要按文件系统化组织, 不再零散补点。

## 目标

1. 为 `src/core/runtime.py` 建立一套独立、系统、按主题分文件的回归测试和行为测试。
2. 为 `src/core/diagnostics.py` 建立独立的诊断格式化测试。
3. 把 `core` 公共行为、输入与路由、高风险内部规则、安全边界四层都补齐到可支撑后续 TDD 的程度。
4. 新增测试默认优先断言外部行为, 只对少量高风险内部规则保留必要强断言。

## 非目标

1. 不扩写 Vision 仓库测试。
2. 不扩写 `main.py`、角色层或入口层测试。
3. 不追求覆盖率数字。
4. 不把 `command.router`、`command.policy` 已经独立覆盖的语义再在 `core` 层重复一遍。
5. 不引入板端自动化或硬件联调脚本。

## 方案比较

### 方案一: 按行为面分层补, 推荐

做法:

1. 按测试主题拆文件, 而不是按 `runtime.py` 函数顺序平铺。
2. 先锁 `TransportCar` 对外公共行为。
3. 再锁串口输入与命令路由主线。
4. 然后锁少量值得长期保留的高风险内部规则。
5. 最后补安全边界与诊断格式化。

优点:

1. 最符合后续 TDD 使用方式。
2. 测试职责清晰, 更容易定位失败含义。
3. 不容易重新写回“跟实现逐行同步”的测试。

### 方案二: 按 `runtime.py` 函数顺序平铺补

做法:

1. 从 `_inverse_kinematics`、`_handle_tick`、`_process_uart` 一路按函数往下补。

问题:

1. 容易把测试写成“实现抄写稿”。
2. 文件会迅速变大, 不利于后续继续扩充。
3. 失败后不容易看出是公共行为坏了, 还是某个实现步骤变了。

本轮不采用。

### 方案三: 只补已知高风险点

做法:

1. 只围绕串口异常、解锁、停车、姿态保持这几个点补几条回归测试。

问题:

1. 能补洞, 但不能形成“完整的一套”。
2. 仍然不满足用户对系统化和分文件组织的要求。

本轮不采用。

## 推荐方案

本轮采用方案一。

一句话概括:

围绕 `core` 公共行为、输入与路由、高风险内部规则、安全边界四层拆分测试文件, 建立一套更适合后续 TDD 的 `core` 运行时回归网。

## 设计细节

### 1. 测试文件组织

本轮测试按主题拆成以下文件:

1. `tests/unit/test_core_diagnostics.py`
   - 负责 `diagnostics.py` 的纯格式化行为。

2. `tests/unit/test_core_runtime_public_api.py`
   - 负责 `TransportCar` 对外公共行为。

3. `tests/unit/test_core_runtime_uart_flow.py`
   - 负责 UART 输入处理、查询/命令分流、缓冲与错误回写。

4. `tests/unit/test_core_runtime_control_flow.py`
   - 负责姿态控制、位置/速度目标切换、逆运动学与目标分配。

5. `tests/unit/test_core_runtime_safety.py`
   - 负责停车、急停、解锁、安全回收和边界保护。

6. `tests/unit/core_runtime_test_support.py`
   - 仅放 `core` 测试公用桩、导入辅助和最小上下文构造。

这里的重点是“按职责拆测试文件”, 而不是继续把所有 `core` 行为塞回现有 `contract` 文件里。

### 2. 公共行为层

这一层只测 `TransportCar` 对外应该稳定提供的能力:

1. `step()` 在正常情况下继续运行。
2. `step()` 收到急停开关变化后会停止并返回结束信号。
3. `stop()` 会停 ticker、清零电机并写出停止提示。
4. `get_query_uart()` 在默认和临时覆写两种情况下都返回正确输出通道。
5. `build_health_snapshot()`、`build_tick_snapshot()`、`build_imu_snapshot()`、`build_encoder_snapshot()`、`build_motor_snapshot()` 能稳定提供最小诊断事实。

这一层不去锁:

1. 初始化日志顺序。
2. 具体字段排列顺序。
3. 内部临时变量名字。

### 3. 输入与路由层

这一层只测 `core` 如何消费和分发输入:

1. `_handle_uart_line()` 能把查询与普通命令分到不同路径。
2. `_process_uart()` 能正确处理多行输入和残留缓冲。
3. `_process_uart()` 异常时会记录最小错误并回写错误行。
4. 空行、残缺行和无换行残留不会提前误处理。
5. 查询输出通道切换不会影响默认控制通道。

这里与 `command.router` 的边界要明确:

1. 路由器本身的命令语义继续由现有 `command` 测试负责。
2. `core` 只负责“有没有正确把输入送到应去的位置”。

### 4. 高风险内部规则层

这一层只锁那些值得长期保留的内部规则:

1. `_compute_omega_cmd()` 在角度模式、角速度模式、保持模式下的关键行为。
2. `_compute_planar_targets()` 在位置模式和速度模式之间的切换。
3. `_apply_target_speeds()` 在全向模式与 `rear_only_mode` 下的关键目标分配。
4. `_inverse_kinematics()` 在超限时仍会整体缩放而不是单轮溢出。
5. `_check_unlock()` 达标后会解除锁定, 必要时回收后轮模式并停车。

这层允许对关键结果保留较强断言, 但不要求验证每一步中间状态。

### 5. 安全边界层

这一层负责“以后改动时最不该悄悄坏掉”的保护逻辑:

1. 过长控制周期会累计 overrun 计数。
2. 未启用轮子会被重置并强制清零。
3. 后轮模式解锁后会回到安全静止状态。
4. 非法串口输入或读串口异常不会让主循环静默失控。
5. 诊断模式下空硬件仍能维持最小运行事实。

### 6. 与现有测试的关系

本轮不会删除现有测试, 但会把职责边界重新拉清楚:

1. `test_non_query_command_reply.py` 和 `test_optional_lock_commands.py` 继续守命令与策略语义。
2. 新的 `core` 测试文件只守 `TransportCar` 与 `diagnostics` 的运行时行为。
3. 现有少量落在 `contract` 文件里的 `core` 行为可后续逐步迁移, 但本轮不以迁移为主目标。

### 7. 完成标准

当以下条件同时满足时, 本轮算完成:

1. `core` 层新增了一组按主题拆分的测试文件。
2. `runtime.py` 的公共行为、输入与路由、高风险内部规则、安全边界四层都被覆盖。
3. `diagnostics.py` 有独立测试文件覆盖主要格式化行为。
4. 新增测试能通过主机侧验证。
5. 新增测试没有明显重新绑定实现细节。
