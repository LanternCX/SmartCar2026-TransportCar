# 主车航向控制稳定性重整设计

## 背景

当前主车底盘已经完成一轮结构清理, 主链路不再依赖 legacy 的整套运行时组织, 但用户在实机联调中明确反馈: **闭环手感相比旧版偏软, 航向保持不够硬, 整体稳定性不如原来熟悉的那一版**。

这一现象已经说明一个关键事实: 问题不应再被简单归因为“系统辨识参数不对”或“再调大一点参数就行”。当前主车的轮速闭环、辨识参数读取和姿态积分主链都已基本打通, 但**航向控制语义已经不再等同于 legacy**, 所以旧版那组参数无法直接等价复用。

用户本轮目标不是单纯回退代码, 而是:

1. 恢复接近 legacy 的底盘稳定性与航向保持手感。
2. 保留当前主车主线已经得到的轻量结构与清晰边界。
3. 避免把 legacy 的重型组织方式整块搬回主线。

因此本轮设计不是“硬切回旧代码”, 而是**在当前主车骨架内重构回 legacy 中真正决定稳定性的航向控制语义**。

## 当前问题归纳

结合当前主车实现与 legacy 对照, 当前偏软的根因主要集中在航向控制行为差异, 而不是某一个数字本身。

### 一、当前主车保留了部分旧参数, 但没有保留完整控制语义

当前主车仍然保留了以下旧风格数值入口:

1. 航向比例与累计参数。
2. 航向输出限幅。
3. 三轮速度环参数。
4. 系统辨识前馈读取。

但当前主线没有完整保留 legacy 中这些数值对应的控制行为环境, 所以“参数看起来一样”并不代表“实际闭环是同一条链路”。

### 二、当前航向保持缺少 legacy 中用于稳定收敛的关键语义

与 legacy 相比, 当前主车航向控制至少缺少或弱化了以下能力:

1. **主动转动与自动保持之间的清晰切换语义。**
2. **停止主动转动后, 按旧版时机重新接管当前航向的规则。**
3. **保持阶段针对当前旋转趋势的抑制项。**

这会直接导致以下联调体感:

1. 转向时系统和人为旋转可能互相抢控制。
2. 停止主动转动后, 系统重新接管的时机不够接近旧版。
3. 航向回正能回去, 但收得不够利索, 容易显得拖或软。

### 三、当前问题应优先收在主车, 不扩大到辅车

本轮用户明确要求先只处理主车。原因如下:

1. 当前体感问题首先来自主车底盘控制。
2. 主辅两边一起统一会显著扩大改动面, 不利于快速恢复稳定联调基线。
3. 先把主车收成“稳定、可复用、结构不臃肿”的版本, 再决定是否将相同语义推广到辅车, 更符合当前任务主线。

## 目标

本轮设计必须同时达成以下目标:

1. 在当前主车主线结构内恢复更接近 legacy 的航向控制语义。
2. 让主车在实机上具备更接近 legacy 的稳定性与闭环硬度。
3. 保留当前 `motion_runtime.py -> ctrl/ -> state/` 的主线组织, 不整块退回 legacy 运行时结构。
4. 把真正决定稳定性的控制行为收回当前轻量骨架中, 而不是继续依赖“参数碰运气”。
5. 让后续调参建立在正确的控制语义之上, 而不是建立在语义缺失的近似链路之上。

## 非目标

本轮明确不做以下事情:

1. 不把 legacy 的整套运行时 owner、底盘控制器对象和装配结构直接搬回主线。
2. 不顺手扩展到辅车。
3. 不重新设计姿态积分主链、轮速闭环或系统辨识脚本。
4. 不为了“结构统一”而额外引入新的空壳类、兼容层或无必要抽象。
5. 不以“大规模参数重调”代替控制语义修复。
6. 不改变当前阶段主车默认不主动承担新增业务动作的验收边界; 本轮只恢复主车底盘基础控制语义与稳定性, 不改变现有主车业务角色。

## 核心设计

### 一、保留当前主车骨架, 只重构航向控制语义

主车继续保留当前主线组织:

1. `src/master/motion_runtime.py` 负责底盘主周期编排、硬件链路驱动和输出下发。
2. `src/master/ctrl/attitude.py` 负责姿态积分、航向目标管理和航向修正计算。
3. `src/master/state/` 继续承接跨周期状态。

本轮不改变这组边界, 只把 legacy 中真正有价值的航向控制行为重构到当前边界里。

### 二、恢复主动转动与自动保持之间的 legacy 语义

当前主车已经解决了“连续 hold 时反复刷新目标航向”的问题, 但仍需继续补齐 legacy 的控制切换逻辑。

本轮要恢复的行为是:

1. 当主车收到明确的主动旋转命令时, 航向保持不应继续按保持状态硬拽当前目标。
2. 只有当主动旋转已经降到接近停止的范围时, 才重新交由航向保持接管。
3. 重新接管时, 目标航向应锁定在当前真实朝向附近, 而不是在后续周期里持续漂移。

这组语义的目的不是“更复杂”, 而是让系统在“人为转动”和“自动稳向”之间切换得更像 legacy, 从而避免当前这种既不够硬又不够干脆的中间状态。

### 三、恢复 legacy 中用于稳定收敛的旋转抑制行为

legacy 的航向控制不只是“角度误差乘一个比例再累一点历史偏差”, 还包含一段对当前旋转趋势的抑制处理。它的作用是:

1. 当车头已经在往目标方向回正时, 防止继续带着过大的旋转趋势冲过去。
2. 在接近目标航向时更快把多余转动压住。
3. 让回正过程更利索, 也更接近用户对旧版“稳”的体感记忆。

本轮将把这段行为重新纳入当前主车控制链, 但不会为了它重新引入 legacy 的整套控制器层级。

### 四、保留当前主线轻量参数入口, 只补回缺失的关键调节点

当前 `src/master/runtime_params.py` 已经收得比较薄。本轮不会把 legacy 全量参数表整包搬回, 只会把恢复 legacy 语义后实际需要的关键调节点补回当前参数入口。

至少需要明确保留的参数类别包括:

1. 航向比例与累计相关参数。
2. 航向积分限幅与整体输出限幅。
3. 主动旋转停止后重新进入保持的判定门槛。
4. 保持阶段用于压制当前旋转趋势的稳定项力度。

这样既能保持当前参数入口清晰, 又能保证后续调参确实是在调“完整语义下的主因”。

## 文件落点

### 一、主要修改文件

1. `src/master/ctrl/attitude.py`
   - 恢复更接近 legacy 的航向保持计算语义。
   - 收口目标航向接管时机、主动旋转释放语义和旋转抑制逻辑。

2. `src/master/motion_runtime.py`
   - 调整主车底盘在 `hold` / `vel` 情况下的航向控制接线方式。
   - 让当前主线按更接近 legacy 的方式决定何时由系统保持、何时允许主动转动。

3. `src/master/runtime_params.py`
   - 补回当前主线真正需要、但尚未重新暴露的航向稳定性调节点。

4. `src/master/state/__init__.py`
   - 继续承接本轮需要跨周期保存的主车航向控制字段。
   - 本轮不新增新的状态层, 相关字段统一继续收口在现有主车状态定义中。

5. `tests/unit/master/` 下与主车航向控制、主车运行时相关的测试文件
   - 只补与本轮行为直接相关的验证。
   - 不顺手扩大到无关边界。

### 二、明确不修改的区域

1. `src/assistant/` 全部主线。
2. `src/master/script/pid_identify.py`。
3. `src/master/script/calibrate_gyro.py`。
4. 当前已验证可用的姿态积分与编码器读取边界, 除非本轮验证证明确实存在直接冲突。

## 控制流程设计

重整后的主车控制流程保持当前骨架, 但航向控制语义改为以下顺序:

1. 先刷新 IMU、编码器、航向和轮速观测。
2. 根据当前目标类型判断主车处于主动平移、主动旋转还是保持状态。
3. 若当前存在明确主动旋转命令, 则按 legacy 语义让航向保持退出或弱化接管。
4. 若当前主动旋转已结束或目标本身要求保持, 则重新锁定或维持目标航向。
5. 使用“角度误差 + 累计项 + 当前旋转趋势抑制”的方式得到旋转修正量。
6. 将最终平移量与旋转修正量一起送入三轮分解和轮速闭环。

这个流程和当前主线最大的差异不在骨架, 而在**什么时候把保持接回来、以及保持接管后如何更稳地把车头收住**。

## 错误处理与边界

### 一、目标航向边界

1. 保持目标仍然只在明确切换到保持或重新接管保持时锁定一次。
2. 不允许恢复成“连续 hold 每拍刷新目标”的错误语义。
3. 在缺失有效目标时, 仍应保持当前最小安全行为。

### 二、航向控制边界

1. 航向保持必须继续受当前输出限幅约束。
2. 恢复旋转抑制项后, 仍需保持数值可解释、可调, 不能写成隐藏式魔法常量。
3. 不能为了追求“更硬”而让当前主链重新出现明显争抢控制的行为。

### 三、结构边界

1. 不引入新的大运行时对象层级。
2. 不新增没有独立职责的空壳文件。
3. 让 `motion_runtime.py` 保持当前 owner 角色, 不重新膨胀成 legacy 风格的大型控制仓库。

## 验收标准

本轮完成后, 至少要满足以下可观察标准:

1. 主车主动给旋转时, 系统不会继续明显和人为转动抢控制。
2. 主动旋转停止后, 主车能重新稳定接住当前朝向。
3. 保持状态下的回正动作比当前版本更干脆, 不再明显偏软。
4. 回到目标航向附近后, 更不容易继续摆动或拖着收尾。
5. 当前主车代码结构仍然保持在现有轻量骨架内, 没有退回 legacy 的重型组织方式。

上面 1-4 条不能只靠单次主观体感判断, 需要按同一块板、同一组接线、同一套供电条件, 至少完成以下留证:

1. **对比对象**: 当前版本、legacy 已知稳定版本。
2. **观察场景**:
   - 主动旋转后松手, 观察是否能接住当前朝向。
   - 纯保持状态下人为扰动后, 观察是否能更快回正。
   - 接近目标朝向后的收尾阶段, 观察是否仍有明显拖尾或摆动。
3. **重复次数**: 每个场景至少重复 3 次。
4. **留证方式**: 至少保留串口日志或控制链日志, 并优先补一段实机视频; 不接受只凭一句“手感更好了”作为完成依据。

## 测试与验证策略

### 一、主机侧验证

本轮主机侧至少应覆盖以下行为:

1. 主动旋转期间不会错误重刷保持目标。
2. 主动旋转停止后, 保持逻辑会在正确时机重新接管。
3. 保持阶段会纳入恢复后的稳定收敛逻辑。
4. 当前主车运行时仍能把航向修正正确送到三轮目标分解链。

### 二、板端联调验证

本轮板端至少应再次观察以下现象:

1. 原地航向纠偏是否比当前版本更果断。
2. 主动转向后松手, 车头是否能更自然地停在当前朝向附近。
3. 持续保持时是否仍然不存在目标航向反复刷新的旧问题。
4. 联调结论必须同时对照当前版本与 legacy 稳定基线, 不接受脱离对比对象的单边评价。

## 为什么不直接硬切 legacy

直接整段切回 legacy 确实更快, 但不符合本轮用户目标, 原因如下:

1. 它会把旧版较重的组织方式一起带回当前主线。
2. 当前已经完成的结构清理会被明显抵消。
3. 后续再继续维护时, 仍然要重新面对“旧结构太重”的问题。

因此本轮的正确方向不是“复制旧代码”, 而是**让当前主线重新获得旧版真正有价值的稳定控制语义**。

## 结论

本轮主车底盘控制应采用“保留当前骨架, 重构回 legacy 航向控制语义”的方案。

该方案同时满足三件事:

1. 优先恢复用户最在意的底盘稳定性与熟悉手感。
2. 不把主车主线重新退回 legacy 的重型组织方式。
3. 为后续调参与可能的辅车推广保留清晰、可维护的实现基础。
