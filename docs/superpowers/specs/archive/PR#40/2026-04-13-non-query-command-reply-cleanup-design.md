# 2026-04-13 非查询命令回包收口设计

> 状态: Archive

## 背景

当前底盘串口入口同时承担两类输出:

1. 查询类输出, 例如 `?health`、`?tick`、`?vision` 的结果回写.
2. 非查询类输出, 例如普通命令回显、状态提示和执行异常提示.

这次要处理的是第二类里的噪声输出, 目标是让普通命令执行更安静, 但不影响查询链路和基本排障能力.

用户已经确认本轮边界如下:

1. 查询类输出继续保留.
2. 真正执行异常时的错误输出继续保留.
3. 普通命令收到时的回显和状态提示删除.
4. `print` 命令在运行时也不得打印, 若当前主线存在统一关闭入口则服从该入口, 否则本轮直接静默.

## 目标

1. 删除普通命令执行过程中的非必要主动回写.
2. 保持查询协议和查询结果格式不变.
3. 保持真正执行异常时的错误提示能力.
4. 不改变现有命令本身的控制语义.
5. 让本轮改动收敛在回包行为层, 不扩大到新的协议设计.

## 非目标

1. 不改查询命令的字段、格式和来源串口选择逻辑.
2. 不新增新的串口协议字段或运行模式开关.
3. 不调整已有控制命令的执行语义.
4. 不为 `print` 额外恢复旧的统一日志机制, 也不新增新的调试开关或替代通道.
5. 不顺带改动其他诊断或日志系统规划.

## 当前问题

当前非查询类主动输出里, 至少包含以下几类信息:

1. 收到普通命令时的 `RCV:` 回显.
2. `rear` 模式切换成功后的提示.
3. 某些动作完成后的状态提示.

这些信息会让普通控制链路持续产生额外文本, 对需要稳定发命令或观察查询结果的场景并不友好. 其中一部分文本也不属于必须保留的排障信息.

## 设计决策

### 决策一: 只清理普通命令成功路径上的主动回写

本轮删除对象只包含“普通命令成功执行时主动写出的提示文字”, 不扩展到查询输出和异常输出.

这样可以直接满足“普通命令更安静”的目标, 同时避免误伤查询和排障链路.

### 决策二: 查询路径保持原样

以下内容继续保留:

1. 所有 `?xxx` 查询结果回写.
2. 未知查询时的 `?unknown=...` 回写.
3. 查询响应写回原来源串口的现有行为.

本轮不改查询格式, 也不改查询路径的写回规则.

### 决策三: 异常路径保持可见

真正执行异常时的错误输出继续保留, 用于现场排障和最小错误可见性.

这意味着:

1. 普通命令成功时不主动提示.
2. 真正发生执行异常时, 仍然允许输出错误信息.

### 决策四: `print` 也纳入运行时静默范围

`print` 命令虽然用于调试, 但用户已经明确要求它在运行时不得打印.

补充约束是: 若当前正式主线里仍有可用的统一关闭入口, `print` 应服从该入口; 若当前正式主线并没有这条可直接复用的路径, 本轮不为它恢复旧机制, 直接收口为静默.

因此本轮固定口径如下:

1. `print` 不再绕开统一控制直接向运行时串口输出文本.
2. 若当前主线存在可用的统一关闭入口, `print` 必须接入并服从该入口.
3. 若当前主线没有可直接复用的统一关闭入口, 本轮直接让 `print` 静默.
4. 如果后续还需要保留调试文本能力, 需要单独设计新的调试入口, 不在本轮顺带增加.

### 决策五: 删除对象按具体提示点收口

本轮按现有明确提示点收口, 不做抽象层重构.

计划删除的行为包括:

1. 普通命令收到后的 `RCV:` 回显.
2. `rear` 切换成功后的提示文本.
3. 动作完成后自动输出的状态提示文本.
4. `print` 命令绕开统一控制的运行时文本输出.

这种做法改动面最小, 也更容易验证是否误伤别的输出路径.

## 协议口径

本轮之后的统一口径如下:

1. 查询命令有回包.
2. 普通命令成功执行时默认无回包.
3. 真正执行异常时允许输出错误信息.
4. `print` 不再作为绕开统一控制的运行时输出特例存在.

对上位来说, 这轮不需要学习新的发包格式. 变化只在于普通命令成功后不再依赖提示文字确认执行.

## 数据流边界

收口后的最小链路如下:

1. 查询输入进入查询处理器, 继续按原方式输出查询结果.
2. 普通命令输入进入命令处理器, 成功时不主动输出额外提示.
3. 命令执行过程中若出现真正异常, 继续输出错误信息.
4. `print` 在运行时不再绕开统一控制产生文本输出; 若无统一入口则直接静默.

## 验收标准

本轮设计落地后, 至少应满足以下结果:

1. 发送普通控制命令时, 不再收到 `RCV:` 这类回显.
2. `rear` 切换和动作完成后, 不再收到额外状态提示文本.
3. 查询命令仍能正常得到原格式响应.
4. 未知查询仍能得到 `?unknown=...`.
5. 真正执行异常时仍能看到错误输出.
6. `print` 命令在运行时不再绕开统一控制输出传入文本; 若无统一入口则保持静默.

## 测试与验证口径

### 主机侧验证

主机侧至少覆盖以下边界:

1. 普通命令执行后不产生被删除的提示文字.
2. 查询命令仍有回包.
3. 未知查询仍有回包.
4. 异常路径仍有错误输出.
5. `print` 在运行时服从统一关闭口径; 若当前主线无该入口则保持静默.

### 板端联调

板端至少确认以下结果:

1. 连续发送普通控制命令时, 串口输出不再被提示文字刷屏.
2. 使用查询命令时, 仍能读到查询结果.
3. 制造真实错误场景时, 仍能看到错误输出.
4. 若当前主线有统一关闭入口, `print` 与其他调试输出遵循同一口径; 若当前主线无该入口, 发送 `print` 时运行时串口保持静默.

## 风险与控制

### 风险一: 误删查询或错误输出

控制方式:

1. 只针对普通命令成功路径下的提示点做删除.
2. 用独立验证覆盖查询和异常路径, 防止一起被静默掉.

### 风险二: 调试信息过少导致现场不好排查

控制方式:

1. 保留查询链路.
2. 保留异常错误输出.
3. 如需调试文本能力, 后续单独设计专用调试入口或正式恢复统一控制链路, 不在本轮混入运行时链路.

### 风险三: 实现时顺手扩大改动面

控制方式:

1. 本轮只做提示点级别收口.
2. 不在本轮引入新的协议开关或日志系统整理.
