# 2026-04-09 辅车主动跟随主车重构设计

> 状态: archive
> 说明: 软件侧实现已完成并完成主机侧回归; 板端联调与上板测试按用户要求跳过。

## 背景

当前仓库的主线仍然建立在“主车双摄、主车统一计算辅车跟随、辅车纯执行”的旧口径上。

这条口径与用户当前确认的目标已经不一致：

1. 主车旧双摄跟随逻辑不再继续保留；主车剩余相机如何落位不属于本轮实现范围。
2. 原本装在主车上的另一颗相机要移动到辅车。
3. 辅车要依靠自己的相机主动跟随主车，而不是继续依赖主车高频计算跟随控制。
4. 跟随闭环不再放在主车，也不回到主车统一计算后再下发。
5. 当前目标只聚焦“辅车跟随主车”本身，不把搬运阶段设计一起展开。

在最新确认中，辅车侧还进一步固定了两条关键边界：

1. 辅车新增相机接入 `UART6`。
2. 辅车相机只跟踪主车上的固定标记，并且由相机侧直接算出控制量，再按当前辅车已经支持的跟随协议发送给辅车执行。

因此，这次重构的核心已经不是继续压榨主车双摄主线，而是把“辅车主动跟随主车”立成新的中心，同时把主车侧与旧跟随主线绑定的逻辑明确删减。

另外，当前范围不再只包含车端仓库。由于辅车相机要直接输出给辅车执行侧消费的控制命令，本轮也必须同步修改视觉仓库 `SmartCar2026-Vision`，否则只改车端无法形成闭环。

## 目标

本轮设计只追求以下目标：

1. 建立“辅车相机观察主车标记 -> 相机侧计算控制量 -> 辅车执行”的新主线。
2. 把主车侧原有的双摄跟随主线删减到与新方向一致，不再继续承担辅车跟随闭环。
3. 把仓库口径从“主车双摄驱动辅车”改成“辅车单摄主动跟主，主车旧双摄跟随逻辑删除”。
4. 把这次验收收口到“辅车能否稳定跟随主车”，不把搬运阶段一起卷入。
5. 保持改动聚焦，不顺手扩展新的主辅协同协议主题。
6. 同步修改视觉仓库，使辅车相机输出语义与新的辅车主动跟随主线一致。
7. 保持辅车现有控制解析与底盘运动计算主线不变，不在本轮重写辅车控制核心。

## 非目标

本轮明确不做以下事情：

1. 不在本轮展开搬运阶段的控制设计。
2. 不在本轮定义进入搬运后是否继续使用视觉跟随。
3. 不在本轮规定新的主车侧通讯协议细节。
4. 不在本轮把主辅整套任务状态机重新设计一遍。
5. 不在本轮讨论搬运物体状态的视觉观测闭环。
6. 不在本轮把所有历史文档一次性全部清理完，只更新和当前方向直接冲突的口径。
7. 不在本轮处理主车剩余相机的最终串口落位与新主线接入。
8. 不在本轮改写视觉仓库中的官方题面整理文档, 题面冲突只作为已知背景记录。
9. 不在本轮重写辅车已有的控制协议解析与底盘运动计算。

## 为什么要重写当前口径

继续保留旧口径会带来四类直接问题：

1. 主车同时承担双摄输入、高频跟随计算和其他任务判断，会继续把运行压力和串口热路径压在同一侧。
2. 辅车仍被定义成“无视觉纯执行”会和当前真实硬件布局冲突。
3. 文档和代码如果继续把主车跟随主线写成既有事实，后续实现很容易一边新增辅车跟随，一边又保留旧主线，形成双线并存。
4. 视觉仓库当前仍把 OpenArt 定义成“只上报观测、不直接输出辅车执行控制”，如果不同步修改，双仓语义会直接打架。

因此，这次设计不是在旧主线外面再补一层，而是要把中心口径换掉。

## 总体设计

新的中心边界如下：

1. 主车当前只删除旧双摄跟随主线，不在本轮处理剩余相机的最终接入方案。
2. 辅车获得自己的单摄跟随能力，重点是主动跟住主车标记。
3. 辅车跟随闭环由辅车侧承担，不再由主车统一闭环。
4. 辅车控制板保留执行、安全停下和基础稳定能力，但不承担视觉跟随算法本身。
5. 这次设计的完成标准只围绕“辅车主动跟随主车”，不额外绑定搬运阶段。

换句话说，这次重构包含两部分同时成立：

1. 辅车侧建立新的主动跟随链路。
2. 主车侧删掉与旧双摄跟随主线直接绑定的职责。
3. 视觉仓库把输出从“给主车看的最小观测”改成“给辅车执行侧消费的位置式跟随命令”。

## 角色边界

### 主车边界

主车在这次重构后应收口为：

1. 不再负责替辅车做跟随判断和高频控制输出。
2. 不再把辅车主动跟随当成自己的实时主链。
3. 不再保留“为了跟随而存在”的双摄仲裁与输出组织逻辑。
4. 本轮不处理主车剩余相机最终接在哪一路。
5. 本轮不展开新的主车找物与避障实现。

这意味着主车这次的主要动作是“删减旧跟随职责”，而不是“新增一条更复杂的主车协议主线”。

### 辅车边界

辅车在这次重构后应收口为：

1. 接入自己的相机输入。
2. 只跟踪主车上的固定标记。
3. 由相机侧直接计算控制量。
4. 按当前已经支持的跟随协议把控制量送到辅车控制板执行。
5. 控制板沿用当前的解析、运动计算、安全约束和基础稳定能力。

因此，辅车不再只是被动接命令执行，而是拥有自己的跟随感知链。

### 视觉仓库边界

视觉仓库在这次重构后应收口为：

1. 继续保持单文件 `main.py` 主入口，不在本轮做结构拆分。
2. 相机只跟踪主车上的固定标记，不继续围绕搬运物主线组织输出。
3. 输出语义从“给主车消费的像素观测”切换到“给辅车执行侧消费的位置式控制量”。
4. 仍然只负责视觉识别、目标选择和控制量计算，不接管底盘执行与安全停下。
5. 输出格式直接对齐当前辅车已支持的跟随请求格式，不再要求辅车为此重写控制核心。
6. 同步更新视觉仓库的 README、协议文档和契约测试，避免文档还停留在旧观测口径。

## 辅车内部主链

辅车内部主链只保留一条最短路径：

`辅车相机 -> 辅车控制板 -> 辅车底盘`

该主链的运行原则如下：

1. 相机持续观察主车标记。
2. 只要标记有效，相机就持续输出当前辅车已支持的跟随控制请求。
3. 控制板每拍只消费最新一条完整命令，不追旧包。
4. 控制板沿用当前已有解析和运动计算，把命令直接变成执行输入。
5. 任意一环失效时，优先进入停下或保持安全状态。

这个设计的核心取舍是：

1. 让视觉判断和跟随控制量生成尽量靠近相机侧完成。
2. 让控制板专注执行，不再背负视觉闭环计算。
3. 让串口主链尽可能短，避免把旧的高频往返负担带回来。

这里还要额外固定一条语义边界：

1. 辅车相机输出的是位置式控制量，不是原样像素误差。
2. 视觉仓库输出要直接对齐当前辅车已经支持的 `follow` 请求语义。
3. 辅车控制板不新增第二套控制链, 继续沿用当前协议解析与底盘运动计算。
4. 因此，这次不是只改接线或改串口入口，而是要同步改视觉输出语义。

## 主车侧删减原则

主车侧这次不是“不展开”，而是要明确做减法。至少要删减以下方向：

1. 完整删除主车读取跟随相机的运行时主线。
2. 完整删除主车基于视觉结果跳转跟随阶段和生成辅车控制量的主线。
3. 完整删除主车向辅车转发高频跟随控制和回读相关状态的主线。
4. 不保留为了兼容旧跟随流程而存在的中间适配层。
5. 主车剩余相机后续如何用于找物与避障，不在本轮展开。

删减后的目标很明确：主车不再和新的辅车主动跟随方向打架。

## 协议边界

本轮只固定辅车侧需要满足的协议边界，不展开新的主车侧通讯设计。

需要固定的只有以下事实：

1. 辅车相机会直接向辅车执行侧发送控制命令。
2. 辅车执行侧只需要稳定接收、消费、执行和做安全收口。
3. 相机输出的是与辅车当前 `follow` 控制请求一致的位置式控制量，不再把像素误差原样塞给辅车执行侧。
4. 辅车执行侧现有解析与底盘运动计算继续保留，不为本轮新增兼容层。
5. 控制链必须支持“有效输入继续执行、无效输入立即停下”的最小闭环。

本轮刻意不写死以下内容：

1. 主车未来如何参与阶段切换。
2. 主车未来是否还需要保留某些低频协同命令。
3. 后续搬运阶段是否需要新增其他控制消息。

这样做不是留坑，而是避免把当前目标再次拉回“顺手重做整套主辅协议”。

## 异常处理

辅车主动跟随这条链必须把异常处理收得很硬，至少满足以下规则：

1. 主车标记丢失时，辅车立即停下。
2. 输入超时时，辅车立即停下。
3. 数据坏包或协议不合法时，辅车立即拒绝并停下。
4. 任何异常都不能沿用上一条命令继续盲跑。
5. 即使在跟随过程中，辅车也要继续保留自己的基础稳定能力，不能因为外部输入存在就放弃安全约束。

本轮设计宁可保守停下，也不接受“猜着继续跟”。

## 影响范围

本轮设计预计会触及以下范围：

1. `src/assistant/` 下与串口输入、执行链和主循环有关的跟随主线。
2. `src/master/` 下与双摄输入、辅车跟随输出直接绑定的旧主线。
3. 与“主车双摄、辅车纯执行”冲突的方向文档和设计文档。
4. `SmartCar2026-Vision/main.py` 及其测试、协议文档、README。
5. 对应的主机侧回归测试与板端留证。

本轮不应扩大到以下范围：

1. 搬运阶段完整流程设计。
2. 新一轮完整主辅任务协议扩展。
3. 与当前跟随目标无关的底盘大重构。
4. 视觉仓库中的官方题面整理正文。

## 验收标准

本轮完成后，至少要同时满足以下标准：

1. 辅车能够依靠自己的相机识别主车标记并稳定跟随主车。
2. 辅车在标记丢失、输入超时或坏包场景下能够稳定停下。
3. 主车不再保留旧的双摄跟随主线，不再继续承担辅车高频跟随计算。
4. 视觉仓库输出已经与辅车执行侧协议语义对齐，不再停留在旧的像素观测口径。
5. 辅车现有控制解析与底盘运动计算行为保持不变。
6. 仓库口径不再把当前方向写成“主车双摄统一驱动辅车”。
7. 这次验收不再以搬运阶段是否完成为前提。

## 测试与验证口径

### 主机侧验证

主机侧至少要固定以下边界：

1. 辅车执行侧对最新命令消费的行为边界。
2. 超时停下、丢目标停下、坏包拒绝的行为边界。
3. 主车侧删减后不再继续组织旧双摄跟随输出的行为边界。
4. 视觉仓库输出字段虽然仍是 `x/y`, 但其语义已经切到辅车当前 `follow` 控制请求。
5. 辅车控制解析与底盘运动计算链不因本轮发生行为漂移。

### 板端验证

板端至少要留下以下证据：

1. 辅车能在真实硬件上跟随主车标记。
2. 丢失主车标记后，辅车不会继续盲跑。
3. 输入停止或异常后，辅车能够稳定停下。
4. 视觉仓库实机输出能被辅车执行侧直接消费，不需要再由主车中转解释。

### 当前不作为验收项的内容

以下内容这次明确不作为阻塞项：

1. 搬运阶段策略是否最终定稿。
2. 搬运物视觉状态是否仍被观测。
3. 更完整的主辅阶段协同协议是否已经定义。

## 风险与控制

### 风险一：主车删减不彻底，旧主线继续残留

控制方式：

1. 主车侧要按职责删减，而不是只停掉一个入口。
2. 只要逻辑仍然以“主车替辅车算跟随”为前提，就不算完成删减。

### 风险二：辅车新增跟随链后，又把视觉计算重新压回控制板

控制方式：

1. 明确坚持“相机侧算控制量、控制板侧做执行与安全收口”的边界。
2. 不在本轮回退成“辅车板自己重算视觉误差”。

### 风险三：本轮顺手改坏辅车当前控制核心

控制方式：

1. 辅车控制协议解析与底盘运动计算只做保护性回归，不做功能性重写。
2. 视觉仓库要直接贴合当前辅车已支持格式，而不是反过来逼辅车适配新格式。

### 风险四：当前目标再次被搬运阶段带偏

控制方式：

1. 所有实现与验收只围绕“辅车跟随主车”。
2. 搬运阶段相关讨论只保留为背景修正，不进入本轮完成定义。

### 风险五：视觉仓库旧文档和正式规则快照与当前路线冲突

控制方式：

1. 视觉仓库中的协议文档与 README 要明确同步到当前路线。
2. 官方题面整理只保留事实记录, 不在本轮擅自改写。
3. 当前实现按用户确认路线推进, 但要把这条冲突写成显式已知前提, 避免后续误读。

## 结论

这次重构不是简单地把一颗相机换位置，而是把当前系统中心从“主车统一双摄跟随”改成“辅车主动跟随主车，主车侧删减旧跟随职责”。

只要后续实现始终围绕这两个动作展开：

1. 辅车立起自己的主动跟随链。
2. 主车删掉旧的双摄跟随主线。
3. 视觉仓库把输出切到辅车可直接消费的位置式跟随语义。

那么当前设计就和用户确认的目标保持一致。
