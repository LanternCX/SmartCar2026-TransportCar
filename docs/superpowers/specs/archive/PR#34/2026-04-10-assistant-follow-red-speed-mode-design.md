# 2026-04-10 辅车跟随红色色块速度模式控制设计

> 状态: archive
> 说明: 软件侧实现已完成; Vision 主机侧回归通过, 当前口径已切到直接输出辅车速度模式入口。

## 背景

当前辅车主动跟随主线已经切到“辅车 OpenArt 直接输出 follow 请求, 辅车控制板沿用现有执行核心”的口径。

最近一轮软件侧已经把视觉目标收口为 `red` 色块, 并把纵向依据从画面上下位置切换为面积误差。但当前视觉输出仍走位置式 `follow` 入口, 也就是继续把 `x/y` 按位置量语义发给辅车执行侧。

用户最新判断是: 现有位置式跟随不够好调, 不再继续围绕位置式调参, 而是直接把当前 `x/y` 控制语义整体切到速度模式。

用户明确要求这次不要继续扩设计面, 只做最小收口:

1. 保留当前误差来源。
2. 保留当前分阶段节奏。
3. 保留当前只识别 `red` 的目标范围。
4. 只把输出从位置式入口切到辅车已经支持的速度式入口。

因此, 这次设计不是重做整套视觉跟随算法, 而是把当前已经形成的 `x/y` 控制链从“位置量输出”收口成“速度量输出”。

## 目标

本轮设计只追求以下结果:

1. 视觉侧继续只识别 `red` 色块。
2. 横向误差继续使用目标中心相对画面中心的偏差。
3. 纵向误差继续使用目标面积相对目标面积的误差。
4. 跟随主线继续采用分阶段节奏: 先横向对齐, 再纵向靠近。
5. 输出协议从当前位置式 `follow` 切到辅车现成支持的速度式 `follow_velocity` 入口。
6. 丢目标时, 视觉侧直接输出零速度停下语义。

## 非目标

本轮明确不做以下事情:

1. 不重写辅车执行核心。
2. 不重写横向和纵向误差来源。
3. 不把分阶段节奏改成同时双轴连续跟踪。
4. 不新增外部角度目标。
5. 不扩展到 `red` 之外的新目标。
6. 不改主车当前边界。

## 用户已确认的设计边界

用户已经明确确认以下边界:

1. 不再继续讨论别的方案, 直接按当前控制语义整体切速度模式。
2. `x` 继续表示横向误差驱动出来的控制量。
3. `y` 继续表示面积误差驱动出来的控制量。
4. 保留分阶段节奏, 不改成同时双轴控制。
5. 直接使用辅车已经支持的速度模式入口, 而不是只在现有位置式报文里偷偷改语义。

## 设计方案

### 总体思路

新的主线保持为:

1. 视觉端只看 `red` 色块。
2. 先判断横向是否对齐。
3. 横向未对齐时, 只输出横向速度。
4. 横向进入允许范围后, 再根据面积误差输出纵向速度。
5. 目标丢失或误差进入保持范围时, 直接输出零速度。

### 输出协议切换

当前视觉侧输出从位置式入口切到辅车已支持的速度式入口。

这意味着:

1. 不再输出当前位置式 `follow` 所需的 `s/v` 语义。
2. 改为输出辅车现成支持的 `f=1,m=1,x=<x>,y=<y>`。
3. 其中 `x/y` 的语义明确变为车体平面速度量, 而不是位置量。
4. 零速度报文就是当前最小停下语义。

这样做的价值是:

1. 直接复用辅车已有速度模式入口, 不需要再让视觉端假装输出位置量。
2. 保持协议语义一致, 避免“报文格式没变但内部含义偷偷换掉”的后续混乱。
3. 调参时更容易把视觉侧速度输出和辅车执行效果直接对应起来。

### 横向控制

横向控制继续沿用当前误差来源, 但输出改为横向速度量:

1. 输入仍是目标中心相对画面中心的横向偏差。
2. 横向阶段仍保留死区。
3. 横向未对齐时, 只输出 `x` 速度, `y=0`。
4. 横向速度由“带死区的 P 速度”生成, 并带速度上限。

### 纵向控制

纵向控制继续沿用当前面积误差来源, 但输出改为纵向速度量:

1. 输入仍是目标面积相对目标面积的误差。
2. 纵向阶段仍保留面积死区。
3. 横向进入允许范围后, 才允许输出 `y` 速度。
4. 纵向速度由“带死区的 P 速度”生成, 并带速度上限。

这保证当前“平放相机用面积反映前后距离”的思路继续成立, 只是把结果从位置量换成速度量。

### 保持与停下语义

当前阶段的保持与停下口径统一为零速度:

1. 目标丢失时, 直接输出零速度。
2. 横向和纵向都进入各自死区时, 直接输出零速度。
3. 不再依赖位置式入口中的 `valid=0` 表达停下。
4. 辅车本地方向保持继续存在, 本轮不新增外部角度目标。

### 参数口径

本轮参数只保留最小必需集合:

1. 横向死区。
2. 横向速度比例系数。
3. 横向速度上限。
4. 目标面积。
5. 面积死区。
6. 纵向速度比例系数。
7. 纵向速度上限。

这些参数都继续保留为可调项, 但本轮不扩展更复杂的分段逻辑。

## 数据流

调整后的链路如下:

`红色色块识别 -> 提取中心与面积 -> 横向阶段生成 x 速度 / 纵向阶段生成 y 速度 -> 输出 f=1,m=1,x=...,y=...`

其中:

1. `x/y` 都是速度量。
2. 当前任一时刻只激活一个阶段输出。
3. 辅车执行侧继续直接消费视觉侧已经生成好的速度请求。

## 异常处理

本轮继续沿用保守安全口径:

1. 目标丢失时立即输出零速度。
2. 不沿用上一拍速度继续盲跑。
3. 速度输出必须经过上限约束。
4. 串口超时、坏包或无效输入仍由辅车执行侧按现有规则停下。

## 测试与验证口径

本轮软件侧至少要验证以下内容:

1. 视觉端合法输出改为速度模式入口。
2. 无目标时输出零速度报文。
3. 横向阶段只输出 `x` 速度。
4. 纵向阶段只输出 `y` 速度。
5. 横向与纵向各自的死区都能把输出压成零。
6. 只保留 `red` 目标参与跟随。
7. 输出继续与辅车现有速度模式入口兼容。

当前阶段仍以软件侧验证和主机侧回归为准, 不把板端调参作为本轮完成前提。

## 实施范围

这次设计预计主要影响:

1. `SmartCar2026-Vision/main.py` 中 follow 报文格式与控制量生成。
2. `SmartCar2026-Vision/tests/unit/test_vision_protocol_rebuild.py`。
3. `SmartCar2026-Vision/tests/contract/test_main_vision_protocol_contract.py`。
4. `SmartCar2026-Vision/README.md` 与 `SmartCar2026-Vision/docs/Protocol.md`。

这次设计不应扩散到:

1. `TransportCar` 辅车执行核心重写。
2. 主车侧新功能。
3. 多颜色识别策略。
4. 同时双轴连续跟随策略。

## 推荐方案结论

在本轮范围下, 推荐采用以下最小方案:

1. 保留当前 `red + 横向偏差 + 面积误差 + 分阶段` 的整体框架。
2. 只把输出语义从位置式切到速度式。
3. 直接切到辅车现成支持的 `f=1,m=1,x=...,y=...` 速度入口。
4. 继续用带死区的 P 速度和双轴速度上限。
5. 目标丢失或保持阶段统一输出零速度。

这个方案最贴近用户的明确要求: 不继续讨论别的花样, 直接把现在的 `x/y` 控制语义整体改成速度模式即可。
