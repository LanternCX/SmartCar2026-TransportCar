# 主辅车最小闭环结构纠偏与硬件层补齐设计

## 背景

上一版设计文档 `docs/superpowers/specs/2026-03-30-master-assistant-hardware-design.md` 已经把当前阶段目标、控制链路和主辅职责写清楚，但本轮实现没有按该文档中自第 70 行开始定义的目录与模块结构落地，而是继续沿用了现有平铺式文件布局，在旧壳子上补齐了“辅车色标二维回中”功能切片。

这说明上一轮的问题不在于目标选错，而在于执行路径选错：功能行为虽然逐步收口到了当前阶段主线，但结构并没有落到预期的新框架上，导致“行为通过但架构不通过”。

因此，本设计不再讨论当前阶段功能目标本身，而是专门解决“如何在不牺牲低碎片与低内存目标的前提下，把当前阶段最小闭环迁移到正确的新框架里”。

## 与旧 spec 的关系

本设计不是推翻 `2026-03-30-master-assistant-hardware-design.md`，而是对它做执行层纠偏。

### 仍然沿用的部分

以下方向和约束继续完全沿用旧 spec：

1. 主车与辅车分别烧录、分别运行。
2. 当前阶段主线仍然是“辅车色标二维回中”。
3. 主车不主动运动，只负责感知、判断和下发二维平移控制量。
4. 辅车只执行二维平移随动，正常跟随不逐拍回包。
5. 状态机低频、控制高频，两者必须解耦。
6. 当前阶段不做灰度、不做角度控制、不做主车主动运动。
7. 硬件层必须补齐，不能只保留主机侧逻辑切片。

### 本设计新增或收紧的部分

本设计对旧 spec 追加三条更硬的执行约束：

1. **先搭框架，再填功能。**
   不允许继续在旧平铺结构上补丁式推进当前阶段功能。
2. **硬件层 review 优先。**
   后续评审必须先检查 `hw/` 层是否真正落地，再检查当前阶段功能是否跑通。
3. **明确取舍：板级相关代码优先为低碎片服务，硬件无关逻辑优先为本机可测服务。**
   当这两者冲突时，先保证板端低碎片和低占用，再在此基础上尽可能保留主机侧可测性。

同时，本设计相对旧 spec 有一处明确的结构调整：

1. 主车侧当前阶段的高层决策模块从根目录下的 `decision.py` 收口到 `vision/decision.py`，表示它属于当前阶段视觉主线的一部分，而不是通用板级入口逻辑。

## 目标

1. 把 `src/master` 与 `src/assistant` 重建到符合新框架的目录边界。
2. 在当前阶段即使主线只直接用到视觉与通信，也先把电机、编码器、IMU、UART 四类硬件层补齐。
3. 让硬件相关代码集中在板级层，避免硬件依赖继续渗透到协议、视觉和状态机逻辑里。
4. 保留当前阶段“辅车色标二维回中”这条最小闭环的主机侧可测性。
5. 为后续底盘完整接入和脚本迁移保留正确的扩展边界，而不是继续沿旧结构堆叠。

这里的“补齐硬件层”有明确含义：

1. 四类硬件层的真实目录边界必须存在。
2. 四类硬件层的板级薄封装必须真实存在，不能只放空占位文件。
3. 运行时装配入口必须存在，能明确说明这些硬件如何被当前框架接入。
4. 这**不等于**当前阶段主车和辅车运行态都必须无条件常驻初始化全部底盘硬件。
5. 若当前阶段主车不主动运动，则主车完整底盘运行时仍可延后装配，但其硬件边界和接入口不能缺失。
6. 当前阶段除当前闭环确实要用到的部分外，不得把其余底盘能力改成启动后默认常驻。

## 非目标

1. 本轮不补齐灰度链路。
2. 本轮不扩展主车主动运动。
3. 本轮不把角度控制并入当前主线。
4. 本轮不要求一次性完成所有底盘板端细节的功能联调，但硬件层骨架和接入口必须真实存在。

## 灰度边界约束

灰度链路仍然沿用旧 spec 的硬约束：

1. 本轮灰度只保留接入位，不展开实现。
2. 不允许因为“这轮不做”而把灰度后续接入口完全删除。
3. 也不允许提前加入未经确认的灰度硬件细节、接口映射或优先级逻辑。
4. 涉及灰度安装位置、路数、接口、引脚、优先级等事实，若仓库正文未确认，后续实现前必须再次向用户确认，禁止猜测。

## 核心取舍原则

### 原则一：板级相关代码优先为低碎片服务

以下内容优先追求更低的内存碎片化和更低的常驻占用：

1. 引脚与外设映射。
2. 电机、编码器、IMU、UART 的硬件句柄创建。
3. 运行时启动装配顺序。
4. 板端常驻对象数量。

因此本设计明确约束：

1. 不做运行时设备注册表。
2. 不做按字符串查找硬件对象。
3. 不做设备工厂或通用装配器。
4. 真实板级映射直接写在 `hw/` 与板级配置常量里。

### 原则二：硬件无关逻辑优先为本机可测服务

以下内容尽量保持不直接依赖真实硬件对象：

1. 视觉协议解析。
2. 双路选中目标逻辑。
3. 低频状态机。
4. 主辅协议构造与解析。
5. 二维控制目标生成。
6. 与当前阶段直接相关的高层控制语义。

因此本设计明确约束：

1. `vision/`、`protocol/`、与当前阶段直接相关的 `ctrl/` 纯逻辑模块不直接 import 板级硬件对象。
2. `app/` 与 `main.py` 只负责把 `hw/`、`ctrl/`、`vision/` 接起来，不把业务逻辑写回入口文件。

## 各层职责边界

### `hw/` 层

`hw/` 层必须是真正的板级层，而不是空目录或抽象占位。

#### `hw/motors.py`

负责：

1. 电机 PWM / 方向控制对象的真实创建。
2. 板级占空比输出接口。
3. 关闭电机与安全停机的最小能力。

不负责：

1. 速度环。
2. 协议解析。
3. 高层控制语义。

#### `hw/encoders.py`

负责：

1. 三路编码器真实创建。
2. 原始计数读取与清零。

不负责：

1. 速度滤波。
2. 里程计积分。

#### `hw/imu.py`

负责：

1. IMU 真实初始化。
2. 原始角速度 / 加速度读取。
3. 零漂偏置应用入口。

不负责：

1. 四元数积分。
2. 偏航角展开。

#### `hw/uart.py`

负责：

1. 主车 `UART6` / `UART8` / `UART3` 的真实创建。
2. 辅车 `UART3` 的真实创建。
3. 串口读写薄封装。

不负责：

1. 视觉协议解析。
2. 主辅协议解析。

### `vision/` 层（仅主车）

#### `vision/parser.py`

只负责把视觉文本报文解析成统一字段，不碰硬件对象。

#### `vision/ingress.py`

只负责：

1. 双路结果缓存。
2. 当前目标选路。
3. 新鲜度判断。
4. 误差语义统一。

不负责：

1. 状态跳转。
2. `dx/dy` 控制输出。

#### `vision/state_machine.py`

只负责低频阶段判断：

1. `MARKER_MISSING`
2. `TRACKING`
3. `CENTER_HOLD`

不负责：

1. 串口接收。
2. 高频控制输出。

#### `vision/decision.py`

只负责把当前选中目标与阶段结果转换成二维控制语义：

1. 输出 `dx`、`dy`
2. 死区归零
3. 丢失归零

不负责：

1. 串口实际发送
2. 板级硬件读写

### `ctrl/` 层

本轮即使不把底盘完整联调做完，也必须先落出正确骨架。

#### 当前阶段必须真实存在的模块

1. `filters.py`
2. `pid.py`
3. `kinematics.py`
4. `attitude.py`
5. `chassis.py`
6. `ident.py`
7. `storage.py`

#### 当前阶段可以先落骨架、后续再扩细节的模块

1. `chassis.py` 可以先形成 `CoreRuntime + ChassisRuntime` 的边界，而不是一次性把完整底盘行为都填满。
2. `ident.py` 与 `storage.py` 先把脚本入口和存储边界落好，再在后续阶段把脚本完整迁入。
3. 若当前阶段主车不主动运动，则主车 `ChassisRuntime` 可以在运行态延后装配，但主车 `ctrl/` 骨架不能缺失。

### `app.py` 与 `main.py`

#### `app.py`

负责装配：

1. 连接 `hw/` 与 `vision/` / `ctrl/`。
2. 提供当前阶段单步运行入口。

不负责：

1. 大量业务逻辑。
2. 设备具体实现。

#### `main.py`

负责：

1. 唯一入口。
2. 当前阶段启动分发。
3. 脚本模式切换。

不负责：

1. 协议细节。
2. 状态机细节。
3. 高频控制逻辑。

## 当前阶段功能如何映射到新框架

### 主车侧

当前阶段主线映射如下：

1. `hw/uart.py` 负责真实接收 `UART6` / `UART8`。
2. `vision/parser.py` 解析视觉报文。
3. `vision/ingress.py` 做双路缓存、目标选中和新鲜度判断。
4. `vision/state_machine.py` 做低频阶段判断。
5. `vision/decision.py` 生成 `dx/dy`。
6. `protocol.py` 构造发给辅车的最小文本协议。
7. `app.py` 把这几层接起来。

### 辅车侧

当前阶段主线映射如下：

1. `hw/uart.py` 负责真实接收 `UART3`。
2. `protocol.py` 解析主车文本命令。
3. `app.py` 负责对外回包语义。
4. `ctrl/chassis.py` 与 `hw/motors.py` 的接入口先建立正确边界。
5. 当前阶段实际执行仍只消费二维跟随语义，但必须通过新框架落地。

## review 门禁补充

这次新 spec 的 review 顺序必须固定为：

1. **先看结构是否按新框架落地。**
2. **再看硬件层是否真实补齐。**
3. **最后再看当前阶段最小闭环是否跑通。**

只有当以下问题都能回答“是”，review 才允许通过：

1. `hw/`、`ctrl/`、`vision/`、`script/` 边界是否已经真实存在，而不是继续沿用旧平铺结构。
2. 电机、编码器、IMU、UART 四类硬件层是否已经真实落目录并形成板级薄驱动。
3. 视觉、协议、状态机、决策是否仍保持硬件无关、可本机测试。
4. 当前阶段主线行为是否仍然满足“辅车色标二维回中”。
5. 视觉无效、超时或进入死区时，高频输出是否能及时归零，而不是等低频状态切换后再处理。
6. 两路视觉进入控制语义前，方向定义是否保持一致。
7. 当前阶段是否仍严格限定为辅车二维回中，没有把角度控制、主车主动运动或灰度链路顺手并入本轮交付。
8. 评审时是否继续沿用仓库已确认的统一方向口径，而不是在评审现场临时改义。

凡是会让当前阶段范围变大的内容，都应直接判为 review 不通过，而不是作为“顺手补充”接受。

## 分阶段实施建议

1. 先搭出新的整体目录框架。
2. 先把 `hw/` 层真实补齐到电机、编码器、IMU、UART。
3. 再把 `vision/`、`protocol/`、`ctrl/` 的当前阶段最小逻辑迁进去。
4. 再把 `app.py` 与 `main.py` 收口到新框架。
5. 最后再补主机侧验证与 HIL 留证。

## 结论

新的设计方向与旧 spec 在当前阶段目标上保持一致，但在执行原则上更严格：它把“先搭框架，再填功能”和“硬件层 review 优先”提升为硬约束，并明确了“板级代码优先为低碎片服务、硬件无关逻辑优先为可测服务”的取舍。这正是上一轮实现没有做到、也是这次必须先纠偏的部分。
