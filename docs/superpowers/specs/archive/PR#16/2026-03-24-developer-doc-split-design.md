# 背景

当前根目录 `README.md` 同时承担了项目介绍、开发说明、协议手册、控制实现解释、调试入口、参数说明和设计决策记录等多种职责。

这带来三个直接问题：

1. 根文档过厚，新进入仓库的人很难快速抓住项目的整体轮廓。
2. 面向开发者真正需要长期阅读的“上层设计信息”与协议字段、参数表、命令示例、部署步骤等实现细节混在一起，阅读负担过高。
3. 仓库里已经有 `docs/developer/strategy.md` 与 `docs/developer/tasks.md` 等文档，但 README 里的很多内容还没有按“给开发者理解系统设计”这个目标重新归位。

用户本次明确提出的目标不是简单删短 README，而是重建一套更适合开发者阅读的文档结构：

- `README.md` 只做项目初步介绍与阅读导航。
- `docs/developer/` 要成为开发者主文档集，其中本次主线是总体方案、电控设计、视觉设计三类文档。
- 一个完全不了解项目的开发者，读完 `README.md`、`docs/developer/strategy.md`、`docs/developer/control.md` 与 `docs/developer/vision.md` 后，应能理解项目整体架构、总体方案、电控设计、视觉设计，以及关键设计取舍。
- 原 README 中的设计决策性 Q&A 必须保留，因为这些内容是用户手写的重要判断，不可直接删除；但它们可以迁移为 `docs/developer/` 中的正式章节，不要求继续留在根 README。

# 用户确认的设计结论

本次讨论中，用户已经确认以下边界：

1. `docs/developer/strategy.md` 继续保留，并维持“更上层的总体方案设计”定位。
2. 文档拆分从三个角度切入：总体方案、电控设计、视觉设计。
3. 所谓“电控设计”不是板级接线文档，而是控制算法层面的上层设计，包含滤波、电机控制、姿态解算、陀螺仪等高实时系统设计。
4. 根目录 `README.md` 目标形态选择“只保留项目简介、文档导航、仓库定位说明”。
5. 原 README 里的 Q&A 不能丢失，可以专门开一章存放，并可迁移为 `docs/developer/` 中的正式章节。
6. 这些文档首先是写给开发者看的，不是给 Agent 做索引用的。
7. 本次调整只做拆分、去重和归位，不做内容层面的系统重写；能保留原文的地方尽量保留原文。

# 设计目标

1. 让 `README.md` 明显变薄，回到“项目初步介绍 + 文档入口 + 仓库定位说明”的职责。
2. 让 `docs/developer/` 成为面向开发者的稳定主入口，而不是零散补充材料。
3. 保留并强化开发者真正需要的上层设计信息，而不是把所有长内容一并删除。
4. 将总体方案、电控设计、视觉设计三类内容分层拆开，减少重复表述。
5. 保留设计决策 Q&A，使关键取舍和经验判断继续可读、可追溯。
6. 以最小改动完成本次文档调整，避免为了“写得更顺”而重写原有正文。

# 设计原则

## 原则 1：README 负责入口，不负责承载全部知识

- `README.md` 只回答“这是什么项目”“仓库处于什么定位”“项目由哪几块组成”“开发者接下来应该看哪里”。
- 协议、参数、命令、部署、逐文件说明等厚内容不再继续留在根文档主体里。

## 原则 2：开发者文档优先解释设计，而不是堆操作说明

- `docs/developer/` 的核心任务是帮助开发者理解系统如何组织、为什么这样设计、各部分如何协作。
- 文档应优先保留方向、边界、职责、链路和设计取舍，而不是把大段参数表或命令示例继续搬过去。

## 原则 3：从整体到专题，按理解顺序组织内容

- 核心阅读路径固定为：`README.md` -> `docs/developer/strategy.md` -> 电控专题 -> 视觉专题。
- 开发者先理解项目整体方案，再进入电控和视觉两个专题视角。

## 原则 4：删除重复实现细节，保留上层设计信息

- 如果某些协议、实现、技术细节已经有其他事实源或并不适合放在开发者主文档中，应从本次目标文档里删去。
- 但“为什么这样做”“这一层承担什么责任”“关键设计选择是什么”必须保留。

## 原则 5：Q&A 作为正式设计内容保留

- 用户手写 Q&A 不是附录杂项，而是对设计决策的直接说明。
- Q&A 应进入开发者主文档中的正式章节，而不是随着 README 瘦身被删除。

## 原则 6：只做拆分与去重，不做重写

- 本次主要动作是拆分、归位、删重复，不是重新写一套新文档。
- 迁移后的正文应尽量保留原有判断、原有表述和原有信息结构。
- 只有在以下情况才允许小幅编辑：补充标题、调整段落顺序、增加必要的过渡句、删去明显重复内容、删去不再适合放在主文档里的细节。
- 不得为了语言统一、风格统一或表达优化，对现有设计说明做大段改写。

# 方案对比

## 方案 A（选中）：README 瘦身 + strategy 保持上层 + 新增电控与视觉专题

- 优点：边界清楚，最符合“总体方案 / 电控 / 视觉”三分结构。
- 优点：`strategy.md` 不会再次被技术细节压厚。
- 优点：后续开发者可以按专题理解项目，而不是反复在 README 中检索。
- 缺点：需要重新整理现有 README 内容归属。

## 方案 B：README 瘦身，但把电控和视觉继续塞进 `strategy.md`

- 优点：文件更少。
- 缺点：`strategy.md` 会再次混合总体方向与专题设计，违背用户确认的分层边界。

## 方案 C：README 保留较多摘要，再分别链接到专题文档

- 优点：第一次进入仓库时信息密度更高。
- 缺点：根文档容易重新膨胀，不符合本次“README 做薄”的目标。

# 选中方案

采用方案 A：重建“入口 README + 三类开发者文档”的结构。

## 目标文档结构

- `README.md`
- `docs/developer/strategy.md`
- `docs/developer/control.md`
- `docs/developer/vision.md`
- `docs/developer/tasks.md`

其中：

- `README.md` 是入口文档。
- `strategy.md` 是总体方案文档。
- `control.md` 是电控设计文档。
- `vision.md` 是视觉设计文档。
- `tasks.md` 继续承担任务路线，但不属于本次“三个设计视角”的主结构。

# 各文档职责与保留内容

## `README.md`

`README.md` 只保留：

- 项目是什么。
- 仓库定位说明。
- 项目当前由哪几个主要设计视角组成。
- 开发者应该先读哪些文档。
- 仓库的阅读入口和文档导航。

`README.md` 不再保留：

- Agent 使用说明与 Skill 索引。
- 面向 AI 的 review 指引和私有流程入口。
- 协议字段表。
- 查询接口表。
- 参数表。
- 快速开始步骤。
- 文件上传清单。
- 逐目录、逐文件解释。
- 大段控制算法展开。
- 大段视觉协议与调试细节。

## `docs/developer/strategy.md`

继续保留并强化以下内容：

- 总目标。
- 主辅协同方案。
- 当前硬件条件对整体方案的影响。
- 搬运策略。
- 核心原则。
- 阶段分层与成功判据。

`strategy.md` 不再承接：

- 具体控制算法链路展开。
- 视觉输入处理细节。
- 协议格式说明。
- 参数辨识实现细节。

## `docs/developer/control.md`

新增文档，用于承接电控设计视角，重点保留：

- 控制系统总体目标与边界。
- 控制分层关系，例如位置、速度、姿态等层次如何协作。
- 滤波思路、电机控制思路、姿态解算思路、陀螺仪在系统中的作用。
- 速度模式、位置模式、角度保持等机制背后的设计意图。
- 运动锁定存在的原因与它解决的问题。
- 软件结构中与电控理解直接相关的层级关系。

该文档不写成：

- 参数手册。
- 命令接口手册。
- 代码逐文件索引。
- 板级接线文档。
- 引脚、电平、接线、装配说明。

该文档应单独包含一个正式章节：

- `设计决策 Q&A`

该章节用于保留原 README 中用户手写的设计问答，尽量保持原有判断与表达，不做不必要的技术改写。

## `docs/developer/vision.md`

新增文档，用于承接视觉设计视角，重点保留：

- 视觉在整套方案中的职责。
- 双摄分工与轮询设计思路。
- 视觉如何为主车状态机提供信息。
- 视觉与主车控制决策、电控执行层之间的边界。
- 视觉在连续搬运与避障中的作用定位。

该文档不再展开：

- 协议字段明细。
- 串口命令格式。
- 兼容规则细表。
- 逐状态实现细节。

# 现有 README 内容迁移策略

## 保留并压缩在 `README.md` 的内容

- 项目概述。
- 很短的项目背景。
- 面向开发者的文档导航。
- 与项目入口直接相关的少量定位性说明。

## 迁移到 `docs/developer/strategy.md` 的内容

- 主辅车角色分工。
- 总体搬运路径。
- 成功标准与阶段目标。

## 迁移到 `docs/developer/control.md` 的内容

- 控制流程中的上层设计说明。
- 控制模式的设计意图。
- 前馈、反馈、滤波、姿态估计等控制侧思路。
- 参数辨识和陀螺仪校准在整套电控设计中的定位。
- 设计决策 Q&A。

## 迁移到 `docs/developer/vision.md` 的内容

- 视觉状态机迁移背后的职责边界。
- 视觉输入在项目整体方案中的定位。
- 双摄相关的上层设计说明。

## 从本次目标文档中删除的内容

- 遥控协议完整正文。
- 查询接口与返回格式表。
- 使用示例。
- 快速开始说明。
- 文件上传清单。
- 过细的目录展开与模块罗列。
- 与其他事实源重复的实现和技术细节。

## 迁移时的编辑限制

- 优先按原文段落拆分到对应文档，而不是先重写再迁移。
- 对保留内容仅做最小必要调整，例如标题整理、去掉重复句、补一两句衔接说明。
- 若某段原文已经能准确表达设计意图，应直接保留，不因文风原因重写。
- 若某段内容需要压缩，只压缩入口性说明，不改动核心判断和设计结论。

## 被移出内容的处理原则

- 如果某类内容已经在仓库其他事实源中稳定存在，例如规则页、协议页或参考页，本次从 README 和开发者主文档中删去时，不再重复迁抄，只保留必要导航。
- 如果某类内容既不属于开发者主文档的上层设计正文，也没有必要继续作为当前项目主入口维护，则本次直接删除，不额外新建承接页。
- 如果某类内容对开发者后续仍有查阅价值，但不适合继续放在 README 或专题正文中，应以独立参考资料形式存在，并由 README 或相关专题文档做一句话导航，而不是重新塞回主文档正文。

# 信息组织建议

为了让新开发者能顺着文档自然建立项目认知，建议文档阅读与组织统一为：

1. `README.md` 提供项目初识与文档入口。
2. `docs/developer/strategy.md` 建立总体方向与系统级目标理解。
3. `docs/developer/control.md` 解释高实时控制系统如何设计。
4. `docs/developer/vision.md` 解释视觉系统如何接入整体任务闭环。
5. `docs/developer/tasks.md` 作为补充文档，负责描述阶段化任务推进，而不是重复设计正文，也不纳入本次核心阅读路径。

# 错误处理与边界

- 如果某段内容主要作用是帮助理解设计边界，应保留在开发者文档中。
- 如果某段内容主要作用是描述接口字段、参数值、操作步骤或部署流程，应优先从 README 和开发者主文档正文中删除。
- 如果某段内容兼有“设计取舍”和“实现细节”，应保留设计取舍，把可独立存在的实现细节删去或压缩为一句话。
- 如果 Q&A 中夹带少量实现细节，也应优先保留原始设计判断，不因局部技术细节而整体删除该问答。
- 如果某段原文已经满足本次目标，应直接迁移，不额外重写。

# 验收方式

完成本次文档拆分后，应能验证：

1. 根目录 `README.md` 明显变薄，只承担项目介绍、仓库定位说明和阅读导航职责。
2. `docs/developer/strategy.md` 继续保持总体方案定位，不重新膨胀为技术细节总汇。
3. 仓库中新增 `docs/developer/control.md` 与 `docs/developer/vision.md` 两份专题文档。
4. 电控文档中明确包含独立的“设计决策 Q&A”章节，并保留当前 README 的核心问答判断。
5. 一个第一次接触项目的开发者，读完 `README.md`、`docs/developer/strategy.md`、`docs/developer/control.md` 与 `docs/developer/vision.md` 后，能够理解项目整体架构、总体方案、电控设计、视觉设计和关键设计取舍。
6. 原 README 中与协议、实现、技术细节重复且不适合继续作为开发者主文档正文的内容，已经被删除或下沉，不再堆在根文档中。
7. 被保留的设计正文以原文拆分迁移为主，没有发生内容层面的系统重写。

# 实施顺序

1. 精简并拆分 `README.md`，保留项目简介、仓库定位和开发者文档入口。
2. 审视并微调 `docs/developer/strategy.md`，确保其只保留总体方案层内容，且优先保留原文。
3. 新建 `docs/developer/control.md`，整理控制系统上层设计并加入“设计决策 Q&A”。
4. 新建 `docs/developer/vision.md`，整理视觉系统上层设计与职责边界。
5. 回头清理 README 中已迁移或应删除的厚内容，避免新旧两份正文长期重复。
