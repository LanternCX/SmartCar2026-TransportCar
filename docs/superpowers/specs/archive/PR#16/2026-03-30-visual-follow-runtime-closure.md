# 主车静止视觉控辅车随动运行收口设计

## 背景

上一轮结构纠偏已经把 `src/master` 与 `src/assistant` 的新框架边界搭出来，也把当前阶段“主车不动、只根据视觉控制辅车二维随动”这条主线迁进了新目录。但 review 结果已经明确表明，这一轮交付仍然停留在“结构骨架 + 主机侧行为迁移”的中间状态，还没有达到“可直接烧录、可独立运行、整条链路真正打通”的程度。

当前存在的核心问题不是目标错误，而是收口不完整：

1. `src/master` 与 `src/assistant` 仍不能直接作为 RT1021 根目录烧录后独立运行。
2. 主车视觉输入、主车控制输出、辅车命令接收、辅车底盘执行，还没有形成真实闭合链路。
3. 当前主线真正需要的 Legacy 参数，还没有完整归位到新框架中的明确位置。
4. 当前没有证据证明这套新框架已经达到与 Legacy 同等级的可运行性，也没有证据证明它在当前主线上的常驻占用更优。

因此，这份设计不再继续讨论“要不要保持主车不动、视觉控辅车随动”这个目标，而是专门解决：

**如何把这条唯一主线真正收口成一套可烧录、可运行、可验证、参数归位清晰，并且在当前主线上比 Legacy 更克制的运行框架。**

## 目标不变

本设计只服务当前唯一目标：

1. 主车自身不主动运动。
2. 主车持续接收双路视觉中的辅车色标信息。
3. 主车根据统一语义下的二维误差，持续向辅车发送随动控制。
4. 辅车根据主车指令执行二维随动。
5. 色标进入死区后辅车保持不动。
6. 色标丢失后辅车立即停住。

## 本轮要解决的问题

### 一、运行收口不完整

当前新框架虽然已经具备 `hw/`、`ctrl/`、`vision/`、`script/` 目录边界，但还不是“可直接烧录运行”的形态。

本轮必须补齐：

1. 主车根目录烧录后，入口导入路径必须真实可用。
2. 辅车根目录烧录后，入口导入路径必须真实可用。
3. `main.py`、`app.py`、运行循环、串口读写与步进关系必须形成真实板端入口，而不是仅供主机测试调用。
4. 任何依赖包名前缀的写法，都必须改造成“以当前烧录根目录为准即可运行”的导入形式。

### 二、整条主线链路没有真正闭合

当前主线逻辑在主机测试中是通的，但板端真实链路还没有完整闭合。

本轮必须补齐：

1. 主车 `UART6` / `UART8` 的持续读取入口。
2. 主车视觉解析与双路选路后的高频控制输出入口。
3. 主车 `UART3` 向辅车持续发送控制文本的真实发送入口。
4. 辅车 `UART3` 的持续收包入口。
5. 辅车收到 `follow` 控制后的真实底盘执行入口。
6. 辅车最小状态回传与超时停机路径。

只有当“视觉输入 -> 主车决策 -> 主车发送 -> 辅车接收 -> 辅车执行 -> 状态回传”这条链路完整闭合，本轮才允许视为运行收口完成。

### 三、参数归位不完整

当前新框架下，真正已经归位的参数只有最小主线中的少数字段；而 Legacy 中与当前主线直接相关的控制与滤波参数，还散落在旧配置与旧运行时里。

本轮必须完成的，不是“把 Legacy 所有参数一次性迁完”，而是：

1. 把**当前主线真实需要的参数**完整迁入新框架。
2. 这些参数必须放在一个用户能直接 review 的明确位置。
3. 运行时装配必须直接读取这份新位置，而不是继续偷偷依赖旧路径。

本轮必须迁入的新参数范围仅限于下列明确项，不允许再按实现路径临时扩项：

1. 主车视觉超时参数。
2. 主车二维中心死区像素参数。
3. 主车横向控制比例参数。
4. 主车纵向控制比例参数。
5. 主线运行循环控制周期。
6. 辅车输出限幅参数。
7. 辅车跟随超时参数。
8. 三轮速度环参数表。
9. 速度输入中值滤波窗口参数。
10. 差值限幅参数。
11. 陀螺仪低通参数。

### 当前主线参数迁移清单

为避免“完整迁移”再次变成主观判断，本轮评审一律按下列清单逐项核对。凡未列入本清单的 Legacy 参数，默认不属于本轮强制迁移范围。

#### A. 必须迁移到新位置并被真实读取的具体项

1. `FOLLOW_TIMEOUT_MS`
2. `FOLLOW_CONTROL_KP_X`
3. `FOLLOW_CONTROL_KP_Y`
4. `FOLLOW_CENTER_DEADZONE_PX`
5. `CONTROL_TICK_MS`
6. `FOLLOW_OUTPUT_LIMIT`
7. `PID_MAP["m"]`
8. `PID_MAP["l"]`
9. `PID_MAP["r"]`
10. `SPEED_FILTER_WINDOW`
11. `SPEED_DIFF_MAX_DELTA`
12. `GYRO_LPF_ALPHA`

#### B. 明确不纳入本轮“必须迁完”清单，但必须标注状态的项

1. 偏航位置环参数
2. 偏航积分限幅
3. 自动回正角速度限幅

这些参数不由实现方式反向决定范围。本轮统一要求：

1. 在新参数总入口中明确列出对应项名。
2. 显式标注为“当前主线未启用”或“本轮不接入”。
3. 不把它们算进本轮“参数完整迁移已完成”的通过条件。

#### C. 本轮明确不纳入强制迁移的参数

1. 灰度链路相关参数
2. 主车主动运动相关参数
3. 搬运主线相关参数
4. 当前主线未经过的 Legacy 模式参数

这里的“完整迁移”含义是：

1. 参数值有新归宿。
2. 新运行时真实读取它们。
3. 用户 review 时不需要再翻 Legacy 文件确认当前主线参数到底在哪里。

## 非目标

本轮仍然不做以下事情：

1. 不恢复主车主动运动。
2. 不恢复灰度主线。
3. 不把当前主线无关的 Legacy 能力一起打包迁完。
4. 不把当前主线外的整套底盘模式作为本轮验收条件。
5. 不以“框架更完整”为理由，扩大到与当前目标无关的功能面。

## 核心收口原则

### 原则一：先让主线真实跑通，再谈剩余能力迁移

本轮唯一验收主线仍然是“主车静止、视觉控辅车随动”。

因此：

1. 只为这条主线真实需要的运行链和参数负责。
2. 其余 Legacy 能力若当前主线没有经过，不纳入本轮强制迁移范围。
3. 任何会让当前任务范围再次膨胀的内容，都必须视为偏题。

### 原则二：运行真实闭合优先于结构表面完整

上一轮问题是“结构有了，但运行没有真正闭合”。

因此本轮必须反过来收口：

1. 目录边界继续保留。
2. 但每一个当前主线必经边界，都必须有真实运行入口。
3. 不允许再出现“模块已存在，但运行时并未真正使用”的假收口。

### 原则三：内存优化必须以当前主线的真实常驻为对象

本轮仍然坚持板端低碎片与低占用优先，但必须把约束落到当前主线上，而不是停留在原则表述。

因此：

1. 只有当前主线必经对象允许常驻。
2. 当前主线不经过的 Legacy 能力，不得因“未来可能要用”而无条件构造。
3. 必须通过主线启动后的实际常驻情况来判断是否比 Legacy 更克制，而不是凭结构印象判断。

## 目标框架

### 主车侧

主车最终必须形成以下真实运行关系：

1. `main.py` 作为唯一启动入口。
2. `app.py` 负责装配 UART、视觉层与当前主线控制输出。
3. `hw/uart.py` 负责真实串口句柄和收发。
4. `vision/parser.py`、`vision/ingress.py`、`vision/state_machine.py`、`vision/decision.py` 负责当前主线视觉判断与控制语义。
5. `protocol.py` 负责发给辅车的最小文本控制协议。
6. 主车运行循环必须真实从 `UART6` / `UART8` 读入视觉输入，再经 `UART3` 发出控制结果。

### 辅车侧

辅车最终必须形成以下真实运行关系：

1. `main.py` 作为唯一启动入口。
2. `app.py` 负责装配串口接收、协议解析、执行运行时和状态回包。
3. `hw/uart.py` 负责 `UART3` 真实收发。
4. `ctrl/chassis.py` 负责当前主线执行运行时。
5. `hw/motors.py`、`hw/encoders.py`、`hw/imu.py` 必须被真实接入当前执行链，而不是只在结构上存在。
6. 辅车运行循环必须真实接收主车控制、执行随动、处理超时停机并回传最小状态。

## 参数收口要求

### 一、参数必须有统一落点

本轮必须新增或明确一个“当前主线参数总入口”，用于承接从 Legacy 迁来的当前主线相关参数。

这个入口必须满足：

1. 主辅两侧当前主线参数可以直接 review。
2. 能清楚区分“当前主线已启用”与“后续阶段保留”。
3. 运行时直接读取，不再依赖 Legacy 配置文件。

### 二、参数必须与运行链一致

参数迁移不是复制文本，而是要保证：

1. 当前主线真实使用到的控制器和滤波器，都有对应参数输入。
2. 当前主线没经过的参数，不得伪装成“已经迁移完成”。
3. 若某个 Legacy 参数当前主线不使用，必须明确标注为“暂不迁移”而不是悄悄缺失。

### 三、需要至少覆盖的当前主线参数

本轮至少要把以下内容归位到新位置：

1. `FOLLOW_CONTROL_KP_X`
2. `FOLLOW_CONTROL_KP_Y`
3. `FOLLOW_TIMEOUT_MS`
4. `FOLLOW_CENTER_DEADZONE_PX`
5. `CONTROL_TICK_MS`
6. `FOLLOW_OUTPUT_LIMIT`
7. `PID_MAP["m"]`
8. `PID_MAP["l"]`
9. `PID_MAP["r"]`
10. `SPEED_FILTER_WINDOW`
11. `SPEED_DIFF_MAX_DELTA`
12. `GYRO_LPF_ALPHA`
13. 偏航参数只要求在新位置显式列出状态，不算本轮必须接入项。

## 验证与留证要求

### 一、主机侧验证

主机侧必须继续保持：

1. 当前主线单元测试通过。
2. 主辅协议契约测试通过。
3. 参数归位后的新位置有明确测试覆盖。

### 二、板端 smoke

本轮必须把板端 smoke 从“部署计划可生成”推进到“真实设备可跑通最小链路”。

至少要有：

1. 主车烧录与启动成功证据。
2. 辅车烧录与启动成功证据。
3. 串口收发实际工作证据。
4. 当前主线最小链路实际现象记录。

### 三、HIL 留证

本轮 HIL 留证必须能明确回答：

1. 主车是否真的不动。
2. 辅车是否真的随动。
3. 死区后是否保持。
4. 丢失后是否停住。
5. 状态回传是否可见。

### 四、内存留证

本轮若要宣称“比 Legacy 更优”，至少必须留出当前主线对应的最小证据：

1. 新框架当前主线启动后的常驻对象边界说明。
2. 当前主线导入后、核心初始化后、功能装配后、主线运行空闲时的内存记录。
3. 与 Legacy 在**同一任务目标、同一主车静止前提、同一只控辅车随动前提**下的对比记录。
4. 最小诊断面在当前主线运行态下仍可存活的留证。

本轮固定比较口径如下：

1. Legacy 基线：主车不动、只保留视觉接收与辅车控制链，不引入与当前主线无关的额外任务对象。
2. 新框架基线：主车不动、只保留当前主线常驻对象。
3. 两边都至少记录 `mem_free_after_import`、`mem_free_after_core_init`、`mem_free_after_feature_init`、`mem_free_runtime_idle` 四个时间点。
4. 两边都要记录 `diag_survival`，用于证明最小诊断面是否仍可工作。

若没有这些证据，本轮只允许说“结构更接近目标”，不允许说“已经比 Legacy 更省内存”。

## review 门禁

这次 review 必须按以下顺序执行：

1. **先看主辅车能不能直接作为独立根目录烧录运行。**
2. **再看整条主线链路是否真正闭合。**
3. **再看当前主线参数是否完整归位。**
4. **最后再看内存留证是否支持“更优”结论。**

只有以下问题都能回答“是”，本轮才允许通过：

1. `src/master` 和 `src/assistant` 是否已经可直接独立烧录运行。
2. 主车视觉输入到辅车执行的整条主线是否已经真实打通。
3. 当前主线相关参数是否都已经迁入新位置并被真实读取。
4. review 时是否不再需要翻 Legacy 文件确认当前主线参数位置。
5. 当前主线范围是否仍严格限定在“主车不动、视觉控辅车随动”。
6. 若声称比 Legacy 更优，是否已经按固定比较口径提供对应内存证据。

只要其中任何一项为“否”，本轮都不允许用“结构已完成”或“框架已可用”来通过评审。

## 分阶段实施建议

1. 先修正主辅车导入路径与板端入口，使其可直接独立烧录运行。
2. 再打通主车真实视觉输入循环与主车发给辅车的真实输出循环。
3. 再打通辅车真实接收、执行、停机和状态回传循环。
4. 再迁移当前主线真正需要的 Legacy 参数到新位置。
5. 最后补板端 smoke、HIL 与内存留证。

## 结论

这份设计不再追求“继续扩结构”，而是要求把当前唯一主线真正收口成一套可独立烧录、真实可跑、参数归位清晰、验证留证完整的运行框架。它明确限定本轮只为“主车静止、视觉控辅车随动”负责，不再把与该主线无关的 Legacy 能力一并打包迁移；同时，它也把“能不能直接烧录运行”“整链路是否闭合”“参数是否完整归位”“是否有内存证据”提升为新的硬门禁。这些正是当前提交之后下一轮必须补齐的核心缺口。
