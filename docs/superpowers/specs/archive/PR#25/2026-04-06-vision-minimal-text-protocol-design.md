# 视觉最小文本协议收缩设计

## 背景

当前视觉链路使用带完整字段名和框坐标的文本报文, 单行内容较长。联调过程中已经观察到上位机抓包内容出现字段截断、行间粘连和中途断裂, 但视觉识别本身又表现为连续稳定。

这说明当前问题至少包含两个待区分变量:

1. 视觉报文本身过长, 导致接收、显示或解析链路压力偏大。
2. 上位机抓包或链路本身可能存在按字节块显示、读写不及时或缓冲异常。

为了先排掉“视觉报文过长”这个变量, 本轮设计不重做整条通信体系, 只把视觉输入收缩到当前闭环真正需要的最小文本协议。

## 目标

本轮设计只追求以下目标:

1. 把视觉输入报文缩到单目标随动闭环所需的最小字段集合。
2. 保持视觉链路继续按文本逐行传输, 便于现场抓包和人工核对。
3. 让主车后续目标选择、阶段判断和对辅车输出逻辑尽量不变。
4. 让主车仓库与视觉仓库使用完全一致的视觉协议语义, 不再长期并存新旧两套口径。
5. 用最小改动验证“报文缩短后, 主车视觉输入是否更稳定”。

## 非目标

本轮明确不做以下事情:

1. 不改 `UART3` 主车到辅车协议。
2. 不把视觉协议改成纯字节或可变长度二进制格式。
3. 不展开多目标协议。
4. 不继续传输框坐标、类别和相机职责语义。
5. 不顺手重做状态机、控制律或串口读取主链。

## 适用范围

本轮改动只覆盖主车视觉输入链路:

1. `../Smartcar2026-Vision` 仓库中的视觉发送端输出格式与协议说明。
2. `UART6` 与 `UART8` 两路视觉发送端输出格式都切到同一套最小文本协议。
3. 主车视觉协议解析入口。
4. 主车视觉输入整理层对最小字段的适配。

本轮不允许只改一路视觉而让另一路继续保留旧文本格式, 以避免双路协议口径分叉。

本轮也不允许只改主车仓库而不改视觉仓库, 或者只改视觉仓库而不改主车仓库, 以避免一边实现新协议、一边仍维护旧协议语义。

其余模块继续沿用当前结构, 但凡直接依赖旧视觉字段的路径都必须在本轮一起清理掉, 不能靠内部补默认字段继续维持旧语义。

## 跨仓库统一原则

这次改动同时涉及两个仓库:

1. 当前主车仓库负责接收、解析和消费视觉协议。
2. `../Smartcar2026-Vision` 仓库负责生成和发送视觉协议。

两边必须共享同一套正式口径, 至少包括:

1. 报文格式一致。
2. 字段名一致。
3. `x/y` 的量纲与正负方向一致。
4. 有效帧和无效帧的发送条件一致。
5. 相关协议文档同步更新, 不允许一边文档写新格式, 另一边还保留旧正式说明。

在两个仓库完成正式协议正文同步前, 本设计文档就是这轮跨仓库协议收缩的唯一审查依据。落地后, 两边协议正文必须更新到与本设计一致, 再恢复各自仓库内文档作为日常入口。

## 最小协议设计

### 报文格式

视觉侧每帧只发送一行最小文本, 仍使用换行作为帧边界。

有效帧格式:

```text
v=1,s=1283,x=7,y=50
```

无效帧格式:

```text
v=0,s=1284
```

### 字段定义

1. `v`: 当前帧是否存在有效目标, `1` 表示有效, `0` 表示无效。
2. `s`: 当前视觉帧序号, 用于观察是否连续递增。
3. `x`: 横向误差, 仅在 `v=1` 时出现。
4. `y`: 纵向误差, 仅在 `v=1` 时出现。

当前阶段这里的 `x/y` 继续沿用现有主线里的视觉误差语义:

1. 数值类型仍为当前文本协议可直接表示的有符号数值。
2. `x` 表示目标中心相对画面中心的横向像素差值。
3. `y` 表示目标底边相对当前期望抓取位置的纵向像素差值, 且 `y=0` 表示目标已到达当前设定抓取距离。
4. 本轮继续沿用视觉仓库当前默认目标位置为 `60` 的口径, 不在本轮改这个目标位置定义。
5. 正负方向继续沿用当前已跑通口径: `x` 为目标在画面中心右侧时取正、左侧时取负; `y` 为目标底边超过期望抓取位置时取正、未达到期望抓取位置时取负。
6. 本轮目标是“缩短报文”, 不是“重定义误差语义”, 因此视觉端与主车端必须按以上同一套像素误差语义工作, 不额外引入归一化或控制量直传新口径。

### 设计约束

1. 字段名统一固定为 `v/s/x/y`, 不保留旧字段别名。
2. 无效帧不发送 `x/y`, 避免把无意义的 `0,0` 混入有效语义。
3. 仍按一行一帧处理, 不引入长度前缀或二进制头。
4. 当前阶段默认单目标, 不再通过协议传输目标类别。

## 主车内部适配方式

### 入口改动原则

主车只替换视觉解析入口, 尽量不改后续决策主链。

也就是说:

1. 新协议先在解析层转成主车内部统一观测结构。
2. 后续输入整理、阶段判断和控制输出尽量复用当前逻辑。
3. 当前实现中凡直接依赖视觉报文 `target`、`camera_id`、框坐标的路径, 都必须在本轮显式收口或删除, 不能通过在内部补固定字段来维持表面兼容。

### 内部统一结果

解析后的最小观测仍需向下游提供以下核心语义:

1. 视觉序号。
2. 当前帧是否有效。
3. 横向误差。
4. 纵向误差。
5. 来源串口, 继续用于双路输入仲裁。

这里明确要求: 下游若仍要求旧字段, 视为主链尚未收口完成, 必须回到使用点做删除或重写, 不能在解析层或整理层补一个“固定单目标”去兜底。

### 双路输入边界

当前仓库主线是 `UART6` / `UART8` 双路持续接收并在主车内统一仲裁, 因此本轮虽然把单行内容缩到最小, 但双路输入边界不能变化:

1. 两路视觉都使用完全一致的最小文本格式。
2. 主车继续通过串口来源区分两路输入, 不依赖报文内 `camera_id` 区分来源。
3. 当前阶段若主线只关心单目标随动, 则两路都只上传各自当前帧的单目标最小结果。
4. 原先依赖 `camera_id`、`category`、框坐标的观测语义在本轮一起退出当前正式主线, 不保留过渡口径。

### 视觉仓库责任边界

`../Smartcar2026-Vision` 仓库在本轮需要同步满足以下约束:

1. 发送格式切到本设计定义的最小文本协议。
2. 原先面向正式主线发送的 `camera_id`、`target`、`bbox_*` 不再继续进入正式输出。
3. 视觉仓库内的协议说明、测试和示例报文必须同步切换到新口径。
4. 若视觉仓库仍需要 richer 调试信息, 必须走独立调试输出方案, 不回塞到当前正式主线协议。

## 异常处理

本轮异常处理保持最小化, 不增加额外兜底策略。

1. 一行文本缺字段或字段无法解析时, 按无效输入处理。
2. `v=0` 时, 直接按当前拍无目标处理。
3. `v=1` 但缺少 `x/y` 时, 按无效输入处理。
4. 不猜测缺失字段, 不自动补默认值去冒充有效观测。

## 验证口径

本轮验证重点不是证明所有串口问题都已解决, 而是先确认“包变小后是否显著更稳定”。

至少需要完成以下验证:

1. `UART6` 与 `UART8` 两路都分别完成最小协议抓包检查, 连续观察不少于 200 帧, 报文逐行完整, 不出现字段中途断裂。
2. 主车接收后, 对每一路都能持续解析到递增的 `s`, 且连续观察窗口内不应出现由格式错误导致的连续 3 拍及以上无效帧。
3. 在视觉原始输出稳定有效的前提下, 主车连续观察 200 拍时, 因解析失败导致的无效拍次数应为 0; 若出现, 必须记录具体样本并转入链路排查。
4. 主车发给辅车的输出中, 对应同一段稳定视觉输入时, “突然清零后又恢复”的跳变次数必须少于当前版本留档样本, 并保留前后对比记录。
5. 视觉仓库的协议文档、示例报文与主车仓库中的协议文档、解析测试必须一致, 不允许出现一边仍引用旧长报文的情况。

若以上改动完成后问题仍旧存在, 说明根因不主要在视觉报文长度, 后续应转向继续排查串口抓包方式、链路丢字节或运行节拍。

## 风险与控制

### 风险一: 现场可读信息减少

收缩后报文不再直接包含类别和框坐标, 人工观察信息会变少。

控制方式:

1. 本轮先接受最小信息集, 以稳定联调为优先。
2. 后续若需要 richer 联调信息, 另行设计调试侧输出, 不回塞进当前最小正式协议。

### 风险二: 下游仍隐式依赖旧字段

若主车某些路径仍直接依赖旧 `target` 或框坐标字段, 协议缩减后会暴露隐性耦合。

控制方式:

1. 只允许在解析入口做最小字段归一, 不允许补旧字段默认值。
2. 发现旧字段依赖时, 必须在使用点直接删掉或改写。

### 风险三: 包缩短后问题依然存在

如果根因其实是链路或抓包端丢字节, 缩短报文只能降低概率, 不能彻底根治。

控制方式:

1. 本轮验收只回答“包缩短后是否改善”。
2. 若无明显改善, 后续排障直接转向链路与接收方式, 不继续扩大协议改造面。

### 风险四: 与长期多检测方向文档并存

仓库长期方向仍保留“协议可扩到多检测结果”的规划, 而本设计只服务于当前阶段的最小联调闭环。

控制方式:

1. 本设计只覆盖当前阶段正式视觉输入协议, 不是对长期方向的永久替换。
2. 后续若重新推进多检测结果协议, 必须另开新设计文档, 不在本轮最小协议上直接叠加。
3. 本轮实现落地后, 相关正式协议正文也必须同步更新, 避免仓库里长期并存新旧两套正式口径。

### 风险五: 跨仓库切换不同步

如果主车仓库和视觉仓库没有在同一轮内同步切换, 现场很容易出现一边已经按新协议工作、另一边仍在发旧报文的错位状态。

控制方式:

1. 本轮实施与验证必须把两个仓库视为同一个交付单元。
2. 任一仓库未完成切换, 都不能宣称本轮协议改造完成。

## 后续计划入口

待本设计经用户确认后, 下一阶段计划只围绕以下最小实施项展开:

1. 更新视觉发送端最小文本格式。
2. 更新视觉仓库中的协议说明、示例和测试。
3. 替换主车视觉解析入口。
4. 清理主车内部对旧视觉字段的直接依赖。
5. 基于“两边都切到新协议后的组合版本”做联调与验收, 不接受单边先完成后再补另一边的收口方式。
6. 补两边仓库的最小回归测试与联调验证记录。
