# 主车视觉输入低碎片止血重构设计

## 背景

当前主车在未接入视觉输入时可以进入主循环, 但一旦接入视觉后, 板端会在主循环早期直接报出内存分配失败。最新现场 traceback 已经把首个失败点收敛到 `src/master/hw/uart.py` 的按行读取路径, 也就是主车尚未完成视觉状态机推进和后续控制处理之前, 最前面的串口文本接入链就已经先撑不住了。

这说明当前问题不应再被笼统描述为“视觉算法太重”或“状态机太复杂”, 而应先明确收口为:

1. 视觉输入进入主车后的文本缓冲、按行切分、字段解析与中间整理过程中存在持续的小块分配与重复包装。
2. 当视觉输入频率上来后, 这些分配会在板端形成更高的碎片化风险, 并把首个失败点提前推到输入链最前面。
3. 当前最需要处理的不是整条主车控制链, 而是“主车如何把视觉文本安全接进来”这件事。

用户本轮要求也已经明确收口为“先对主车规划一个重构方案”, 且希望按最小止血范围处理。因此本设计不追求一次性解决主车所有内存问题, 而是优先把视觉接入最前段改成更克制、更可验证的低分配路径。

## 当前问题归纳

结合当前主车代码与最新报错位置, 当前风险主要集中在以下四个层面。

### 一、串口按行读取路径对连续文本缓冲过于依赖

当前 `src/master/hw/uart.py` 会把本轮读到的字节先解码成字符串, 再拼到内部文本缓冲里, 随后通过按换行符切分的方式取出一整行。这个路径的问题不在于逻辑是否能工作, 而在于它会持续制造新的字符串对象, 并且要求在某个时刻还能申请出一块足够大的连续内存来完成字符串拼接或切分。

当视觉输入持续到来且每行内容较长时, 这种写法会让板端最容易先在“还没来得及做业务判断之前”的文本处理中失败。

### 二、视觉解析链把同一份输入反复包装为多个临时对象

当前主车视觉解析路径会依次经历:

1. 原始串口文本。
2. `observations` 列表中的字典包装。
3. `VisionIngress.prepare_observation()` 内的新字典。
4. 解析后 observation 的缓存副本。
5. 当前目标的再次标记与再次复制。
6. 应用层对本拍 selected observation 的再次合并。

这条链的问题不是单次对象特别大, 而是同一拍里围绕同一条输入做了太多次复制、改写和重新组装。对于板端环境, 这种高频小分配比一次性大对象更容易把堆打碎。

### 三、坏输入与半行输入没有在最前面尽快止损

当前输入链仍偏向“先把文本完整收进系统, 再逐层判断能不能用”。这会导致以下情况:

1. 半行输入也要先留在文本缓冲里继续等待。
2. 非法行要先完成解码和切分, 才能在更后面被识别为无效。
3. 多路输入共存时, 无效输入也会占用和有效输入相同的整理成本。

这会放大输入链前段的内存压力, 并增加坏输入拖垮主循环的概率。

### 四、当前主线缺少针对这条新输入链的最小内存证据

仓库规则已经把 `mem_free_after_import`、`mem_free_after_core_init`、`mem_free_after_feature_init`、`mem_free_runtime_idle` 和最小诊断面存活列为内存评审硬指标, 但当前 `master` 主线并没有与这次视觉接入止血方案直接对应的最小打点证据。

这意味着即使改完写法, 若没有最小留证, 也只能说“看起来更省”, 不能证明“板端接入视觉后确实更稳”。

## 目标

本轮设计必须同时达成以下目标:

1. 把主车视觉接入最前段改成更低分配的输入路径, 让板端不再优先死在按行读取位置。
2. 在不改动主车控制语义、视觉状态机语义和主辅通信语义的前提下, 明显减少视觉输入链上的重复包装和临时对象数量。
3. 让坏输入、半行输入和无效输入尽量在最前面被消化或丢弃, 不再带着额外负担继续下沉。
4. 为这次止血重构补齐最小板端内存留证, 证明问题已经从首个失败点后移或消失。
5. 把改动面锁死在主车视觉接入链, 不顺手扩大到主车控制层、辅车或其他任务主线。

## 非目标

本轮明确不做以下事情:

1. 不重写视觉状态机。
2. 不修改主车跟随控制语义与底盘控制链。
3. 不调整辅车协议或辅车实现。
4. 不顺手重构整个 `master` 主线的数据模型。
5. 不为了“结构更漂亮”额外引入新的常驻抽象层或兼容层。
6. 不把这轮任务扩大为整仓库级内存治理工程。

## 方案比较

### 方案一：只替换串口按行读取实现

只修改 `src/master/hw/uart.py`, 让它不再依赖当前的整段文本拼接再切分路径。

优点:

1. 改动最小。
2. 直接命中当前 traceback 首个失败点。

缺点:

1. 后续视觉解析和应用层仍保留大量重复包装。
2. 即使首个失败点后移, 仍可能在后续整理链中继续因为碎片过多而出问题。

结论: 只适合作为临时补丁, 不足以形成本轮正式止血方案。

### 方案二：收口主车视觉输入最前段整条链路

同时处理以下四层:

1. UART 读行。
2. 视觉文本解析。
3. 视觉输入整理。
4. 主车单拍输入拼装。

优点:

1. 仍然保持在“最小止血”范围内。
2. 可以把当前首个失败点和其后最主要的重复包装一起收掉。
3. 不需要碰控制语义和状态机职责, 风险可控。

缺点:

1. 比只改 UART 略大。
2. 需要补一组针对主线输入链的验证和内存留证。

结论: 这是本轮推荐方案。

### 方案三：沿主车整条视觉主线一起重构

除了输入链, 再继续下沉到决策输出、底座快照和跨层状态复制, 试图一次性解决长期碎片问题。

优点:

1. 长期潜在收益更高。

缺点:

1. 改动面显著扩大。
2. 很容易把当前“先止血”的任务拖成一次结构性重写。
3. 会让验证和归因成本明显上升, 不符合当前主线节奏。

结论: 这轮不采用。

## 核心设计

### 一、把串口读行路径改成低分配的逐步吐出模型

本轮第一优先级是把主车 `UartPort.read_line()` 从“不断扩展文本缓冲并整体切行”的路径, 改成更克制的逐步读取、逐步吐出模型。

同时, 本轮把“止损阈值”和“串口适用范围”一起明确写死:

1. 止损阈值按解码后的单行字符数计量。
2. 当前正式协议正文里的全字段视觉示例最长为 `132` 个字符, 因此本轮对 `UART6` / `UART8` 两条视觉口统一使用 `160` 字符上限, 作为当前主线的明确执行口径。
3. 该上限只服务于当前视觉输入主线; 若未来视觉协议字段扩展导致合法报文超过该上限, 必须以新任务重新评审和调整, 不在本轮默默放宽。
4. `UART3` 仍然承担主车到辅车遥控通信, 本轮不把视觉口的超长行止损策略直接施加到 `UART3` 上, 以避免把最小止血任务扩大到非目标链路。

设计要求如下:

1. 不再把新到数据无条件并入一个持续膨胀的文本字符串。
2. 尽量减少对“大块连续字符串”申请的依赖。
3. 遇到未形成完整行的数据时, 仅保留最小必要残留, 不保留多份等价副本。
4. 对超长单行输入设置明确止损策略, 防止异常输入把整个主循环拖进低内存状态。
5. 一旦判定当前半行或当前整行为异常并触发止损, 重新对齐必须以下一个完整换行边界为准, 不能把异常行尾巴与后续正常输入重新拼接成一条伪正常消息。

这里的关键不是追求“零分配”, 而是把当前最容易触发大块申请的位置改成更可控的增量式路径。

### 二、视觉解析入口改成单次消费、单次产出的整理口径

主车视觉解析层的目标不再是“方便各层都拿到一份自己的字典”, 而是“同一条输入在进入主线后尽快收口成唯一一份可用结果”。

设计要求如下:

1. 原始视觉文本只做一次字段拆解。
2. 合法性判断尽量前置, 非法输入不继续进入后续拼装。
3. 当前拍只保留一份主语义结果, 不再为同一条输入生成多份等价中间副本。
4. 若当前输入只够回答“无效”或“缺失”, 则直接产出最小无效结果, 不再补做多余包装。

### 三、视觉整理层只保留当前拍真正需要的一份结果

`VisionIngress` 当前同时承担输入准备、当前目标缓存和新鲜度标记, 但内部复制次数偏多。本轮不改变它的职责, 只改变它的对象使用方式。

设计要求如下:

1. 同一拍的目标整理结果只保留一份当前结果。
2. 缓存仍然允许存在, 但不再为返回值、当前目标和按串口缓存各自复制一遍完整结构。
3. 新鲜度、来源串口、有效性这些标记继续保留, 但应尽量在同一份结果上完成。
4. 两路 UART 的选择逻辑保持不变, 但整理成本下降。

### 四、应用层改单拍最小骨架输入, 不再重复堆中间壳

`MasterRuntimeLoop.step()` 和 `MasterApp.step()` 目前会围绕当前拍构造多个中间字典和列表。本轮不改变这两个入口的职责, 但要减少它们对视觉输入做的重复包装。

设计要求如下:

1. 当前拍输入只保留运行循环真正需要的最小字段集合。
2. 视觉观测列表不再被额外复制或改写多次。
3. 应用层与 ingress 之间的接口尽量稳定, 避免为了方便而继续制造新中间层。
4. 底座快照、状态机输出与视觉结果的合并顺序保持不变, 只减少不必要的中间结果。

## 涉及范围

1. `src/master/hw/uart.py`
   - 重写主车串口逐行读取路径。

   - 明确区分视觉口与 `UART3` 的止损口径: `UART6` / `UART8` 使用本轮视觉上限, `UART3` 保持当前遥控链路的通用逐行语义。

   - 保持当前主车单拍驱动职责不变。

   - 新增针对半行、坏行、超长行和双路输入整理的失败测试与回归保护。

6. `tests/hil/`
   - 必须新增或更新这轮最小止血方案的板端留证记录。
   - 留证中至少包含操作步骤、设备环境、关键观测点、实测结果和结论边界, 不能以口头说明或未来补文档代替。

2. `src/master/vision/decision.py`
3. `src/master/motion_runtime.py`
4. `src/assistant/` 全部主线
5. 主辅通信协议语义

## 输入链流程设计

重构后的主车视觉输入流程应满足以下顺序:

1. UART 每轮按当前可用数据做增量读取。
2. 若尚未形成完整一行, 仅保留最小残留并等待下一轮。
3. 对 `UART6` / `UART8`, 若当前半行或当前整行已经超过 `160` 字符上限, 则整条异常输入都必须被视为不可继续拼接的废弃段, 直到下一个完整换行边界才允许重新接收新的候选消息。
4. 对 `UART3`, 本轮只保留更省分配的逐行读取路径, 不引入视觉口这套超长行止损语义。
5. 一旦形成完整视觉行, 立即交给视觉解析入口做单次合法性判断。
6. 非法行或超出约束的视觉输入在最前面直接丢弃, 只有那些已经成功通过行边界整理、但业务字段判定为“当前拍无效”的输入, 才允许降级为最小无效结果。
7. 合法行只生成一份当前拍可消费结果, 交给 ingress 更新当前目标缓存。
8. 应用层只拿当前拍最小骨架输入推进状态机与后续流程。

这个流程的重点不是改变主车“看到视觉后做什么”, 而是改变主车“如何把视觉安全接进来”。

## 错误处理与边界

### 一、半行与残留边界

1. 未形成完整行的数据允许跨拍保留, 但保留量必须可控。
2. 同一段残留不得在内部以多种等价形式重复保存。
3. 对 `UART6` / `UART8`, 若残留超过 `160` 字符上限, 必须明确丢弃当前异常半行, 并进入“等待下一次完整换行边界后重新对齐”的恢复路径, 不能让异常输入长期占坑。
4. 重新对齐完成前, 不允许把异常半行尾部与之后到达的字节重新拼成一条候选正常消息。

### 二、非法输入边界

1. 非法视觉行尽量在解析入口就结束处理。
2. 非法输入不应继续触发后续多层包装。
3. 非法输入不能破坏当前可用缓存的稳定性。
4. 非法输入被丢弃后, 后续正常输入必须仍能恢复接入, 不能进入持续卡死、持续错位或长期挂住旧缓存的状态。
5. 单路坏输入不能拖垮另一路仍然正常的输入消费。
6. 只有在已经成功按行边界收口之后, 才允许把“字段合法但当前拍不可用”的输入降级为最小无效结果; 纯粹的坏行和越界半行不进入这条降级路径。

### 三、范围边界

1. 这轮只追求输入链止血, 不改变主车视觉阶段语义。
2. 若后续仍存在运行期内存压力, 应作为下一轮独立任务处理, 不在本轮顺手扩范围。
3. 不允许为了这轮止血新增常驻大对象、全局共享缓存或新的 owner 层。

## 验收标准

本轮完成后, 至少要满足以下可观察标准:

1. 在接入视觉输入后, 主车不再优先死在 `hw/uart.py` 的按行读取位置。
2. `UART6` / `UART8` 统一按 `160` 字符上限执行止损, `UART3` 不受这条视觉阈值影响。
3. 超长半行或坏行触发止损后, 系统会以下一个完整换行边界重新对齐, 不会把异常尾巴与下一条正常消息拼接成假恢复。
4. 双路视觉输入仍保持当前主线语义, 不因止血方案改变目标选择结论。
5. 当前主车状态机与控制链对外行为保持现有口径, 不因为输入链重构发生语义回归。
6. 坏输入被丢弃后, 后续正常输入仍能恢复接入, 不会因为旧残留或单路异常导致整条输入链持续失效。
7. 板端在接入视觉并持续运行一段时间后, 主循环仍能继续推进, 且视觉输入仍能被正常消费。
8. `tests/hil/` 中必须存在本轮设备留证, 能说明视觉接入后首个失败点已经消失或明显后移, 同时明确当前结论边界。

## 测试与验证策略

### 一、主机侧验证

主机侧至少应覆盖以下内容:

1. UART 逐行读取在正常输入、半行输入、连续多行输入下的行为。
2. `UART6` / `UART8` 在 `160` 字符阈值下对超长行与坏行的止损行为。
3. 视觉解析对合法输入、非法输入和缺字段输入的处理。
4. `VisionIngress` 在双路输入下的当前目标选择语义未变。
5. `UART3` 现有逐行遥控读取语义未被视觉止损规则误伤。
6. `MasterRuntimeLoop.step()` 与 `MasterApp.step()` 在现有主线测试下仍能输出同口径结果。

### 二、板端验证

板端必须在 `tests/hil/` 中补以下最小留证:

1. 接入视觉前的可用空闲内存基线。
2. 进入主循环后的空闲内存。
3. 首次收到视觉输入后的空闲内存变化。
4. 持续接收一段视觉输入后的空闲内存与最小运行状态。
5. 当前阶段最小诊断面是否仍可存活。
6. 坏输入或半行输入出现后, 下一批正常输入是否还能恢复接入。

这里不要求本轮把整套内存治理一次做完, 但至少要证明这次止血已经真正改变了当前首个失败点。

## 后续边界

若本轮止血完成后, 板端仍然在主车视觉运行期出现内存压力, 后续工作应按以下顺序继续, 但不属于本设计范围:

1. 再评估 `VisionIngress` 与应用层结果骨架是否还存在可进一步压缩的重复缓存。
2. 再评估主车决策输出与底座快照之间的重复包装。
3. 最后才考虑是否需要把主车更后面的视觉与决策链做更深一级的低碎片重构。

也就是说, 本轮先止住“视觉一接进来就炸”的问题, 后续再决定是否继续向后收口。
