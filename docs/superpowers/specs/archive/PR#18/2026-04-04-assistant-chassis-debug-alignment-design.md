# 辅车底盘链路按主车 debug 基线对齐设计

## 背景

最近几轮主车底盘联调已经形成一条明确的 debug 收口链:

1. 更早一轮先确认板端不能假设完整 CPython 环境, `types`、`typing`、`os.path`、包上下文等依赖都可能成为上板首个 blocker。
2. 随后又确认 `seekfree_demo v3.0.0` 下 IMU 与编码器采样不能只靠“每拍去读”, 而要先建立 `ticker.capture_list(...)` 触发链并尽量在初始化期绑定数据读取边界。
3. 再往后主车底盘控制链继续收口到更一致的姿态更新口径、动态时间基准、航向保持语义与硬件映射。

当前用户要求不是只修辅车某一个显眼报错, 而是:

1. 按主车最近几次 debug 的标准, 把相同的 debug 在 `assistant` 再做一遍。
2. 让主辅两车底盘链路真正对齐到同一套可验证基线。
3. 允许直接移植主车已经验证通过的底盘基础代码, 只要能保证辅车当前职责不被无关改写。

重新核查当前辅车代码后, 已经可以确认至少存在以下不一致:

1. 辅车主运行链仍残留板端不稳依赖, 例如 `types.MethodType` 与 `typing`。
2. 辅车入口当前仍未建立与主车一致的采样触发链。
3. 辅车姿态与航向保持链仍停留在主车最近几轮收口之前的旧语义。
4. 辅车左右轮电机与编码器映射当前与主车不一致, 而用户已明确确认辅车现场接线应与主车一致。

这说明当前主辅两车虽然都在新主线目录下运行, 但**底盘基础链路并不是真正同一条语义链**。如果继续只在主车上收口、辅车停留在更旧的状态, 后续任何“双车底盘行为应一致”的判断都会失真。

## 目标

本轮设计必须同时达成以下目标:

1. 让辅车当前正常上板会经过的整条主运行链, 与主车已验证通过的底盘 debug 基线一致。
2. 清掉辅车主运行链里板端不存在或不稳的依赖, 不再让导入阶段成为隐藏 blocker。
3. 让辅车 IMU / 编码器采样、姿态更新、航向保持与硬件映射都对齐到主车当前标准。
4. 在不改动主辅通信协议语义和辅车业务职责的前提下, 让两车底盘基础行为尽可能同构。
5. 为后续板端联调提供一套可以复核的“主辅已按同一底盘基线运行”的验证口径。

## 非目标

本轮明确不做以下事情:

1. 不改主车实现。
2. 不改主辅通信协议文本格式与当前业务分工。
3. 不扩展灰度、视觉、状态机或运输任务主线等无关范围。
4. 不为了兼容旧写法再补新的兜底层、假对象或导入回退。
5. 不把辅车整轮改造扩大成新的架构重写; 仅收口到“主车已验证过的底盘基础链”。

## 当前问题归纳

### 一、板端兼容边界仍未按主车标准收口

主车更早的 debug 已经明确过一条规则: 板端运行要优先相信平铺上传、最小标准库、最小导入假设, 不能继续依赖 CPython 习惯。

当前辅车主运行链仍残留:

1. `types.MethodType`。
2. `typing` 中的 `Callable`、`Optional`、`Tuple`。

这些依赖在主机侧可能看不出问题, 但在板端会重新打开“导入阶段失败”的老问题。用户要求是把主车已经踩过的坑在辅车也补齐, 因此这里不能继续保留“看起来没坏”的侥幸路径。

### 二、采样触发链与主车不一致

主车近期联调已经确认 `seekfree_demo v3.0.0` 下 IMU / 编码器采样需要显式建立 `ticker.capture_list(...)` 触发链, 且设备引用应尽量在初始化阶段绑定。

当前辅车入口仍只是构造硬件装配后直接进入主循环, 尚未像主车那样在正常运行分支显式建立采样触发链。这会造成两车底盘链虽然都叫“5ms 主循环”, 但底层采样事实并不一致。

### 三、姿态与航向保持链仍停留在旧版本

主车最近几轮 debug 已经把以下行为收回当前主线:

1. 姿态积分按真实时间推进, 不再死守固定节拍估算。
2. 陀螺仪量级先统一到已验证诊断脚本口径。
3. 航向保持的积分按真实时间累计。
4. 主动转动时允许让出保持控制, 转完后重新接管当前朝向。
5. 保持阶段加入当前旋转趋势抑制。

当前辅车仍保留的是更早一版语义:

1. 姿态更新仍直接使用固定 `tick_s`。
2. 保持积分没有按真实时间缩放。
3. 主动转动仍与保持修正叠加。
4. 没有和主车一致的保持接管门槛与阻尼项。

这意味着即使两车接线一样、参数名字一样, 底盘行为也不会真正一致。

### 四、硬件映射与用户确认事实冲突

当前辅车代码中的左右轮电机与编码器映射和主车不一致。用户已明确确认辅车现场接线应与主车一致, 因此当前辅车映射不应继续保留为另一套“辅车专属事实”。

对这类底盘基础链路而言, 已验证脚本和已确认接线事实属于最高优先级依据。若主车已收口到一套映射, 辅车也确认应一致, 那么当前差异就应视为待清理的历史残留。

## 核心设计

### 一、对齐范围只覆盖辅车当前正常运行主链

本轮只处理 `assistant` 当前正常上板会走到的整条主运行链, 包括:

1. `main.py` 正常启动分支。
2. `app.py` 中的硬件装配与运行循环。
3. `motion_runtime.py` 中的底盘基础链。
4. `ctrl/attitude.py` 中的姿态与航向保持能力。
5. `hw/encoders.py` 与 `hw/motors.py` 中的映射事实。
6. `state/` 中被当前主链直接依赖的运行时状态定义。

这一定义的目的，是把任务面锁在“辅车当前真实会跑到的路径”里, 不再顺手扩到旧服务、旧视觉或无关模块。

### 二、允许直接移植主车已验证代码, 但只限底盘基础链

用户已明确允许直接移植主车代码。本轮不再追求“辅车必须自己重新长出一套近似实现”, 而是优先采用以下原则:

1. 若主车某段底盘基础代码已经被最近几轮 debug 与测试验证过, 且职责与辅车当前基础链一致, 则优先直接移植到辅车对应边界。
2. 移植时只保留与辅车当前职责兼容的部分, 不把主车的视觉、调度或业务语义一并带入辅车。
3. 优先减少“同一逻辑写出两种近似版本”的情况, 因为这种分叉最容易让后续双车行为再次漂移。

也就是说, 本轮设计不是“让辅车模仿主车”, 而是**让主辅在底盘基础链上尽量共享同一套已验证行为语义**。

### 三、先收口板端兼容, 再统一采样与姿态语义

本轮改动顺序固定如下:

1. 先清掉辅车主运行链中会在板端失效的依赖和写法。
2. 再把采样触发链与姿态更新时间基准对齐到主车。
3. 然后把航向保持语义切到主车当前版本。
4. 最后收口左右轮映射到与主车一致。

这样排序的原因是:

1. 若板端导入都不稳, 后续任何“行为一致”都没有讨论基础。
2. 若采样与时间基准没统一, 映射问题和控制问题会互相污染归因。
3. 若先改映射、后改采样与姿态, 很容易再次陷入“方向不对到底是映射错还是积分链错”的混乱。

### 四、辅车当前业务职责保持不变, 只替换其依赖的底盘基础链

本轮明确保持以下边界不变:

1. 辅车仍然负责接收控制、执行跟随、维持朝向、超时停机和最小状态回传。
2. 辅车不新增主车才有的视觉和决策职责。
3. 辅车当前跟随 / 停机 / 回包行为不做新的业务重写。

但这些业务行为下方依赖的底盘基础链, 会替换成与主车一致的版本。这样既能保住当前业务边界, 也能把真正影响底盘手感与一致性的部分统一起来。

## 文件落点

### 一、主要修改文件

1. `src/assistant/main.py`
   - 对齐主车的正常运行入口语义。
   - 补齐采样触发链与必要的运行观察点。

2. `src/assistant/app.py`
   - 保持当前辅车应用职责不变。
   - 只调整为对齐新的底盘基础链与唯一硬件 owner 语义。

3. `src/assistant/motion_runtime.py`
   - 去掉板端不稳依赖。
   - 对齐主车当前的状态绑定、姿态更新、控制节拍和航向接管语义。

4. `src/assistant/ctrl/attitude.py`
   - 直接对齐主车当前已验证的姿态更新与航向保持实现。
   - 补齐动态时间基准、积分缩放和旋转趋势抑制。

5. `src/assistant/hw/motors.py`
   - 收口左右轮电机映射到与主车一致。

6. `src/assistant/hw/encoders.py`
   - 收口左右轮编码器映射到与主车一致。

7. `src/assistant/state/__init__.py`
   - 去掉板端不稳类型依赖。
   - 补齐与主车当前控制链一致所需的跨周期状态字段。

8. `tests/unit/assistant/` 下与辅车运行时、姿态与底盘行为直接相关的测试
   - 只补本轮对齐行为的失败测试与回归保护。

9. `tests/hil/`
   - 补一份辅车按主车 debug 基线收口后的设备侧留证文档。

### 二、明确不修改的区域

1. `src/master/`。
2. 主辅通信协议格式。
3. 与本轮底盘基础链无关的视觉与状态机实现。
4. 已不在辅车正常运行主链中的旧服务路径。

## 控制流程设计

对齐后的辅车底盘基础链应满足以下流程:

1. 上电进入辅车正常运行分支。
2. 初始化硬件装配后, 先建立与主车同口径的 IMU / 编码器采样触发链。
3. 每个控制周期先刷新基础观测, 包括 IMU、编码器、航向与里程。
4. 姿态更新按真实时间推进, 不把打印、阻塞或周期波动误当作固定 5ms。
5. 跟随或速度命令需要转动时, 先按主车当前规则判断是否应暂时让出航向保持。
6. 当主动转动降回保持门槛以内时, 重新接管当前朝向并恢复保持。
7. 将最终平移量与旋转修正量一并送入轮速分解与三轮速度闭环。
8. 若命令无效、丢失、超时或要求停机, 仍由辅车现有业务语义负责停机与状态回传。

这个流程的重点不是改变辅车“做什么”, 而是让辅车“底下怎么做”对齐到主车已经验证过的标准。

## 错误处理与边界

### 一、板端兼容边界

1. 不再为 `types`、`typing`、`os.path` 或包环境差异保留兜底分支。
2. 直接把主运行链收口成板端可运行写法。
3. 若某段主机侧便利写法会破坏板端导入稳定性, 以板端真实运行优先。

### 二、行为一致性边界

1. 本轮追求的是底盘基础行为一致, 不是把主辅全部代码文本完全复制。
2. 若主车代码中的某段逻辑携带了主车特有业务语义, 只允许提取其中与底盘基础链直接相关的部分。
3. 若辅车现有业务职责与主车基础链在个别点上天然不同, 应保留职责差异, 但不能破坏底盘基础行为一致性。

### 三、映射边界

1. 电机与编码器映射一律按用户已确认事实处理, 不再保留“辅车代码现状优先”的旧口径。
2. 一旦映射收口完成, 不再通过翻符号试错替代明确映射事实。

## 验收标准

本轮完成后, 至少要同时满足以下标准:

1. 辅车当前主运行链中不再残留板端不存在或不稳的依赖。
2. 辅车正常启动后能进入真实运行链, 不会在导入或初始化阶段因旧依赖失败。
3. 辅车采样触发链与主车当前标准一致。
4. 辅车姿态更新时间基准、航向保持积分与主动转动接管语义与主车一致。
5. 辅车底盘控制链的关键环节使用同一拍真实时间基准, 不允许只把动态时间修到姿态链前半段。
6. 辅车左右轮电机与编码器映射与主车一致。
7. 辅车板端已存在并已加载有效零漂校准结果。
8. 辅车板端已存在并已加载有效电机辨识参数。
9. 辅车现有跟随、超时停机与最小状态回传职责不被无关改写。

## 测试与验证策略

### 一、主机侧验证

本轮主机侧至少应补齐并通过以下验证:

1. 辅车运行时不再依赖板端不存在模块。
2. 辅车姿态更新按真实时间推进。
3. 辅车航向保持积分按真实时间累计, 并包含与主车一致的旋转趋势抑制。
4. 辅车主动转动与自动保持的切换语义与主车一致。
5. 辅车底盘控制链后半段也使用同一拍真实时间基准, 至少要能证明轮速控制等关键环节拿到的时间基准已与姿态链保持同拍。
6. 辅车硬件映射与主车一致。
7. 辅车主运行入口仍能持续推进, 不破坏现有命令、停机与回包边界。

所有行为改动都应先有失败测试, 再实现, 最后跑通过目标测试集。

### 二、设备侧验证与留证

本轮涉及真实设备路径, 不能只靠主机侧测试收口。设备侧至少要留下以下证据:

1. 本轮设备侧只保留 `stage3` 人工联调留证, 不再使用 `stage2`。
2. `stage3` 留证必须明确记录辅车可正常上板进入运行分支, 不因旧依赖在导入或初始化阶段失败。
3. `stage3` 留证必须明确记录辅车当前底盘基础链已经按与主车相同的标准装配运行。
4. `stage3` 必须明确检查并记录辅车板端已具备有效零漂校准结果, 且运行时确实加载了对应结果。
5. `stage3` 必须明确检查并记录辅车板端已具备有效电机辨识参数, 且运行时确实加载了对应结果。
6. `stage3` 必须留下“同一拍真实时间基准已贯穿到底盘控制链关键环节”的证据, 至少能区分“只修姿态链”与“关键控制环节已统一”。
7. 若允许最小动作观察, 至少要能复核“左右轮方向事实一致”“航向保持基础行为未退化”。
8. 留证文档中必须写清步骤、预期、实测和结论, 不接受只写一句“看起来一样”。

## 为什么本轮允许直接移植主车代码

本轮用户已经明确允许直接移植主车代码, 这是合理的, 原因如下:

1. 目标不是探索新功能, 而是复用主车最近几轮已经验证过的 debug 结果。
2. 若继续让主车和辅车各自维护一份近似但不完全一致的底盘基础链, 很快又会重新分叉。
3. 对双车协同系统而言, 底盘基础链越一致, 后续联调和问题归因越可靠。

因此本轮最优策略不是“辅车也重新想一遍”, 而是**在辅车当前职责不变的前提下, 最大化复用主车已验证过的底盘基础实现**。

## 结论

本轮辅车应采用“按主车 debug 基线整条对齐主运行链”的方案。

该方案同时满足四件事:

1. 把更早的板端依赖修正和最近的姿态 / 映射 / 节拍收口合并成一套辅车基线。
2. 让主辅两车底盘基础链重新回到同一事实和同一行为语义。
3. 不扩大到无关业务范围。
4. 为后续真正讨论“双车底盘行为是否一致”提供可信前提。
