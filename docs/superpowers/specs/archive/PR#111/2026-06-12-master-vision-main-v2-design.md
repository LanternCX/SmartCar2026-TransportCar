# 主车视觉 main_v2 重构设计

> 执行状态: Archive
> 关联计划: Spec 审核通过后创建
> 适用范围: `../SmartCar2026-Vision/master/main_v2.py`, `../SmartCar2026-Vision/master/main.py`, `../SmartCar2026-Vision/tests/`, 本仓库主车本地视觉同步命名、协议文档和相关测试

## 1. 目标

本轮目标是为主车 OpenART 视觉创建一个以 YOLO 为核心的 `master/main_v2.py`。新入口满足主车完整视觉职责: 接收 RT1021 的本地视觉任务同步, 输出主车本地视觉速度, 在条件满足时可靠回报主车视觉事件, 并与主车底盘侧通信链路闭合。

`main_v2.py` 以 `yolo/main.py` 的板端基准推理路径为准: 启动时加载 `/sd/yolo.tflite`, 每帧 `sensor.snapshot()`, 执行 `img.lens_corr(strength=2.8, zoom=1.0)`, 再使用 `img.copy(0.75, 1)` 作为 `tf.detect(net, detect_img)` 的输入。除非板端验证证明必须调整, YOLO 推理调用形态保持与该验证脚本一致。

`main_v2.py` 必须完全对齐主车当前协议和行为。识别层差异只允许发生在候选框来源: 基准脚本通过色块识别得到候选框集合, `main_v2.py` 通过 YOLO 得到候选框集合。候选框集合生成之后, 候选选择、目标点误差计算、速度控制量计算、稳定帧判定、事件值生成和可靠事件回报策略都必须与主车当前脚本保持一致。

本轮同时统一主车和辅车视觉设计语言。主车对视觉端下发的是本地视觉任务同步, 新脚本、底盘侧命名、文档和测试中的正式概念统一使用 `task`。主车保留 `context_id`, 因为主车可靠事件需要绑定业务上下文; 辅车任务同步没有 `context_id`, 两者只在命名和职责口径上对齐, 不强行抹平字段差异。

## 2. 改动面评估

本轮改动跨两个仓库, 改动面较大, 需要独立 Plan 拆分执行:

- 视觉仓库新增 `../SmartCar2026-Vision/master/main_v2.py`, 从 0 编写主车视觉入口。
- 视觉仓库的 `master/main.py` 作为对照入口, `main_v2.py` 通过测试和板端验证后再决定入口切换方式。
- 视觉仓库测试需要覆盖 `main_v2.py` 的固定短帧、任务同步、事件回报、YOLO 候选提取、主循环阶段分发和无目标速度输出。
- 视觉仓库测试需要证明 YOLO 候选框进入候选集合后, 后续选择和控制策略与主车当前脚本一致。
- 本仓库需要把主车本地视觉同步命名从 `MASTER_VISION_HOOK_SYNC` 收口为主车任务同步命名, 并同步编解码函数、配置名、主车运行时、状态机、测试和开发文档。
- 协议 topic 编号和 body 字节布局保持不变, 只做命名收口; 若实现阶段发现必须调整编号或 body, 需要单独确认。

## 3. 设计取舍

### 方案 A: 在 `master/main.py` 上局部修改

该方案能少改文件, 但深调用栈、`MasterVisionHook` 类和多层函数式分发依然存在。它不利于定位 `tf.detect` 板端死机点, 也无法满足线性阅读和主辅语言统一目标。

### 方案 B: 新建 `master/main_v2.py`, 单文件扁平重写

该方案直接建立新的主车视觉入口。脚本仍是单文件, 但结构按“常量 -> 协议函数 -> 状态全局 -> 小工具 -> 阶段处理 -> 主循环”线性展开。运行时状态使用少量全局变量维护, 主循环显式串起接收、拍照、推理、阶段处理、发送。该方案最符合本轮目标。

### 方案 C: 把视觉仓库拆成多文件模块

该方案能降低单文件长度, 但 OpenART 部署和板端导入复杂度会上升, 也偏离本轮“单文件脚本线性可读”的目标。

本设计采用方案 B。

## 4. 职责边界

### OpenART 主车视觉

- 接收 RT1021 通过本车 `UART6` 下发的主车本地视觉任务同步。
- 根据任务同步中的 `context_id / state / target / arg` 切换当前本地视觉任务。
- 在需要识别物体的任务中使用 YOLO 生成候选框。
- 在搜索、搬运入口对正和绕行修正任务中输出 `LOCAL_VISION_VELOCITY`。
- 在搜索、搬运入口对正、搬运收尾和回库黄线任务中按稳定条件可靠回报 `MASTER_VISION_EVENT_REPORT`。
- 只维护视觉端当前任务、稳定计数、待确认事件和接收残片, 不维护主车全局状态机。

### RT1021 主车底盘侧

- 维护主车全局状态机和主辅协同主线。
- 通过本车 `UART6` 下发主车本地视觉任务同步。
- 消费本车 `UART6` 的视觉速度和可靠事件。
- 只处理匹配当前 `context_id` 的主车视觉事件。
- 使用通信服务管理 ACK、重发、去重和固定帧收发。

### 不在本轮范围

- 不重写辅车视觉入口。
- 不改变主辅 `UART8` 通信语义。
- 不新增图像诊断包或调试字段到高频速度链路。
- 不新增 OpenART 多文件部署结构。
- 不把 YOLO 之外的模型选择机制做成可扩展框架。

## 5. `main_v2.py` 结构

`main_v2.py` 保持单文件, 但阅读顺序固定为线性块:

1. 文件说明和导入。
2. 串口、相机、YOLO、协议、状态、目标点、速度参数和阈值常量。
3. 固定短帧和业务 body 编解码函数。
4. 全局运行时状态: 当前任务、最新上下文、稳定计数、待确认事件、事件序号、接收缓冲、上一帧黄线观测。
5. 串口输入处理: 读取 bytes, 拼接残片, 扫描合法任务同步帧和事件 ACK。
6. YOLO 检测处理: 按验证脚本复制图像并调用 `tf.detect`, 生成统一候选框。
7. 阶段处理: 搜索、绕行修正、搬运入口对正、搬运收尾、回库黄线。
8. 串口输出处理: 速度帧、同步 ACK、可靠事件重发。
9. 相机初始化、串口初始化和主循环。

实现时允许使用少量纯计算函数, 但主车视觉状态不使用类封装, 主循环不依赖多层函数才能看懂一帧的完整行为。所有阶段处理函数只能读写同一组明确的全局状态, 不通过多层参数传递隐藏上下文。

## 6. YOLO 识别路径

YOLO 是 `main_v2.py` 的默认物体识别路径。启动时加载模型一次, 主循环复用同一个 `net`。每帧识别流程为:

1. `sensor.snapshot()` 获取原图。
2. 对原图执行镜头校正。
3. 调用 `img.copy(0.75, 1)` 生成推理图。
4. 调用 `tf.detect(net, detect_img)`。
5. 只使用置信度大于 `0.90` 的检测结果。
6. 将归一化检测框按原图宽高换算为像素框。
7. 根据标签编号映射到物体名和物体编号。

目标选择默认只从当前任务允许的物体中选择。搜索阶段允许全部配置物体; 搬运或对正阶段如 RT1021 已下发具体物体编号, 只选择该物体。候选选择、速度输出和事件命中使用同一个候选结果, 避免同一帧内“速度选中目标”和“事件判定目标”不一致。

若实现阶段需要色块识别实验入口, 只能放在明确的调试开关下, 默认主线必须是 YOLO。

## 7. 候选框后处理等价边界

主车当前脚本的识别链路可以抽象为两段:

1. 识别器输出候选框集合。
2. 主车视觉任务根据候选框集合完成目标选择、控制量计算和事件判定。

`main_v2.py` 只重写第 1 段的识别器实现。YOLO 输出需要被转换成与色块候选相同的候选框语义, 至少包含任务名、中心点、底边、面积和原始框对象。进入第 2 段后, 行为约束如下:

- 搜索阶段仍按目标点距离选择候选框。
- 搬运收尾阶段仍按目标窗口过滤后选择面积最大的候选框。
- 目标点配置、死区、限幅、最小速度、纵向归一化方式和无目标搜索速度保持一致。
- `TARGET_FOUND` 的物体编号来自选中候选框的任务名映射。
- `ALIGNED`、`ARRIVED` 和回库完成事件的稳定帧条件保持一致。
- 同一帧的速度控制量和事件判定必须使用同一个选中候选框。

实现上可以把第 2 段整理成更清晰的线性过程, 但不能借重构改变对外行为。

## 8. 视觉任务语义

主车本地视觉任务使用 `context_id / state / target / arg` 描述:

- `context_id`: 主车底盘侧分配的业务上下文编号, 用于匹配主车视觉事件。
- `state`: 主车全局状态编号, 视觉端只用于选择本地任务分支。
- `target`: 当前视觉目标类型, 例如物体或边线。
- `arg`: 本地视觉配置编号, 必要时承载物体编号。

`arg` 的语义应与辅车任务同步保持一致: 低字节表示本地视觉配置编号, 高字节表示物体编号。主车搜索阶段表达“任意物体”时, 物体编号使用 `0`。

`main_v2.py` 中的正式命名使用 “task / sync / context / event”, 不使用 “hook”。对应底盘侧命名也按这个口径收口。

## 9. 阶段行为

### 搜索物体

搜索任务使用 YOLO 候选生成主车视觉速度。无目标时输出配置搜索速度; 有目标时根据候选框目标点误差输出 `vx / vy`。目标达到面积、目标窗口和连续稳定帧条件后, 可靠回报 `EVENT_TARGET_FOUND`, `value` 为选中物体编号。

### 绕行修正

绕行修正任务使用 YOLO 候选生成平移修正速度。无目标时输出零速度。该阶段只提供本地视觉修正, 不决定主车绕行完成。

### 搬运入口对正

搬运入口对正任务使用 YOLO 候选生成对正速度。目标达到对正窗口并连续稳定后, 可靠回报 `EVENT_ALIGNED`。

### 搬运收尾

搬运收尾任务使用黄色环带接触判定。该阶段可以使用当前物体候选框构造环带, 再统计黄色占比。黄色接触满足连续稳定条件后, 可靠回报 `EVENT_ARRIVED`。

### 回库黄线

回库黄线任务使用黄色采样线输出纵向速度。后退找线阶段和黄线平移阶段使用同一任务同步机制区分 `state`。黄线完成判定沿用已验证的固定采样逻辑, 满足条件后可靠回报 `EVENT_RETURN_GARAGE_FINISHED`。

## 10. 通信协议要求

`main_v2.py` 的固定短帧、topic、body 布局、ACK 方向、可靠事件重发和幂等规则必须完全对齐主车当前协议。固定短帧结构保持 `HEAD / MODE / TOPIC / SEQ / BODY / CRC8`, `HEAD = 0xA5`, `BODY = 8 bytes`, `FRAME_SIZE = 13`。

高频速度链路:

- Topic: `LOCAL_VISION_VELOCITY`
- Mode: `UDP`
- Direction: OpenART -> RT1021
- Body: `vx / vy / omega / has_omega`
- 主车视觉默认 `omega = 0`, `has_omega = False`

主车本地视觉任务同步:

- Topic 编号使用 `0x10`
- Mode: `TCP`
- Direction: RT1021 -> OpenART
- Body: `context_id / state / target / arg`
- 名称收口为主车任务同步语义

主车视觉事件回报:

- Topic: `MASTER_VISION_EVENT_REPORT`
- Mode: `TCP`
- Direction: OpenART -> RT1021
- Body: `context_id / event / value`

可靠同步必须具备 ACK、重发和幂等处理。高频速度包只承载当前速度, 不携带任务名、候选框、调试文本或状态上下文。

## 11. 底盘侧同步收口

本仓库需要把主车本地视觉同步命名与辅车对齐。目标命名:

- `TOPIC_MASTER_VISION_TASK_SYNC`
- `encode_master_vision_task_sync_body`
- `decode_master_vision_task_sync_body`
- `MASTER_SEARCH_TASK_CONFIG_ID`
- `MASTER_TRANSPORT_TASK_CONFIG_ID`
- `MASTER_TRANSPORT_FINISH_TASK_CONFIG_ID`
- `MASTER_ORBIT_TASK_CONFIG_ID`
- `MASTER_RETURN_GARAGE_LINE_TASK_CONFIG_ID`
- `poll_task_request`
- `_pending_task_sync`
- `_active_task_context_id`

这些命名只表达当前职责, 不写兼容别名。正式协议只维护一套字段和命名。测试、文档和视觉仓库测试辅助函数必须同步使用新命名。

## 12. 工程化要求

`main_v2.py` 的实现质量目标是更优雅、结构化、工程化和整洁, 但这种整理只服务可读性和可验证性, 不改变协议和候选框后处理行为。

具体要求:

- 主循环按“收串口 -> 拍照 -> 识别候选 -> 阶段处理 -> 发速度或可靠事件”的顺序显式展开。
- 全局状态集中命名, 不散落在多个对象和闭包中。
- 阶段处理以线性分支表达, 避免深层嵌套和跨多层函数跳转。
- 纯计算函数只承担明确的小职责, 不隐藏串口发送、状态切换或事件创建副作用。
- 协议编解码、YOLO 候选生成、候选框后处理和串口收发边界清晰分组。
- 注释只说明职责、单位、坐标语义和容易误解的边界, 不重复代码流程。

### 热点函数和 API 设计

热点函数的边界必须由语义、阅读顺序和数据所有权决定, 不为了拆分而拆分, 也不为了更容易写测试而牺牲主线可读性。测试覆盖只能证明行为存在, 不能替代 API 设计判断。

设计要求:

- 热点函数名称要直接表达业务语义, 例如“生成 YOLO 候选集合”“选择当前任务候选”“根据候选生成速度”, 不使用只描述技术动作的模糊名字。
- 热点函数输入优先使用当前阶段真正需要的数据, 不传入整包上下文、临时字典或无关状态。
- 热点函数返回值要表达稳定语义, 例如候选集合、选中候选、速度二元组、事件请求; 不返回需要调用方猜字段含义的松散混合结构。
- 热点函数副作用要可见。计算函数不写串口、不修改任务状态、不创建可靠事件; 状态推进函数不隐藏图像识别和速度计算。
- 高频路径避免构造不必要的大临时对象、深层字典和调试字符串。
- 如果一个函数拆出来后调用方仍需要来回追 2 层以上才能理解一帧行为, 该拆分不合格。
- 如果一个函数只被调用一次, 但能承载清晰阶段语义, 可以保留; 如果只是在复述两三行代码, 应直接留在主流程里。

### 架构可读性标准

`main_v2.py` 是单文件脚本, 架构目标不是把代码拆短, 而是让读者可以按文件顺序理解完整运行过程。好的结构应让第一次接手的人先看到主线, 再按需要下钻到协议、识别、候选处理和事件细节。

设计要求:

- 文件顶部常量按职责分组, 顺序为运行环境、协议、任务状态、YOLO、候选框、速度控制、事件判定和调试开关。
- 全局运行状态集中放置, 每个状态变量只属于一个职责, 不在多个阶段重复表达同一事实。
- 主循环是脚本的阅读锚点, 需要保持短而完整; 读者不进入细节函数也能看懂一帧从输入到输出的顺序。
- 阶段处理函数只表达阶段业务, 不混入协议扫描、相机初始化或模型加载。
- 协议层只处理 bytes、topic、seq 和 body, 不理解视觉任务业务。
- 识别层只负责把图像变成候选框集合, 不决定速度、不创建事件、不写串口。
- 候选框后处理层负责选择候选和计算观测误差, 不直接发送速度或可靠事件。
- 事件层负责稳定计数、事件请求和重发状态, 不重新选择候选框。
- 输出层负责把速度或可靠事件写出, 不重新计算业务判断。
- 坐标语义必须在边界处命名清楚: 原图坐标、协议底边坐标、目标点误差不能共用含糊变量名。
- 配置项名称要表达单位和含义, 例如像素、比例、帧数、速度上限; 不使用需要查上下文才能理解的短名。
- 布尔变量必须表达判断结论, 避免 `flag`、`ok`、`valid2` 这类失去语义的名字。
- 相邻代码块之间应保持单一抽象层级, 不在同一段里交替出现底层字节处理和高层任务决策。
- 对于难读但必须存在的算法步骤, 优先通过变量命名和局部结构说明意图, 注释只补充边界和原因。
- Review 时如果只能通过测试知道代码正确, 但不能通过阅读理解为什么正确, 该实现不合格。

## 13. 直接失败边界

`main_v2.py` 面向 OpenART 板端正式运行环境, 不写无意义的兜底代码。必要 API 不存在时, 脚本应直接失败并暴露真实错误, 不通过假路径继续运行。

实现要求:

- `sensor`、`tf`、`machine.UART`、`time` 等正式运行依赖使用直接导入, 不写 `try / except ImportError` 兜底。
- `sensor.reset()`、`sensor.snapshot()`、`img.lens_corr(...)`、`img.copy(...)`、`tf.load(...)`、`tf.detect(...)`、`uart.any()`、`uart.read(...)`、`uart.write(...)` 等正式 API 使用直接调用, 不通过 `getattr` 探测后绕路。
- 不为了主机测试伪造板端能力, 测试需要的替身应通过加载隔离或测试夹具提供, 不进入正式脚本主线。
- 不捕获无法恢复的异常。只有明确可恢复、且不会掩盖真实故障的串口残片解析错误可以局部处理。
- 不用空输出、默认空候选或静默跳过掩盖必要依赖失败。无目标是识别结果, 依赖缺失是运行失败, 两者不能混在同一条分支里。

## 14. 测试与验证

视觉仓库主机侧测试:

- `main_v2.py` 能编码和解析固定短帧。
- 主车任务同步帧解析合法, 辅车任务同步帧不会被主车入口误收。
- 同步帧收到后会回 ACK, 重复同步帧幂等。
- 事件帧使用 `MASTER_VISION_EVENT_REPORT`, 并携带当前 `context_id`。
- 分段输入、前导坏字节和错位假帧不会破坏后续合法帧解析。
- 正式脚本主线不包含 import 兜底、板端 API `getattr` 探测调用或依赖缺失后的静默继续运行。
- YOLO 检测桩返回结果时, 候选框按原图尺寸换算, 标签和置信度过滤正确。
- 色块候选和 YOLO 候选进入同一候选框后处理入口后, 选择结果、速度计算和事件判定一致。
- 搜索、绕行修正、搬运入口、搬运收尾和回库黄线分别覆盖至少一条行为路径。

本仓库主机侧测试:

- topic 注册名、编解码函数和 body 布局与主车任务同步命名一致。
- 主车运行时下发主车任务同步, 收到 ACK 后激活对应 `context_id`。
- 主车只消费匹配当前 `context_id` 的视觉事件。
- 高频速度链路和可靠状态链路分别闭合。
- 主辅端到端通信流程测试使用新命名表达同一行为。

板端验证:

- 先运行 `../SmartCar2026-Vision/yolo/main.py` 作为基准确认模型、相机和 SD 卡路径正常。
- 再运行 `master/main_v2.py` 的最小 YOLO 搜索任务, 只验证 `tf.detect(net, detect_img)` 不死机。
- 再接入 RT1021 本车 `UART6`, 验证任务同步 ACK、速度输出和 `TARGET_FOUND` 事件。
- 最后执行完整主车流程, 分别观察搜索、绕行修正、搬运入口、收尾和回库黄线。

## 15. 验收标准

- `master/main_v2.py` 默认以 YOLO 模式运行, 不需要修改开关才能进入主线识别。
- 板端运行 `main_v2.py` 时, YOLO 搜索阶段不会在 `tf.detect(net, detect_img)` 处死机。
- 主车 RT1021 能通过本车 `UART6` 建立主车视觉任务, 收到 ACK, 接收速度, 并收到匹配 `context_id` 的可靠事件。
- 除候选框来源由色块识别变为 YOLO 外, 候选框选择、速度计算、稳定判定和事件回报行为与主车当前脚本一致。
- 主车和辅车视觉同步命名统一为任务同步口径, 正式文档和测试中不把主车任务同步称为 `hook`。
- 新脚本阅读顺序线性, 主循环能直接看出每帧执行顺序。
- 正式脚本不使用无意义兜底隐藏依赖或 API 调用失败。
- 高频速度链路不携带可靠同步字段, 可靠事件链路不依赖最后一帧零速度。

## 16. 风险与约束

- `tf.detect` 死机已排除内存问题, 但仍可能与图像对象、镜头校正、副本生命周期或模型输入对象有关。`main_v2.py` 必须先保持与 `yolo/main.py` 相同的推理输入形态, 再逐步接入通信和任务分支。
- YOLO 候选框坐标如果没有转换成主车当前候选框语义, 后续控制量会表现为行为变化; 实现阶段必须先锁定候选框等价测试。
- 主车任务同步命名会影响底盘侧大量测试和文档, 实现时必须双仓同步收口。
- 主车需要 `context_id` 绑定事件, 不应为了和辅车字段完全一致而删除该字段。
- OpenART 正式入口不使用桌面 Python 便利字节写法, 多字节整数继续使用显式位运算。
- 必要依赖和正式 API 失败时应暴露错误, 不能用兜底分支制造“还在运行”的假象。
- 串口接收必须跨轮询保存残片, 不能按理想整帧到达设计。
