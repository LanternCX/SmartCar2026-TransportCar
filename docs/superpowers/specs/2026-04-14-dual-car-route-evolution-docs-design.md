# 2026-04-14 双车协同搬运路线重规划文档改造设计

## 背景

当前项目开发文档里的正式口径，仍然把双车协同理解为“主车统一决策、辅车持续执行、整体横向搬运、不重建阵型”的路线。

这和本轮新的项目判断已经不一致。新的判断不是单点调参，而是对整条完赛路线的重新规划：

1. 总体方案拆成两个大的状态机集：寻找态状态机集、搬运态状态机集。
2. 搬运构型不再只有一种，而是至少包含“前后推”和“左右推”两种模式。
3. 主车和辅车都参与运动，但主车仍负责统一决策、状态切换和协同编排。
4. 纯视觉跟随响应不够快，导致闭环偏软，因此主车到辅车的高频通信和速度前馈要进入正式路线。
5. 当前最近要做的速度前馈验证，只是整条路线中的一段，不应被写成全部目标。

另外，`issue #35` 已经把“搬运时跟随物体、寻找时双车跟随”“需要用状态机拆开策略”“通过开环设计和状态机绕开纯闭环调试困难”的判断提了出来。这说明本轮文档改造需要同时收口总方向和演进路线，而不是只补一段局部说明。

## 目标

本轮设计只解决项目开发文档的方向重写，目标如下：

1. 让 `docs/developer/strategy.md` 正式表达新的总体方案。
2. 让 `docs/developer/tasks.md` 表达新的项目演进路线，并正确安放“近期先做速度前馈验证”的位置。
3. 让 `docs/developer/control.md` 解释为什么高频通信和速度前馈属于关键能力，而不是附属优化。
4. 让 `docs/developer/vision.md` 表达不同阶段使用不同视觉输入的路线。
5. 让以上四份文档之间不再互相冲突。

## 非目标

本轮不做以下事情：

1. 不直接修改运行时代码、协议代码或测试代码。
2. 不在项目文档中展开到动作级实现细节。
3. 不为 `0 / 90 / -90 / 180` 四类角度分支写出完整动作策略，只固化它们是后续必须分流的正式入口。
4. 不新建一套新的开发文档架构，继续沿用现有 `strategy / tasks / control / vision` 分工。
5. 不猜测新的硬件事实、引脚、具体通信频率或新的协议字段。

## 用户已确认的设计边界

本轮讨论中已经明确确认以下边界：

1. 这轮要整理的是总体项目演进路线，而不是最近某一个业务动作的局部改动。
2. 现有文档架构已经能承载这次重写，不需要再自创一层新结构。
3. 新总方案要直接进入当前正式路线，而不是仅写成一份旁路专项设计。
4. `0 / 90 / -90 / 180` 四类朝向关系本轮先固化为正式分支，不写到动作级策略。
5. 高速通信和速度前馈要被写成整套路线里的关键能力。
6. “近期先实现速度前馈并验证跟随方案是否可行”只是演进路线中的一个阶段样例，不是整份路线的全部内容。

## 核心设计

### 一、文档结构保持不变，只重写各自承担的内容

本轮不新增新的总览文档，也不把路线拆成新的文档层级。继续使用现有四份开发文档，但让每份文档回到自己该承担的位置：

1. `strategy.md` 负责写项目总方向。
2. `tasks.md` 负责写项目演进路线和阶段任务。
3. `control.md` 负责写控制侧能力边界与控制判断。
4. `vision.md` 负责写视觉输入和阶段性观测职责。

这样改的原因是：用户已经明确指出当前文档架构本身没有问题，问题在于里面装的是旧口径。如果继续叠加新的结构，只会增加审核负担。

### 二、`strategy.md` 改写为新的总方向文档

`strategy.md` 需要完成以下收口：

1. 明确项目总方案由“寻找态状态机集”和“搬运态状态机集”组成。
2. 明确主车和辅车都参与运动，但主车仍然承担统一决策、搜索、切换和协同编排。
3. 明确搬运至少存在两种构型：
   - 前后推：搬运过程中的直行协同推进。
   - 左右推：横向协同时，两车各转固定角度后协作推进。
4. 明确寻找态和搬运态不是同一套状态的展开，而是两个大的状态机集合。
5. 明确整条路线依赖高频多车通信和速度前馈。

这里的重点不是写实现步骤，而是把项目对“最终路线长什么样”的共识写清楚。

### 三、`tasks.md` 在现有阶段框架内重排项目演进路线

`tasks.md` 不增加新结构，继续保留现有阶段化任务文档的写法，但要重排阶段目标和任务内容。

推荐的重排原则如下：

1. 前面的阶段先解决“路线基础对齐”和“关键能力可行性验证”。
2. 中间阶段再逐步落地寻找态和搬运态两个状态机集的最小闭环。
3. 后面的阶段补完整切换、角度分类、避障与连续搬运。
4. 近期要做的速度前馈验证，放在靠前阶段，作为“关键能力验证”的内容。

按这个原则，`tasks.md` 需要把现有任务改写成类似下面的推进顺序：

1. 对齐总方向、角色边界、成功判据和硬件条件。
2. 打通主车到辅车的高频通信与速度前馈，先验证跟随链路可行性。
3. 建立寻找态最小闭环：边线平移避让、主前辅后、主车搜索、辅车跟随主车标记。
4. 建立搬运态最小闭环：找到物品、进入搬运、前后推、避障插入。
5. 扩展完整路线：左右推构型、四类角度分支、寻找态与搬运态切换。
6. 继续推进连续搬运、稳定性验证、提速和赛前封板。

这里不要求每个阶段的任务名和序号与上述示例完全一致，但必须体现出“总体路线”与“近期验证重点”的上下关系。

### 四、`control.md` 改写控制侧判断依据

`control.md` 需要把控制侧的项目判断写清楚，重点不是底盘通用控制原理，而是本项目为什么需要这条控制路线。

需要新增或改写的重点如下：

1. 纯视觉跟随响应不够快，因此仅靠视觉闭环会让双车协同偏软。
2. 主车到辅车的高频控制链路是整条方案的基础能力。
3. 速度前馈的作用是把主车的运动意图提前传给辅车，提升双车协同的跟随硬度。
4. 前馈策略要按状态切换，而不是整程只有一种表达。
5. 寻找阶段和搬运阶段的视觉输入不同，因此前馈应用场景也不同。

其中本轮只需要把“为什么要这样做、它在整条路线里扮演什么角色”写清楚，不需要在文档里发明新的协议字段或具体参数。

### 五、`vision.md` 改写为阶段驱动的视觉职责文档

`vision.md` 需要从“单套视觉状态机”口径切换到“按阶段服务不同任务”的口径。

核心内容应包括：

1. 寻找阶段的视觉职责：
   - 主车负责搜索下一个目标。
   - 辅车通过识别主车上的标记进行跟随。
2. 搬运阶段的视觉职责：
   - 视觉关注搬运物体及搬运过程中的环境信息。
   - 视觉输入服务于物体保持、构型切换和避障插入。
3. 文档要明确不同阶段的视觉输入来源不同，不再把整程视觉任务混写成同一种观测。

这里的关键不是写检测算法，而是写清视觉在不同阶段分别为谁服务。

### 六、四份文档之间需要统一的共识项

无论具体内容写在哪一份文档里，以下共识必须跨文档一致：

1. 项目总路线由寻找态状态机集和搬运态状态机集组成。
2. 搬运至少包含前后推和左右推两种构型。
3. 主车和辅车都参与运动，但主车负责统一决策。
4. 高速通信和速度前馈是关键能力。
5. 近期的速度前馈验证只是演进路线中的一个阶段。
6. 四类角度关系是正式分支入口，但本轮文档不写到动作级策略。

## 验收标准

本轮文档改造设计落地后，至少应满足以下结果：

1. `strategy.md` 不再把项目总路线表述成单一横向搬运思路。
2. `tasks.md` 能让读者看清总体路线和近期验证重点之间的关系。
3. `control.md` 能回答“为什么必须加高频通信和速度前馈”。
4. `vision.md` 能回答“为什么不同阶段要看不同视觉输入”。
5. 四份文档之间不再互相冲突。
6. 文档不出现新的硬件猜测、动作级过细承诺或不便审核的模糊表述。

## 风险与控制

### 风险一：把近期打算写成整条路线的全部内容

控制方式：

1. 在 `tasks.md` 中把速度前馈验证明确放入阶段路线，而不是写成终局方案。
2. 在 `strategy.md` 中始终先写总方向，再写关键能力。

### 风险二：继续保留旧口径，导致文档前后矛盾

控制方式：

1. 重写四份文档时统一检查“主车是否主动参与运动”“是否仍写成横向搬运”“是否仍写成单套状态机”。
2. 交叉复核四份文档里的关键共识项是否一致。

### 风险三：文档写得太细，提前锁死后续实现

控制方式：

1. 四类角度分支只写成正式入口，不写动作级策略。
2. 不新增未确认的协议字段、频率和硬件事实。
