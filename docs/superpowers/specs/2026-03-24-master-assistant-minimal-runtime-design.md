# 主车 / 辅车最小运行时拆分设计

## 1. 背景

当前项目的运行时结构已经演化得过于复杂, 主要问题不是单点 bug, 而是整体设计过于通用、过于耦合, 已经明显偏离“两台不同车辆分别烧录、分别运行”的真实目标。

现状中的几个核心问题如下:

- 主车与辅车共用一套运行时, 通过角色、开关和延迟装配区分行为, 导致状态边界不清晰
- 为了复用而引入的大量兼容桥接、lazy mixin、动态装配和 facade, 提高了 import / init / 首次访问时的内存与调试复杂度
- 板端问题已经表现为: 即使理论常驻内存未必更大, 仍会因为运行时路径过长、阶段切换过多、堆碎片和隐式依赖而频繁出现 OOM 或兼容性问题
- 继续在现有统一运行时上打补丁, 只会让系统越来越难以理解、验证和裁剪

因此, 本次重构的目标不是继续优化现有统一运行时, 而是直接回到更贴近真实部署方式的结构: 原系统作为冻结参考保留, 主车和辅车作为两套独立应用重新设计。

## 2. 目标

本次重构的核心目标如下:

1. 将 `src` 下的运行时代码整理为三部分:
   - `src/legacy`
   - `src/master`
   - `src/assistant`
2. `src/legacy` 作为原系统冻结参考实现保留, 不再作为未来运行时架构继续演化, 且必须成为原系统代码的实际归档位置
3. 主车与辅车在运行时代码层面默认不共享实现
4. 只保留核心最小系统, 删除非必要功能与为兼容历史路径保留的复杂结构
5. 主车负责视觉、决策、协同和自身运动
6. 辅车只负责执行来自主车的运动级命令, 保留最小安全与通信能力
7. 优先降低系统复杂度、运行时耦合和板端内存风险, 而不是追求抽象复用
8. 所有新设计都必须服从竞赛完赛目标, 不允许为了架构整洁牺牲完赛能力

## 3. 硬约束

本次重构存在 3 条不可违反的硬约束:

1. 整体方案设计不能偏离本 spec 确认的方向
2. 竞赛完赛目标导向不能改变
3. 未完成方案设计和实施计划前, 不允许直接进入代码实现

这 3 条约束意味着:

- 不能边想边大面积改代码
- 不能在没有大方案的前提下直接重写运行时
- 不能为了“更优雅的架构”牺牲已经明确需要保留的稳定性设计
- 不能为了局部清爽而破坏最终完赛路径
- 不能只创建 `legacy` 占位目录, 却让旧系统代码继续散落在 `src` 根下
- 在 `legacy` 实际归档并通过验收前, 不得继续扩张 `master` / `assistant` 运行时

## 4. 基本判断

这次重构应采用“一个仓库, 两套独立应用”的模式, 而不是继续保留单一运行时加角色分支。

推荐方案如下:

- 保持一个 Git 仓库, 方便统一管理工具、测试和文档
- 运行时代码整理成 `src/legacy`、`src/master` 和 `src/assistant`
- `src/legacy` 保存原系统完整实现, 作为冻结参考基线, 不是空壳目录
- `src/master` 和 `src/assistant` 在代码组织上视作两套独立产品, 而不是一套产品的两种 profile
- 即使存在相似逻辑, 运行时代码也优先复制两份, 不以共享为默认目标

不推荐继续沿用以下模式:

- 单一 `services.car` 或单一 `transport_car` 运行时 + `vehicle_role` 分流
- 通过兼容层、动态导入、lazy mixin、facade 维持“表面统一, 实际分叉”的结构
- 在板端场景中为了减少重复而引入更多抽象层

## 5. 目标架构

### 5.1 `src/legacy`

`src/legacy` 承担以下职责:

- 保留原系统完整实现
- 提供稳定性相关设计的参考基线
- 保留原系统任务目标与业务目标语义
- 承接当前 `src` 根下旧系统运行时代码的实际归档

`src/legacy` 不再承担以下职责:

- 不再作为未来运行时架构模板继续扩展
- 不再作为主车 / 辅车新系统的直接代码骨架
- 不再作为新协议和新状态机的默认宿主
- 不再作为当前主线测试对象

新系统保留的是 `legacy` 的设计真义, 不是 `legacy` 的历史代码组织方式

同时, 目录清晰度本身也是本次重构的硬要求之一:

- 目标态下, `src` 根下不应继续散落旧系统主干运行时代码
- 旧系统代码应明确收拢到 `src/legacy`
- `src/master` 和 `src/assistant` 应与 `src/legacy` 并列存在, 而不是在旧结构旁边临时追加
- 旧仓库对应测试在归档后应整体退出当前主线验证面

### 5.2 `src/master`

`src/master` 作为主车专用应用, 只保留主车真实需要的能力:

- 双视觉输入与视觉解析
- 简化后的视觉状态机
- 主车任务决策
- 向辅车发送协同指令
- 主车自身底盘运动控制
- 最小诊断与最小日志

主车拥有所有任务语义和任务状态:

- 目标识别
- 任务阶段判断
- 主辅车协同调度
- 发送给辅车的运动目标

### 5.3 `src/assistant`

`src/assistant` 作为辅车专用应用, 只保留执行链路:

- 接收主车下发的运动级命令
- 执行底盘运动
- 上报最小执行状态
- 提供安全停止、超时保护、最小通信保活

辅车不保留以下能力:

- 视觉识别
- 任务级状态机
- 任务语义理解
- 主车视角下的协同决策

辅车被视为“可被主车驱动的执行底盘”, 而不是“弱化版主车”。

## 6. 边界规则

为避免重构后重新滑回复杂通用系统, 需要建立强边界规则:

1. `src/master` 不允许导入 `src/assistant`
2. `src/assistant` 不允许导入 `src/master`
3. `src/legacy` 既是参考基线, 也是原系统代码的实际归档位置, 不作为新系统的耦合依赖
4. 运行时代码默认不共享
5. 即使轮子相似, 也先复制两份, 后续若要合并必须单独论证
6. 允许共享的范围仅限于:
   - `tools/`
   - `tests/` 中的辅助假对象和测试工具
   - `docs/`
7. 共享工具不能反向决定运行时结构

这组规则的目标是: 让主车和辅车的 import 图谱、初始化路径、状态所有权和板端问题都能被分别理解。

补充约束:

- `legacy` 仅作为代码与设计参考, 不要求继续保持可运行
- 旧仓库对应测试不再作为当前重构阶段的通过门槛
- 当前重构阶段的验证对象只保留 `master`、`assistant`、主辅协议和设备留证

## 7. 必须保留的稳定性内核

本次重构必须完整保留一组稳定性相关设计, 这些内容可以重写代码实现, 但不能丢失其控制语义、参数语义和稳定性行为。

必须保留的内容包括:

- 底盘控制
- 滤波链
- 运动学
- 陀螺仪解算
- 四元数 / 欧拉角转换与姿态解算

这里“保留”的含义是:

- 保留算法行为
- 保留方向和符号语义
- 保留关键参数语义
- 保留已经验证有效的稳定性设计

这里“不要求保留”的内容是:

- 原文件结构
- 原模块边界
- 原函数接口
- 原运行时组织方式

因此, 推荐原则是:

- 保留控制真义
- 不保留历史架构外壳

## 8. 视觉与协同的最小化原则

视觉系统不再追求保留当前复杂实现, 但必须保留最重要的输入拓扑和足够驱动比赛动作的能力。

必须保留的视觉结构前提:

- 主车通过单视觉串口轮询两颗相机
- 保留双摄输入拓扑
- 未被点名相机保持静默

新 `master` 的视觉系统只保留到“能驱动动作”的程度:

- 接收双摄轮询输入
- 做目标选择
- 进入简化后的视觉状态机
- 输出给主车自身和辅车的运动目标

应删除或收紧的视觉外围包括:

- 不必要查询项
- 过厚的协议面
- 不必要的状态复杂度
- 为统一运行时服务的兼容逻辑

协同通信仍采用最小运动级协议, 其目标不是让辅车理解任务, 而是让主车集中思考、辅车集中执行。

## 9. 最小协同协议

主车与辅车之间不再采用任务级协议, 而是采用最小运动级协议。

### 6.1 状态所有权

主车拥有:

- 视觉观测
- 任务状态机
- 协同决策
- 下发给辅车的运动目标

辅车拥有:

- 当前执行中的运动命令
- 自身底盘执行状态
- watchdog / 超时保护
- 最小 odom / heading / 执行完成状态

### 6.2 主车 -> 辅车协议

第一版只保留最小控制命令与运动命令。

控制类:

- `ARM`
- `DISARM`
- `STOP`
- `PING`
- `STATE?`

运动类:

- `VEL vx vy omega`
- `MOVE dx dy dtheta`
- `HOLD`
- `RESET_ODOM`

### 6.3 辅车 -> 主车回报

辅车只回最小状态:

- `ACK`
- `BUSY`
- `DONE`
- `ERR`
- `STATE`

其中 `STATE` 仅包含最少字段, 如:

- `armed`
- `busy`
- `last_cmd`
- `odom`
- `heading`

不建议在第一版中加入任务 ID、复杂阶段同步、动作模板、任务名等更高层语义, 以避免复杂度重新回流到辅车。

## 10. 完赛导向验收原则

本次重构必须以竞赛完赛为最终导向, 不能以架构优雅替代可完成比赛的能力。

设计与实现时, 每个决策都需要回答 3 个问题:

1. 是否有助于提升完赛概率
2. 是否会破坏已经验证有效的稳定性设计
3. 是否会让调试、烧录、联调和故障定位更困难

若一个改动仅提升结构美观, 但会让完赛链路更长、更难验证或更难稳定运行, 则不应进入第一版。

第一版验收应优先关注:

- 主车能稳定完成视觉输入、目标判断、自身运动和辅车协同
- 辅车能稳定接收命令、执行运动、回报最小状态并安全停止
- 两边能以更短的启动链路和更小的运行时复杂度完成核心比赛动作

## 11. 第一版最小系统范围

### 11.1 主车第一版保留

- 启动脚本
- 底盘控制闭环
- 双视觉输入链
- 简化后的视觉状态机
- 一条任务决策链
- 一条辅车运动指令发送链
- 最小诊断输出

### 11.2 辅车第一版保留

- 启动脚本
- 底盘控制闭环
- 运动命令接收与执行
- 最小状态回包
- 急停、超时、停车保护

## 12. 第一批直接删除或不迁移的内容

以下内容不应进入第一版最小系统:

- 基于 `vehicle_role` 的统一运行时分流逻辑
- 为兼容历史脚本保留的大量 `__getattr__` / facade 桥接
- 复杂 lazy mixin 装配
- 自动发现式命令 / query handler 装配
- 辅车上的任何视觉链
- 非核心 diagnostics 聚合能力
- 仅为保留统一抽象而存在的运行时 owner 分层
- 不影响最小执行闭环的调试装饰逻辑

简言之: 第一版重构优先保证“能烧录、能启动、能通信、能动、能停、能完成核心比赛动作”, 不保证“旧体系平滑兼容”。

## 13. 迁移策略

推荐采用并行迁移, 而不是在旧结构上原地拆解。

### 第一步

第一步必须先把旧系统代码实际归档到 `src/legacy` 并完成验收, 然后才能继续建立新的目录和入口:

- `src/legacy/`
- `src/master/`
- `src/assistant/`

其中 `src/legacy/` 用于冻结保留原系统完整实现, 不是只放 README 的说明目录。

### 第二步

先实现 `assistant` 的最小执行闭环:

- 最小控制循环
- 最小运动协议接收
- 最小状态回报
- 最小安全停止

这是因为辅车更薄, 更容易先形成稳定基线。

### 第三步

实现 `master` 的最小闭环:

- 自身运动控制
- 视觉输入
- 决策输出
- 向辅车下发运动命令

### 第四步

在新系统都跑通后, 再决定旧统一 transport/runtime 结构是否仅作为归档参考保留。

## 14. 预期收益

完成该重构后, 预期会得到以下结果:

- 主车和辅车职责清晰, 不再互相污染
- 每台车的运行时 import 图谱明显缩短
- 初始化路径更短, 更容易压低板端风险
- 调试时可以直接判断问题属于主车还是辅车
- 删除大量“为了通用而存在”的结构后, 后续系统更容易继续简化
- 在不丢失稳定性设计的前提下, 使系统更贴近真实比赛部署方式

## 15. 当前结论

本次讨论已经确认以下决策:

1. 采用“一个仓库, 三部分代码”的方案
2. 目录整理为 `src/legacy`、`src/master` 与 `src/assistant`
3. `src/legacy` 保留原系统完整实现, 作为冻结参考基线, 且必须承接旧系统代码的实际归档
4. 主车负责双摄轮询输入、简化视觉状态机、决策、协同和自身运动
5. 辅车只做执行车
6. 主车到辅车采用最小运动级协议
7. 运行时代码默认不共享, 即使轮子相似也先复制两份
8. 必须完整保留底盘控制、滤波、运动学、陀螺仪解算和姿态解算相关稳定性设计
9. 视觉系统保留“单视觉串口轮询两颗相机”的接入拓扑, 但删减不必要查询面和复杂外围
10. 整个重构必须服从竞赛完赛导向
11. 未完成方案设计与实施计划前, 不进入代码实现
12. 迁移采用并行长出新系统的方式, 不在旧统一运行时上继续打补丁

这份 spec 现在回答的是“为什么拆、拆成什么、哪些东西必须保留、哪些东西应该删、以及哪些约束不能碰”。下一步应继续细化实施计划, 明确第一批目录、入口文件、最小协议格式、视觉状态机最小职责以及逐步替换顺序。
