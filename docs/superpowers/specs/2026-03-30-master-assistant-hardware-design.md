# 主辅车硬件接入层与低内存运行时重构设计

## 背景

当前 `src/master` 与 `src/assistant` 只包含主机侧最小逻辑，缺少可以直接烧录到 RT1021 根目录并运行的硬件接入层。现有 `src/legacy` 虽然具备完整底盘控制链路与板端脚本，但结构上仍然带有旧时代的统一角色运行时痕迹，无法满足当前“主车目录烧主车、辅车目录烧辅车”的直接部署目标。

本次设计目标不是复用旧实现，而是保留已经验证过的控制算法结论，在新的目录边界下重写一套面向 RT1021 + MicroPython 的低内存、低碎片、可直接烧录运行的运行时。

## 与现有基线文档的关系

当前仓库中的 `docs/developer/strategy.md`、`docs/developer/tasks.md` 与 `docs/developer/control.md` 仍保留了上一阶段口径，例如 `boot.py` 入口、双摄轮询、角色 profile 仍通过统一运行时区分等。本设计用于覆盖其中与当前硬件事实和用户最新确认不一致的部分，覆盖范围仅限以下项目：

1. 启动入口从 `boot.py` 收口为 `main.py`。
2. 视觉链路从“主车轮询双摄”更新为“UART6/UART8 两路持续回传、主车主动接收”。
3. 主辅车运行时边界从“统一角色运行时”更新为“分别烧录、分别运行、目录内完全自足”。
4. 主辅协议常态反馈从“可能需要频繁回包”收紧为“跟随主链路默认单向，但保留最小状态回传能力”。
5. 主辅通信方式从旧口径中的其他表述统一收口为 `UART3` 直连主辅通信。

未被上述范围覆盖的比赛目标、主辅分工、控制层级、灰度边界检测目标与验证方向，仍继续以现有方向文档为准。

若 `docs/developer/strategy.md`、`docs/developer/tasks.md`、`docs/developer/control.md` 中的旧口径与本文冲突，则以本文为后续实现与评审基线；旧文档应通过显式跳转或后续清理来消除冲突，不再作为这些冲突项的最终依据。

## 目标

1. 让 `src/master` 与 `src/assistant` 都能作为板端根目录独立烧录并直接运行。
2. 在主车与辅车中都保留完整底盘稳定性链路，不削弱速度环、姿态估计、位置环与逆运动学。
3. 保留电机参数辨识脚本与陀螺仪零漂校准脚本。
4. 在实现层面显式压低内存开销与碎片化风险，优先保证长时间运行稳定性。
5. 为后续灰度边界检测链路预留明确接入点，但本轮不实现灰度链路。

## 非目标

1. 不保留 `legacy` 的模块布局、类分层或字典状态结构。
2. 不继续维护统一角色运行时，也不再依赖 D8/D9 拨码做主辅角色切换。
3. 不保留旧版重日志、动态装配、懒加载式运行时编排。
4. 灰度链路本轮不实现，但必须为其保留接入边界与文档说明。

## 关键约束

1. 主车与辅车硬件引脚一致。
2. 主车使用 UART6 与 UART8 接收两路视觉输入，使用 UART3 向辅车发送命令。
3. 辅车使用 UART3 接收主车命令，UART6/UART8 不参与运行时主链路。
4. 入口只保留 `main.py`。`boot.py` 删除。
5. 新固件已经在硬件开关层决定是否进入 `main.py`，代码侧不再处理此开关。
6. `main.py` 仍负责通过按钮长按切换“正常运行 / PID 辨识 / 零漂校准”。
7. `DualWindowRegressionFilter` 算法保留，窗口参数保持长 30、短 8。
8. 当前阶段主辅协议保持位置式语义，但只使用二维平移控制量，即主车向辅车发送 `dx`、`dy` 这类位移增量命令。
9. 底盘内部速度环继续使用增量式 PI，以保持已有稳定性。
10. 主车是唯一状态机 owner，辅车不处理视觉，只执行命令并提供最小状态反馈。
11. 状态机与控制逻辑必须解耦：状态机低频运行，只负责阶段判断与跳转；控制逻辑高频运行，只负责连续输出控制量。

## 总体方案

采用“主车、辅车完全独立自足”的目录方案。`master` 与 `assistant` 各自包含本车需要的全部代码，不再共享运行时包，不再跨目录引用。两边允许保留相同实现的两份副本，以换取更稳定的板端边界、更明确的烧录语义，以及更容易控制的内存生命周期。

该方案的核心不是减少仓库里的重复代码，而是减少板端运行时的动态行为：

1. 不依赖角色判断决定装配路径。
2. 不依赖共享包的跨层导入。
3. 不在运行中动态发现模块、注册 handler 或按字符串查找控制对象。
4. 所有关键对象在启动时一次构造完成，运行期只更新标量状态与固定数组。

但“所有关键对象”并不等于“所有功能对象”。运行时仍要区分最小常驻对象与可延后对象：

1. 板端活不下去就不能缺失的对象属于常驻资产。
2. 只有进入某个功能阶段才需要的对象，应延后装配。
3. 调试、诊断和扩展感知对象默认不进入常驻集合。

## 入口设计

`main.py` 同时承担固件入口与启动分发职责，流程如下：

1. 上电后等待一个很短的稳定时间。
2. 检测 C8 按钮长按，若成立则执行 `script/pid_identify.py`。
3. 检测 C9 按钮长按，若成立则执行 `script/calibrate_gyro.py`。
4. 若没有进入脚本模式，则初始化正常运行所需的硬件与运行时对象。
5. 启动 5ms ticker，并进入主循环。

删除 `boot.py` 后，板端只有一个公开入口，烧录后路径更清晰，也减少了一层无意义跳转。

`D8/D9` 仍可保留为板级校验输入或诊断输入，但不再承担主辅角色切换职责。

## 控制算法边界

本次重构只要求保留算法能力与控制链路，不要求保留旧实现形式。

### 必须保留的算法结论

1. 编码器速度读取后的多级滤波链。
2. `DualWindowRegressionFilter` 的双窗口回归速度估计。
3. 基于陀螺仪的四元数积分与偏航角连续展开。
4. 里程计积分与三轮全向轮正逆运动学。
5. 位置式偏航控制。
6. 位置式上层位移目标语义。
7. 增量式速度环控制。
8. 电机参数辨识与零漂校准流程。

### 允许重写的实现边界

1. 状态容器形式。
2. 类与模块组织方式。
3. 串口接入与主循环编排。
4. 脚本与运行时的公共代码组织方式。
5. 存储格式读取封装。

## 底盘运行时设计

### 统一底盘对象

主车与辅车各自只有一个核心底盘对象 `ChassisRuntime`。该对象直接持有全部运行时状态，不再嵌套 `ChassisState`、`Quaternion`、`Odometry` 这类对象。

同时，应用层不再默认把全部领域对象都拉起，而是拆成两层：

1. `CoreRuntime`：最小常驻层，负责入口、串口、按钮、最小状态、故障状态与阶段装配。
2. `ChassisRuntime`：底盘功能层，在进入正常运行或脚本模式时按阶段装配。

这样可以避免主车在“当前阶段不驱动自身运动”时仍无条件常驻一整套非必要对象。

它的字段分成四类：

1. 硬件句柄：电机、编码器、IMU、关键串口。
2. 控制器：三个轮速控制器、一个偏航控制器、三个速度滤波器、一个陀螺仪低通。
3. 姿态与位置状态：四元数标量、偏航角、偏航目标、里程计、角速度等。
4. 目标状态：当前 `vx`、`vy`、`omega` 指令，位置参考目标，以及最近一次锁定目标。

### 状态存储策略

为了压低常驻内存与碎片化风险，状态采用以下约束：

1. 三轮共享固定索引约定，例如 `0=中轮`、`1=左轮`、`2=右轮`。
2. 三轮相关状态统一使用固定长度列表存放，例如 `raw_speed[3]`、`filtered_speed[3]`、`duty[3]`、`target_speed[3]`。
3. 四元数不创建对象，直接用 `q0`、`q1`、`q2`、`q3` 四个浮点属性。
4. 里程计不创建对象，直接使用 `odom_x`、`odom_y` 两个浮点属性。
5. 偏航相关状态只保留必要标量，例如 `heading_est`、`heading_target`、`yaw_rate`、`last_yaw_rad`。
6. 运行期不使用按轮名字符串索引的字典结构。

该设计牺牲一定表达性，但可以显著减少临时字典、字符串键和值对象的常驻占用，也更适合板端固定拍控制。

## 控制链路设计

### 执行时序

底盘控制由 5ms ticker 驱动。中断只设置 `pit_flag`，真正的控制计算仍在主循环中完成，避免在中断里做复杂运算。

单拍控制流程如下：

1. 读取三轮编码器原始值。
2. 依次通过输入低通、差值限幅、双窗口回归、输出低通，得到三轮滤波速度。
3. 读取 IMU 数据并减去零漂偏置。
4. 用三轴角速度更新四元数，并计算新的偏航角。
5. 对偏航角做连续展开，避免跨越 180 度时跳变。
6. 用轮速和当前姿态更新里程计。
7. 根据偏航目标与当前位置目标计算 `vx`、`vy`、`omega` 目标。
8. 用逆运动学把车体系目标转换成三轮轮速目标。
9. 用三路增量式 PI 计算电机占空比并输出。

### 控制环语义

上层与底层的语义分离如下：

1. 当前阶段主辅协议与视觉输出使用位置式二维语义，只传递 `dx`、`dy`。
2. 底盘位置环根据这些位置参考生成期望 `vx`、`vy`。
3. 偏航环根据角度目标生成 `omega`。
4. 最终速度环仍然对三轮轮速做增量式闭环。

这样既保留了视觉与状态机层的“位置量”表达，也不牺牲底层速度环已经验证过的稳定性。角度控制能力仍保留在底盘算法里，但不进入当前阶段主线。

## 主车视觉设计

### 接入原则

主车同时接入两路视觉，但不再做轮询式“选一路问一路”的串口工作流。改为两路 UART 独立接收、独立解析、独立更新最近状态。

### 当前阶段唯一视觉任务

当前阶段只交付一个最小闭环：

1. 主车从两路视觉中读取辅车色标位置。
2. 主车自己默认不主动运动，但允许人工推动主车改变相对位置。
3. 主车根据色标相对画面中心的二维偏差生成辅车平移控制量。
4. 辅车执行二维随动，把色标拉回画面中心。
5. 当色标进入固定像素死区后，辅车保持不动。
6. 当色标丢失时，辅车立即停住。

其中必须遵守一条实现边界：状态机低频、控制高频，两者不能混成同一套拍次语义。

同时必须遵守一条实时边界：

1. “立即停住”与“进入死区立即保持”不能只依赖低频状态机跳转。
2. 高频控制层每拍都要直接检查一份最小共享状态，例如“目标是否有效”“目标是否新鲜”“是否进入死区”。
3. 只要目标无效、超时或已进入死区，高频层当拍立即输出零控制量。

这意味着当前阶段不做以下内容：

1. 不做物体搬运主线。
2. 不做角度控制。
3. 不做复杂目标切换。
4. 不把主车自身运动纳入默认任务链路。

### 数据流

1. UART6 读取摄像头 A 回传。
2. UART8 读取摄像头 B 回传。
3. 两路数据都进入统一视觉解析器。
4. 主车选择当前有效的辅车色标结果，计算相对中心的 `err_x`、`err_y`。
5. 高频控制层持续读取最新误差，按固定高频节拍生成 `dx`、`dy`。
6. 低频状态机根据“是否看到色标 / 是否进入中心死区 / 是否丢失”推进状态。
7. 决策层只消费状态机输出和高频控制层产出的最新控制目标，不直接依赖串口细节。

### 误差归一化规则

两路相机在进入控制层之前，必须先把视觉误差统一到同一套车体平移语义，避免两路画面各自解释方向。

当前阶段规则如下：

1. 控制层只认统一后的 `err_x`、`err_y`。
2. 统一后的 `err_x`、`err_y` 必须以辅车平移控制所使用的同一车体参考系表达。
3. 当前设计以统一车体方向 `x+ = 右移`、`y+ = 前进` 为准。
4. `err_x > 0` 表示辅车应朝车体系 `x+` 方向修正，`err_y > 0` 表示辅车应朝车体系 `y+` 方向修正。
5. 当前软件侧协议要求 `UART6` 与 `UART8` 都直接输出已经按上述语义归一化后的 `err_x`、`err_y`；本轮软件不再对单路相机做第二次方向翻转或坐标重解释。
6. 若任一路相机输出不符合上述统一语义，视为视觉协议不满足当前阶段要求，而不是在车端临时补偿。
7. 两路都有效时，默认采用“最新且未超时的数据”；若两路同样新鲜，则固定优先采用 `UART6`，避免运行时分叉。

灰度链路本轮不实现；这里只保留后续接入边界与待确认清单。

### 低频状态机与高频控制解耦

当前阶段必须把“跳转逻辑”和“控制逻辑”拆成两层：

1. 低频状态机层：只处理 `MARKER_MISSING`、`TRACKING`、`CENTER_HOLD` 这类阶段判断。
2. 高频控制层：只根据最近一次有效视觉误差持续输出 `dx`、`dy`。
3. 中间只共享一份轻量目标层，例如“当前是否有效”“最近误差”“是否进入死区”“最近更新时间”这类最小状态。

禁止以下耦合方式：

1. 在每次高频控制拍里推进完整状态机。
2. 让状态机等待控制完成后再跳转。
3. 让控制层直接持有大任务状态并自行改阶段。

推荐边界如下：

1. 高频层持续刷新 `dx`、`dy` 或输出零控制量。
2. 低频层只决定当前应处于“丢失 / 回中 / 保持”哪一种阶段。
3. 当状态从 `TRACKING` 切到 `CENTER_HOLD` 或 `MARKER_MISSING` 时，只是改变高频层的输出策略，不阻塞高频拍。
4. 高频层对“无效 / 超时 / 已进入死区”具备直接归零权限，不等待低频层下一拍命名状态。

### 主车 profile 与阶段装配

虽然不再保留统一运行时，但“主车 / 辅车 profile 边界”仍然存在，只是变为目录级静态边界：

1. 主车目录允许装配视觉接收、双摄仲裁与唯一任务状态机。
2. 辅车目录禁止装配视觉处理对象。
3. 主车视觉模块属于主车侧常驻资产。
4. 主车自身底盘控制对象是否在当前阶段常驻，取决于是否真的参与当前任务；在“主车不动、只控辅车跟随”的阶段，应允许以更轻的 profile 启动。

### 视觉与主控边界

当前阶段主车不根据视觉驱动自身运动，只负责：

1. 解析两路视觉位置数据。
2. 跟踪辅车色标相对画面中心的二维偏差。
3. 以低频节拍推进“看到 / 回中 / 保持 / 丢失”这一条最小状态机。
4. 以高频节拍生成发给辅车的二维位置式控制量。

主车自身底盘仍保留完整控制链路，但当前功能目标是“主车不动，控制辅车跟随”。

这意味着：

1. 算法能力必须保留在主车目录中，不能在结构上删除。
2. 但若当前任务阶段确实不使用主车底盘控制，则主车可使用更轻的运行 profile，避免无条件初始化整套底盘控制对象。
3. 当前阶段默认只围绕辅车色标回中闭环构建视觉逻辑，不扩展到搬运或姿态控制任务。

## 主辅协议设计

### 常态跟随

主车通过 UART3 向辅车发送位置式高频控制命令，当前阶段只服务“二维回中随动”主线，核心字段为：

1. `seq`：递增控制序号。
2. `valid`：当前拍是否存在有效目标。
3. `dx`、`dy`：二维平移位置增量控制量。

辅车侧只要 `seq` 前进就采纳，否则丢弃重复命令。

### 回包策略

常态跟随不要求辅车为每条控制报文都回包，因为视觉已经形成外环反馈。但辅车仍必须保留最小状态回传能力，用于主车判定辅车当前是否空闲、执行中或超时。

当前阶段最小状态面要求只覆盖：

1. `IDLE`
2. `BUSY`
3. `TIMEOUT`

停止、保持、重置等需要确认的指令，辅车继续回 `ACK`。跟随阶段不强制逐拍回包，但主车随时可以主动查询或在关键阶段读取最小状态。

### 状态回传关联规则

为避免主车把旧状态误判为当前结果，所有状态回传与 `ACK` 都必须带上最近一次已接受或正在执行的控制序号，或一个等价的单调递增标记。

最小要求如下：

1. 跟随控制命令带 `seq`。
2. 辅车内部状态保存 `last_seq`。
3. 主车主动查询状态时，辅车返回当前状态和对应的 `last_seq`。
4. `ACK` 与 `TIMEOUT` 这类确认或异常结果，也必须带对应的 `last_seq`。
5. 超时进入 `TIMEOUT` 后，只有收到更新的控制序号或显式复位命令，才能离开该状态。

### 当前阶段最小状态回传契约

当前阶段最小状态回传固定为一条文本状态线，至少包含以下必带字段：

1. `state=1`
2. `state_label=<IDLE|BUSY|TIMEOUT>`
3. `last_seq=<int>`
4. `follow_active=<0|1>`

当前阶段允许的状态集合固定为：

1. `IDLE`：当前未执行跟随控制。
2. `BUSY`：当前正在执行有效的二维回中跟随。
3. `TIMEOUT`：跟随链路超时后已停住。

当前阶段规则如下：

1. 主车主动查询状态时，辅车返回上述最小状态线。
2. `ACK` 与 `TIMEOUT` 这类确认或异常结果必须与 `last_seq` 保持一致。
3. 本轮不把里程、航向等扩展字段纳入最小契约；若保留，只能作为附加字段，不能替代以上必带字段。
4. `DONE`、`ERROR` 不属于本轮连续二维回中主线的最小状态集合，若未来阶段确有需要，再单独扩展。
5. 当前阶段最小状态回传契约若与仓库其他旧协议正文冲突，以本节为准。

### 辅车执行语义

辅车收到 `dx`、`dy`` 后：

1. 将位移增量映射为本车参考目标。
2. 把平面位移目标送入位置环。
3. 当前阶段偏航目标保持不变，不引入新的角度控制量。
4. 最终仍由底层速度环驱动三轮。

### 当前阶段最小视觉状态机

当前阶段视觉状态机只保留 3 个状态：

1. `MARKER_MISSING`：未看到辅车色标，辅车立即停住。
2. `TRACKING`：已看到色标，且色标尚未进入中心死区，主车持续下发 `dx`、`dy`。
3. `CENTER_HOLD`：色标已进入固定像素死区，辅车保持。

当前阶段不引入更大的任务状态机；只要这个闭环稳定成立，就认为视觉主线完成。

### 当前阶段高频控制层

高频控制层独立于低频状态机运行，职责只有：

1. 读取最近一次有效的 `err_x`、`err_y`。
2. 按二维位置式映射生成 `dx`、`dy`。
3. 当状态机标记为 `CENTER_HOLD` 时输出零控制量。
4. 当状态机标记为 `MARKER_MISSING` 时立即输出零控制量。
5. 即使低频状态机尚未切换，只要共享状态显示“目标无效 / 超时 / 已进死区”，高频层也必须当拍直接归零。

它不负责决定是否切换阶段，也不负责等待“已经回中”后再继续运行。

## 存储与脚本设计

### 零漂校准

保留 `calibrate_gyro.py`，采集 IMU 静止样本并写入 `/flash/gyro_offset.txt`。正常运行时，底盘对象在初始化阶段读取该文件并缓存为六轴偏置数组。

### 参数辨识

保留 `pid_identify.py`，按照既有阶跃输入方式辨识每轮一阶对象增益与时间常数，并保存到 Flash。正常运行时优先加载这些辨识结果，推导或恢复每轮 PI 参数。

### 存储原则

1. 文件格式允许延续旧格式，降低迁移成本。
2. 文件读取只在启动时发生一次，运行期不反复打开参数文件。
3. 存储读取模块只返回最小必要数值，不拼接大对象。

## 低内存与低碎片实现原则

### 原则一：对象一次分配

所有进入当前运行阶段的核心对象必须在该阶段开始时一次构造完成；进入运行态后，不再反复创建控制器、滤波器、状态容器或大列表。

### 原则二：避免字典热路径

热路径不用字典保存轮子状态、目标速度和姿态信息，避免字符串键带来的额外常驻开销与访问成本。

### 原则三：避免运行期动态导入

不使用运行期模块发现、命令自动注册、按字符串查找 handler，也不依赖懒加载。模块边界在 import 时完全静态确定。

### 原则四：减少日志系统

不引入复杂日志框架。正常运行时只保留必要的 UART 文本输出。高频链路默认不打印。

### 原则五：固定缓存

视觉接收缓冲、辨识样本数组、滤波窗口数组都使用固定大小容器，在初始化或脚本启动时一次性创建。

### 原则六：脚本与运行时共用最小基础模块

辨识脚本、校准脚本与正常运行共享同一套底层硬件和数学模块，避免复制逻辑后再引入第二套运行时状态结构。

### 资产分类原则

按低内存实现要求，新增运行时对象应在设计上主动分成三类：

1. `A` 类：最小常驻资产，例如当前目录必要入口、关键串口、最小状态与故障状态。
2. `B` 类：按车角色常驻资产，例如主车视觉接收与状态机、辅车协议执行器。
3. `C` 类：按功能延后资产，例如当前阶段未启用的主车底盘控制对象、扩展诊断对象、灰度详细处理对象。

本设计默认：

1. 主车双视觉接收与任务状态机是主车侧 `B` 类资产。
2. 辅车协议执行与最小状态回传是辅车侧 `B` 类资产。
3. 若主车当前阶段不参与运动，则主车完整底盘闭环对象可降为 `C` 类延后资产。

### 最小阶段表

| 阶段 | 触发条件 | 必须装配 | 可延后装配 |
| --- | --- | --- | --- |
| 主车轻量正常运行阶段 | 上电后进入当前主线“主车不动，只控辅车跟随” | 入口分发、必要串口、主车视觉接收、主车状态机、主辅通信 | 主车完整底盘闭环、灰度详细处理、扩展诊断 |
| 辅车轻量正常运行阶段 | 上电后进入当前主线，由主车持续下发跟随命令 | 入口分发、必要串口、辅车协议执行、辅车完整底盘闭环、最小状态回传 | 灰度详细处理、扩展诊断 |
| 主车参与运动阶段 | 后续任务需要主车自身加入动作控制 | 主车轻量阶段全部资产 + 主车完整底盘闭环 | 扩展诊断、灰度详细处理 |
| 脚本阶段 | 进入辨识或零漂校准脚本 | 脚本所需底层硬件、最小存储模块 | 主业务状态机、扩展诊断、非脚本必要功能 |

## 风险与应对

### 风险一：完全去字典后可读性下降

应对方式是在固定索引上定义清晰常量，例如 `WHEEL_M = 0`、`WHEEL_L = 1`、`WHEEL_R = 2`，并把数组读写集中在少量模块中。

### 风险二：主车视觉与底盘主循环相互干扰

应对方式是把 ticker 控制计算保持在固定拍，视觉输入只做“有数据才解析”，避免轮询切换或等待式串口读。

### 风险三：状态机低频逻辑与控制高频逻辑耦合后互相拖慢

应对方式是显式拆分低频状态机层与高频控制层，只共享最小状态，不允许用“等状态跳完再控制”或“控制里顺手改状态”的写法。

### 风险四：最小状态回传被削弱后主车无法判定辅车是否失控

应对方式是保留最小状态面，不要求逐拍回包，但必须允许主车在关键阶段确认辅车状态。

### 风险五：位置环受编码器精度限制，累计误差较大

应对方式是明确位置环只作为必要参考量使用，不夸大其绝对定位精度；稳定性主体仍由底层轮速闭环与偏航闭环保证。

### 风险六：主辅两套代码重复维护

应对方式是接受仓库级重复，以换取板端边界清晰与内存行为稳定。该重复属于可控维护成本，不属于运行时风险。

## 验证要求

### 主机侧验证

1. `master` 与 `assistant` 目录结构满足作为根目录烧录的约束。
2. 关键模块 import 路径自洽，不依赖 `legacy`。
3. 协议解析与构造测试覆盖主辅通信主线。
4. 最小状态回传协议可在主机侧验证。
5. 视觉输入到二维回中控制量的映射可在主机侧验证。
6. 两路相机对同一目标输出的 `dx`、`dy` 方向一致性可在主机侧验证。

### 板端验证

1. 主车烧录 `master` 后可直接进入 `main.py`。
2. 辅车烧录 `assistant` 后可直接进入 `main.py`。
3. C8/C9 按钮能正确进入辨识与校准脚本。
4. 正常运行时不出现导入期 OOM。
5. 主车能稳定接收两路视觉中的辅车色标数据，并输出二维平移控制命令。
6. 在人工推动主车后，辅车能把色标重新拉回画面中心。
7. 辅车最小状态面可被主车读取并正确反映空闲、执行中与超时。
8. 色标进入固定像素死区后，辅车能稳定保持，不出现明显来回抖动。
9. 色标丢失后，辅车立即停住。
10. 视觉输入停止更新时，高频控制能在约定时限内归零，不等待低频状态机下一拍。
11. 灰度链路在本轮仅保留文档接入位，不进入当前板端交付范围。

## 分阶段实施建议

1. 先清理当前 `master` / `assistant` 的空壳目录与遗留缓存，收口现状。
2. 再搭出新的目录骨架与 `config.py`、`main.py` 启动分发逻辑。
3. 接着实现主辅共通的底盘硬件层与控制核心。
4. 再接入“辅车色标二维回中”这条主车视觉与辅车协议执行主线。
5. 最后迁移辨识脚本与校准脚本，并进行板端联调。

## 结论

本次重构的重点不是“把 legacy 复制过来”，而是“把已经验证过的控制算法，迁移为适合当前主辅双目录烧录模型的低内存静态运行时”。只要新的实现同时满足直接烧录、完整链路、脚本保留和低内存目标，就不要求对旧实现形式保持兼容。

当前这一轮实现与验收只以“辅车色标二维回中”这条最小闭环为准；目录重构扩面、底盘完整重写、脚本迁移若不直接服务这条闭环，一律后置到后续任务，不并入本轮交付范围。
