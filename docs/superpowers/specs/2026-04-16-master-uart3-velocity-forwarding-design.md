# 2026-04-16 主车 UART3 速度转发角色层设计

> 状态: archive

## 背景

当前仓库已经完成辅车侧最小速度前馈闭环: 辅车角色层会优先接管 `UART3` 上的 `vx / vy / omega` 速度控制量, 再结合本地视觉输入完成速度融合并写回共享底盘执行链。

与之对应, 主车侧 `vision/master/` 仍然只是共享底盘的空入口, 还没有承担主辅协同里的主车角色职责。因此, 当前双车之间虽然已经具备“辅车能接速度”的一半链路, 但还缺少“主车把速度稳定送过去”的另一半链路。

本轮用户给出的方向有两条已经对齐:

1. 主车侧实现思路尽量贴近辅车侧的角色层外壳方式, 不把主车专属协同逻辑直接压回共享底盘。
2. 当前阶段先做简单转发: 辅车现在能接什么控制量, 主车就发什么控制量, 不为主辅通信另外发明新主题。

因此, 本轮设计只聚焦一件事: 把主车当前阶段固定成一条单串口透传链路, 也就是主车只响应 `UART3` 下行控制, 再把其中辅车已经支持的速度字段经 `UART3` 上行转给辅车, 形成最小联动链路。

## 目标

1. 在 `vision/master/` 内建立主车角色运行时外壳, 让主车侧也通过角色层承担主辅协同边界。
2. 让主车通过 `UART3` 向辅车发送辅车当前已经支持的速度控制量, 也就是 `vx / vy / omega`。
3. 保持主车本地共享底盘继续按现有命令链执行, 不改当前控制主链和查询语义。
4. 保持主辅通信继续沿用现有控制协议文本格式, 不新增新的主辅通信报文主题。
5. 把“主车响应 `UART3` 下行控制”和“主车经 `UART3` 上行给辅车转发速度字段”收口到同一个角色层周期边界里, 避免后续出现两套平行的 `UART3` 处理逻辑。
6. 明确主车当前阶段不接入视觉输入, 也不承担任何自主行控或自主决策职责。

## 非目标

1. 不在本轮把主车的位置命令、角度命令或状态机输出换算成另一套专门给辅车的派生速度。
2. 不在本轮修改辅车速度融合规则、辅车视觉输入规则或辅车状态机边界。
3. 不在本轮改共享底盘里的控制算法、PID、里程计、方向保持或命令路由语义。
4. 不在本轮新增辅车状态回传协议、序号字段、去重机制或比赛级总状态机。
5. 不在本轮讨论新的板级串口分配、引脚变更或额外硬件改线方案。
6. 不在本轮为主车接入任何视觉串口、视觉观测字段或视觉判断逻辑。
7. 不在本轮让主车基于本地状态自主生成动作, 主车只响应 `UART3` 下行控制。

## 已确认边界

1. `UART3` 是当前主车到辅车协同通信链路。
2. 辅车角色层当前正式接收边界是 `UART3` 上的现有控制协议速度字段, 至少包含 `vx / vy / omega`。
3. 辅车角色层已经具备“优先消费速度字段, 其余查询和非速度命令透传给共享底盘”的运行边界。
4. 主车侧当前还没有对应的角色层转发逻辑, `vision/master/runtime.py` 只是共享底盘装配壳。
5. 用户本轮要求主车实现思路与辅车角色层接近, 但主车的职责不是融合视觉, 而是把速度字段转给辅车。
6. 本轮以“简单转发”作为设计边界, 因此只围绕主车当前收到的速度字段组织转发, 不扩成派生控制。
7. 当前主车串口职责固定为: `UART3` 下行负责主车接收控制, `UART3` 上行负责主车向辅车输出速度字段。
8. 当前主车不接收视觉信号, 不消费视觉输入, 也不进行自主行控。

## 方案比较

### 方案一: 主车角色层接管 UART3 读取, 提取速度字段后转发, 原始命令继续交给主车底盘

这个方案的核心做法是:

1. 主车角色层像辅车一样接管 `UART3` 的读取边界, 但主车本轮只围绕这一条串口链工作。
2. 角色层拿到完整文本行后, 先提取其中的 `vx / vy / omega / w` 片段。
3. 若本行里存在有效速度字段, 就把这些速度字段重新组织成一条发给辅车的文本行。
4. 同一条原始命令仍然继续交给主车共享底盘处理, 保证主车本地行为不变。

这个方案的优点是:

1. 主车侧边界和辅车侧边界对称, 都由角色层接管 `UART3`。
2. 转发逻辑只依赖现有协议字段, 不要求共享底盘额外暴露新的派生状态。
3. 主车本地执行语义继续保留, 不会因为增加辅车转发而改坏原有控制链。
4. 主车调试入口单一, 当前阶段只需要围绕 `UART3` 排查链路。

它的代价是:

1. 需要把主车入口从空壳提升为真正进入控制周期的角色运行时。
2. 本轮转发的是“主车当前收到的速度字段”, 不是“主车所有动作最终落实出的实际速度”。

这个方案与用户当前给出的方向一致, 本轮推荐采用。

### 方案二: 在共享底盘里直接增加 UART3 速度转发

这个方案看起来文件更少, 但有两个直接问题:

1. 主车专属协同职责会直接压回共享底盘。
2. 后续如果主车还要继续扩展角色层判断, 又会从共享层往外拆回来。

这不符合“主车实现思路尽量贴近辅车角色层”的要求, 本轮不采用。

### 方案三: 把主车当前动作进一步换算成派生速度后再发给辅车

这个方案能覆盖更深的控制语义, 但会立刻扩大改动面:

1. 需要重新界定哪些主车动作应该派生成辅车速度。
2. 需要额外定义位置/角度动作与辅车前馈之间的映射边界。
3. 这已经超出了用户当前要求的“先做简单转发”。

本轮不采用。

## 推荐方案

本轮采用方案一。

一句话概括就是:

`vision/master/` 建立主车角色运行时, 由它接管 `UART3` 输入, 从原始命令里抽取辅车已经支持的 `vx / vy / omega` 速度字段发给辅车, 同时把原始命令继续交给主车共享底盘执行。

这个方案的判断依据如下:

1. 它和辅车当前的角色层实现思路最接近, 角色边界清楚。
2. 它满足“主车发辅车已经能接的控制量”这一条当前核心要求。
3. 它不要求共享底盘新增主车专属协同逻辑。
4. 它把主车当前阶段固定成单一 `UART3` 调试入口, 不把视觉或自主逻辑混进来。
5. 它把改动收口在 `vision/master/` 角色边界内, 便于后续继续扩展主车协同职责。

## 角色层职责

本轮 `vision/master/` 角色层承担以下职责:

1. 接管主车角色下 `UART3` 的读取边界。
2. 维护主车角色层自己的按行缓冲。
3. 识别一条命令里是否包含 `vx / vy / omega / w` 速度字段。
4. 把识别出的速度字段转成一条发给辅车的文本行。
5. 把原始命令继续交给主车共享底盘处理, 保证主车本地控制链保持原样。
6. 在转发失败时只记录最小错误信息, 不阻断主车底盘控制周期。
7. 保持主车当前阶段不接入任何视觉输入, 不增加自主决策入口。

共享底盘在本轮继续只承担以下职责:

1. 继续处理主车本地控制命令和查询。
2. 继续执行当前控制链、模式切换和方向保持。
3. 不直接理解“给辅车发速度”这类主车协同语义。
4. 不承担主车视觉输入消费和自主行控语义。

## 控制周期与数据流

主车角色层的单拍流程固定如下:

1. 角色层读取 `UART3` 可用字节并拼到自己的接收缓冲。
2. 角色层按换行切出完整文本行。
3. 对每一条完整文本行, 先做最小拆分, 判断是否含有 `vx / vy / omega / w` 片段。
4. 若该行中存在有效速度字段, 角色层就把这些速度字段重新组织为一条单独文本并经 `UART3` 上行写出给辅车。
5. 无论是否发生转发, 原始整行命令仍然继续交给主车共享底盘处理。
6. 完成角色层这一拍的 `UART3` 处理后, 再进入主车共享底盘本身的控制周期。

这条流程的关键点是:

1. 主车角色层对辅车做的是“转发速度字段”, 不是“替主车改写本地命令”。
2. 主车共享底盘处理的仍然是原始命令, 因此本地行为不依赖转发是否成功。
3. 角色层和共享底盘之间的边界与辅车侧保持相同风格: `UART3` 由角色层先接管, 共享底盘自身不参与这一路的重复读取。
4. 主车当前阶段所有外部控制输入都收口到 `UART3` 下行, 不并入视觉或其他自主输入源。

## 转发规则

### 转发对象

本轮只转发以下速度字段:

1. `vx`
2. `vy`
3. `omega`
4. `w`

其中 `w` 与 `omega` 继续视为同一类角速度字段语义。

### 不转发的内容

以下内容继续只服务主车本地, 不进入主车到辅车的转发链:

1. 查询指令, 例如 `?health`
2. 位置和角度目标, 例如 `x / y / angle / dx / dy / d_angle`
3. 模式和系统命令, 例如 `rear / lock / reset / print`
4. 纯文本、空行和不含 `=` 的片段
5. 任何视觉相关输入或视觉观测字段

### 混合包规则

若一条命令同时包含速度字段和其他字段, 规则固定为:

1. 速度字段被抽出来单独转发给辅车。
2. 原始整行仍然完整交给主车共享底盘。

例如:

```text
vx=1.0,vy=2.0,rear=1
```

角色层对辅车只转发其中的速度部分, 但主车本地仍然按整行继续处理 `rear=1` 等字段。

### 非法输入规则

若一条命令命中了速度字段, 但速度字段内容非法, 本轮规则固定为:

1. 不向辅车转发这一条速度内容。
2. 原始命令仍然继续交给主车共享底盘处理。
3. 角色层记录最小错误信息, 便于联调时判断是“转发失败”而不是“主车本地控制失败”。

这里刻意不让主车角色层反向改变主车本地命令收口语义, 这样才能把“辅车转发异常”和“主车本地执行异常”区分开。

## 文本格式

主车发给辅车的文本格式继续沿用辅车现有入口能直接接住的单行文本:

```text
vx=<vx>,vy=<vy>,omega=<omega>
```

补充约束:

1. 只发送当前这条原始命令里实际出现过的速度字段, 不为缺失字段额外补默认值。
2. 转发文本按单行协议写出, 以 `\r\n` 结束。
3. 本轮不新增 `follow=1`、`seq=` 或其他新主题字段。

## 运行时状态与诊断

主车角色层本轮只维护最小状态, 不扩成新的比赛级状态机。

建议保留的最小状态如下:

1. `UART3` 未成行缓冲。
2. 最近一次转发错误文本。
3. 最近一次成功转发的最小结果标签。

这些状态的目的只有两个:

1. 让主车角色层在控制周期里稳定处理串口边界。
2. 让联调时能够快速区分“主车没读到 `UART3` 下行命令”“主车没从 `UART3` 上行转发出去”“辅车没消费到”这几类问题。

本轮不为主车新增新的查询主题; 若需要最小诊断, 继续优先复用已有错误文本承载方式。

## 目录与职责建议

本轮推荐 `vision/master/` 至少形成以下职责分工:

1. `runtime.py`
   负责主车角色入口装配, 给启动壳返回主车角色运行时对象。
2. `forward_runtime.py`
   负责主车角色层主循环、`UART3` 接管、速度字段转发和最小错误收口。

这样可以和辅车侧的 `runtime.py + follow_runtime.py` 保持同风格分层: 入口文件只负责装配, 角色周期逻辑独立落在单独实现文件中。

## 风险与控制

### 风险一: 角色层转发影响主车本地命令处理

控制方式:

1. 原始命令继续完整交给主车共享底盘。
2. 转发只抽取速度字段, 不改写主车本地命令文本。

### 风险二: 非速度命令被误转发给辅车

控制方式:

1. 角色层只识别 `vx / vy / omega / w`。
2. 其他字段一律不进入转发链。

### 风险三: 调试期把视觉或自主逻辑混入主车当前链路

控制方式:

1. 主车当前阶段只保留 `UART3` 单链路输入。
2. `vision/master/` 不接视觉串口, 不消费视觉观测, 不新增自主输出入口。

### 风险四: 转发异常拖停主车控制周期

控制方式:

1. 写串口失败只记录错误文本。
2. 主车共享底盘周期继续推进, 不把辅车转发失败升级成主车停机。

### 风险五: 现场若存在 UART3 写出回读链路, 可能造成重复读入

控制方式:

1. 本轮默认按当前主辅直连链路理解, 即主车写出的转发报文不会被本车再次当成上游输入读回。
2. 若现场链路实际存在回环, 应单独开新设计处理去重或链路隔离, 不在本轮简单转发内混做。

## 验收标准

本轮完成后, 至少需要满足以下标准:

1. 主车角色入口返回主车角色运行时对象, 而不是共享底盘空对象。
2. 主车收到纯速度命令时, 会把对应速度字段转发给辅车, 同时本地仍继续执行该命令。
3. 主车收到混合命令时, 只把其中速度字段转发给辅车, 其他字段仍只服务主车本地。
4. 查询和非速度命令不会被错误转发给辅车。
5. 主车当前阶段不接入视觉输入, 也不从其他来源生成自主动作。
6. 转发失败不会阻断主车本地控制周期。

## 测试与验证口径

### 主机侧自动验证

本轮至少需要补齐以下测试:

1. 主车包入口继续按角色创建主车角色运行时对象。
2. 主车角色运行时接管 `UART3` 后, 纯速度命令会被转发, 同时原始命令继续交给主车本地共享底盘。
3. 混合包里只有速度字段会被转发, 其他字段不进入辅车链路。
4. 查询和非速度命令不会被转发。
5. 主车角色层不接任何视觉输入, 也不触发自主行控分支。
6. 串口写出异常时, 主车角色层仍保持控制周期可继续推进, 并留下最小错误信息。

### 板端确认

由于本轮实际效果最终落在主辅串口链路上, 完成主机侧测试后, 还需要通过对话协作记录以下最小板端确认:

1. 主车上电进入正常运行后, 角色入口确实切到主车角色运行时。
2. 主车发送速度命令时, 辅车侧能在 `UART3` 上收到对应速度字段。
3. 主车发送查询或非速度命令时, 辅车侧不会被误触发对应动作。
4. 主车现场运行时没有接入视觉输入, 也没有自主动作输出。
5. 主车本地仍保持原有命令执行能力。

## Review 重点

这份 spec 当前最值得你重点确认的是 5 件事:

1. 本轮边界是否就停在“简单转发速度字段”, 不额外派生位置或角度动作。
2. 混合包是否应该采用“速度字段转发, 原始整行继续交给主车本地”的口径。
3. 主车角色层是否仍然应该像辅车一样接管 `UART3`, 而不是把转发逻辑压回共享底盘。
4. 主车当前阶段是否明确固定为“只响应 `UART3` 下行控制, 不接视觉, 不做自主行控”。
5. 若现场链路存在回读风险, 是否要在下一轮单独设计去重, 而不是在本轮混入实现。
