# 2026-04-12 当前底盘协议可选 `lock` 扩展设计

## 背景

当前仓库里的底盘控制协议已经支持两类明显不同的控制方式：

1. 速度命令，例如 `vx/vy/omega`。
2. 位置或模式命令，例如 `x/y/angle/dx/dy/d_angle/rear`。

其中，位置或模式命令当前默认按“发一条，执行到位，再处理下一条”的等待完成语义工作。

这套默认语义适合离散动作，但会限制后续高频上位控制场景。用户这次确认的当前目标，不是立刻改视觉仓库，而是先把当前底盘协议本身收干净：

1. 原来带锁的命令，要支持由上位显式选择带锁或不带锁。
2. 这轮只实现当前仓库里的可选 `lock` 语义。
3. 视觉仓库与 OpenArt 侧改动暂时不进入本轮范围。

因此，这份设计只处理“当前底盘协议如何扩展可选 `lock`”这件事，不假定视觉仓库同步落地，也不把别的仓库实现写进本轮目标。

## 目标

1. 为当前底盘协议中的原锁定命令增加可选 `lock` 语义。
2. 保留旧的默认行为，不破坏现有离散动作能力。
3. 让上位能够显式选择“等待完成”或“无锁覆盖”。
4. 保持协议语义统一，不按串口来源拆成两套解释。
5. 让联调时能够明确看出当前底盘处于带锁执行、无锁执行，还是没有激活目标。

## 非目标

1. 不修改视觉仓库。
2. 不在本轮定义 OpenArt 侧如何发包。
3. 不把 `UART6` 的视觉观测协议改成新的控制协议。
4. 不把当前位置式控制重写成速度式控制主链。
5. 不为 `lock=0` 增加自动超时撤销策略。

## 当前问题

当前协议如果不扩展显式 `lock`，会有两个直接问题：

1. 旧的 `dx/dy/x/y/angle/d_angle/rear` 默认都会落到等待完成语义里。
2. 如果未来需要高频上位覆盖控制，只能靠改旧语义、按来源分流，或者另起一套很像旧协议的新协议。

这两条都不是这轮想要的方向。本轮要做的是把“是否等待完成”从隐含行为改成协议显式选项。

## 设计决策

### 决策一：原锁定命令统一支持可选 `lock`

凡是当前会进入等待完成流程的命令，本轮统一支持可选 `lock` 字段，包括：

1. `x`
2. `y`
3. `angle`
4. `dx`
5. `dy`
6. `d_angle`
7. `rear`

语义固定如下：

1. 不带 `lock` 时，保持当前默认行为。
2. `lock=1` 时，显式要求按等待完成语义执行。
3. `lock=0` 时，显式要求按无锁覆盖语义执行。
4. `lock` 不扩展到 `vx/vy/omega` 这组速度命令。

### 决策二：`lock` 按整包字段解释

当前串口命令按单行 `key=value[,key=value...]` 解析，因此本轮把 `lock` 定义为整包级字段：

1. 一条命令行里的全部位置 / 模式键共用同一个 `lock` 语义。
2. 不支持在同一条命令行里给不同键分别指定不同的 `lock`。
3. 组合命令允许混发，例如 `rear=1,dx=...,dy=...,lock=0`。

这样可以保持协议解析直接、可读、易排障，不把一行命令拆成彼此冲突的多段执行语义。

### 决策三：`lock=0` 表示“无锁覆盖，最后目标持续有效”

`lock=0` 的执行边界固定如下：

1. 底盘不进入当前的等待完成流程。
2. 新的无锁命令到来时，直接覆盖当前生效目标。
3. 对 `dx/dy/d_angle` 这类相对量，仍然保持当前位置式含义，不改成速度语义。
4. 本轮不为 `lock=0` 增加自动超时撤销。
5. 上位停发后，底盘继续以最后一次无锁目标为当前目标，直到被后续命令覆盖。

### 决策四：新命令总是抢占旧命令

本轮固定统一抢占规则：

1. 新命令到来时，总是按新命令接管当前动作。
2. 这条规则不区分旧命令是 `lock=1` 还是 `lock=0`。
3. 这条规则也不要求上位先等当前动作空闲。

### 决策五：`rear` 也纳入同一套 `lock` 语义

`rear` 本轮不单独例外，而是和其他原锁定命令走同一套语义：

1. `rear=1,lock=1` 保持当前动作式语义。
2. `rear=1,lock=0` 表示模式切换立即生效。
3. `rear` 与 `dx/dy/angle` 可在同一条命令里组合，由这一拍一起生效。

### 决策六：补出独立的执行方式诊断字段

`?lock` 继续只表达“当前是否处在等待完成流程”这一件事，不改它的核心含义。

为了避免联调时出现“底盘还在按无锁目标运行，但 `?lock=0` 看起来像空闲”的误读，本轮要求在 `?health` 快照里补一个明确状态字段 `command_mode`，取值固定为：

1. `locked`：当前按等待完成语义执行。
2. `unlocked`：当前按无锁覆盖语义执行。
3. `none`：当前没有激活的位置 / 模式目标。

这样“等待流程状态”和“当前执行方式”就成为两个独立可观察的事实。

## 协议口径

本轮之后，当前底盘协议的统一口径如下：

| 场景 | 推荐写法 | 语义 |
| :--- | :--- | :--- |
| 默认离散动作 | `dx=0.05,dy=0.10` | 保持当前默认带锁行为 |
| 显式带锁 | `dx=0.05,dy=0.10,lock=1` | 显式要求等待完成 |
| 显式无锁 | `dx=-0.01,dy=0.03,lock=0` | 显式无锁覆盖 |
| 无锁组合 | `rear=1,dx=0.00,dy=0.04,lock=0` | 模式与目标同拍立即生效 |

关键边界固定如下：

1. `lock` 是当前底盘协议字段，不是视觉专用字段。
2. 同一条命令的含义不取决于它来自哪个串口，而只取决于命令内容本身。
3. `vx/vy/omega` 继续保持原速度命令语义，不纳入本轮 `lock` 扩展范围。

## 数据流边界

本轮收口后的最小链路如下：

1. 上位通过当前串口入口发送底盘控制协议。
2. 底盘按整包 `lock` 语义决定这条命令走等待完成还是无锁覆盖。
3. 若后续收到新命令，直接按统一抢占规则切换到新命令。
4. 联调侧通过 `?lock` 与 `?health.command_mode` 观察当前状态。

这里故意不把上位写死成 OpenArt，也不规定视觉仓库如何消费这套能力。本轮只把当前仓库的协议边界收干净。

## 验收标准

本轮设计落地后，至少应同时满足以下标准：

1. 原有不带 `lock` 的动作式命令行为保持不变。
2. `lock=1` 与当前旧行为一致。
3. `lock=0` 能由上位显式选择，并走无锁覆盖语义。
4. 新命令总是能够接管旧命令，不要求等待空闲。
5. `rear` 与位置命令在 `lock=0` 下可以同拍组合。
6. 联调时能够从诊断信息里明确看出当前底盘是带锁执行、无锁执行，还是没有激活目标。
7. 当前主线仍保持位置式控制表达，不退化成速度式控制主链。

## 测试与验证口径

### 主机侧验证

主机侧至少要覆盖以下边界：

1. 不带 `lock` 的旧命令行为不漂移。
2. `lock=1` 与旧行为一致。
3. `lock=0` 下新命令能覆盖旧目标。
4. 带锁命令与无锁命令之间的双向抢占都符合“新命令总是抢占”。
5. `rear` 与位置命令在同一条带 `lock=0` 的命令里可以一起生效。
6. `?health.command_mode` 能正确表达当前执行方式。

### 板端联调

板端至少要确认以下结果：

1. 连续发送多条无锁命令时，不会被旧的等待完成流程卡住。
2. 发送新命令时，底盘会按新命令立即接管。
3. 上位停发后，底盘按最后一次无锁目标继续收敛，而不是自行撤销。
4. 组合命令例如 `rear=1,dx=...,dy=...,lock=0` 的行为符合整包语义。

## 风险与控制

### 风险一：`lock=0` 又被实现成串口特例

控制方式：

1. 协议正文直接把 `lock` 写成当前底盘协议字段。
2. 不接受“来自某一路串口才无锁”的隐式语义。

### 风险二：无锁与旧锁逻辑并存后出现优先级含糊

控制方式：

1. 统一固定为“新命令总是抢占旧命令”。
2. 不保留额外的隐藏优先级规则。

### 风险三：联调时把 `?lock=0` 误读成完全空闲

控制方式：

1. 保留 `?lock` 的原含义。
2. 额外补出 `?health.command_mode`，避免把“未进入等待流程”和“没有目标”混为一谈。

### 风险四：停发后的预期不一致

控制方式：

1. 在协议与诊断口径里明确写死：`lock=0` 不做自动超时撤销。
2. 上位若需要停下或改目标，必须显式发送后续命令，不把“停发”当成归零命令。
