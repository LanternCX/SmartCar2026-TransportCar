# 辅车 legacy 控制内核对齐设计

## 背景

当前辅车已经完成一轮独立的控制模式修复，主要解决了以下问题：

1. 普通跟随模式与速度模式的跨周期持续性。
2. 默认保头与显式角速度例外的模式规则收口。
3. 保护状态下不再把程序跑着但整车输出误清成完全静止。

这轮修复让链路重新可用，但用户已经明确指出一个更高优先级的约束：辅车控制内核应尽量贴回已经在实车验证过的 legacy 方案，而不是继续沿用当前最小系统里与 legacy 存在偏差的内部口径。

这里的“对齐 legacy”不是把整套旧外壳、协议和目录结构重新搬回来，而是只回到用户已经验证过的控制内核语义。

因此，本轮需要为这部分内容单开新的 spec，避免继续在“辅车控制模式一致性修复设计”上叠加新主题。旧 spec 保持不动，当前新 spec 只描述新引入的变更单元。

## 目标

本轮只追求以下目标：

1. 保留当前辅车的协议入口与应用层组织方式，不回退到 legacy 外壳。
2. 让辅车控制内核在关键控制语义上贴齐 legacy。
3. 让“位置累计、保头补偿、三轮输出”之间的耦合表现更接近用户已经验证过的 legacy 手感。
4. 保留上一轮已经修好的模式持续性，不因为对齐 legacy 内核而重新退回单拍行为。
5. 让保护状态下的行为满足当前用户要求：停平移，但继续保头；显式真停机仍保持真停机。

## 非目标

本轮明确不做以下事情：

1. 不修改当前主车到辅车的协议文本格式。
2. 不把旧版 legacy 命令系统、目录结构或应用外壳整体迁回当前仓库主路径。
3. 不处理单位重标定、主车视觉比例调整或硬件接线话题。
4. 不把主车控制链、视觉状态机或其它无关模块一起拉回 legacy。
5. 不把显式 `STOP`、`DISARM` 这类真停机语义弱化成只保头不停车。

## 为什么要单开新 spec

`2026-04-08-assistant-control-mode-consistency-design.md` 的主题是“控制模式持续性与一致性修复”。它回答的是：

1. 普通模式和速度模式如何持续。
2. 默认保头规则如何在模式层收口。
3. 模式状态如何避免后续周期退回错误路径。

而本轮要新增的内容已经变成另一件事：

1. 位置累计使用哪一个朝向时刻。
2. 三轮目标如何限幅才更接近 legacy。
3. 零周期时速度环采用什么拍长口径。
4. 保护状态如何在不放弃保头的前提下仍保持安全语义。

这部分不再属于原 spec 的自然延伸，因此必须单开新 spec。原 spec 继续保留为上一轮问题的完整记录。

## 现状与 legacy 的关键差异

### 差异一：里程累计使用的朝向时刻不同

legacy 的姿态与里程顺序是：

1. 先根据上一拍朝向解释当前轮速。
2. 用这个朝向把当前平移速度积分进世界系里程。
3. 再把这一拍的姿态更新结果写回当前朝向。

当前辅车最小系统在一段时间里使用的是“先更新当前朝向，再按更新后的朝向累计当前里程”的顺序。这样会改变位置累计和转向补偿之间的耦合表现，实车手感可能与 legacy 不同。

### 差异二：三轮输出限幅方式不同

legacy 的做法是：只要任一轮超过上限，就把三轮目标统一按同一比例缩小。

当前辅车最小系统曾采用逐轮各自硬截断的方式。这样虽然实现简单，但会破坏平移和保头之间原本的三轮配比，容易出现：

1. 大平移目标时保头被挤弱。
2. 轮间比例被截坏后，实车动作和 legacy 不一致。

### 差异三：零周期时速度环拍长口径不同

legacy 在固定控制节拍下工作。即使遇到首拍或特殊场景，本质上仍按固定控制拍长来理解速度环更新。

当前辅车最小系统在零周期场景里，一度会把速度环更新口径退化成与 legacy 不同的处理方式。这样会让首拍、保护态或时间戳异常时的输出与 legacy 偏离。

### 差异四：保护状态的保头语义需要在当前系统中明确补齐

legacy 基线里“超时停机”是稳定性要求的一部分，但当前用户的现场要求已经更明确：

1. 链路保护后可以停平移。
2. 但只要系统没有进入显式真停机，就仍要继续保持车头方向。

因此，本轮不会机械复制“超时后整车全零”这一种实现，而是保留当前用户认可的安全边界：保护时继续保头，显式真停机时彻底停机。

## 设计原则

### 原则一：优先对齐用户已经验证过的控制手感

只要当前最小系统与 legacy 在控制内核语义上存在差异，优先回到 legacy 口径，而不是继续保留“更简化但用户未验证”的做法。

### 原则二：只回退控制内核，不回退系统外壳

本轮只对齐控制数学、积分顺序和三轮配比，不回退：

1. 当前协议。
2. 当前 app 入口。
3. 当前测试与文件组织的主路径。

### 原则三：模式持续性修复必须保留

上一轮已经修好的以下能力不能丢：

1. 普通模式后续周期继续保持位置控制。
2. 速度模式后续周期继续保持速度目标。
3. 默认保头不是只在收包当拍生效。

legacy 对齐只能在这个基础上继续收口，不能把系统重新带回“只第一拍正确”的状态。

### 原则四：保护与停机要分层处理

本轮明确区分两类语义：

1. 保护态：停平移，继续保头。
2. 真停机：彻底停机，不再继续输出保头修正。

这条规则优先服从当前用户要求，而不是机械复制历史代码路径。

## 控制内核对齐设计

### 设计一：里程累计改为使用姿态更新前朝向

辅车每个控制周期内，里程累计改为按 legacy 口径解释：

1. 先记住本拍姿态更新前的朝向。
2. 再更新这一拍姿态估计。
3. 里程累计阶段使用“更新前朝向”把当前轮速解到世界系。

这样做的目的不是追求抽象上更漂亮，而是让位置累计与 legacy 的耦合关系保持一致，避免实车控制手感继续偏离用户熟悉的行为。

### 设计二：三轮目标改为统一按比例缩放

辅车底盘输出在进入速度环之前，统一采用 legacy 的三轮限幅口径：

1. 先根据平移和转向求出三轮目标。
2. 找出三轮中的最大绝对值。
3. 如果超过上限，则三轮一起按同一比例缩放。
4. 不再对每个轮子单独硬截断。

这样做的目标是保住平移和保头的配比关系，减少“大平移指令把保头截坏”的现象。

### 设计三：零周期速度环使用固定拍长回退

在首拍、零周期或时间戳暂时异常的情况下：

1. 保头输出仍允许继续进入控制链。
2. 但速度环内部拍长不再退化成与 legacy 不一致的特殊口径。
3. 速度环应显式回退到固定控制拍长，保持与 legacy 的节拍理解一致。

这样做可以同时满足两件事：

1. 不让保头链路被零周期直接断掉。
2. 不让速度环因为零周期而给出过大的假动作。

### 设计四：保护态保持零平移加保头输出

保护态下，辅车控制内核按以下规则执行：

1. 平移目标清零。
2. 朝向保持继续输出。
3. 状态标签仍保留保护态，便于对外观察。

这意味着保护态不是“整车彻底无输出”，而是“车辆不再推进，但继续尝试把车头拉回目标朝向”。

### 设计五：显式真停机保持彻底停机

以下场景仍维持真停机：

1. `STOP`
2. `DISARM`
3. 任何明确要求立刻撤销全部输出的停机路径

这些路径不会因为“保护态继续保头”而被弱化。

## 与旧 spec 的关系

旧 spec 继续负责以下内容：

1. 模式持续性。
2. 默认保头和显式角速度例外。
3. 普通模式与速度模式的周期分发。

新 spec 在此基础上补充以下内容：

1. 如何按 legacy 口径处理位置累计和朝向耦合。
2. 如何按 legacy 口径处理三轮限幅。
3. 如何按 legacy 口径处理零周期速度环节拍。
4. 如何把保护态和真停机分层。

两份 spec 的关系是串联，不是替换：

1. 旧 spec 不作废。
2. 新 spec 只描述后续新增的控制内核对齐单元。

## 测试与验收口径

### 自动化验证

本轮至少需要覆盖以下自动化行为：

1. 位置累计使用姿态更新前朝向时，结果符合 legacy 顺序。
2. 三轮目标超过上限时，三轮统一按比例缩放。
3. 零周期下速度环按固定控制拍长回退，而不是产生放大的假动作。
4. 保护态仍输出零平移加保头。
5. 显式真停机仍保持彻底停机。
6. 旧 spec 已经固定住的模式持续性测试仍全部通过。

### HIL 验收

本轮实车只回答以下问题：

1. 发过位置指令后，再手动转动车体，轮子是否仍持续保头。
2. 大平移指令下，保头手感是否更接近 legacy。
3. 保护态下车辆是否停止推进，但仍尝试拉回车头。
4. 显式停机后是否真正停住。

## 风险与控制

### 风险一：legacy 对齐打坏上一轮模式持续性修复

控制方式：

1. 新 spec 只允许修改控制内核差异点。
2. 模式持续性相关回归必须与本轮测试一起跑。

### 风险二：保护态继续保头与真停机边界混淆

控制方式：

1. 保护态和真停机必须分别有单独测试。
2. 任何显式停机路径不得被“继续保头”覆盖。

### 风险三：零周期回退口径继续偏离 legacy

控制方式：

1. 单独固定“零周期速度环使用固定控制拍长”的测试。
2. 不允许把零周期直接当成超大拍长或任意特殊值。

## 实施入口

本 spec 对应的实现只围绕以下最小内容展开：

1. 对齐里程累计与姿态更新顺序。
2. 对齐三轮统一按比例限幅。
3. 对齐零周期速度环拍长口径。
4. 固定保护态继续保头、真停机仍真停机的边界。

如果后续还要继续向 legacy 靠拢其它控制细节，应再开新的 spec，不在本文件上继续叠加新主题。
