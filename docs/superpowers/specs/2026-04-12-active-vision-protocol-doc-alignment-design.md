# 2026-04-12 当前视觉协议生效文档对齐设计

## 背景

当前代码对视觉协议的事实边界是明确的:

1. `src/services/vision_protocol.py` 将来自 `uart6` 的纯 `x=...,y=...` 文本解析为视觉观测。
2. `src/services/transport_car.py` 创建并消费 `uart6` 视觉输入。
3. 当前代码的正式输入模型不包含 `v/s` 字段、完整识别框字段、`camera_id/category` 或多检测结果语义。

当前生效文档中存在与上述事实不一致的口径:

1. 视觉输入按 `UART6/UART8` 双路持续回传描述。
2. 正式视觉输入按 `v=1,s=<seq>,x=<x>,y=<y>` 描述。
3. 正式协议正文包含识别框摘要、`camera_id/category` 或多检测结果语义。
4. 部分非归档设计 / 计划文档位于生效位置, 容易被读作当前有效方案。

本轮工作只处理文档口径对齐, 让所有生效文档与当前代码事实一致。

## 目标

1. 以当前仓库代码作为唯一事实源, 统一当前生效文档中的视觉协议口径。
2. 让规则入口正文与 `docs/developer/*` 对当前视觉协议的描述保持一致。
3. 让生效文档正文统一使用只描述当前事实的口吻。
4. 明确区分当前现状与后续规划。
5. 处理位于生效位置、但内容描述与当前代码不一致的非归档设计 / 计划文档。

## 非目标

1. 不修改任何运行时代码。
2. 不实现协议瘦身或协议重构。
3. 不改 `archive/`、memory 等记录文件。
4. 不改 `AGENTS.md`，相关调整由用户手动处理。
5. 生效文档正文不复述提交记录或沿革说明。
6. 不扩展到测试补全、视觉控制改造或双路输入实现。

## 当前事实源

本轮只以下列内容作为事实源:

1. `src/services/vision_protocol.py`
2. `src/services/transport_car.py`
3. 位于生效位置的规则入口正文与 `docs/developer/*`

归档设计、归档计划和 memory 只作为背景参考, 不覆盖当前代码事实。

## 设计决策

### 决策一: 当前视觉协议按“`uart6` 单向接收纯 `x,y` 文本”表述

所有生效文档统一按以下现状表述:

1. 视觉侧向主控侧单向发送观测信息。
2. 当前正式视觉输入按 `uart6` 理解。
3. 当前解析入口只把纯 `x=...,y=...` 两字段文本视为正式视觉观测。
4. 当前视觉协议表达的是观测, 不是动作命令。

若后续采用别的格式, 另开设计并同步实现。

### 决策二: 生效文档正文统一使用当前口吻

本轮改写后的生效文档正文统一采用以下写法:

1. 直接描述当前事实, 例如“视觉输入来自 `uart6`”“正式观测字段为 `x,y`”。
2. 避免使用依赖方案沿革才能理解的时态表达。
3. 文档正文不承担解释演化过程的职责, 变更过程由 `git log`、归档设计和记录文件承接。
4. 后续规划单独标记, 不混入当前现状正文。

### 决策三: 生效文档现状正文只包含当前代码事实

以下内容不写入当前生效文档的现状正文:

1. `UART6/UART8` 双路视觉输入现状描述。
2. `v=1,s=<seq>,x=<x>,y=<y>` 当前正式输入格式描述。
3. 完整识别框 `left/top/right/bottom` 当前正式输入描述。
4. `camera_id/category`、多检测结果或双摄仲裁当前正式主线描述。
5. `?vision` 返回识别框摘要字段的当前现状描述。

这些内容如需保留, 仅放入后续规划或归档资料, 不进入当前现状正文。

### 决策四: 硬件事实与运行时事实分开表达

本轮文档需要区分两类信息:

1. 板级或接线层面的硬件事实。
2. 当前代码使用的运行时链路。

如果某个串口或硬件链路在硬件上客观存在, 但当前代码未把它作为正式视觉协议主线使用, 文档可以保留“硬件预留 / 已确认存在”的事实, 但现状正文不写成当前运行时协议。

### 决策五: 生效文档与归档文档分开处理

本轮直接改写的, 只应是当前作为入口阅读的生效文档:

1. `.agents/skills/using-rules/references/openart-protocol.md`
2. `.agents/skills/using-rules/references/hardware-and-protocol.md`
3. `docs/developer/strategy.md`
4. `docs/developer/tasks.md`
5. `docs/developer/vision.md`
6. `docs/developer/control.md`

位于生效位置、但内容描述与当前代码不一致的文档, 转入归档目录。当前确定要处理的是:

1. `docs/superpowers/specs/2026-04-06-vision-minimal-text-protocol-design.md` -> `docs/superpowers/specs/archive/PR#25/2026-04-06-vision-minimal-text-protocol-design.md`
2. `docs/superpowers/plans/2026-04-06-vision-minimal-text-protocol-implementation-plan.md` -> `docs/superpowers/plans/archive/PR#25/2026-04-06-vision-minimal-text-protocol-implementation-plan.md`

`archive/` 与 memory 保持原样。

`AGENTS.md` 不在本轮改动范围内，由用户手动维护。

### 决策六: 开发文档显式区分现状与后续规划

本轮改写后, 开发文档需要满足两个要求:

1. 对当前代码事实, 直接写清楚。
2. 对双路输入、更丰富的协议或多检测等后续规划, 单独标记, 不混入当前有效口径。

这样后续阅读者可以先看到当前真实基线, 再决定是否开启下一轮协议改造。

## 验收标准

当满足以下条件时, 本轮文档对齐可视为完成:

1. 当前所有生效文档对视觉协议现状的描述一致。
2. 当前生效文档正文都使用直接描述当前事实的口吻。
3. 当前生效文档都不把 `UART8`、`v/s`、完整框、`camera_id/category`、多检测结果写成当前已落地事实。
4. 规则入口正文与 `docs/developer/*` 口径一致。
5. `docs/superpowers/` 下与当前代码不一致的非归档视觉协议设计 / 计划不位于生效位置。
6. `archive/` 与 memory 保持原样。
7. `AGENTS.md` 未被改动。

## 风险与控制

### 风险一: 把硬件事实和运行时事实一起删掉

控制方式:

1. 明确保留硬件存在事实。
2. 只删除把硬件存在性写成当前运行时协议的错误表述。

### 风险二: 只改了一部分文档, 仍留两套入口

控制方式:

1. 本轮按“规则入口 + 开发入口 + 非归档 superpowers 文档”三类一起清点。
2. 不接受只改协议正文、不改开发文档的半收口状态。

### 风险三: 文档正文继续带沿革式口吻

控制方式:

1. 生效文档正文统一改为静态、当前事实式表达。
2. 变更过程只留在提交记录、归档设计和记录文件中。

### 风险四: 后续规划与当前现状再次混写

控制方式:

1. 后续规划单独标记。
2. 当前现状正文只描述当前代码事实。
