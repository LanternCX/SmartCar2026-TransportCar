# 主辅包独立直烧运行补全规范

## 背景

当前仓库已经完成了一批重要收口工作：

1. `src/master` 与 `src/assistant` 目录边界已经分开。
2. 主辅两边已经没有直接跨包导入依赖。
3. 主机侧测试已经覆盖了入口导入、协议、主车视觉决策、辅车执行与部分底盘基础能力。

但重新核查后，可以明确确认：

**当前代码仍然不能被定义为“主车包与辅车包都可以直接作为根目录上传到板端后形成完整可运行系统”。**

原因不是业务目标错误，而是运行收口还差最后一层：

1. `main.py` 当前仍然只是“返回运行对象或脚本标记”，没有真正进入持续主循环。
2. 辅车入口当前把完整硬件装配裁成了最小子集，导致运行时边界不再等同于一个完整底盘系统。
3. 现有上传配置和 smoke 口径仍然主要围绕主车目录，没有形成“主车独立直烧 + 辅车独立直烧 + 双边联合链路”这三层统一收口。

因此，本规范的目标不再是继续讨论业务主线，而是专门补齐：

**如何把 `src/master` 与 `src/assistant` 真正收口成两个互不依赖、可分别直烧、上电即进入持续运行、并且组合后形成完整链路的板端运行包。**

## 当前确认的问题

### 一、入口不是完整运行入口

当前 `main.py` 的问题不是不能导入，而是：

1. 它会返回 `RuntimeLoop` 对象。
2. 但模块执行时没有自动进入持续循环。
3. 因此“运行 `main.py` 不报错”不等于“上板后系统会自己持续运行”。

本轮必须明确撤销以下误判：

1. “能创建运行对象”就等于“完整可运行”。
2. “主机侧入口测试能通过”就等于“板端入口已收口完成”。

### 二、辅车当前不是完整底盘运行包

当前辅车入口存在结构性缺口：

1. `build_hw_bundle()` 已经能构造完整的 `uart`、`motors`、`encoders`、`imu`。
2. 但 `main.py` 又把它裁成只剩 `uart3` 和 `motors`。
3. 之后这个裁剪包还会覆盖进运行时 owner。

这意味着当前辅车更像“最小协议执行壳”，而不是“完整底盘运行包”。

本轮必须修正为：

1. 辅车运行时 owner 拿到的必须是完整硬件装配包。
2. 不允许入口层为了当前最小链路方便，再把完整运行时边界偷偷裁回半套系统。

### 三、独立直烧口径没有真正闭合

当前虽然已有“主车根目录导入可用”“辅车根目录导入可用”的主机侧测试，但还没有形成以下统一口径：

1. 主车可作为根目录独立上传。
2. 辅车可作为根目录独立上传。
3. 两边都以上电即运行的方式进入持续主循环。
4. 两边组合后，形成“视觉输入 -> 主车决策 -> UART3 下发 -> 辅车执行 -> 最小状态回传”的完整链路。

也就是说，当前完成的是“独立导入边界”，还不是“独立运行边界”。

## 目标

本轮必须同时达成以下目标：

1. `src/master` 可以单独作为板端根目录上传并上电运行。
2. `src/assistant` 可以单独作为板端根目录上传并上电运行。
3. 两边都不再依赖对方目录中的任何代码、入口或共享运行时包。
4. 主车与辅车的 `main.py` 都是“上电即运行”的真实入口，而不是只返回运行对象。
5. 主车运行包保持当前业务主线：主车自身不主动运动，只持续接收摄像头消息并向辅车下发二维控制。
6. 主辅车底盘在正常运行分支上电后，都必须自动进入自身航向角保持状态，不能依赖外部再发一条“开启方向保持”命令。
7. 辅车运行包保持完整底盘执行边界：接收控制、维持方向闭环、执行二维随动、状态回传、超时停机。
8. 主车独立运行、辅车独立运行、主辅联合运行，这三层都要有清晰的验证和留证口径。

## 非目标

本轮仍然不做以下内容：

1. 不恢复主车当前阶段的主动运动业务。
2. 不扩展灰度链路。
3. 不把这轮补全变成新一轮大规模架构重写。
4. 不因为要补持续主循环，就重新引入统一角色运行时或跨包共享运行时。

## 核心结论

### 一、`main.py` 必须是上电即运行入口

从本轮开始，`main.py` 的定义必须收紧为：

1. 负责按钮长按脚本分发。
2. 在正常运行分支中，装配运行时对象。
3. 立即进入持续主循环。
4. 不再把“持续运行”这个动作留给外部调用方假定完成。

也就是说，`main.py` 的“返回运行对象”只能作为主机侧测试辅助能力存在，不能再作为板端入口的最终语义。

### 二、主辅两边都必须完整自足

“完整自足”在本轮有严格含义：

1. 主车包内部拥有主车所需全部运行代码。
2. 辅车包内部拥有辅车所需全部运行代码。
3. 两边不跨包 import。
4. 两边入口都能只以当前目录为根运行。
5. 两边运行时 owner 拿到的都是各自完整硬件与运行时边界，而不是半套临时壳。

### 三、独立运行与链路闭合必须分成三层验证

后续评审和验证必须分成以下三层，不能再混成一句“应该可以跑”：

1. **主车独立层**：主车单独上传后，上电进入持续运行，持续接收 `UART6/UART8`，并能在无辅车时维持自身主循环稳定。
2. **辅车独立层**：辅车单独上传后，上电进入持续运行，持续监听 `UART3`，并能对最小查询、超时和控制命令做出符合预期的响应，同时默认维持自身航向角保持状态。
3. **联合链路层**：两边同时运行后，主车持续读取摄像头消息、主车控制输出、辅车执行与最小状态回传组成完整链路，且辅车在执行随动时仍维持航向角保持。

只有三层都满足，才允许说“主辅包作为两个独立包且组合后形成完整系统”。

## 必须补齐的实现约束

### 一、入口约束

1. `boot.py` 继续不存在。
2. `main.py` 是唯一公开入口。
3. `main.py` 正常运行分支必须进入持续循环。
4. 持续循环不得依赖板外再包一层 while。
5. 正常运行分支上电后必须默认建立底盘航向角保持，不允许等外部命令再打开。

### 二、装配约束

1. 主车运行时 owner 必须持有主车完整硬件装配。
2. 辅车运行时 owner 必须持有辅车完整硬件装配。
3. 禁止入口层把完整硬件包裁成“只够当前一条测试路径工作”的最小壳后再写回 owner。

### 三、独立包约束

1. 主车包内不得依赖辅车包。
2. 辅车包内不得依赖主车包。
3. 上传工具或 smoke 工具不得只默认主车路径而忽略辅车路径。
4. 若工具默认路径只能覆盖一边，则不能再宣称“双边独立直烧口径已完成”。

## 验收口径

### 一、代码层面必须同时满足

1. 主车 `main.py` 作为脚本执行时，正常运行分支会进入持续主循环。
2. 辅车 `main.py` 作为脚本执行时，正常运行分支会进入持续主循环。
3. 辅车运行时拿到的是完整硬件装配，不缺 IMU / 编码器边界。
4. 主辅之间不存在跨包导入依赖。
5. 主辅车底盘在正常运行分支上电后默认进入航向角保持。
6. 主车正常运行分支会持续读取摄像头消息并向辅车下发控制，而不是只停留在对象构造或空循环。

### 二、验证层必须分别给出

1. 主机侧：入口、独立导入、循环装配、协议和运行时测试。
2. Stage 2：主车独立上传 smoke、辅车独立上传 smoke。
3. Stage 3 / HIL：联合链路观察与动作现象留证，包括“主车读摄像头并控制辅车”“主辅默认航向保持”两类现象。

### 三、以下情况一律不得判定通过

1. 只能证明“main.py 可以导入或退出不报错”。
2. 只能证明“主车路径可上传”，不能证明辅车路径也可独立上传。
3. 只能证明“对象能创建”，不能证明主循环会持续运行。
4. 只能证明“某条最小命令路径可通”，但辅车底盘运行边界仍是半套装配。
5. 上电后底盘不会自动进入航向角保持，只能等外部再发使能命令。
6. 主车没有在正常运行分支中持续读取摄像头消息并控制辅车。

## 后续实现顺序

后续补全应按以下顺序推进：

1. 先把“返回运行对象”补成“真实持续主循环入口”。
2. 先修辅车入口装配裁剪问题，恢复完整运行时边界。
3. 再补主车独立上传与辅车独立上传的工具和 smoke 口径。
4. 最后再补联合链路留证。

## 总结

当前仓库已经接近“两个独立包”的形态，但还没有到“两个独立完整系统”的程度。缺的不是新的业务目标，而是最后一层运行收口：真实主循环入口、完整运行时装配、双边独立上传口径，以及把“独立导入”升级为“独立运行 + 联合闭合”的统一验收方式。本规范就是为这最后一层补全提供新的唯一口径。
