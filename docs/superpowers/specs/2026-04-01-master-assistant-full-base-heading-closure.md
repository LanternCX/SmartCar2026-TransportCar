# 主辅包完整底座航向角闭环补全规范

## 背景

当前仓库已经完成了一批重要但不等于“完整可跑”的收口工作：

1. `src/master` 与 `src/assistant` 目录已经拆开。
2. 主辅入口已经从“只构造对象”收紧到“正常分支进入持续主循环”。
3. 主机侧测试、协议测试和部分 smoke 工具已经补齐。
4. 一批明显的板端启动问题已经被修掉。

但这几轮实现暴露出一个根本偏差：

**仓库一直在完成“接近完整可跑”的前置层，却没有把“主辅两包可以直接烧录到 RT1021 根目录，并依靠完整底座数据链维持各自航向角闭环运行”当成唯一硬门槛。**

结果就是：

1. 主机侧测试能通过。
2. 入口持续循环能成立。
3. 串口最小链路能走通。
4. 但真正决定系统是否完整可跑的底座主链还没有收口完成。

本规范就是为了解决这个偏差：

**从现在开始，本轮目标不再是“最小运行壳”或“接近完整”，而是“主辅两包直接烧录 + 完整底座航向角闭环 + 主辅联合链路真实闭合”。**

## 当前确认的问题

### 一、根目录直烧语义还没有真正完成

当前主辅主线虽然已经拆成两个包，但前几轮实现与测试仍然混入了“包路径导入是否成立”“主机侧入口是否成立”这类中间目标。

用户已明确要求：

1. 主线运行时代码不保留 import fallback。
2. `master` 和 `assistant` 都必须以最终部署形态存在。
3. 能否直烧到 RT1021 根目录并启动，必须成为真实验收项，而不是主机侧推定项。

这意味着后续实现不能再围绕“兼容多种入口形态”展开，而必须围绕“最终板端形态”展开。

### 二、完整底座数据链还没有真正接回主线

当前最严重的问题不在入口，而在底座主链：

1. 参数已经部分迁入新主线。
2. 部分硬件边界对象已经存在。
3. 但 IMU、编码器、里程、航向角闭环并没有作为一整套稳定数据链在主辅两边真正收口。

也就是说，当前主线仍更接近：

1. 主车：持续收视觉并发串口命令的运行壳。
2. 辅车：接收串口命令并做最小执行的运行壳。

而不是：

1. 主车：具备完整底座航向角闭环与自身底座基础能力的主车运行包。
2. 辅车：具备完整底座航向角闭环、执行随动与状态回传的辅车运行包。

### 三、TDD 边界没有被写清，导致实现被“测试通过感”带偏

前几轮的另一个根因是：

1. 本来应该依靠板上验证判定的内容，被主机侧测试“近似完成”了。
2. 本来适合 TDD 的纯逻辑部分，又没有被单独定义成硬门槛。

这样会导致一个明显风险：

**Agent 会自然向“最容易拿到绿色测试”的方向优化，而不是向“最终板上完整闭环”方向优化。**

本轮必须明确拆开：

1. 哪些内容必须做 TDD。
2. 哪些内容不以 TDD 作为完成判据，但必须实现，并且必须做板上验证。

## 目标

本轮必须同时达成以下目标：

1. `src/master` 可以直接作为 RT1021 根目录烧录并启动。
2. `src/assistant` 可以直接作为 RT1021 根目录烧录并启动。
3. 主车与辅车都具备完整底座航向角闭环，而不是只有参数或壳对象。
4. 主车与辅车都必须接回完整底座主数据链：`IMU + 编码器 + 里程 + 航向角闭环`。
5. 主车继续保持当前业务边界：主车自身不主动运动，但必须保留完整底座基础能力，并持续读取视觉输入、向辅车下发控制。
6. 辅车继续保持当前业务边界：接收主车控制、执行随动、维持自身航向角闭环、状态回传、超时停机。
7. 主辅联合运行时，主车视觉输入、主车串口下发、辅车响应执行、两车各自航向角保持必须组成真实闭环。
8. 评审与验收必须把 TDD 范围和板上验证范围严格拆开，不再允许混淆。

## 非目标

本轮仍然不做以下内容：

1. 不恢复主车当前阶段的主动运动业务。
2. 不扩展灰度链路。
3. 不引入新的统一角色运行时。
4. 不为了兼容旧形态继续保留 import fallback、部署回退或运行时双轨。
5. 不把“主机侧测试通过”包装成“板上完整可跑”。

## 核心结论

### 一、完整底座航向角闭环是这轮唯一真实收口目标

从本轮开始，底座收口的定义必须统一为：

1. IMU 真读数进入主线运行时。
2. 编码器真读数进入主线运行时。
3. 里程积分在主线运行时内真实更新。
4. 航向角估计与航向角目标在主线运行时内形成闭环。
5. 上电进入正常运行分支后，不依赖额外外部命令，即默认维持自身航向角。

如果以上 5 条有任一条没有实现，就不得说“完整底座航向角闭环已完成”。

### 二、主车和辅车都必须维持自身航向角，不允许只靠辅车补齐

用户已经明确确认：

1. 主车和辅车都要维持自身姿态。
2. 这不是只有辅车才需要的能力。
3. 这也不是“之后再补”的增强项。

因此本轮不能再把主车写成“只收视觉、只发串口、不接完整底座主链”的弱壳。

当前业务上主车不主动运动，只表示：

1. 本轮业务验收不要求主车主动行驶。
2. 不表示主车可以缺失完整底座主链。

### 三、legacy 只作为底座主数据链参考，不再作为结构兼容目标

用户已经指定：

1. 数据接入要参考 legacy。
2. 但目标不是把 legacy 整体复制回来。

本轮应参考 legacy 的部分是：

1. IMU 读数和零偏接入方式。
2. 编码器接入与轮速估计链路。
3. 里程积分与姿态估计主链。
4. 航向角闭环所需的控制参数与运行顺序。

本轮不要求保留 legacy 的：

1. 目录结构。
2. 类分层。
3. 统一角色运行时。
4. 历史兼容壳。

## TDD 与板上验证边界

### 一、必须做 TDD 的内容

以下内容必须作为主机侧失败测试先行的硬门槛：

1. 根目录直烧所要求的包路径与入口装配规则。
2. legacy 参数到主线参数的映射规则。
3. 协议编解码和状态回包格式。
4. 视觉输入到控制目标的纯逻辑变换。
5. 辅车控制输入到执行目标的纯逻辑变换。
6. IMU / 编码器读数进入主线后的纯计算逻辑。
7. 里程积分与航向角闭环的纯算法部分。
8. owner 唯一性、装配边界、超时与停机语义。

这些内容如果不先做 TDD，就很容易在主线里反复漂移。

### 二、不以 TDD 作为完成判据，但必须实现并上板验证的内容

以下内容不能仅凭主机侧测试判定完成：

1. RT1021 根目录直烧后真实启动。
2. IMU 实际姿态读数是否正常。
3. 编码器实际计数是否正常。
4. 里程在板上真实更新是否正常。
5. 两车上电后是否真的默认维持自身航向角。
6. 主车是否真的持续接收视觉串口数据。
7. 辅车是否真的持续接收主车控制并执行随动。
8. 电机实际输出方向、响应与稳定性。
9. 主辅联合链路在真板上的完整闭环。

这些内容必须实现，但完成判据必须以板上验证和留证为准。

### 三、实现优先级必须先做这一层

本轮实现顺序必须明确规定为：

1. **先实现本节这类“不以 TDD 作为完成判据”的板端主链内容。**
2. 这些内容的目标是先把真实系统做出来，而不是先把主机侧测试做绿。
3. 在这一步完成前，不允许因为测试设计方便，就把实现改造成更容易测试但偏离真实板端形态的结构。

这样做的原因不是否定 TDD，而是避免实现过程被“自己设计的测试奖励”带偏，误把“容易测通”当成“真实完整闭环已完成”。

### 四、以下情况一律不得再作为“接近完成”的证明

1. 主机侧测试通过。
2. 入口能持续循环。
3. 协议最小链路可通。
4. 参数已经迁入新文件。
5. 底座边界对象已经存在。

以上都只能算前置条件，不能替代完整底座航向角闭环完成。

## 必须补齐的实现约束

### 一、包路径与入口约束

1. `src/master` 与 `src/assistant` 都必须以最终板端根目录形态存在。
2. 主线运行时代码不保留 import fallback。
3. `main.py` 是唯一公开入口。
4. `main.py` 正常运行分支必须直接进入持续主循环。
5. 根目录直烧后的启动成功，必须以真实板端路径为准，不再以主机侧兼容形态推定。

### 二、底座数据链约束

1. 主车和辅车都必须持有各自完整硬件装配。
2. IMU 必须进入主线运行时真实参与姿态估计。
3. 编码器必须进入主线运行时真实参与速度与里程计算。
4. 里程必须在主线运行时真实更新。
5. 航向角闭环必须在主线运行时真实闭合。
6. 不允许把“默认航向角保持”写成仅参数存在或仅接口存在。

### 三、主辅联合链路约束

1. 主车持续读取视觉串口输入。
2. 主车持续向辅车下发控制。
3. 辅车持续接收并执行控制。
4. 两车在联合运行时都维持自身航向角。
5. 辅车状态回包要能反映关键闭环状态，至少应包含足以判断航向与底座状态是否正常的字段。

## 验收口径

### 一、代码层面必须同时满足

1. 主车和辅车都能以 RT1021 根目录形态启动。
2. 主线代码中不存在部署回退或 import fallback。
3. 主辅两边都具备完整底座航向角闭环数据链。
4. 主车视觉输入到辅车控制输出的纯逻辑链有主机侧测试保护。
5. 辅车控制输入到执行目标的纯逻辑链有主机侧测试保护。

### 二、板端层面必须分别给出

1. 主车独立层：可烧录、可启动、可维持主循环、可读取 IMU / 编码器 / 底座状态、默认维持自身航向角。
2. 辅车独立层：可烧录、可启动、可接收控制、可读取 IMU / 编码器 / 底座状态、默认维持自身航向角。
3. 联合链路层：主车读视觉、主车发控制、辅车执行随动、两车各自维持航向角。

### 三、以下情况一律不得判定通过

1. 只能证明“能启动”，不能证明“底座主链已闭合”。
2. 只能证明“有姿态参数”，不能证明“姿态闭环已真实运行”。
3. 只能证明“有码盘或 IMU 对象”，不能证明“真值已进入主线控制链”。
4. 只能证明“主车发了命令”，不能证明“辅车执行且两车姿态稳定”。
5. 只凭主机侧测试绿色，就宣称板端完整系统已完成。

## 后续实现顺序

1. 先收口 `master` / `assistant` 的根目录直烧包路径。
2. 再按 legacy 接回主辅两边的底座主数据链：IMU、编码器、里程、航向角闭环。
3. 再把主车视觉输入与辅车随动重新挂到完整底座主链上。
4. 在以上真实板端主链落地后，再补适合 TDD 的纯逻辑测试保护。
5. 最后按“主车独立 / 辅车独立 / 联合链路”三层做板端验证与留证。

## 总结

这轮之后，仓库不能再以“接近完整可跑”的口径推进，而必须以“可直烧根目录 + 完整底座航向角闭环 + 主辅联合真实闭合”作为唯一目标。TDD 只负责纯逻辑和可确定性边界，不再替代板端完整系统验收；板上验证也不再被推迟为“后续再看”的附属事项，而是这轮收口定义的一部分。
