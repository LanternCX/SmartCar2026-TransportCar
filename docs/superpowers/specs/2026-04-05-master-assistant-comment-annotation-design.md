# 主辅车目录注释补全设计

## 背景

当前仓库已经明确将 `src/legacy/` 冻结为参考代码, 现行主线收口在 `src/master/` 与 `src/assistant/` 两个目录。最近几轮重构与联调已经把主辅双车的职责边界、运行时骨架和底盘链路逐步稳定下来, 但代码注释密度仍然跟不上结构演进速度。

从当前文件现状看, 两个目录里虽然已经存在少量文件头注释和方法说明, 但仍有几个明显问题:

1. 很多文件打开后仍然无法在第一眼说明“这个文件在整条主辅链路中负责什么”。
2. 很多方法只有名称, 没有把它在设计上承担的责任、输入输出和边界说清楚。
3. `motion_runtime.py`、`app.py`、`main.py` 这类长文件里, 关键流程虽然已经成型, 但过程注释不足, review 时仍需要靠反复顺着代码跳读才能恢复链路结构。
4. `script/` 与参数文本文件仍缺乏“为什么存在、服务哪条链路、改动会影响什么”的统一说明。

用户这次的目标不是补成“逐行翻译代码”的注释, 而是让参与过设计的人在 review 代码时, 能从第一性原理快速恢复当前实现结构, 看懂每块代码为什么这样分、每个文件和方法在整体链路里承担什么作用。

## 目标

本轮设计需要同时满足以下目标:

1. 覆盖 `src/master/` 与 `src/assistant/` 目录下除 `test/` 以外的全部目标文件。
2. 让每个文件都能在文件头直接说明自身职责、所处层次和对整条链路的意义。
3. 让每个方法都能快速看出其设计目的、输入输出语义和与上下游的协作关系。
4. 对关键长流程补齐阶段性注释, 让 review 时能先抓住骨架, 再决定是否下钻到实现细节。
5. 严格遵守仓库现有注释规范: 中文、Doxygen 风格、注释贴近对象、重点解释职责与原因, 不写聊天式和机械复述式注释。

## 非目标

本轮明确不做以下事情:

1. 不处理 `src/legacy/`。
2. 不处理 `src/master/test/` 与 `src/assistant/test/`。
3. 不为了补注释去改写业务逻辑、控制策略或协议语义。
4. 不把简单直接、从命名即可看懂的代码重复翻译成注释。
5. 不追求“每一行都有注释”, 只追求“review 结构和设计时没有理解断点”。

## 设计原则

### 一、注释服务于结构 review, 不是服务于代码朗读

本轮注释的核心价值, 是帮助已经参与过整体设计的人快速恢复实现结构, 因此注释应优先回答下面几类问题:

1. 这个文件在当前主辅双车链路里负责哪一层。
2. 这个方法为什么单独存在, 它承担哪一段设计责任。
3. 这个长流程是如何分阶段推进的, 每一阶段承接了什么输入并产出了什么结果。
4. 这个状态字段、参数文件或硬件装配点为什么被放在这里。

相反, 下列内容默认不写:

1. 代码表面已经直接表达出的简单动作。
2. 与理解整体结构无关的琐碎分支细节。
3. 机械复述变量名、函数名或条件判断结果的注释。

### 二、注释密度按“理解成本”分配, 不是按“代码行数”平均分配

不同文件和方法的理解成本不同, 本轮不按“每个函数都写一样多”处理, 而按以下原则分配注释密度:

1. 入口文件、装配文件、运行时主链文件的注释密度最高, 因为它们决定整体链路是否易懂。
2. 控制、状态、协议和硬件子模块优先讲职责边界与协作方式。
3. 简短适配层或显而易见的工具函数, 只补最少但必要的说明。
4. 长方法只对关键阶段分段, 不把注释写成流水账。

### 三、主车和辅车对齐表达方式, 便于横向 review

`master` 与 `assistant` 在目录结构上高度相似, 但承担职责不同。本轮注释会统一使用同一套表达框架:

1. 同层文件尽量用一致的职责描述方式。
2. 相似方法尽量用一致的注释颗粒度。
3. 对差异点明确写出“这一块为什么与另一侧不同”, 避免 review 时误把职责差异当成遗漏。

这样用户在横向对照主车与辅车实现时, 可以更快看清哪些是故意不同, 哪些只是分层不同。

## 注释分层设计

### 一、文件头注释

每个目标文件都补文件头说明, 统一回答三个问题:

1. 这个文件负责哪一层职责。
2. 它在当前主辅链路中的上下游是谁。
3. 它对外暴露什么能力或装配入口。

文件头注释不追求写成长文, 但必须能让人打开文件时立即建立定位。

### 二、类与状态结构注释

对于类、状态容器和关键结构体, 注释重点是说明“为什么这份状态或职责要集中放在这里”。主要包括:

1. 这个类对外承担什么稳定责任。
2. 它持有的是长期状态、过程状态, 还是单次装配关系。
3. 它和同文件或邻接模块的边界如何切分。

对字段本身, 仍按仓库规则给变量和常量补显式说明, 但说明长度按理解成本控制: 简单对象使用贴身短注释标明角色、来源或用途, 复杂状态再补充边界与原因, 不把所有简单字段扩写成大段说明。

### 三、方法注释

方法注释以 Doxygen 风格为主, 但重点聚焦设计语义而不是实现朗读。对外方法、关键流程方法和理解成本高的方法必须补完整说明; 明显直白的小工具函数仅在确有必要时补最短说明, 避免把注释做成函数名复述。方法注释优先说明:

1. 这个方法在当前链路中的阶段职责。
2. 它接收什么类型的信息, 返回什么类型的结果。
3. 它是否会推进长期状态、依赖硬件装配或触发对外输出。
4. 它为什么值得独立成一个方法。

对于明显的私有小工具函数, 可以缩短说明, 但仍要让人知道其存在价值。

### 四、复杂流程的分段注释

对 `main.py`、`app.py`、`motion_runtime.py`、协议解析与状态组织等长流程, 会在方法内部加入少量分段注释。分段注释只做以下事情:

1. 标出关键阶段切换。
2. 说明本阶段的输入来源与阶段目的。
3. 说明这一段为什么必须在当前顺序执行。

不会给简单循环、单步赋值和直接判断单独加注释, 以免淹没真正重要的流程骨架。

### 五、参数文本与脚本说明

对于 `gyro_offset.txt`、`ident_params.txt` 以及 `script/` 下脚本, 重点说明:

1. 它们各自服务于哪条控制或调试链路。
2. 为什么独立成文件或脚本, 而不是并入运行时。
3. 改动它们会影响哪类行为或校准结果。

参数文本文件的完成形态统一为“文件用途说明 + 邻近读取逻辑说明”: 若文件本身适合承载说明, 就在文件内补最小必要说明; 若文件形态不适合直接写注释, 就在读取和使用它的代码旁说明文件用途、读取时机与影响范围。同类参数文件保持同一口径, 不把它们扩写成操作文档。

## 执行范围

### 一、包含范围

本轮包含以下范围:

1. `src/master/` 下除 `test/` 与 `__pycache__/` 外的全部目标文件。
2. `src/assistant/` 下除 `test/` 与 `__pycache__/` 外的全部目标文件。
3. 两个目录下的 `script/`、`ctrl/`、`hw/`、`state/`、`vision/` 等子目录源码文件。
4. 两个目录下与当前链路直接相关的参数文本文件。

### 二、排除范围

本轮明确排除:

1. `src/legacy/`。
2. `src/master/test/`。
3. `src/assistant/test/`。
4. 任意 `__pycache__/`。

## 执行顺序

为保持整套注释口径统一, 执行顺序固定如下:

1. 先补 `main.py`、`app.py` 这类入口与总装配文件, 先把主链骨架讲清楚。
2. 再补 `motion_runtime.py`、`protocol.py`、`status.py`、`safety.py` 等运行时主链文件, 收口“输入如何进入、状态如何推进、结果如何输出”的流程骨架。
3. 再补 `ctrl/`、`hw/`、`state/`、`vision/` 等子目录文件, 重点讲清子模块职责和边界。
4. 最后补 `script/` 和参数文本相关说明, 说明它们与主链的关系和使用场景。

这个顺序的目的, 是保证就算中途抽样 review, 也能先看到完整骨架, 再看到细部说明, 不会出现外围注释很完整但主链仍难以理解的情况。

## 验收标准

本轮完成后, 至少应满足以下标准:

1. 打开任意目标文件, 文件头就能说明它在主辅双车链路中的定位。
2. 查看任意方法时, 可以快速知道它承担的设计责任, 而不必先通读完整实现才能建立定位。
3. 对关键长流程文件, review 时可以依靠注释先恢复流程骨架, 再决定是否深入细节。
4. 源码文件的文档注释统一为中文和 Doxygen 风格; 脚本与参数文本文件按本设计约定的形态补说明, 但同样遵守中文、解释职责与原因、不做机械复述的规则。
5. `master` 与 `assistant` 相似结构的注释表达基本对齐, 便于横向对照。
6. 变量和常量的显式说明满足仓库规则, 但简单对象保持短注释, 不被扩写成无信息增量的说明。
7. 脚本与参数文本文件的说明口径保持一致: 脚本以文件头和关键入口说明为主, 参数文本文件以文件用途说明与邻近读取说明为主。

## 风险与控制

### 一、风险: 注释过量, 反而稀释主链信息

控制方式:

1. 只对复杂流程写分段注释。
2. 简单逻辑不重复翻译。
3. 优先保留帮助结构理解的信息, 删除机械说明。

### 二、风险: 两侧相似文件注释风格不一致

控制方式:

1. 同层文件采用统一表达模板。
2. 先补骨架文件, 再横向回看主辅是否对齐。
3. 对确有职责差异的文件, 明确说明差异原因。

### 三、风险: 补注释时无意带入旧系统口径

控制方式:

1. 始终以 `master` / `assistant` 现行主线为准。
2. 不把 `legacy` 作为当前职责说明的一部分。
3. 若需要提及历史背景, 只用于说明现行边界为何存在, 不把旧路径写成当前依赖。
