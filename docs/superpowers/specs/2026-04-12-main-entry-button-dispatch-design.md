# 2026-04-12 `main.py` 单入口与按钮脚本分发设计

## 背景

当前仓库已经回到单一 `src/` 基线, 入口仍然停留在旧的 `boot.py` 分发方式。现有 `boot.py` 通过 `D8` 判断是否切换脚本, 但当前项目又需要继续使用 `D8/D9` 做车号识别, 两者在语义上已经冲突。

用户要求本轮只做入口层重构, 不扩大到运行时结构、控制链路或通信链路。目标是把入口从 `boot.py` 收口到 `main.py`, 并把脚本切换迁移到按钮长按方式, 同时尽量对齐之前 3.0 方向里已经确认的入口写法。

对 `seekfree_demo/v3.0.0/` 的核对结论是: 本轮不需要顺手重写 IMU、编码器或其他底层读写链。`v3.0.0` 在这些设备上的核心语义仍然是 `ticker.capture_list(...)` 触发采样, 与当前仓库关注的这层入口改造并不冲突。本轮真正需要对齐的是入口组织、按钮判定方式和板端可落地的启动写法。

## 目标

1. 将当前正式入口从 `src/boot.py` 切换为 `src/main.py`。
2. 用按钮长按替代拨码开关脚本分发, 避免与 `D8/D9` 车号识别语义冲突。
3. 保持当前三类脚本职责不变: 参数辨识、零漂校准、正常运行。
4. 只改入口层和与其直接相关的最小测试、文档边界, 不顺手扩大改动面。

## 非目标

1. 不重排当前 `src/` 的单目录结构。
2. 不切回 `master / assistant` 双目录结构。
3. 不改写 `TransportCar`、控制算法、通信协议、视觉链路或传感器驱动。
4. 不在本轮补齐“整个仓库”的测试体系, 只补入口层必须的约束测试。
5. 不把现有 `script/` 脚本整体重写成新的运行时接口。

## 已确认事实

1. 板级按钮 1-4 对应 `C8`、`C9`、`C14`、`C15`。
2. `D8/D9` 当前需要继续承担车号识别语义, 不应再兼任脚本入口选择。
3. 用户确认本轮的脚本分发规则为:
   - 长按 `C8` 进入 `pid_identify`
   - 长按 `C9` 进入 `calibrate_gyro`
   - 不长按进入 `remote_control`
4. 用户确认长按判定应按 `v3.0` demo 的 `KEY_HANDLER` 语义实现, 而不是仅做一个固定上电窗口内的电平读取。
5. 当前 `src/script/remote_control.py`、`src/script/pid_identify.py`、`src/script/calibrate_gyro.py` 都仍然是脚本式文件, 没有统一的函数入口。

## 设计决策

### 决策一: 正式入口收口到 `src/main.py`

本轮新增 `src/main.py` 作为唯一正式启动入口, 并删除当前 `src/boot.py`。这样可以把当前仓库的启动语义和用户确认的下一阶段方向对齐, 避免继续保留一个已经承载错误职责的旧入口。

`main.py` 只承担三件事:

1. 完成最小启动等待。
2. 读取按钮长按状态并决定进入哪个脚本。
3. 按当前脚本路径把控制权转交给已有脚本。

它不负责重写业务初始化, 也不负责在这一轮里吸收下层运行时逻辑。

### 决策二: 用 `KEY_HANDLER` 完成入口阶段的长按判定

本轮入口的“长按”语义直接对齐 `seekfree_demo/v3.0.0/` 的 `KEY_HANDLER` 用法。`main.py` 在启动早期临时创建一个最小按键扫描链路, 通过短生命周期的 `ticker + KEY_HANDLER` 完成长按判断, 判定结束后立即停止这条链路, 再跳转到目标脚本。

这样做有三个目的:

1. 与用户要求的旧 3.0 写法保持一致。
2. 不再把“按钮长按”偷换成简单电平判断。
3. 把按键扫描影响严格限制在入口阶段, 不侵入当前正常运行脚本自己的控制循环。

本轮不把 `KEY_HANDLER` 常驻进运行时主链, 只把它作为入口期的一次性判定工具。

### 决策三: 保留当前脚本文件边界, 只改分发方式

由于当前三个脚本仍然是脚本式文件, 本轮不额外把它们重写成统一的 `main()` 形式。`main.py` 只复用现有 `script/` 路径去执行已有脚本, 让“入口方式改变”和“脚本内部逻辑改变”保持分离。

这条决策的价值在于:

1. 避免本轮因为入口改造而顺手改动三份脚本主体。
2. 把风险集中在入口层, 方便定位问题。
3. 保持当前正常运行链路的行为尽量不变。

### 决策四: 明确异常启动分支

当 `C8` 与 `C9` 同时被判定为长按时, `main.py` 不进入任一正常脚本, 而是直接进入异常启动分支。异常分支只负责输出明确提示并停止继续分发, 避免把两个维护入口叠加成不清晰的行为。

### 决策五: 文档与测试只同步这一轮的最小事实

本轮只同步三类约束:

1. 正式入口已经从 `boot.py` 改为 `main.py`。
2. 脚本分发改由 `C8/C9` 长按承担。
3. `D8/D9` 不再承担脚本分发职责。

测试层只围绕入口边界补最小保护网, 不提前为未来更大规模的测试体系扩建。重点是锁住“入口文件名”“脚本映射规则”“不要再把 `D8/D9` 拉回脚本分发”这几件事。

## 测试与验证策略

### 主机侧自动测试

本轮新增或改写的主机侧测试只覆盖入口层:

1. `src/main.py` 存在, `src/boot.py` 不再作为正式入口存在。
2. 入口层的按钮到脚本映射符合当前确认规则。
3. 入口层不再依赖 `D8/D9` 进行脚本分发。
4. 入口层采用 `KEY_HANDLER` 作为长按判定来源。

这些测试的作用是把本轮边界钉死, 不是一次性补完整仓库测试体系。

### 板端确认

由于本轮改动真实触及板端入口, 实现后仍需要保留板端确认记录。最小确认项包括:

1. 上电后默认分支能进入正常运行脚本。
2. 长按 `C8` 能进入参数辨识脚本。
3. 长按 `C9` 能进入零漂校准脚本。
4. `D8/D9` 车号识别链路没有因为入口切换被误伤。
5. 同时长按 `C8/C9` 不会误进正常业务脚本。

## 风险与边界

1. `KEY_HANDLER` 需要入口阶段临时启动一个最小 `ticker`, 实现时必须确保判定结束后立即停止, 不把临时扫描链带入后续脚本。
2. 当前脚本仍然是脚本式文件, 因此本轮入口跳转应优先保持现有脚本执行方式, 不顺手扩到脚本接口重构。
3. 这轮如果顺手去改下层运行时, 会把“入口切换问题”和“业务链问题”重新混在一起, 与用户要求的整洁改动面相违背。

## 结果判据

当满足以下条件时, 本轮可视为完成:

1. 当前仓库正式入口已从 `boot.py` 切到 `main.py`。
2. `C8/C9` 长按脚本分发可用, 默认分支仍能进入正常运行脚本。
3. `D8/D9` 已从脚本分发语义中退出, 只保留车号识别职责。
4. 主机侧入口测试通过。
5. 板端入口确认记录齐全, 且没有发现因为入口切换引入的新语义冲突。
