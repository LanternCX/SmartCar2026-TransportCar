## Title
用帧头和 CRC8 收敛固定短帧错位假包问题

## Background / Issue
单主车视觉跟随联调中出现主车长时间收不到新速度包、速度状态不更新的现象。最初容易把问题误判为 UDP 高频速度包被过载清理丢弃, 但进一步审查发现: 高频 UDP 允许丢旧帧本身符合设计, 真正的问题是固定 11 字节帧没有明确帧边界和软件校验。

当串口输入前面混入坏字节、半包残留或丢失字节后, 旧解析逻辑会按固定窗口或仅靠 `mode/topic/role` 扫描候选帧。若错位片段刚好像合法速度帧或 ACK 帧, 接收层会误消费假帧并跳过后面的真帧, 表现为持续收不到有效新包或读到错误速度 body。

## Change Unit
把车端 `SmartCar2026-TransportCar` 与视觉端 `SmartCar2026-Vision` 的本地视觉固定短帧统一升级为 13 字节格式: `head/mode/topic/seq/body[8]/crc8`。其中 `head=0xA5`, CRC8 覆盖 `mode/topic/seq/body[8]`。接收层只分发帧头正确且 CRC8 通过的固定帧, 让串口字节流在坏字节、半包和粘包后能够重新对齐, 同时保留 UDP 最新值语义和过载丢旧帧设计。

## Actions / Outcome
- 在车端协议帧编码中加入 `FRAME_HEAD` 和 CRC8 -> 固定帧从 11 字节变为 13 字节, 错位假帧无法仅凭 topic/mode 通过解码。
- 将车端 RX 扫描改为使用完整 `FRAME_SIZE` 并依赖 `decode_frame()` 校验 -> 前导坏字节、丢字节造成的假 UDP/假 ACK 不再吞掉后续真帧。
- 同步 OpenART 主车与辅车入口的帧编解码 -> 视觉端发送与接收均使用同一 13 字节格式, 避免车端和视觉端协议不匹配。
- 补车端和视觉端回归测试 -> 覆盖前导噪声、错位假 UDP、错位假 ACK、分段 ACK 与基础帧校验失败场景。
- 同步协议文档与视觉仓库 README -> 明确车端软件 CRC 只负责业务层分帧安全, 无线模块自身仍按模块参数执行空中链路 CRC 和重发。

## Lessons / Refinements
- 高频 UDP 可以丢旧帧, 但不能把“允许丢帧”误解为“接收端可以没有可靠分帧边界”。丢旧帧和错位失锁是两类问题。
- 固定长度字节帧如果没有帧头和校验, 只靠 `mode/topic` 扫描会产生假阳性; 错位片段一旦像合法头, 后续真帧会被跳过。
- 车端和 OpenART 视觉端复制了协议实现时, 任意帧格式调整必须两个仓库同时修改并同时验证。
- 无线模块文档中的 2Mbps 空中速率和 16bit CRC 不能替代主控侧业务分帧; 新增字节主要影响主控到无线模块的串口输入排队压力。
