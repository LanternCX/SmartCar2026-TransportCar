## Title
收敛主辅车新协议联调中的板端兼容写法与分段 ACK 丢失问题

## Background / Issue
本轮把车端和 OpenART 视觉仓库一起切到固定长度短帧后，现场出现了一个很容易误判的现象：主车能正常启动，主车视觉能继续找物体，辅车也能跟随主车，但主辅状态就是不往下跳。最开始只看到主车停在 `master->camera sync start`，看起来像“视觉没起来”或“没有刷到最新代码”，但进一步补板端完整调用链后，确认是多层问题叠在一起：

- 车端和视觉端都残留了板端不稳的桌面 Python 写法，导致收到第一包后直接在板端崩掉。
- 角色层里层异常此前只记摘要，不打印完整调用链，外层 `main` 兜底也就永远接不到真正的异常。
- `transport` 接收层没有保留不满一帧的尾巴，低频 ACK / 事件包只要被串口拆成两段，就会被当场吞掉。
- 高频视觉速度链和低频可靠状态链是两条不同链路，前者能工作，不代表后者也已经闭环。

## Change Unit
把这次新协议联调中真正阻断状态跳转的三类问题一次收口：统一板端完整异常打印、移除板端运行主线中不合适的桌面 Python 字节编解码与调用方式，并让固定帧接收层按端口保留残片再拼帧，从而让“车先上电、视觉后上电”的真实时序下，可靠状态同步和 ACK 闭环不再依赖理想串口到达形态。

## Actions / Outcome
- 在主车、辅车、`remote_control` 和 `main` 的异常路径上补完整调用链打印 -> 先把“里层吃掉异常、外层永远看不到”的诊断盲区去掉，现场能直接看到真实崩点。
- 把主车角色运行时里板端不接受的带名字调用改成顺序传参 -> 解决主车刚进入 `SEARCH_OBJECT` 就报 `function doesn't take keyword arguments` 的第一处板端兼容问题。
- 把车端 `protocol/codec.py` 中 `int.to_bytes` / `int.from_bytes` 改成显式字节位运算 -> 解决车端可靠同步 body 编解码在板端运行主线里的不稳定点。
- 把视觉仓库主车 / 辅车入口中的同类整数打包写法也改成显式字节位运算 -> 避免 OpenART 在收到第一包同步时直接崩在本地解析路径。
- 把 `startup_log.write_exception_trace()` 改成板端直接打印时只走单参数 `print_exception(exc)`，写文件时才走带输出对象版本 -> 解决补完整调用链后又触发 `stream operation not supported` 的二次故障。
- 给 `transport` 每个端口增加 `rx_buffer`，把不足一帧的尾巴跨轮询保留下来 -> 解决 ACK / 事件帧分段到达时被直接丢掉的问题，让可靠状态链不再依赖“一次正好读满 11 字节”。
- 补主机侧回归覆盖“状态机板端兼容调用”“完整异常打印”“分段 UDP / ACK 重组”“视觉仓库避免板端不稳定字节辅助写法” -> 当前主线相关本地验证全部通过。

## Lessons / Refinements
- 视觉速度链能工作，只能证明 `UDP` 最新值链在工作；状态不跳时必须立刻把“高频速度链”和“低频可靠状态链”拆开分析，不能因为车还能动就误判成通信整体没问题。
- MicroPython / OpenART 运行主线里不要再默认使用桌面 Python 的便利写法，尤其是 `int.to_bytes`、`int.from_bytes`、以及板端不稳定的带名字调用方式；这类写法在主机测试里常常没问题，但会在板端第一拍直接炸掉。
- 固定长度串口协议如果不保留残片，现场最容易丢的不是高频速度包，而是低频 ACK / 事件包；接收层必须跨轮询拼帧，不能把不足一帧的尾巴直接当坏包清掉。
- 里层 `catch` 如果只记一句摘要，外层致命兜底永远不会替你打印完整链路；以后只要在运行主线里拦异常，就必须同步输出完整调用链。
- 联调口径要默认按“车先上电、视觉后上电、串口分段到达”这种真实时序设计，不要再按“双方几乎同时起来、每帧整包到达”的理想路径思考。
