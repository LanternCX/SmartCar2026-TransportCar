## Title
主车视觉状态机后的内存恶化主因是串口收发而不是双窗口滤波

## Background / Issue
主车在接入视觉状态机后, 现场继续出现严重内存恶化。虽然主车轮速链路里确实存在双窗口滤波带来的额外常驻和计算开销, 但用户进一步对比后确认: 保持原有辅车控制链路时可以长期运行, 而真正把内存问题放大的, 是视觉状态机引入后更频繁的串口发送与接收路径。

## Change Unit
围绕主车 `UART3/UART6/UART8` 的收发热路径做一次调试闭环: 先把根因收敛到串口缓冲和发送文本构造, 再为读入缓存、坏包重同步、最新行消费和发送尾缀写出做约束, 最后把主车轮速滤波切回双窗口后再次验证, 确认滤波并不是这轮内存问题的主要因素。

## Actions / Outcome
- 沿着主车串口全链路排查 -> 确认更危险的是串口路径里的缓存增长和高频短命字符串分配, 而不是双窗口滤波本身。
- 收紧主车串口读取策略 -> 为 `uart3/uart6/uart8` 增加分块读取、行长上限、超长坏包丢弃和重同步, 避免 Python 侧读缓冲被迟迟不换行或异常长文本持续撑大。
- 调整主车最新消息消费方式 -> 视觉口和辅车状态口改为优先拿“本拍最后一条有效完整消息”, 降低积压旧消息继续滞留在缓冲里的风险。
- 收紧主车串口发送方式 -> `write_line()` 不再先拼出完整 `payload+CRLF`, 改为正文和换行分开发送, 减少热路径额外瞬时字符串分配。
- 回退主车轮速尾滤波到原双窗口 -> 实测加回后仍然没有重新触发这次内存问题, 进一步证明双窗口滤波不是当前主因。

## Lessons / Refinements
- 对 MicroPython 板端这类低内存环境, 串口热路径里的“坏包无上限积压”和“每拍额外拼整串文本”往往比单个滤波器的常驻开销更容易成为主故障源。
- 当现场怀疑多个因素同时耗内存时, 应优先用回退验证法区分“真实主因”和“次要负担”: 这次加回双窗口后仍稳定, 说明它存在成本, 但不是导致崩溃的主触发点。
