## Title
修复视觉运行时装配与调试回包导致的回归失败

## Background / Issue
在完成 Skill 文档迁移后，重新运行完整测试集时出现 4 个失败，其中主症状集中在两类：一类是视觉运行时在主车路径下没有及时挂出协调器对象，导致运行时接口访问报错；另一类是协议查询测试把串口上的调试 trace 一并当成正式回包，误判了 `?lock` 查询结果。由于这类失败是重新跑完整验证时暴露出来的，它们必须被当作独立 debug closure 收口。

## Change Unit
修复视觉运行时装配时序和视觉轮询入口的一致性，并收紧协议测试对正式回包的断言方式。

## Actions / Outcome
- Approach 1: 先单独跑 4 个失败用例，确认真正仍失败的是“主车视觉运行时缺协调器”和“`?lock` 查询混入 trace 文本”这两条主链 -> 排除了另外两条只是套跑上下文触发的噪声症状
- Approach 2: 在 `src/services/runtime/vision_runtime_service.py` 中让主车路径在可用 builder 存在时立即挂好 `vision_coordinator`，并在 `src/services/car/vision.py` 中统一通过公开模块入口返回轮询顺序 -> 视觉运行时装配和轮询顺序恢复稳定
- Final approach: 将 `tests/contract/services/test_transport_runtime_protocol.py` 的断言改为只校验 UART3 最后一条正式查询回包，再重新执行 `pytest` -> 当前完整测试集 `396 passed`

## Lessons / Refinements
- 重新跑全量测试时暴露的失败，不能直接假定都来自最新改动；需要先把真正持续失败的根因链缩到最小，再决定修哪一层
- 对带调试 trace 的串口测试，断言应优先锁定“正式结果是否出现”，不要把附加调试输出误当协议本身的一部分
