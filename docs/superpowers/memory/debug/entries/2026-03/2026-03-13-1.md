## Title
修复 remote_control 启动脚本对旧 wheel_states 接口的依赖

## Background / Issue
- 上一轮 transport runtime 重构后, `TransportCar` 的轮组状态已收敛到 `chassis_state.wheel_states`, 但 `src/script/remote_control.py` 仍继续读取旧的 `car.wheel_states`。
- 板端启动日志停在 `Creating ticker...`, 说明脚本在 ticker 创建后继续访问旧接口时中断, 导致控制循环没有真正启动。

## Change Unit
修复 remote_control 启动脚本仍依赖旧 wheel_states 接口导致 ticker 无法真正启动的问题。

## Actions / Outcome
- Approach 1: 先新增 `tests/unit/services/test_remote_control_script.py`, 用只暴露 `chassis_state.wheel_states` 的假车对象加载启动脚本 -> 测试稳定复现 `AttributeError`, 证明问题在启动脚本接口未跟上重构。
- Approach 2: 将 `src/script/remote_control.py` 的采集列表接线改为从 `car.chassis_state.wheel_states` 取编码器, 并显式断言 `chassis_state` 存在 -> ticker capture 接线恢复到新状态拥有者。
- Final approach: 运行 `python3 -m pytest tests/unit/services/test_remote_control_script.py -q` 与 `python3 -m pytest tests/unit/services/test_transport_car_diag_mode.py tests/unit/services/test_transport_car_logging.py tests/unit/services/test_remote_control_script.py -q`, 得到 `1 passed` 和 `34 passed` -> 启动脚本回归与相关 transport 回归均通过。

## Lessons / Refinements
- 服务层重构后, 启动脚本这类板端入口也必须纳入回归测试, 否则 host 侧核心对象全绿, 仍可能因脚本层旧接口残留而在真机启动时卡死。
- 对运行时状态单一所有权已经迁移到 `chassis_state` 的场景, 不应再补回 legacy 代理属性, 直接让调用方显式依赖新 owner 更能防止兼容壳长期残留。
