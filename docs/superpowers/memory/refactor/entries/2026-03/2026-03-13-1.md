## Title
解耦 transport runtime 并收紧设备验证表述

## Background / Issue
- `TransportCar` 长期同时承担命令解析、底盘状态、视觉协同、诊断输出与板端 smoke 装配职责, 文件持续膨胀, 且存在 legacy command/vision 路径与兼容代理, 不符合当前服务层解耦目标。
- 用户明确要求继续推进解耦、不要保留兼容层, 并要求设备验证结论必须基于 fresh evidence, 跳过的 Stage 3 不能被表述为完整 HIL 通过。

## Change Unit
解耦 transport runtime 管线，删除兼容壳，并收紧设备验证结论与证据表述。

## Actions / Outcome
- Approach 1: 先以 TDD 方式补齐 `control/`、`services/commanding/`、`services/runtime/` 与 `vision/` 的主机侧保护网, 再将 `TransportCar` 中的命令路由、诊断 facade、UART ingress 与视觉状态协作逐步拆出 -> host 侧 `unit/contract` 回归覆盖保持可用。
- Approach 2: 删除 `src/services/commands/`、旧 `commander` / `command_router` 和 vision legacy 路径, 并继续移除 `TransportCar` 与 fake context 上的兼容代理, 让 diagnostics/query 直接依赖 `command_session` 与 `chassis_state` -> 兼容壳没有继续残留到新层次。
- Final approach: 用 `python3 -m pytest tests/unit tests/contract -q`、`python3 -m pytest tests/unit/services/test_micropython_compatibility.py -q` 与 `python3 tools/run_stage2_smoke.py --port /dev/cu.usbmodem1101` 做 fresh verification, 确认 host 侧 `263 passed`、MicroPython 兼容 `2 passed`、设备侧 Stage 2 输出 `mode=lite` 且 `queries count=9 missing=none`; 同时在 `tests/hil/` 中明确记录 Stage 3 skipped by user 与 overall `PARTIAL` -> 运行时解耦与证据表述一致收口。

## Lessons / Refinements
- 真正删除兼容层时, 不能只把旧 API 包一层转移到新对象上, 必须让调用方显式依赖新的状态拥有者, 否则文件看似变短但架构耦合并未消失。
- Stage 2 lite smoke 只能证明最小 query/结构化输出链路可执行, 不能替代 `uart3` observe; 当用户要求跳过 Stage 3 时, HIL 文档必须同步降级为 `PARTIAL` 而不是默认 PASS。
