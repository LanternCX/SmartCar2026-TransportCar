## Title
记录 src 运行时代码低内存重构与板级排障结论

## Background / Issue
主车在 `remote_control.py` 正常启动后, 视觉轮询阶段出现板端 OOM。早期现象包括 `load_gyro_offsets()` 启动日志触发 `diagnostics.format.sanitize_log_text()` 的 `MemoryError`, 随后在视觉链路接通后又出现 `vision.state` 高频日志与异常日志路径的内存压力问题。本轮不仅处理单点日志触发, 还对 `src/` 上线运行时代码做 repo 级低内存重构, 重点回收 logger 自身常驻结构与视觉运行时分散 owner。用户最终发现, 将相同代码烧录到另一块板子后问题明显缓解, 因而需要把“代码侧对象生命周期/冗余状态”和“可疑板级固件/内存损坏”这两类结论一并记录下来。

## Change Unit
围绕板端 OOM 对 src 运行时代码进行低内存重构，并沉淀板级排障结论。

## Actions / Outcome
- Approach 1: 沿启动链排查 `VEHICLE_ROLE`、`boot.py` 与 `remote_control.py` 的角色暴露路径 -> 确认入口问题已修复, 真正的早期 OOM 发生在 `load_gyro_offsets()` 的启动日志格式化阶段
- Approach 2: 为 `TransportCar` 启动链增加临时内存打点, 对比 `boot.after_ident` 与 `boot.after_gyro_offsets` -> 证明零偏加载本身不是主因, 启动日志回调才是直接触发点, 因而保留“`load_gyro_offsets()` 不接 `INFO` logger”的修复并移除临时打点
- Approach 3: 面向 `src/` 上线运行时代码做 repo 级低内存重构, 重点清理 logger 自身常驻结构、收紧日志 formatter 降级路径, 并收口视觉运行时分散 owner -> 减少多点持有与隐式常驻状态带来的长期内存占用
- Approach 4: 排查视觉协议链路与 OpenArt 回包, 发现旧板上容易复现日志 OOM 和串口异常, 但换板后同代码可以收到合法 `FRAME camera=cam_a ...` 日志 -> 说明至少一部分问题与旧板固件/内存状态相关, 不应把全部现象归因到主控业务逻辑
- Final approach: 保留对主控最有工程价值且风险最低的修复组合 -> 1) 启动期不再为 `load_gyro_offsets()` 打 `INFO` 日志; 2) 默认 `RUN` 档下将高频 `vision.state` 的 `POLL` 日志降到 `DEBUG`; 3) 为 `diagnostics.manager` 增加 formatter OOM fallback; 4) 持续推进以 owner 收口替代分散运行时状态, 作为 repo 级低内存重构的正式方向
- Approach 5: 将 `services.commanding.handlers` 从目录扫描自动发现改为静态模块装配, 并把 `TransportCar` 拆成 staged init -> 降低启动期 import 峰值, 避免在 runtime 未建立前就因装配链 OOM
- Approach 6: 为 `?health` 增加轻量 `oom_count` / `oom_stage`, 并把 `vision` 轮询查询串改为热路径缓存 -> 让“系统还活着但状态机不跳”时能区分最近是否发生过 logger 路径 OOM
- Approach 7: 将 handler 装配从 `transport_car.py` 顶层全量导入改为 query / command 首次使用前按需加载, 并用 MicroPython 兼容的 `__import__` 替代 `importlib` -> 板端已能跨过启动导入链, `remote_control.py` 可进入主循环
- Approach 8: 把 query 失败路径改成“运行时记录优先 + 最小错误回包”, 再为 `health/tick/vision` 增加直出响应, 同时把 `FRAME` 与 `VSM TRANS` 从默认 `INFO` 降到 `DEBUG` -> 板端现象从“只剩 log.oom”推进到“主循环可运行、状态机可跳转、query 至少能回 `error:MemoryError`”

## Lessons / Refinements
- 本轮已对 `src/` 上线运行时代码做 repo 级低内存重构, 结论不能只停留在单个报错点, 而要回到常驻对象、状态 owner 和日志链路整体审视
- logger 自身常驻结构和视觉运行时分散 owner 是本轮重点清理对象; 对 RT1021 + MicroPython 这类板端系统, 高频观测日志默认不应放在 `INFO`, 运行期必须优先保证控制循环和错误可归因
- 板端 OOM 不能只看“当前哪一行报错”, 要区分“业务逻辑导致内存不足”与“日志格式化把原始问题放大”这两层因果
- `MemoryError: memory allocation failed, allocating **** bytes` 不总是单纯的瞬时 OOM, 也可能更接近“对象生命周期失控 / 冗余状态长期滞留 / 内存泄漏”; 尤其当脱机运行后再次连接 Thonny 更容易复现时, 需要同步检查 Python 侧是否存在冗余全局变量, 模块级对象重复持有, 或多文件作用域下状态长期滞留
- 对这类 MicroPython 项目, 若怀疑存在长期占用而非单次尖峰分配, 优先考虑把跨文件共享状态收口进 class / owner 对象, 通过显式传递对象而不是散落的全局变量协作, 减少多文件作用域带来的隐式内存常驻风险
- 当相同代码在换板后现象显著改善时, 必须把“板子硬件故障”或“当前板上的 MicroPython 固件损坏/状态异常”列为正式排查方向; 这类问题既可能来自代码侧对象生命周期/冗余状态, 也可能与板子硬件或 MicroPython 固件状态异常有关
- 板端内存治理必须覆盖启动期, 初始化期, 运行期和诊断期 4 个阶段; 只盯单个报错点容易把“导入期峰值 OOM”和“运行期高频分配 OOM”混为一谈
- 对“系统还活着但状态机不跳”这类现场问题, 优先保留 `?health/?tick/?vision` 的最小诊断面, 不要依赖重日志判断 OOM
- 当 `?health/?tick/?vision` 都只能返回 `error:MemoryError` 时, 说明问题已经从“query 路由坏掉”收敛到“诊断查询本身在当前堆状态下也分配失败”; 这通常更接近长期高占用, 堆碎片或高频日志把系统推到低内存边缘, 而不是单个 handler 逻辑错误
- 板端日志里若仍持续出现大量 `FRAME` / `VSM TRANS` 并夹杂 `log.oom`, 应优先降低高频 `vision.state` 默认日志等级, 保证控制循环和最小 query 诊断面的生存优先级
