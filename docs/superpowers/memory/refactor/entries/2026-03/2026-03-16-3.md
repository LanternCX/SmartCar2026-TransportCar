## Title
将搬运车运行时重构为 `services.car` 分包并补齐轻量静态契约

## Background / Issue
review 明确指出, 仅把 `transport_car.py` 拆成 `transport_*` 平铺文件并不能算真正分包, `src/services/` 根目录继续用统一前缀模拟命名空间仍不通过。同时, 新的 `services.car` 分包在 VS Code / Pylance 下出现大量 `reportAttributeAccessIssue`, 根因是 mixin 依赖宿主动态提供属性, 但静态分析无法识别这些承诺。

## Change Unit
将搬运车运行时从平铺文件迁到 services.car 真正分包，并补齐轻量静态契约。

## Actions / Outcome
- Approach 1: 延续 `transport_*` 平铺拆分 -> 行数下降但 review 继续拒绝, 因为命名和分层边界仍不成立
- Approach 2: 迁到 `services.car` 真正分包, 并统一更新 `src` / `tools` / `tests` 导入 -> `src/services/` 根目录不再保留 `transport_*.py`, `services.car` focused suite 通过
- Final approach: 在 `services.car` 下引入轻量宿主契约类, 只声明 mixin 所需最小接口, 再把 `TransportCar` 的基类顺序调整为真实实现优先 -> `python3 -m pyright src/services/car src/services/stage2_smoke/full.py src/script/remote_control.py tools/stage2_full_trace_probe.py tools/device_observe_probe.py` 为 `0 errors`, 同时 `139` 个 focused pytest 通过

## Lessons / Refinements
- 对 MicroPython 运行时代码, 修 Pylance 红线不能靠放松编辑器配置, 也不能盲目引入重型 `typing` 依赖; 更适合用轻量静态契约和明确 MRO 收口
- 静态分析占位成员若参与多继承, 必须验证运行时 MRO 是否会抢到真实实现, 否则会出现“pyright 绿了但行为坏了”的反向回归
