## Title
冻结 legacy 并建立 master-assistant 最小运行时主线

## Background / Issue
仓库原先以统一运行时承载主车与辅车职责, 通过角色分流、兼容桥接和延迟装配维持复杂共用结构。该结构已经明显偏离“两台不同车辆分别烧录、分别运行”的真实目标, 同时持续放大板端内存、调试和职责边界问题。用户随后明确要求将旧系统降级为纯参考代码, 不再保持其测试和入口可运行, 并把当前主线收敛到 `src/legacy`、`src/master`、`src/assistant` 三部分。

## Change Unit
把旧运行时代码整体归档到 `src/legacy`, 删除旧测试面, 同时建立 `assistant` 最小执行闭环、`master` 最小主控链和主辅最小运动级协议契约, 使仓库主机侧验证范围收敛到新主线并恢复稳定通过。

## Actions / Outcome
- 将旧系统主干从 `src/` 根下真实归档到 `src/legacy/` -> 旧代码与新运行时边界被明确拉开, 目录结构收敛为 `legacy / master / assistant`
- 建立 `src/assistant/` 最小执行闭环与自足稳定性层 -> 辅车不再依赖旧根目录模块, 主机侧最小闭环通过
- 建立 `src/master/` 最小主控链, 收口为“单视觉串口轮询双摄 -> 简化状态机 -> 决策 -> 主车目标/辅车命令” -> 主车主机侧最小闭环通过
- 固定主辅最小运动级协议契约并收紧 `STATE` 回包字段 -> 主辅协议测试面稳定收敛
- 删除旧仓库对应测试, 仅保留 `master` / `assistant` / `legacy` 归档检查 / 主辅协议 / HIL 留证 -> `python3 -m pytest tests/unit tests/contract -q` 达到 `29 passed`
- 写出迁移 spec、实施 plan、legacy 裁剪清单和阶段进度记录 -> 后续删减和设备验证有了统一依据

## Lessons / Refinements
- 当旧系统被明确降级为“纯参考”时, 不应再花成本维持其测试和旧入口可运行, 而应立即让验证面与新主线对齐
- 真实归档旧系统后, 新运行时必须真正自足, 不能偷偷依赖旧根目录模块, 否则结构问题会立刻暴露
- 先冻结删减顺序和裁剪清单, 再继续推进新系统, 能显著降低“边重构边误删”的风险
