## Title
完成辅车主动跟随主车的软件侧双仓重构

## Background / Issue
围绕 issue #29 的当前目标, 项目需要把旧的“主车双摄统一读取、判断并转发辅车控制”的链路切换为“辅车 OpenArt 直接生成 follow 请求, 辅车本车执行, 主车删除旧跟随整链”。约束同时很明确: 辅车现有控制核心不重写, 主车新的找物主线不在本轮展开, 本轮只完成软件侧收口, 用户明确跳过上板测试。

## Change Unit
本次改动形成了一个完整的软件侧闭环重构单元: transport 仓库把辅车高频输入切到 `UART6`、删除主车旧跟随整链并把主车收成最薄起点; vision 仓库把 OpenArt 从“观测上报”切到“直接生成辅车已支持的 follow 请求”, 同步更新协议与 README 口径。

## Actions / Outcome
- 辅车执行侧保留现有协议解析与底盘运动计算, 仅把高频输入切到 `UART6` -> 保住控制核心不变, 新链路能直接吃 OpenArt follow 请求
- OpenArt 输出从像素观测改成直接 follow 请求 -> 视觉侧不再需要主车二次解释, 默认主链可直接闭合到辅车执行侧
- 主车旧的读相机、跳流程、转发控制整链整体删除 -> 主车只剩后续继续做找物前的最薄软件起点
- transport 与 vision 双仓文档同步改口 -> 对外口径不再把当前方案写成“主车双摄统一驱动辅车”
- 完成双仓软件侧最终回归 -> `transport` 关键回归 `218 passed`, `vision` 关键回归 `41 passed`

## Lessons / Refinements
- 当真实目标本身就是“删旧链并收成薄骨架”时, 不要把“删除旧链”和“收骨架”机械拆成两步执行, 否则容易在 review 时人为制造边界冲突
- 视觉仓库与车端仓库的协议默认值必须一起收口, 否则很容易出现单仓自洽但默认链路仍不闭合的假通过
