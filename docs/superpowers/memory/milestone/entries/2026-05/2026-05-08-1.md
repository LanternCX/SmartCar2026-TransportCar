## Title
确立 UDP 数据流与 TCP 可靠同步双模式控制协议

## Background / Issue
主辅车联动和视觉闭环同时需要高频控制量与低频状态同步。高频包如果携带完整上下文或逐包确认, 会占用串口带宽并拖慢控制周期；低频状态同步如果只按一次性发送处理, 又会在丢包或重复包场景下破坏状态机一致性。因此控制协议需要先区分高频数据流和可靠同步, 再承接后续状态机开发。

## Change Unit
PR#60 和 PR#61 将控制协议收口为双模式短包基线：UDP 模式承担高频数据流, 只关注最新值并允许丢包；TCP 模式承担低频可靠同步, 使用重复发送、确认和幂等处理保证上下文建立。随后运行时入口、主辅通信链路、视觉链路和测试逐步迁移到 `v/s/a/o/r` 短包语义, 为后续主辅联动状态机提供统一通信基础。

## Actions / Outcome
- 定义 UDP 数据流模式 -> 高频速度、视觉误差和观测包保持短小, 不逐包确认, 接收端按最新值消费。
- 定义 TCP 可靠同步模式 -> 状态同步、hook 建立和结果回报使用序号、确认、重发和幂等处理。
- 将协议正文集中到 `docs/developer/protocol.md` -> 开发文档和 Skill 规则只做路由, 不分散维护协议事实。
- 将车端运行时迁移到 `v/s/a/o/r` 短包入口 -> 状态机接入点不再依赖旧键值命令系统。
- 对齐主车前馈、辅车视觉跟随和 OpenART 视觉链路 -> 高频通信与可靠同步在主车、辅车和视觉侧使用同一套解释边界。

## Lessons / Refinements
- 高频控制链路优先保证包短和最新值优先, 不要为了可靠性把所有包都做成重字段结构。
- 低频状态同步必须具备确认、重发和幂等语义, 否则状态机在丢包和重复包场景下会出现隐式分叉。
- 协议迁移必须同时更新文档、运行时入口、测试和归档, 不能只新增解析函数。
