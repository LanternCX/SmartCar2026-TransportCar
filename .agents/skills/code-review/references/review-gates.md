# 收口评审门禁

## 一、先看是否值得保留

- 满足要求：先对照 `docs/developer/strategy.md`, 确认当前实现真的覆盖当前阶段目标与成功定义
- 最小改动：先对照当前任务上下文, 确认没有引入与当前任务无关的额外改动、额外抽象或额外路径
- 正贡献：默认只认可直接提升稳定完赛能力的改动, 不把“功能更全”“结构更大”当作加分项

## 二、架构与实现收口门禁

- 风格一致性：复核分层位置、依赖方向、中文文档要求、异常处理口径、参数集中管理与 5ms 控制周期约束
- 架构健康：优先保证代码简洁、设计合理和松耦合; 发现 God object、隐式上下文协议、状态双写、职责漂移、过度设计或伪扩展性时, 必须在收口结论中明确指出并要求简化
- 板端内存：运行时、协议、控制和诊断改动必须优先检查常驻对象、导入集、qstr 压力和最小观测口, 不把测试便利或可读日志当作默认保留理由
- 结论质量：review 结论不能只给表面判断, 必须说明职责边界、状态归属、耦合方式和抽象成本是否健康

## 三、板端验证与结果留证

- 板端路径禁令：不允许先写完再补测试, 不允许主机测试过了就不上板, 不允许直接让车动一下看看, 不允许看到串口有输出就算完成, 不允许把板端确认永久后补
- 板端路径交付：进入板端路径后, 交付物必须包含主机测试、板端操作步骤、关键结果、观测输出、失败归因和现场确认记录
- 控制系统收口：必须覆盖单轮与三轮协同控制、速度模式与位置模式、模式切换、锁定 / 解锁状态一致性和长时稳定性
- 控制系统交付：控制算法或参数变更必须补充参数说明、调参与验证记录, 必要时提供回归测试脚本或验证命令
- 通用交付：最终交付物必须包含结果、关键验证步骤、验证记录与必要的变更说明
