# 硬件与协议规则

## 事实源与使用方式

- 完整 OpenArt 协议正文统一维护在 `references/openart-protocol.md`
- 本页只保留已确认硬件事实、联调入口和协议查阅路由, 不与完整长协议正文混排
- 若代码现状与正文冲突, 先以正文和用户确认结果为准, 再回头修实现
- 若正文未明确给出引脚、串口、电平或接线事实, 必须先问用户, 禁止猜测

## 已确认硬件事实

- `src/boot.py` 中 Button 1-4 的板级引脚分别为 `C8`、`C9`、`C14`、`C15`
- `D8/D9` 角色输入带上拉电阻, 读到 `1` 表示开关关闭, 读到 `0` 表示开关闭合
- 现场判断角色时先看输入电平, 不要直接按开关朝向口头推断
- 主车通过单视觉串口轮询两颗相机; 被点名相机立即返回当前缓存结果, 未被点名相机必须严格静默
- `uart3` 用于人工联调与最小 query 回包, `uart6` 保持命令与视觉正式通信链路

## 视觉与坐标语义

- 坐标、查询格式、字段语义与兼容规则统一以 `references/openart-protocol.md` 为准, 旧描述不得当成最新事实源
- 坐标与正方向固定为: `y+` = 前进, `x+` = 右移, `omega+` / `d_angle+` = 顺时针
- `dx/dy/d_angle` 表示车体系相对增量, `x/y/angle` 表示世界系绝对目标
- 说“左 / 右 / 前 / 后 / 顺时针 / 逆时针”时必须标明参考系
- `push_angle_deg = -90` 只能解释为相对当前复位零点的绝对航向目标, 没有 HIL 证据前不要口头改写方向含义

## 协议正文路由

- 需要完整协议目的、链路约定、查询格式、字段表、兼容规则、迁移建议时, 直接查看 `references/openart-protocol.md`
- 需要确认 `?frame=<camera_id>`、`frame_end=1`、`?vision`、`UART6` 等协议事实时, 直接以 `references/openart-protocol.md` 为准

## 视觉输入与状态机判据

> 本段只保留稳定协议事实与必须统一的状态机判据; 临时排障经验不要直接写进这里。

- 视觉输入只认 `UART6` 上完整框 `left,top,right,bottom`
- 旧 `x,y` 或混合载荷会被视觉协议吞掉, 不得继续作为主控输入依赖
- 最终画面坐标已完成翻转处理, 主控侧不得再次翻转
- 当前视觉链路默认采用斜俯视类人视角, 目标默认位于地板平面, 因而 `bottom` 可作为接近程度代理量
- 对正与推行状态的符号关系必须集中定义并保持一致, 包括 `ALIGN_ANGLE`、`ALIGN_DX`、`ALIGN_DIST`、`ORBITING`、`PUSHING`、`RETURNING`

## 联调前检查与异常排查

- 联调前必须成组检查: `?vision` 可读、`obs_center_x` 和 `obs_bottom` 变化方向正确、`ALIGN_ANGLE -> ALIGN_DIST -> ALIGN_DX` 阶段顺序正确、旧 `x,y` 没有误入普通控制链路
- 若出现方向异常, 先按顺序排查 OpenArt 翻转、镜头安装方向、视觉发送格式、识别框字段顺序、车体坐标理解、电机方向、编码器方向
- 输出结论前必须完成语义自检: 参考系、字段 / 控制量、阶段语义、相对量 / 绝对量
- 联调输出必须使用统一失败分类: `connect_failed`、`deploy_failed`、`probe_failed`、`observe_failed`、`hil_pending`

> 本页负责“硬件 / 协议事实 + 联调核对口径”, 不负责比赛方向与任务优先级。
