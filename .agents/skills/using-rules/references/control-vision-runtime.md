# 控制、视觉与运行时规则

## 适用范围

- 本页用于控制链、角色运行入口、视觉速度输入、调参与诊断顺序相关实现。
- 项目路线目标以 `docs/developer/strategy.md` 为准, 任务推进顺序以 issue 管理为准。
- 控制事实以 `docs/developer/control.md` 为准, 视觉职责以 `docs/developer/vision.md` 为准, 串口字段以 `docs/developer/protocol.md` 为准。

## 项目与角色边界

- 项目路线、角色职责和当前阶段目标以 `docs/developer/strategy.md` 为准。
- 高速多车通信与速度前馈属于正式控制主线能力。
- 任何实现扩展都要先回答是否直接服务完赛主线; 不能直接服务时默认不扩大范围。

## 运行入口与角色层事实

- 运行入口阅读顺序以 `docs/developer/control.md` 为准。
- 角色职责阅读顺序以 `docs/developer/vision.md` 为准。
- 状态机所有权阅读顺序以 `docs/developer/state.md` 为准。
- 角色层只做角色编排和输入融合, 不额外堆叠第二套底盘执行内核。
- 共享控制内核负责通用底盘执行与方向稳定, 不承载角色层业务决策。

## 控制系统固定事实

- 5ms 控制周期预算属于实现阶段硬约束, 超预算先降复杂度, 再讨论新特性。
- 参数与阈值集中在 `src/config/` 分层配置下, 按运动、视觉、安全、通信和持久化边界取用。
- 角度主链路优先依赖零漂校准、滤波、四元数积分和动态控制周期, 不依赖视觉角度。
- `xy` 编码器积分不作为高精度位置真值, 但 `xy` 位置式控制保留为多段误差修正链路。

## 速度前馈与视觉修正

- 速度字段、来源职责和融合行为以 `docs/developer/protocol.md`、`docs/developer/vision.md`、`src/vision/` 代码和行为测试为准。
- 改动速度融合前, 先确认每一路输入的来源、时效、清零语义和最终写回边界。
- 不把调试字段、视觉内部状态或业务上下文塞进高频速度链路。

## 状态机与协议边界

- 全局状态机由主车维护, 状态编号和事件编号以 `docs/developer/state.md` 为准。
- 协议层只定义字段、报文格式和同步语义, 不承载具体业务状态机职责。
- 业务状态机不得反向要求高频串口包携带冗长上下文字段。
- 需要可靠建立的上下文走状态同步短包; 高频运动、前馈和修正数据走速度控制文本。
- 状态机任务设计应避免阻塞式等待语义, 保持控制周期持续推进。

## 调参与诊断顺序

- 控制系统调参流程固定为: `calibrate_gyro.py` -> `pid_identify.py` -> 内环 -> 外环 -> 航向保持 -> 组合轨迹联调。
- 参数辨识先行, 使用 `pid_identify.py` 生成电机参数。
- 改控制算法前先确认硬件基线: 编码器方向、电机方向、IMU 校准。
- 控制问题按固定顺序排查: 振荡、响应慢、稳态误差、航向漂移、轨迹偏差。
- 高频跟随相关实现先收口输入边界、状态所有权与角色层职责, 再决定是否需要额外解耦层。
- 若出现状态抖动, 先排查输入时效、协议边界和滤波, 不要直接扩大架构层次。
- 进入设备路径后, 对控制相关变更必须准备调参与验证记录, 不接受只凭主观体感下结论。
