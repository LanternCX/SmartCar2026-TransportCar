# 2026-03-16-5

## Date
2026-03-16

## Title
批准 src 运行时代码 300 行硬门禁并重写拆分设计

## Background / Issue
上一轮 owner 下沉后, `TransportCar` 和多个运行时代码文件仍然超过 300 行, review 明确不通过。用户新增硬要求: 本次 review 范围内, `src` 运行时代码每个 Python 文件都不能超过 300 行。

## Actions / Outcome
- Approach 1: 先确认 300 行规则的适用范围 -> 用户明确本轮只要求 `src` 运行时代码满足 `<= 300` 行, 不包含 tests
- Approach 2: 重新盘点当前超限文件 -> 确认 `src` 下共有 5 个超限运行时代码文件: `transport_car.py`、`diagnostics_facade.py`、`vision/protocol.py`、`vision/state_machine.py`、`diagnostics/manager.py`
- Approach 3: 重新比较拆分方案 -> 放弃“只拆 transport_car”与“激进包重组”, 采用“薄壳 + 子模块分拆”方案, 保留公开 import 路径, 把重实现迁入内部子模块
- Final approach: 新增设计文档 `docs/superpowers/specs/2026-03-16-runtime-file-size-design.md` 和实施计划 `docs/superpowers/plans/2026-03-16-runtime-file-size-plan.md`, 为后续 TDD 拆分提供新的硬门禁基线

## Lessons / Refinements
- owner 下沉并不自动等于编排层变薄, 必须单独用文件大小和职责边界门禁继续推进
- 对 MicroPython 运行时代码, “超长单文件”通常意味着 import 面和定义密度仍然过高, 适合作为结构告警指标
- 保留公开 import 路径、只拆内部实现, 是当前设备仍不稳定时风险最低的继续重构方式
