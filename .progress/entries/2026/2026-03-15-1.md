## Date
2026-03-15

## Title
记录视觉链路 OOM 排障与换板结论

## Background / Issue
主车在 `remote_control.py` 正常启动后, 视觉轮询阶段出现板端 OOM。早期现象包括 `load_gyro_offsets()` 启动日志触发 `diagnostics.format.sanitize_log_text()` 的 `MemoryError`, 随后在视觉链路接通后又出现 `vision.state` 高频日志与异常日志路径的内存压力问题。用户最终发现, 将相同代码烧录到另一块板子后问题明显缓解, 因而需要把“可疑板级固件/内存损坏”结论与本轮保留的必要代码改动记录下来。

## Actions / Outcome
- Approach 1: 沿启动链排查 `VEHICLE_ROLE`、`boot.py` 与 `remote_control.py` 的角色暴露路径 -> 确认入口问题已修复, 真正的早期 OOM 发生在 `load_gyro_offsets()` 的启动日志格式化阶段
- Approach 2: 为 `TransportCar` 启动链增加临时内存打点, 对比 `boot.after_ident` 与 `boot.after_gyro_offsets` -> 证明零偏加载本身不是主因, 启动日志回调才是直接触发点, 因而保留“`load_gyro_offsets()` 不接 `INFO` logger”的修复并移除临时打点
- Approach 3: 排查视觉协议链路与 OpenArt 回包, 发现旧板上容易复现日志 OOM 和串口异常, 但换板后同代码可以收到合法 `FRAME camera=cam_a ...` 日志 -> 说明至少一部分问题与旧板固件/内存状态相关, 不应把全部现象归因到主控业务逻辑
- Final approach: 保留对主控最有工程价值且风险最低的两类修复 -> 1) 启动期不再为 `load_gyro_offsets()` 打 `INFO` 日志; 2) 默认 `RUN` 档下将高频 `vision.state` 的 `POLL` 日志降到 `DEBUG`, 并为 `diagnostics.manager` 增加 formatter OOM fallback, 让日志格式化失败时降级为最小 `log.oom` 文本而不是直接带死运行时

## Lessons / Refinements
- 板端 OOM 不能只看“当前哪一行报错”, 要区分“业务逻辑导致内存不足”与“日志格式化把原始问题放大”这两层因果
- 对 RT1021 + MicroPython 这类板端系统, 高频观测日志默认不应放在 `INFO`; 运行期必须优先保证控制循环和错误可归因, 再讨论日志细节
- 当相同代码在换板后现象显著改善时, 应把“可疑板级固件/内存损坏”作为正式结论记录, 避免后续继续围绕错误硬件状态过度改代码
- 现场经验上, `MemoryError: memory allocation failed, allocating **** bytes` 不总是单纯的瞬时 OOM, 也可能表现为更接近“对象生命周期失控 / 内存泄漏”的问题; 尤其当脱机运行后再次连接 Thonny 更容易复现时, 需要同步检查 Python 侧是否存在冗余全局变量, 模块级对象重复持有, 或多文件作用域下状态长期滞留
- 对这类 MicroPython 项目, 若怀疑存在长期占用而非单次尖峰分配, 优先考虑把跨文件共享状态收口进 class / owner 对象, 通过显式传递对象而不是散落的全局变量协作, 减少多文件作用域带来的隐式内存常驻风险
- 若相同代码在另一块板子上恢复正常, 也必须把“板子硬件故障”或“当前板上的 MicroPython 固件损坏/状态异常”列为正式排查方向, 不要默认所有 `MemoryError` 都来自应用层代码
