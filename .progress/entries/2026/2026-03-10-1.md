## Title
建立工业级全局日志系统并拆分到 diagnostics 包

## Background / Issue
仓库原有日志输出主要散落在 `TransportCar` 的直接 `uart3.write(...)` 中, 缺少统一的日志等级、模块过滤、格式化、运行时调档能力和清晰的模块边界. 最初实现虽然先把能力跑通, 但日志核心被放在 `src/services/` 下, 与编排层职责不完全匹配, 继续发展会把 `services/` 堆成杂物间.

## Actions / Outcome
- Approach 1: 继续沿用散落的 `uart3.write(...)`, 只在局部补一点格式 -> 调试可见性差, 无法统一控制等级、过滤和颜色
- Approach 2: 先在 `services/` 中完成全局 logger 功能闭环, 再评估目录归属 -> 能快速完成 host 侧 TDD, 但架构边界仍需后续收口
- Final approach: 先完成日志核心、formatter、sink、命令路由字符串解析、运行时 `log_*` / `?log`、`TransportCar` 首批接入和协议文档更新, 再将日志核心统一迁移到 `src/diagnostics/` 包, 保留 `services/commands/` 作为协议入口 -> `python3 -m pytest tests/unit/services/test_logging.py tests/unit/services/test_command_router.py tests/unit/services/test_transport_car_logging.py tests/unit/services/test_transport_car_vision_integration.py tests/contract/services/commands/test_log_commands.py -q` 通过 `68` 项, `python3 -m pytest tests/unit tests/contract -q` 通过 `197` 项

## Lessons / Refinements
- 全局日志系统应先把“是否允许输出”和“如何格式化 / 写出”拆开, 用 host 侧 unit / contract test 先把等级、过滤、颜色、命令协议钉稳
- 运行时字符串配置一旦允许人工输入, 就不能让非法模式静默失败, 否则现场排障会出现“没有日志但也不知道为什么”的问题
- 当一套能力已经具备自身状态、协议和生命周期时, 应尽早拆成独立包, 不要继续把 `services/` 或 `utils/` 当总收纳箱
