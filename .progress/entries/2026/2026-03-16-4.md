## Background / Issue
在完成 Task 5-8 的 owner 拆分和 memory review 文档化后, 还需要继续完成 Task 2 / Task 5 / Task 9 的板端 smoke、trace probe 和 HIL 留证。但这些步骤都依赖控制口 `/dev/cu.usbmodem11101` 或新的可用 MicroPython 端口。

## Actions / Outcome
- Approach 1: 先完成所有可在 host 侧推进的重构与回归 -> 抽出 `MinimalCommandRuntime`、`MotionRuntime`、`VisionRuntimeService`, 更新 memory review 规范和文档
- Approach 2: 用最终主机验证命令确认 host 面已闭环 -> 运行 `python3 -m pytest tests/unit tests/contract -q`, 得到 `376 passed`
- Approach 3: 在进入板端验收前重新做设备发现 -> 运行 `ls "/dev/cu.usbmodem11101"` 返回 `No such file or directory`, 再运行 `mpy-cli list --scan-mode known-first` 返回 `未探测到可用的 MicroPython 设备`
- Final approach: 认定当前剩余任务只被真实设备离线阻塞, 不是代码或主机测试失败 -> 板端 Stage 2 smoke、trace probe 和 HIL 留证暂时无法继续, 需等控制口恢复后再执行

## Lessons / Refinements
- 在嵌入式重构里, host 全绿只能证明 Stage 1 已完成, 不能替代 Stage 2 / HIL 验收
- 当 `mpy-cli list` 明确找不到设备时, 不应把板端任务伪装成“已完成但未验证”; 应直接记录为硬件阻塞
- 将 host 完成状态和设备阻塞状态写入 `.progress` 能避免后续恢复工作时重复排查已通过的主机面回归
