## Title
为低内存板端补齐 Stage 2 full/lite 回退

## Background / Issue
新实板 `/dev/cu.usbmodem11101` 在 `stage2` 裸片 smoke 中无法稳定完成 `TransportCar` 的完整导入与初始化，导致 `mpy-cli run` 期间出现 `MemoryError` 或半初始化现象。用户目标不是板端全量自动化，而是以尽量非侵入的方式保证 agent 生成的代码在板端不会出现明显报错和低级链路问题。

## Actions / Outcome
- Approach 1: 先核对现有测试与实现差距 -> 确认单测已经要求 `full -> lite` 回退，但 `src/services/stage2_smoke.py` 与 `tools/run_stage2_smoke.py` 仍停留在 full-only。
- Approach 2: 在 `stage2_smoke` 中实现 full/lite 双路径 -> full 保持 `TransportCar(diagnostic_mode=True)` 的完整安全 smoke；lite 改为轻量 query 注册、query 回包链路与 `transport_car.py` 关键查询入口检查，避免继续向业务代码注入额外测试接口。
- Approach 3: 首版 lite 通过读取整个 `transport_car.py` 做源码标记检查 -> 在实板上再次触发 `MemoryError`，定位到 `_check_transport_source()` 读取整文件过重。
- Final approach: 将源码检查改为逐行扫描，并收紧主机侧 `mode=lite` 解析规则 -> 主机 `python3 -m pytest tests/unit tests/contract -q` 达到 `119 passed`，实板 `python3 tools/run_stage2_smoke.py --port /dev/cu.usbmodem11101` 输出 `status=ok` 且 `smoke mode=lite`。

## Lessons / Refinements
- 在低内存 MicroPython 板端，lite 回退不仅要避免完整业务对象初始化，也要避免一次性读取大源码文件。
- 板端 `stage2` 应把目标收敛为“最小可信验证”，而不是强行追求全量自动化运行；完整行为保障仍应主要依赖 host `unit/contract`。
