# 2026-03-15-2

## Date
2026-03-15

## Title
确认板端仍在运行旧版错误日志路径并阻塞 deploy

## Background / Issue
主机侧 `src/services/transport_car.py` 已把 `_emit_error_log()` 改成直接 `uart3.write("ERRRAW ...")` 的轻量降级路径, 但板端真实运行时仍持续出现 `E [log.oom       ] format oom`。需要确认这是新的日志入口, 还是设备上仍保留旧版 `transport_car.py`, 同时排查为什么 reset 后 `mpy-cli` 仍会立刻遇到 `MemoryError: allocating 1280 bytes`。

## Actions / Outcome
- Approach 1: reset 后立即用 `mpy-cli list --scan-mode known-first` 探测控制口 -> `/dev/cu.usbmodem11101` 可枚举, 但探测阶段直接返回 `MemoryError: memory allocation failed, allocating 1280 bytes`, 说明板子虽然重启, 但很快又回到低内存运行态
- Approach 2: 通过普通 REPL 发送 `Ctrl-C` 后执行 `print(gc.mem_free())` 和 `print('car' in globals())` -> 连简单 `print(...)` 都会触发同样的 `1280 bytes` OOM, 证明问题不只是 `mpy-cli` 探针本身
- Approach 3: 在普通 REPL 中手动 `del pit1`, `del car`, 再 `gc.collect()` -> 控制口恢复可操作, 后续读取到 `MEM 124832`, 证明 reset 后自动启动的 `script/remote_control.py` 只被 `Ctrl-C` 打断, 但 `car` / `pit1` 仍作为全局对象滞留在解释器中
- Final approach: 直接在板端 REPL 读取 `services/transport_car.py` 第 595-610 行 -> 实际部署内容仍是旧版 `_emit_error_log()`, 先执行 `self.log_health.error(text)`, 只有在 `MemoryError` 后才回退到 `ERRRAW`; 这与主机工作区当前文件不一致, 解释了为什么板端仍持续出现 `E [log.oom       ] format oom`
- Approach 4: 在确认板端文件过旧后, 尝试用 `mpy-cli upload` 仅上传 `src/services/transport_car.py` -> 失败于 `mpremote.transport.TransportError: could not enter raw repl`, 说明当前未闭环点已经收敛为“部署握手 / raw REPL 接管失败”, 而不是 `_emit_error_log()` 根因不明确
- Approach 5: 用户手动 reset + stop 后重新 `mpy-cli deploy`, 再次用普通 REPL 读取板端 `services/transport_car.py` 第 595-610 行 -> 确认 `_emit_error_log()` 已更新为直接 `uart3.write("ERRRAW ...")` 的新版本, 旧版错误日志路径已经不再是当前板端主因
- Approach 6: 重新执行 `python3 tools/run_stage2_smoke.py --port /dev/cu.usbmodem11101` -> Stage 2 仍为 `status=ok mode=lite`, 说明 full 路径依旧在导入 / 初始化链某处 OOM, 但最小 query 链路还能工作
- Approach 7: 新增临时板端跟踪探针 `tools/stage2_full_trace_probe.py`, 逐阶段输出 full 路径内存 -> 结果显示 `TRACE start mem_free=81696`, `_clear_modules()` 后恢复到 `105248`, 导入 `services.commanding.router` 后降到 `100976`, 随后在 `from services.transport_car import TransportCar` 这一步直接抛出 `MemoryError: memory allocation failed; allocating 4168 bytes`; 这把当前根因进一步收敛为“`TransportCar` 导入链本身仍然过重”, 而不是旧版 `_emit_error_log()` 继续放大问题

## Lessons / Refinements
- 对这类板端 OOM 排障, 必须区分“主机工作区代码已经修好”和“设备上真实部署文件已经更新”, 不能用主机侧 grep 替代板端文件核实
- `boot.py` 默认自动执行 `script/remote_control.py`; reset 之后若只做 `Ctrl-C`, 往往只是停掉主循环, 并不会回收 `car` / `pit1` 之类的全局对象, 这会把后续 deploy 直接拖进低内存状态
- `mpy-cli` / `mpremote` 报 `could not enter raw repl` 时, 不能直接假设是工具问题; 在本案里更像是“板子已经回到运行态或串口状态异常, 导致 raw REPL 接管窗口丢失”
- 当前最强证据链已经收敛为: 旧版板端 `_emit_error_log()` -> 先走结构化 `ERROR` 日志 -> formatter OOM -> `E [log.oom       ] format oom`; 因此后续优先级应放在把这份新文件真正同步到板子, 再复测真实 OpenArt 链路
- 当板端新文件已确认同步后, 仍需继续把“旧版日志路径”与“full 导入链过重”分开看待: 前者已经闭环, 但后者依然会在 `TransportCar` 导入阶段申请约 `4168 bytes` 时失败, 这就是 Stage 2 回退到 lite 的直接原因
- 以当前证据看, 板端问题已经从“错误日志再次触发 formatter OOM”推进到“`TransportCar` 模块导入峰值仍超板端可用内存”; 后续应优先审视 import-time 依赖链和顶层常驻对象, 而不是继续围绕 `_emit_error_log()` 打转
